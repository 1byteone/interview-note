### 第 1 题：关于 IoT 后端架构，以下哪个说法是正确的？

A. 设备数据上报应直接写入 MySQL，以保证数据实时性
B. 使用消息队列削峰填谷是应对高并发设备数据上报的关键策略
C. MQTT 协议比 HTTP 协议更适合低功耗设备
D. 设备状态应全部存储在 MySQL 中，不使用 Redis 缓存

**正确答案：B**

**解析：** A 错误，直接写入 MySQL 会导致数据库连接被打满；C 错误，MQTT 基于 TCP 需要维持长连接，功耗高于 CoAP；D 错误，设备实时状态应使用 Redis 缓存，提高查询性能。

### 第 7 题：MQTT 协议中，QoS 2 的含义是？

A. 至多一次，消息可能丢失

C. 恰好一次，消息不重不漏

**正确答案：C**

**解析：** QoS 2（Exactly Once）通过四步握手确保消息恰好到达一次，性能开销最大，适用于跌倒检测等关键事件。

## 三、简答题（8 题）

### 第 1 题：简述 Spring Boot IoT 后端的架构分层设计

**参考答案：**

Spring Boot IoT 后端采用四层架构：

1. **Controller 层**：负责协议转换和数据校验，接收设备上报数据，快速返回响应
2. **Service 层**：核心业务逻辑，包括数据校验、转换、分发、告警判断
3. **Repository 层**：数据持久化，JPA/MyBatis 操作数据库
4. **基础设施层**：MQTT 客户端连接管理、RocketMQ 消息队列、Redis 缓存、MySQL 持久化

关键设计原则：Controller 层不包含业务逻辑，消息队列实现异步解耦，Redis 缓存热数据，MySQL 持久化冷数据。

---

### 第 2 题：百度千帆 AI 的流式输出如何与微信小程序对接？

**参考答案：**

1. 千帆 API 设置 `stream=true` 参数，返回 SSE 格式数据流
2. 后端使用 Spring WebFlux 的 `bodyToFlux` 接收 SSE 流
3. 后端建立 WebSocket 连接，将 SSE 数据逐字转发到小程序端
4. 小程序端 WebSocket 接收消息，实现打字机效果逐字展示
5. 微信小程序不支持原生 SSE，因此必须通过 WebSocket 桥接

---

### 第 3 题：华为 IoTDA 的设备影子模式解决了什么问题？

**参考答案：**

设备影子模式解决的核心问题：**应用层与设备层的解耦**。

具体来说：
1. **网络不稳定**：设备离线时，应用层仍然可以读写影子中的期望状态，设备上线后自动同步
2. **并发控制**：多个应用同时操作设备时，影子作为中间层协调状态
3. **状态缓存**：影子始终保存设备最新状态，应用层无需等待设备响应
4. **离线配置**：设备离线时下发配置，设备上线后立即生效

### 第 4 题：微信小程序 Token 鉴权流程是怎样的？

**参考答案：**

1. 前端调用 `wx.login()` 获取临时 code
2. 前端将 code 发送到后端登录接口
3. 后端用 code 调用微信 `jscode2session` 接口，换取 `openId` 和 `session_key`
4. 后端生成自定义 token（UUID），将 `{token, userId, openId, sessionKey}` 存入 Redis
5. 后端返回 token 给前端，设置过期时间（7 天）
6. 前端将 token 存入 Storage，后续请求携带在 Authorization 头中
7. 后端拦截器验证 Token 有效性，每次请求刷新 Token 过期时间

### 第 5 题：Vue 3 Composition API 相比 Options API 的优势是什么？

**参考答案：**

1. **逻辑复用**：Composition API 可以将相关逻辑封装为 composable 函数，跨组件复用
2. **代码组织**：按功能组织代码，而非按选项（data/methods/computed）分散，大型组件更清晰
3. **类型推导**：TypeScript 类型推导更完善，无需额外声明
4. **Tree Shaking**：未使用的 API 不会打包，减少体积
5. **更好的 this 绑定**：避免 Vue 2 中 this 指向问题

### 第 6 题：设备时序数据的分层存储策略是怎样的？

**参考答案：**

| 层级 | 介质 | 范围 | 粒度 | 策略 |
|------|------|------|------|------|
| 热数据 | Redis | 最近 1 小时 | 原始数据 | TTL 自动过期 |
| 温数据 | MySQL 当月表 | 最近 30 天 | 原始数据 | 按月分表 |
| 冷数据 | MySQL 历史表 | 30-90 天 | 1 分钟聚合数据 | 定时任务聚合 |
| 归档 | 文件存储 | 90 天以上 | 1 小时聚合数据 | 导出后删除 |

定时任务每天凌晨执行：聚合 30 天前的数据，删除原始数据，释放空间。

### 第 7 题：MQTT QoS 0/1/2 的选择策略是什么？

**参考答案：**

| QoS | 适用场景 | 养老场景示例 |
|-----|----------|-------------|
| QoS 0 | 允许丢失的数据 | 设备状态上报（如电量、信号强度），偶尔丢失不影响 |
| QoS 1 | 不能丢失但可重复 | 心率数据上报、命令下发，少量重复可接受 |
| QoS 2 | 不能丢失也不能重复 | 跌倒检测事件，必须严格一次，避免重复告警 |

**原则：** 在满足业务需求的前提下，选择最低的 QoS 级别以降低性能开销。

### 第 8 题：设备离线检测机制有哪些？

**参考答案：**

1. **MQTT 遗嘱消息**：设备连接时设置遗嘱消息，异常离线时 Broker 自动发布
2. **心跳超时检测**：定时任务扫描 Redis 在线设备，超过 10 分钟未上报则标记离线
3. **Redis TTL 过期**：设备在线状态设置 TTL，停止上报后自动过期
4. **IoTDA 状态回调**：IoTDA 平台检测到设备离线时，主动回调通知系统
5. **三次握手确认**：发送心跳 Ping 包，连续三次无响应判定离线

## 四、场景题（4 题）

### 场景 1：高峰期 1000 台设备同时上报数据，如何保证系统稳定？

**问题：** 养老院早高峰时段，1000 台设备同时上报心率数据，每 5 秒上报一次，如何保证系统不崩溃？

**参考答案：**

**流量评估：** 1000 台设备 × 每 5 秒 1 次 = 200 次/秒，每次请求约 1KB，峰值流量约 200KB/s。

**防护方案：**

1. **消息队列削峰**：数据先进入 RocketMQ，消费端控制写入速率，每秒最多写入 500 条
2. **批量写入**：每积累 100 条或 1 秒 flush 一次，合并写入 MySQL
3. **限流**：接入层限流 300 次/秒，超出部分降级丢弃（非关键数据记录日志）
4. **缓存最新状态**：最新数据写入 Redis，查询实时数据走缓存，不查数据库
5. **异步处理**：Controller 只做校验和投递消息队列，立即返回，不阻塞

---

### 场景 2：AI 健康咨询回复太慢，如何优化？

**问题：** 家属在小程序上咨询"父亲血压偏高怎么办"，AI 回复需要 5-10 秒，用户体验差，如何优化？

**参考答案：**

1. **流式输出**：从非流式改为 SSE 流式输出，用户 1-2 秒就能看到开头内容
2. **WebSocket 桥接**：SSE 转 WebSocket 推送到小程序，实现逐字展示
3. **Prompt 优化**：缩短系统 Prompt 长度，减少输入 Token 数
4. **缓存常见问题**：常见问题（如"血压正常范围"）的回复缓存到 Redis，直接返回
5. **模型降级**：简单问题使用文心一言 3.5（更快），复杂问题使用 4.0
6. **超时处理**：设置 30 秒超时，超时后返回兜底回复"正在分析，请稍后再试"

---

### 场景 3：老人跌倒检测触发大量重复告警，如何避免？

**问题：** 老人跌倒后，设备在短时间内连续上报多次跌倒事件，导致家属收到大量重复告警推送，如何避免？

**参考答案：**

1. **QoS 2 保证**：跌倒检测事件使用 QoS 2，确保消息不重不漏
2. **去重机制**：在 Redis 中设置 `alert:fall:{deviceId}:{timestamp}` 的 key，TTL 60 秒，相同事件在 60 秒内不重复处理
3. **状态机过滤**：设备状态为"已跌倒"时，忽略后续相同事件，直到状态重置为"正常"
4. **告警合并**：同一设备 5 分钟内的同类告警合并为一条，避免重复推送
5. **人工确认**：首次告警后推送"请确认"按钮，护工确认前不再重复推送

---

### 场景 4：设备离线导致数据断档，如何在恢复后补全？

**问题：** 某设备因网络故障离线 2 小时，恢复后如何补全这 2 小时的数据？

**参考答案：**

1. **设备本地缓存**：设备离线期间将数据缓存到本地 Flash，容量至少支持 24 小时数据
2. **断点续传**：设备重连后，从断点处开始批量上传缓存数据，附带时间戳
3. **服务端去重**：服务端根据 `deviceId + collectTime` 唯一索引去重，避免重复数据
4. **批量写入优化**：补传数据可能量较大（2 小时 × 720 条/5 秒 = 1440 条），使用批量接口减少请求次数
5. **数据完整性校验**：补传完成后，服务端返回确认，设备删除已确认的缓存数据

### 深挖 2：如何保证设备数据从采集到存储的端到端可靠性？

**参考答案：**

**端到端可靠性保障链路：**

1. **设备端**：数据本地缓存 + 重传机制，MQTT QoS 1/2 保证传输可靠性
2. **网络层**：MQTT 自动重连 + 遗嘱消息，EMQX 集群高可用
3. **接入层**：Controller 快速返回，数据写入 RocketMQ 后才返回成功
4. **消息队列**：RocketMQ 同步刷盘 + 主从复制，消息不丢失
5. **消费端**：手动 ACK + 重试机制，失败消息进入死信队列人工处理
6. **存储层**：MySQL 主从复制 + 定时备份，Redis 持久化（RDB + AOF）

**可靠性指标：** 端到端数据丢失率 < 0.001%，单条数据延迟 < 5 秒。
