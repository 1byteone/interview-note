## 二、技术选型矩阵

| 层级 | 组件 | 选型 | 理由 |
|------|------|------|------|
| 展示层 | 前端框架 | Vue 3 + Element Plus | 与 JeecgBoot/RuoYi 生态一致，组件丰富 |
| 展示层 | 数字大屏 | ECharts + DataV | 制造业看板刚需，ECharts 支持实时刷新 |
| 接入层 | 网关 | Spring Cloud Gateway | 路由 + 限流 + JWT，与微服务生态契合 |
| 业务层 | 框架 | Spring Boot 3 | 成熟、生态丰富、人才储备充足 |
| 业务层 | ORM | MyBatis-Plus | 复杂查询友好，批量操作性能好 |
| 业务层 | 工作流 | Flowable | 工单审批流、质量异常处置流 |
| 领域层 | 状态机 | Spring StateMachine | 工单/质检状态流转管理 |
| 基础设施 | 数据库 | MySQL 8.0 | 事务支持、递归 CTE、JSON 字段 |
| 基础设施 | 缓存 | Redis + Redisson | 工单状态缓存、分布式锁（防并发报工） |
| 基础设施 | 消息队列 | RocketMQ | 工单事件发布、MES→ERP 异步集成 |
| 基础设施 | 搜索 | Elasticsearch | 追溯查询、日志检索 |
| 基础设施 | 对象存储 | MinIO | 工艺文件、质检图片、SOP 文档 |
| 设备通信 | 协议 | OPC-UA / MQTT | 工业标准协议，设备数据采集 |
| 设备通信 | 时序库 | TDengine / InfluxDB | 设备运行数据（OEE、温度、压力） |

## 三、MES 服务拆分

### 3.1 单体 vs 微服务

| 维度 | 单体 | 微服务 |
|------|------|--------|
| 适用规模 | 50-200 人的制造企业 | 200+ 人，多工厂 |
| 开发效率 | 快，一个代码库 | 慢，需要治理 |
| 部署复杂度 | 低 | 高（K8s + 服务网格） |
| 技术选型 | 统一技术栈 | 每个服务可选技术栈 |
| 推荐 | ✅ 中小企业首选 | ⚠️ 大型企业 |

**推荐**：中小企业用单体（Spring Boot 模块化），大型企业按域拆分微服务。

### 3.2 模块化单体结构

```
mes-server/
├── mes-common/           # 通用组件（工具类、异常、枚举）
├── mes-system/           # 系统管理（用户、角色、菜单、日志）
├── mes-masterdata/       # 主数据管理（物料、BOM、工艺、工位）
├── mes-production/       # 生产管理（工单、排产、报工、过站）
├── mes-quality/          # 质量管理（质检模板、质检单、不合格品）
├── mes-equipment/        # 设备管理（设备档案、点检、保养、维修）
├── mes-trace/            # 追溯管理（批次、SN、正反向追溯）
├── mes-erp-adapter/      # ERP 适配层（接口转换、协议适配）
├── mes-gateway/          # API 网关
└── mes-admin/            # 管理后台（Vue 前端）
```

## 四、实时性设计

MES 与普通 CRUD 系统的最大区别：**实时性要求高**。

### 4.1 数据采集实时性

| 数据类型 | 延迟要求 | 采集方式 |
|---------|---------|---------|
| 设备运行状态 | < 1 秒 | OPC-UA / MQTT → 时序库 |
| 报工数据 | < 5 秒 | WebSocket / HTTP → MySQL + Redis |
| 质检数据 | < 10 秒 | HTTP → MySQL |
| 追溯查询 | < 3 秒 | ES + MySQL 联合查询 |

### 4.2 数字大屏刷新

```
方案一：WebSocket 推送
  设备 → MQTT → 消费者 → Redis Pub/Sub → WebSocket → 大屏
  优点：延迟低（毫秒级）
  缺点：连接管理复杂

方案二：前端轮询
  大屏 → 每 3 秒 GET /api/mes/dashboard → 返回最新数据
  优点：实现简单
  缺点：延迟高（3 秒），并发压力大

推荐：WebSocket 推送（核心指标）+ 轮询（辅助指标）
```

## 五、可靠性设计

### 5.1 报工防重复

操作员可能多次点击报工按钮，需要防重复：

```java
// 方案：Redis 分布式锁 + 幂等 Key
String lockKey = "mes:report:lock:" + jobCardId;
String idempotentKey = "mes:report:idempotent:" + jobCardId + ":" + operatorId;

// 1. 幂等检查
if (redis.hasKey(idempotentKey)) {
    return Result.success("已报工，请勿重复提交");
}

// 2. 获取分布式锁
RLock lock = redissonClient.getLock(lockKey);
try {
    lock.lock(5, TimeUnit.SECONDS);
    // 3. 双重检查
    if (redis.hasKey(idempotentKey)) {
        return Result.success("已报工");
    }
    // 4. 执行报工
    reportService.submitReport(jobCardId, operatorId, qty);
    // 5. 标记幂等
    redis.setex(idempotentKey, 3600, "1");
} finally {
    lock.unlock();
}
```

### 5.2 MES→ERP 事件可靠性

采用 **Outbox 模式** 保证消息不丢：

```
1. MES 完工 → 写入 mes_outbox 表（status=PENDING）
2. 后台线程每 5 秒扫描 PENDING 记录
3. 投递到 RocketMQ
4. 投递成功 → status=SENT
5. ERP 消费确认 → status=ACKED
6. 超过 3 次失败 → status=FAILED → 告警人工处理
```

## 六、安全设计

| 安全维度 | 实现方案 |
|---------|---------|
| 认证 | JWT + Spring Security |
| 授权 | RBAC（角色-权限-菜单）+ 数据权限（按工厂/产线） |
| 传输 | TLS 1.2+（HTTPS） |
| 敏感数据 | AES-256 加密（员工薪资、客户信息） |
| 审计 | 全量操作日志（who/when/what/result） |
| 设备通信 | MQTT TLS + X.509 证书认证 |
