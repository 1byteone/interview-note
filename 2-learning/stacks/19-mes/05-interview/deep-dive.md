# MES 面试深挖题（15 题 · L3-L4）

> 在速记版基础上深挖"为什么"，覆盖业务建模、架构设计、集成方案、AI 增强四类深问。

---

## 一、业务建模深挖

### 1. 工单状态机设计时，为什么要记录状态变更日志？

**追问背景**：考察审计意识和追溯能力。

**参考回答**：
制造业的质量体系（如 ISO 9001、IATF 16949）要求所有生产过程可追溯。状态变更日志记录了"谁在什么时间把工单从什么状态改成了什么状态"，是追溯链的重要组成部分。

具体价值：
1. **质量审计**：ISO 审计时需要出示工单流转记录
2. **问题定位**：工单异常时，通过状态日志还原操作轨迹
3. **责任认定**：谁执行了关键操作（如放行不合格品）
4. **流程优化**：分析状态停留时间，发现瓶颈环节

**考察点**：是否理解制造业合规要求，而非只把状态机当技术问题。

---

### 2. BOM 的版本控制为什么如此重要？如果两个部门用不同版本的 BOM 会怎样？

**追问背景**：考察对 BOM 变更管理的理解。

**参考回答**：
BOM 是生产执行的"配方"，一旦出错会导致批量报废。

版本控制的重要性：
1. **工程变更（ECO）**：设计部门修改 BOM 后，需要通知生产部门切换到新版本
2. **可追溯性**：出了质量问题，需要知道当时用的是哪个版本的 BOM
3. **多版本并存**：同一产品可能有多个 BOM 版本同时在产（老订单用旧版，新订单用新版）

如果两个部门用不同版本：
- 设计部门发布了 V2.0（替换子件 A 为 B）
- 生产部门还在用 V1.0（继续领料子件 A）
- 结果：用错物料，成品不合格，批量报废

解决方案：BOM 发布需要走审批流，MES 只接受"已发布"状态的 BOM，变更时自动通知相关工单。

**考察点**：是否理解 BOM 变更的业务影响，而非只谈技术实现。

---

### 3. 为什么追溯关系表要设计成"不可变"？

**追问背景**：考察数据设计理念。

**参考回答**：
追溯记录是法律证据——食品召回、药品追溯、产品缺陷调查都依赖追溯数据的完整性和不可篡改性。

设计原则：
1. **只追加，不修改**：追溯关系一旦建立，不允许 UPDATE 或 DELETE
2. **审计日志**：任何对追溯表的操作都记录审计日志
3. **物理隔离**：追溯数据可以定期归档到只读存储
4. **法律要求**：《食品安全法》《药品管理法》都要求追溯数据保存 2 年以上

如果允许修改追溯关系：
- 某人误操作删除了追溯记录 → 无法完成召回追溯 → 法律风险
- 某人故意修改追溯记录掩盖质量问题 → 信任危机

**考察点**：是否理解追溯数据的法律和合规意义。

## 二、架构设计深挖

### 4. MES 为什么推荐用模块化单体而不是微服务？

**追问背景**：考察架构权衡能力。

**参考回答**：
大多数制造企业是中小企业（50-200 人），MES 的业务域相对集中（工单、排产、质检、追溯），模块间耦合度高（工单→报工→质检→追溯是紧密的业务链）。

模块化单体的优势：
1. **开发效率高**：一个代码库，本地启动快，调试方便
2. **部署简单**：一个 JAR 包，Docker 一个容器
3. **事务简单**：工单完工→报工→质检在同一进程内，本地事务即可
4. **运维成本低**：不需要 K8s、服务网格、链路追踪等基础设施

微服务适合的场景：
- 多工厂部署（每个工厂独立服务）
- 不同模块技术栈不同（如追溯用图数据库）
- 团队规模大（50+ 开发人员）

**考察点**：是否能根据业务规模做合理的架构决策，而非盲目追新。

### 5. MES 的实时性要求高，你怎么设计数据采集方案？

**追问背景**：考察对 MES 与普通 CRUD 系统差异的理解。

**参考回答**：
MES 与普通管理系统的最大区别是实时性——设备数据秒级采集、报工数据毫秒级响应、大屏数据实时刷新。

数据采集方案分三层：
1. **设备层**：OPC-UA/MQTT 协议采集 PLC 数据，写入时序库（TDengine），延迟 < 1 秒
2. **执行层**：操作员报工通过 WebSocket 上报，后端写 MySQL + Redis 缓存，延迟 < 5 秒
3. **展示层**：大屏通过 WebSocket 推送（核心指标）+ 前端轮询（辅助指标），刷新间隔 1-3 秒

关键技术点：
- Redis 缓存当前工单状态，避免每次查库
- WebSocket 长连接推送大屏数据
- 时序库存储设备运行数据（温度、压力、振动），支持趋势分析

**考察点**：是否理解 MES 的实时性要求与普通系统的差异。

---

### 6. Outbox 模式中，后台线程扫描的频率怎么定？

**追问背景**：考察工程实践细节。

**参考回答**：
扫描频率需要权衡实时性和数据库压力：

| 频率 | 实时性 | 数据库压力 | 适用场景 |
|------|--------|-----------|---------|
| 1 秒 | 高 | 高 | 对实时性要求极高的场景 |
| 5 秒 | 中 | 中 | **推荐默认值** |
| 30 秒 | 低 | 低 | 对实时性要求不高的场景 |
| 1 分钟 | 很低 | 很低 | 日报类批量同步 |

推荐 5 秒的理由：
1. MES→ERP 的完工回报不需要毫秒级延迟，秒级可接受
2. 5 秒扫描一次，每分钟 12 次，对 MySQL 压力很小
3. 配合 RocketMQ 的批量投递，吞吐量足够

优化手段：
- 批量扫描（每次 100 条），减少数据库交互
- 扫描间隔动态调整：PENDING 记录多时缩短间隔，少时延长

**考察点**：是否能根据业务场景做工程化的参数调优。

## 三、集成方案深挖

### 7. MES 和 ERP 如果是不同厂商的系统，集成时最大的挑战是什么？

**追问背景**：考察异构系统集成经验。

**参考回答**：
最大挑战是**语义鸿沟**——两个系统对同一业务概念的理解不同。

典型问题：
1. **编码体系不同**：MES 的物料编码和 ERP 的物料编码可能不一致，需要映射表
2. **数据模型不同**：MES 的"工单"和 ERP 的"生产订单"字段不完全对应
3. **接口协议不同**：MES 可能只支持 REST，ERP 可能只支持 SOAP/WebService
4. **时间窗口不同**：MES 实时，ERP 批量，需要适配层做缓冲

解决方案：
1. **ERP 适配层**：MES 侧构建独立的 Adapter，屏蔽不同 ERP 的接口差异
2. **统一数据字典**：建立跨系统的编码映射表（物料编码、仓库编码、组织编码）
3. **消息格式标准化**：定义统一的 JSON Schema，适配层负责转换
4. **对账机制**：每日批量校验数据一致性，发现差异告警

**考察点**：是否有异构系统集成的实战意识。

---

### 8. 如果 MES 和 ERP 共享同一个数据库，还需要 Outbox 模式吗？

**追问背景**：考察对分布式事务的理解。

**参考回答**：
如果共享同一个数据库，可以用本地事务保证一致性，不需要 Outbox 模式。

```
同一数据库事务：
BEGIN;
  UPDATE mes_work_order SET status = 'COMPLETED' WHERE id = ?;
  UPDATE erp_production_order SET status = 'COMPLETED' WHERE order_no = ?;
COMMIT;
```

但实际中共享数据库的情况很少：
1. MES 和 ERP 通常是独立系统，由不同团队/厂商维护
2. 共享数据库会导致耦合度极高，任何一方的表结构变更都会影响另一方
3. 性能互相影响（MES 的高频写入可能拖慢 ERP 的查询）

所以 Outbox 模式适用于**独立系统之间的集成**，本地事务适用于**同一系统内的跨模块操作**。

**考察点**：是否能区分"同库"和"异库"场景的不同方案。

## 四、AI 增强深挖

### 9. 智能排产用 LLM 的话，如何保证排产结果的可行性？

**追问背景**：考察对 LLM 局限性的认识。

**参考回答**：
LLM 本身不擅长精确的约束求解——它可能生成"不合理"的排产方案（如让一台设备同时加工两个工单）。

正确方案是**LLM + 求解器混合架构**：
1. LLM 负责：理解自然语言意图、生成约束参数、解释排产结果
2. 求解器负责：精确求解（OR-Tools CP-SAT、OptaPlanner）
3. LLM 不直接产出排产方案，而是生成求解器的输入参数

这样既有 LLM 的自然语言交互能力，又有求解器的精确性保证。

**考察点**：是否理解 LLM 的能力边界，而非盲目信任。

---

### 10. 质量根因分析用 LLM 的话，如何防止 LLM "幻觉"导致错误诊断？

**追问背景**：考察 AI 落地的工程意识。

**参考回答**：
LLM 可能生成看似合理但实际错误的诊断（如把温度波动归因于"操作员失误"，实际是设备老化）。

防止幻觉的手段：
1. **RAG 增强**：把历史质量案例、设备手册、工艺文档作为知识库，LLM 基于证据推理
2. **数据约束**：LLM 的输入必须是结构化数据（质检记录、设备日志），而非自由描述
3. **置信度输出**：要求 LLM 输出每个根因的置信度，低置信度的标记为"待人工确认"
4. **人工兜底**：最终根因判定需要质量工程师确认，LLM 只是辅助

**考察点**：是否理解 LLM 在工业场景的落地约束。

## 五、场景设计深挖

### 11. 设计一个"紧急插单"的处理流程

**参考答案**：

```
1. 接收紧急插单请求（来自 ERP 或手动输入）
2. 评估影响：
   · 查询当前排产计划
   · 识别可延迟的工单
   · 检查物料齐套（紧急订单的原料是否到位）
3. 调整排产：
   · 暂停可延迟工单
   · 插入紧急工单到指定工位
   · 重新计算后续工单的排产时间
4. 通知相关方：
   · 操作员：新工单已分配
   · 仓库：紧急领料需求
   · ERP：排产变更通知
5. 执行与监控：
   · 紧急工单优先报工
   · 监控是否按期完成
6. 恢复：
   · 紧急工单完成后，恢复被暂停的工单
   · 更新排产计划
```

### 12. 设计一个"设备故障导致工单中断"的处理流程

**参考答案**：

```
1. 设备故障发生
   · 操作员上报故障（扫码枪/终端）
   · 或设备自动上报（PLC 异常信号）
2. 工单中断
   · 当前作业卡状态 → ABNORMAL
   · 记录已完成数量和不良数量
3. 故障处理
   · 通知设备维护人员
   · 维修工单创建
   · 设备状态 → 维修中
4. 工单调整
   · 评估：修复时间
   · 如果短（< 30 分钟）：等待修复后继续
   · 如果长（> 30 分钟）：工单转移到其他工位
5. 恢复生产
   · 设备修复后 → 状态恢复正常
   · 工单恢复或重新分配
   · 补偿生产（加班/加线）
6. 数据记录
   · 设备故障记录（故障类型、维修时间、备件消耗）
   · 工单中断记录（中断原因、中断时长、恢复方式）
   · 影响分析（本次故障对 OEE 和交期的影响）
```
