## 二、STAR 法则包装

### 亮点一：工单状态机与并发控制

**S（场景）**：制造车间 200+ 操作员同时报工，工单状态频繁变更，存在并发冲突和重复报工问题。

**T（任务）**：设计一套可靠的工单状态机，保证并发安全和数据一致性。

**A（行动）**：
1. 基于 Spring StateMachine 实现工单状态机，定义 7 个状态和 12 个状态转换事件
2. 报工接口使用 Redis 分布式锁 + 幂等 Key，防止重复提交
3. 状态变更记录审计日志（who/when/what/result），支持追溯

**R（结果）**：
- 并发报工冲突率从 5% 降至 0%
- 报工响应时间 < 500ms（P99）
- 工单状态 100% 可追溯

---

### 亮点二：批次追溯引擎

**S（场景）**：客户投诉产品缺陷，需要在 2 小时内完成反向追溯（成品→原料批次→供应商），传统方式靠 Excel 手工排查。

**T（任务）**：设计并实现正向/反向追溯引擎，实现分钟级追溯响应。

**A（行动）**：
1. 设计批次关系表（`mes_batch_relation`），记录原料批次→成品批次的消耗关系
2. 基于 MySQL 8.0 递归 CTE 实现正向/反向追溯查询
3. 追溯结果写入 Elasticsearch，支持模糊搜索（按供应商名、产品名）
4. 热门追溯结果用 Redis 缓存，命中率 > 80%

**R（结果）**：
- 追溯响应时间从 2 小时缩短至 3 分钟
- 支持 10 层递归追溯（原料→半成品→成品）
- 成功支撑 3 次客户召回事件

---

### 亮点三：MES↔ERP 事件驱动集成

**S（场景）**：MES 完工数据需要实时同步到 ERP 进行入库和成本归集，传统数据库直连方式经常出现数据不一致。

**T（任务）**：设计可靠的 MES→ERP 集成方案，保证数据最终一致。

**A（行动）**：
1. 采用 Outbox 模式：完工时在同一事务中更新工单状态 + 写入 Outbox 表
2. 后台线程每 5 秒扫描 PENDING 记录，投递到 RocketMQ
3. ERP 消费端实现幂等（messageId 去重）
4. 每日对账任务校验 MES 工单 vs ERP 生产订单数量一致性
5. 死信队列 + 告警，失败消息人工介入处理

**R（结果）**：
- 消息投递成功率 99.97%
- 数据不一致问题从每周 3 次降至 0
- ERP 入库延迟 < 10 秒

---

### 亮点四：智能排产（AI 增强）

**S（场景）**：排产员每天花 2 小时手动排产，面对紧急插单和物料短缺时反应慢。

**T（任务）**：用 AI 辅助排产，缩短排产时间并支持自然语言交互。

**A（行动）**：
1. 用 Google OR-Tools 建模排产约束（设备互斥、交期、物料齐套）
2. LLM Agent 理解自然语言排产指令，生成约束模型参数
3. 排产结果以 ECharts 甘特图可视化展示
4. 支持"把 3 号线的紧急订单提前"等自然语言调整

**R（结果）**：
- 排产时间从 2 小时缩短至 15 分钟
- 交期达成率从 85% 提升至 95%
- 支持自然语言排产交互

## 四、面试官可能追问

| 追问 | 参考回答方向 |
|------|------------|
| 为什么用 Outbox 不用 Seata？ | MES 和 ERP 是独立系统，Seata 侵入性太高，最终一致性够用 |
| 递归 CTE 性能怎么样？ | 深度限制 + 索引覆盖 + 缓存热门结果，实测 10 层追溯 < 100ms |
| 幂等 Key 存多久？ | 24 小时，覆盖重试窗口，之后自动过期 |
| 智能排产的约束求解器怎么选的？ | OR-Tools（Google 开源，支持 CP-SAT 求解器，性能好） |
| 追溯数据量大了怎么办？ | 分区表（按月分区） + ES 全文检索 + 预计算快照 |
