## 二、审批流设计

### 2.1 审批流模板

一个审批流模板定义了"这个类型的业务走什么流程"：

```
请假审批流程
├── 发起人提交
│   └── 关联表单：请假单（请假类型、天数、原因）
├── 审批节点 1：部门负责人审批
│   ├── 审批人：发起人的直属领导
│   ├── 动作：通过 / 驳回 / 转办
│   └── 条件：无（所有请假都走这步）
├── 审批节点 2：HR 审批（条件分支）
│   ├── 条件：请假天数 > 3 天
│   ├── 审批人：HR 部门指定人员
│   └── 动作：通过 / 驳回
├── 审批节点 3：总经理审批（条件分支）
│   ├── 条件：请假天数 > 7 天
│   ├── 审批人：总经理
│   └── 动作：通过 / 驳回
└── 完成
    └── 通知发起人：审批结果
    └── 联动：HR 系统更新考勤
```

### 2.2 审批模式

| 模式 | 场景 | 说明 |
|------|------|------|
| 串行审批 | 请假、报销 | A→B→C 依次审批 |
| 并行审批 | 合同评审 | 法务、财务、业务同时审批 |
| 会签 | 董事会决议 | 所有人都要通过 |
| 或签 | 部门审批 | 任意一人通过即可 |
| 加签 | 复杂审批 | 审批人可以临时增加审批人 |
| 退签 | 退回重审 | 审批人退回给上一步 |

### 2.3 审批人分配策略

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| 指定人员 | 固定某个人审批 | 总经理审批 |
| 角色审批 | 该角色的所有人之一 | 部门经理审批 |
| 部门负责人 | 发起人的直属领导 | 请假审批 |
| 发起人自选 | 发起人选择审批人 | 项目评审 |
| 按字段值 | 根据表单字段动态确定 | 按金额分级审批 |

## 三、表单设计

### 3.1 动态表单 vs 外置表单

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| 动态表单 | 审批流引擎内置表单设计器 | 开箱即用，配置简单 | 复杂表单表达力不足 |
| 外置表单 | 业务系统自己开发表单 | 灵活，可做复杂交互 | 需要手动关联审批流 |

**推荐**：简单审批用动态表单，复杂业务用外置表单 + Flowable 关联。

### 3.2 表单与审批流关联

```
业务表单（请假单）
    │
    │ 业务数据存储
    ▼
mes_leave_request 表（请假天数、原因、状态）
    │
    │ 流程变量传递
    ▼
Flowable 流程实例
    │
    │ 通过流程变量控制分支
    ▼
${days > 3} → HR 审批节点
${days > 7} → 总经理审批节点
```

## 四、权限体系设计

### 4.1 权限加载流程

```
用户登录
    │
    ├── 查询用户角色（sys_user_role）
    │   └── SELECT role_id FROM sys_user_role WHERE user_id = ?
    │
    ├── 查询角色权限（sys_role_permission）
    │   └── SELECT permission_id FROM sys_role_permission WHERE role_id IN (?)
    │
    ├── 查询权限详情（sys_permission）
    │   └── SELECT * FROM sys_permission WHERE id IN (?)
    │
    └── 缓存到 Redis
        └── Key: perm:user:{userId}
        └── Value: Set<权限标识>
        └── TTL: 30 分钟
```

### 4.2 权限校验流程

```
请求进入
    │
    ├── 1. JWT 解析 → 获取 userId
    │
    ├── 2. Redis 查询权限缓存
    │   ├── 命中 → 直接使用
    │   └── 未命中 → 查数据库 → 写缓存
    │
    ├── 3. 检查按钮权限
    │   └── 请求的接口标识是否在用户权限集合中
    │
    └── 4. 检查数据权限
        └── 拼接数据权限 SQL 条件（通过拦截器）
```

### 4.3 权限缓存策略

| 场景 | 缓存策略 |
|------|---------|
| 用户登录 | 加载全部权限到 Redis |
| 角色变更 | 清除该角色下所有用户的权限缓存 |
| 权限变更 | 清除相关角色的权限缓存 |
| 定时刷新 | 每 30 分钟主动刷新一次 |

## 五、消息通知设计

### 5.1 通知类型

| 类型 | 触发时机 | 通知方式 |
|------|---------|---------|
| 审批提醒 | 有待处理任务 | 站内信 + 推送 |
| 审批结果 | 审批完成 | 站内信 + 邮件 |
| 抄送通知 | 流程抄送 | 站内信 |
| 系统公告 | 管理员发布 | 站内信 + 邮件 |

### 5.2 消息存储

```sql
CREATE TABLE sys_notification (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL COMMENT '接收人',
    title VARCHAR(128) NOT NULL,
    content TEXT,
    type VARCHAR(32) COMMENT 'APPROVAL/RESULT/CC/SYSTEM',
    biz_type VARCHAR(32) COMMENT '业务类型：LEAVE/PURCHASE/CONTRACT',
    biz_id BIGINT COMMENT '业务ID',
    is_read TINYINT DEFAULT 0,
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

## 六、面试建模题

### Q1：如何设计一个灵活的审批流引擎？

**参考答案**：
1. **流程定义层**：用 BPMN 2.0 标准定义流程，支持排他网关（条件分支）、并行网关、会签/或签
2. **流程实例层**：流程定义实例化，每个审批单对应一个流程实例
3. **任务层**：每个审批节点生成一个 Task，Task 支持通过/驳回/转办/加签
4. **表单层**：审批流与业务表单解耦，通过流程变量传递业务数据
5. **监听器层**：任务监听器 + 执行监听器，实现审批后的业务联动（如更新业务状态、发送通知）

### Q2：数据权限和菜单权限有什么区别？

**参考答案**：
- 菜单权限控制"能不能看到这个页面"（粗粒度）
- 数据权限控制"能看到这个页面里的哪些数据"（细粒度）
- 两者独立控制：某人可能有"请假列表"菜单权限，但只能看到本部门的请假单（数据权限）
- 实现方式：菜单权限通过路由拦截实现，数据权限通过 SQL 拦截器实现
