# Redis 持久化 — RDB · AOF · 混合持久化

> 等级：👶 入门 → 🎯 面试进阶
> 目标：理解 RDB 和 AOF 两种持久化方式的工作原理、配置策略、优缺点，以及如何选择。

---

## 一、为什么需要持久化？

Redis 是内存数据库，一旦进程退出或机器宕机，内存中的数据就会全部丢失。持久化机制将数据保存到磁盘，以便重启后恢复。

**没有持久化的 Redis 只适合做"纯缓存"**——丢了可以从 DB 重建。但用于分布式锁、计数器、Session 时，丢数据就会造成业务故障。

---

## 二、RDB（Redis Database）—— 快照持久化

### 2.1 原理

RDB 在指定时间间隔内将内存中的数据生成**全量二进制快照**，保存到 `dump.rdb` 文件中。

### 2.2 触发方式

**自动触发**（配置 `save` 指令）：
```bash
# redis.conf 配置
save 900 1          # 900 秒内至少有 1 个 key 变化
save 300 10         # 300 秒内至少有 10 个 key 变化
save 60 10000       # 60 秒内至少有 10000 个 key 变化
```

**手动触发**：
```bash
# 阻塞式保存（不推荐生产使用）
> SAVE

# 非阻塞式保存（fork 子进程，推荐）
> BGSAVE
```

### 2.3 执行流程

```
1. 父进程 fork 子进程
2. 子进程将内存数据写入临时 RDB 文件
3. 原子替换正式 RDB 文件
4. 子进程退出
```

### 2.4 优点

| 优点 | 说明 |
|------|------|
| 文件紧凑 | 二进制压缩，适合备份、传输、冷备 |
| 恢复极快 | 直接加载到内存，比 AOF 重写快得多 |
| 性能影响小 | fork 子进程做持久化，父进程继续服务 |

### 2.5 缺点

| 缺点 | 说明 |
|------|------|
| 丢失数据多 | 最后一次快照之后的数据全部丢失（可能 1 分钟到 N 分钟的数据） |
| fork 耗时 | 数据量大时 fork 阻塞主进程几十毫秒甚至几秒 |
| 无法实时持久化 | 不适合需要高数据完整性的场景 |

## 三、AOF（Append Only File）—— 追加日志持久化

### 3.1 原理

AOF 将每一条**写命令**追加到 `appendonly.aof` 文件中，格式为 Redis 协议文本，可以直接读取。

### 3.2 配置

```bash
# redis.conf
appendonly yes               # 开启 AOF
appendfilename "appendonly.aof"  # 文件名
appendfsync everysec         # 刷盘策略（关键！）
```

### 3.3 三种刷盘策略

| 策略 | 说明 | 安全性 | 性能 |
|------|------|--------|------|
| `always` | 每个写命令都 fsync 到磁盘 | 最安全（最多丢 1 条） | 最慢（QPS 降至几千） |
| `everysec` | 每秒 fsync 一次 | 折中（最多丢 1 秒数据） | 性能接近无持久化 |
| `no` | 由操作系统决定何时刷盘 | 最不安全（丢几十秒数据） | 最快 |

**生产推荐**：`everysec`——在性能和安全之间取得最佳平衡。

### 3.4 AOF 重写（Rewrite）

AOF 文件会不断增长，需要压缩。重写**不是"重写旧文件"**，而是读取当前内存状态，生成重建该状态所需的最小命令集。

```bash
# 手动触发重写
> BGREWRITEAOF

# 自动触发配置
auto-aof-rewrite-percentage 100    # 文件增长超过 100% 时触发
auto-aof-rewrite-min-size 64mb     # 文件至少 64MB 才触发
```

**重写流程**：
```
1. fork 子进程
2. 子进程将当前内存数据转为命令写入新 AOF
3. 父进程将重写期间的增量命令写入 AOF 缓冲区
4. 重写完成后，父进程追加增量命令到新 AOF
5. 原子替换新 AOF 文件
```

### 3.5 优点与缺点

| 维度 | 说明 |
|------|------|
| 优点 | 数据安全性高（everysec 最多丢 1 秒），AOF 文件可读性强 |
| 缺点 | 相同数据 AOF 文件体积远大于 RDB；恢复速度慢（逐条执行命令） |

## 四、RDB + AOF 混合持久化（Redis 4.0+）

### 4.1 原理

同时开启 RDB 和 AOF 时，AOF 重写不再是纯命令文本，而是**先写一个 RDB 快照作为"基座"，再追加增量命令**。

### 4.2 配置

```bash
# redis.conf
aof-use-rdb-preamble yes    # 开启混合持久化（Redis 4.0+ 默认开启）
```

### 4.3 文件结构

```
[ RDB 快照数据 ] + [ AOF 增量命令 ]
```

### 4.4 优势

- **恢复极快**：加载 RDB 快照（秒级）而不是逐条执行命令（分钟级）
- **数据安全**：AOF 部分保证最多丢 1 秒数据
- **文件更小**：比纯 AOF 小得多

### 4.5 生产推荐配置

```bash
# redis.conf 最佳实践
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# 建议同时保留 RDB 作为备份策略
save 900 1
save 300 10
save 60 10000
```

## 五、持久化策略选择

### 5.1 选型矩阵

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 纯缓存（可重建） | 关闭持久化 | 省 10%-20% 性能 |
| 缓存 + 数据辅助 | RDB 或 RDB + AOF | 恢复快，备份方便 |
| 分布式锁/计数器 | AOF everysec | 最多丢 1 秒数据 |
| 数据库级场景 | AOF everysec + RDB 辅助 | 兼顾安全与恢复速度 |
| 金融级 | AOF always（结合集群） | 不丢数据 |

### 5.2 恢复优先级

Redis 重启时自动恢复的优先级：
```
AOF 开启 → 加载 AOF
AOF 关闭 → 加载 RDB
两者都无 → 空数据库
```

### 5.3 面试高频问题

> **RDB 的 fork 阻塞怎么解决？**
> fork 阻塞是"写时复制"（Copy-On-Write）带来的：fork 时父进程必须暂停服务来复制页表。数据量大时可能阻塞几十毫秒。解决方案：
> - 控制单实例内存 < 8GB
> - 开启 `lazy-free`（异步释放内存）
> - 使用 SSD 磁盘减少 fork 后的 IO 压力
> - 用 Redis Cluster 做分片，每个分片数据量小

> **AOF 文件坏了怎么办？**
> Redis 提供了 `redis-check-aof` 工具修复：
> ```bash
> redis-check-aof --fix appendonly.aof
> ```

> **RDB 文件和 AOF 文件可以同时存在吗？**
> 可以。Redis 启动时优先加载 AOF（数据更完整）。混合持久化模式下，AOF 文件本身就包含 RDB 头。

## 六、面试速记

| 对比维度 | RDB | AOF | 混合 RDB+AOF |
|----------|-----|-----|-------------|
| 数据完整性 | 低（可能丢分钟级） | 高（最多丢 1 秒） | 高 |
| 恢复速度 | 极快 | 慢 | 快 |
| 文件大小 | 小 | 大 | 中小 |
| 对性能影响 | fork 阻塞 | 取决于 fsync 策略 | 折中 |
| 适用场景 | 备份、冷备 | 数据安全 | 生产首选 |
