## 一、数据结构（6 个考点）

| # | 考点 | 一句话 |
|---|------|--------|
| 1 | String 底层编码 | int（整数）、embstr（<44B）、raw（长字符串），由阈值自动转换 |
| 2 | Hash 底层编码 | ziplist（字段少时）→ hashtable，ziplist 最大字段数 512、最大值 64B |
| 3 | List 底层编码 | quicklist（ziplist 节点组合的双向链表），兼顾内存与速度 |
| 4 | Set 底层编码 | intset（全整数且 <512 个）→ hashtable |
| 5 | ZSet 底层编码 | ziplist（成员少且值小）→ skiplist（跳表 + dict），跳表 O(logN) 范围查询 |
| 6 | 跳表 vs 红黑树 | 跳表实现简单、支持范围查询、区间内锁范围小，更适合 ZSet |

## 二、缓存（6 个考点）

| # | 考点 | 一句话 |
|---|------|--------|
| 1 | 缓存穿透 | 查不存在的数据，解决方案：布隆过滤器 + 空对象缓存 |
| 2 | 缓存击穿 | 热点 key 过期瞬间并发打到 DB，解决方案：互斥锁 或 逻辑过期 |
| 3 | 缓存雪崩 | 大量 key 同时过期或 Redis 宕机，解决方案：随机过期 + 多级缓存 + 高可用 |
| 4 | 缓存一致性 | 先更新 DB 再删缓存（Cache-Aside），或 Canal 订阅 binlog 异步刷新 |
| 5 | 布隆过滤器 | Redis Bitmap 实现，说"不存在"一定不存在，说有误判，不可删除 |
| 6 | 多级缓存 | Caffeine（本地 <1ms）→ Redis（5ms）→ MySQL（50ms），广播失效 |

## 三、分布式锁（6 个考点）

| # | 考点 | 一句话 |
|---|------|--------|
| 1 | SETNX 加锁 | `SET key value NX EX 30`，原子操作，UUID 标识持有者 |
| 2 | Lua 释放锁 | `if get(key)==val then del(key) end`，原子性防止误删 |
| 3 | Redisson 可重入 | Hash 结构记录重入次数，`hincrby` 加锁，`hincrby -1` 解锁 |
| 4 | Watch Dog | 默认 30s 过期，每 10s 自动续期，客户端崩溃时停止续期 |
| 5 | RedLock | 同时在 N 个独立节点加锁，大多数成功才算加锁成功，解决主从切换锁丢失 |
| 6 | 锁过期时间设置 | 太短：业务未完成锁释放；太长：宕机后等待久。Watch Dog 自动续期是最佳实践 |

## 四、持久化（6 个考点）

| # | 考点 | 一句话 |
|---|------|--------|
| 1 | RDB 原理 | fork 子进程生成全量二进制快照，恢复极快，但可能丢分钟级数据 |
| 2 | RDB 触发 | `save 60 10000` 自动触发，`BGSAVE` 手动 fork 子进程 |
| 3 | AOF 原理 | 追加写命令日志，`everysec` 每秒 fsync，最多丢 1 秒数据 |
| 4 | AOF 重写 | 读取当前内存状态生成最小命令集，子进程异步执行 |
| 5 | 混合持久化 | RDB 头 + AOF 增量，恢复快且数据安全，Redis 4.0+ 默认开启 |
| 6 | 恢复优先级 | AOF 开启则加载 AOF，否则加载 RDB，两者都无则空数据库 |

## 五、集群（6 个考点）

| # | 考点 | 一句话 |
|---|------|--------|
| 1 | 主从复制 | RDB 全量复制 + 增量复制（repl_backlog），异步，从节点只读 |
| 2 | 哨兵模式 | 监控主节点 + 主观下线(sdown) + 客观下线(odown) + 自动选举新主 |
| 3 | Cluster 分片 | 16384 个哈希槽 `CRC16(key) % 16384`，均匀分配到各个主节点 |
| 4 | 重定向 MOVED | 客户端请求的 key 不在当前节点，返回 MOVED 告知正确节点 |
| 5 | 哈希槽限制 | 跨槽多 key 操作失败，用 hash tag `{user1001}` 强制同一槽 |
| 6 | 哨兵 vs Cluster | 数据量 < 100GB 用哨兵，> 100GB 或需要水平扩展用 Cluster |

---

## 六、性能（6 个考点）

| # | 考点 | 一句话 |
|---|------|--------|
| 1 | 内存淘汰策略 | LRU（最久未使用）最常用，LFU（频率最低）适合热点场景 |
| 2 | 大 Key 危害 | 阻塞 Redis 单线程、网络延迟、数据倾斜，> 10MB 或 > 5000 成员 |
| 3 | 大 Key 处理 | 拆分（hash 分桶）、分页操作（LRANGE 0 99）、UNLINK 异步删除 |
| 4 | 热 Key 处理 | 本地缓存、散列打散（加随机后缀）、读写分离 |
| 5 | 慢查询 | `slowlog-log-slower-than 10000(μs)`，大 Key 操作、复杂命令是主因 |
| 6 | Pipeline | 批量发送减少 RTT，非原子；需要原子性时用 Lua 脚本 |
