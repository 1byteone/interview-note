## 一、Redis 单线程模型为什么快？

### 1.1 核心答案

Redis 的单线程指的是**处理命令的线程是单线程**（主线程）。但 IO 操作由多路复用处理，数据持久化由子进程处理。

### 1.2 为什么单线程还能这么快？

| 原因 | 说明 |
|------|------|
| **纯内存操作** | 数据在内存中，读写纳秒级，不涉及磁盘 IO |
| **非阻塞 IO** | 基于 epoll（Linux）多路复用，单线程管理大量连接 |
| **避免上下文切换** | 单线程没有线程切换开销，没有锁竞争 |
| **数据结构高效** | 跳表 O(logN)、哈希表 O(1)、ziplist 紧凑编码 |

### 1.3 多路复用模型

```
1. 主线程创建 socket 绑定端口
2. 注册 accept/read/write 事件到 epoll（事件驱动）
3. epoll_wait() 阻塞等待事件就绪
4. 事件就绪 → 主线程按顺序处理命令
5. 处理完继续等待下一个事件
```

**与多线程模型的对比**：

```
Redis（单线程）：                 Memcached（多线程）：
主线程 → 事件循环 → 执行命令       主线程 → 分发任务 → 工作线程池 → 执行命令
         ↓                                 ↓
    无锁竞争，无切换开销              有锁竞争，有切换开销
```

### 1.4 Redis 6.0 引入 IO 多线程

6.0 后的 IO 多线程**只负责网络 IO 读写**，命令执行仍然是单线程的。这样兼顾了：
- 网络 IO 瓶颈（大量客户端读取/写入数据）由多线程处理
- 命令执行依旧单线程，避免锁竞争

### 1.5 面试关键点

> **Redis 单线程的瓶颈在哪里？**
> CPU 不是瓶颈，瓶颈是**内存和网络带宽**。单线程模式下，一条慢命令（如 `KEYS *`、`HGETALL` 大 Hash）会阻塞所有后续命令。

> **为什么 Redis 6.0 要引入 IO 多线程？**
> 随着网络带宽提升（10Gbps+），单线程处理网络 IO 成为瓶颈。IO 多线程将网络读写分摊到多个线程，但命令执行仍保持单线程。

## 二、跳表（Skip List）实现原理

### 2.1 为什么 ZSet 用跳表不用红黑树？

| 对比维度 | 跳表 | 红黑树 |
|----------|------|--------|
| 范围查询 | 直接遍历链表，O(logN + M) | 中序遍历后还需要处理，相对复杂 |
| 实现复杂度 | 简单，几十行代码 | 复杂，旋转平衡逻辑 |
| 内存占用 | 指针更多，但可控 | 更紧凑 |
| 区间锁 | 锁范围小（只需锁相邻节点） | 旋转可能影响全局 |

**核心原因**：ZSet 需要频繁的**范围查询**（如 `ZRANGE`、`ZREVRANGE`），跳表的链表结构天然支持范围遍历。

### 2.2 跳表结构

```
Level 4:  ┌──────────────────────────────────────────────────────┐
           │  1 ───────────────────────────────────────────── 100 │
Level 3:  ┌┼───────────────────────────┐  ┌───────────────────────┼┐
           ││  1 ────────── 50 ────────┼──┼── 100                ││
Level 2:  ┌┼┼───────────┐  ┌───────────┼──┼───────────┐  ┌───────┼┼┐
           │││  1 ── 25 ─┼──┼── 50 ────┼──┼── 75 ─────┼──┼── 100 │││
Level 1:  ┌┼┼┼───┐  ┌───┼──┼──┼───┐  ┌┼──┼──┼───┐  ┌──┼──┼──┼───┼┼┼┐
           ││││ 1 │  │ 25│  │  │50 │  ││  │  │75 │  │  │  │  │100││││
           └┘└┘└───┘  └──┘  └──┘───┘  └┘  └──┘───┘  └──┘  └──┘───┘┘┘┘
```

### 2.3 跳表核心操作

**查找**：从最高层开始，向右找，遇到大于目标值则向下继续。

```java
// 伪代码：查找元素 70
// 1. 从 Level 4 开始：1 → 100（大于70），向下
// 2. Level 3：1 → 50 → 100（大于70），向下
// 3. Level 2：50 → 75（大于70），向下
// 4. Level 1：50 → 75（大于70），向下到 Level 0
// 5. Level 0：50 → 75（找到），返回
```

**插入**：随机决定层数（概率 50% 升一层），从最高层插入。

**删除**：找到节点，逐层删除指针。

### 2.4 跳表 vs 平衡树

> **跳表的时间复杂度是多少？**
> 查找、插入、删除都是 O(logN) 平均，最坏 O(N)（概率极低，通过随机层数控制）。

> **跳表层数怎么确定？**
> 随机：每层有 50% 概率升到下一层，最高层数通过 `ZSKIPLIST_MAXLEVEL = 32` 限制。

## 三、分布式锁底层实现细节

### 3.1 Redisson 加锁的 Lua 脚本

```lua
-- 加锁：所有操作在 Lua 中一步完成，保证原子性
-- KEYS[1] = 锁的 key
-- ARGV[1] = 锁过期时间（毫秒）
-- ARGV[2] = 客户端唯一标识（UUID:threadId）

if redis.call('exists', KEYS[1]) == 0 then
    -- 锁不存在，直接加锁
    redis.call('hincrby', KEYS[1], ARGV[2], 1)
    redis.call('pexpire', KEYS[1], ARGV[1])
    return nil
end

if redis.call('hexists', KEYS[1], ARGV[2]) == 1 then
    -- 锁存在且是当前线程持有，重入计数 +1
    redis.call('hincrby', KEYS[1], ARGV[2], 1)
    redis.call('pexpire', KEYS[1], ARGV[1])
    return nil
end

-- 锁被其他线程持有，返回剩余过期时间
return redis.call('pttl', KEYS[1])
```

**为什么用 Hash 而不用 String？** 因为 Hash 可以记录重入次数（`hincrby` 计数），而 String 只能记录是否存在。

### 3.2 Watch Dog 实现

```java

    public void startRenewal(String key, String value) {
        timer.scheduleAtFixedRate(new TimerTask() {
            @Override
            public void run() {
                // Lua 脚本：检查锁是否还在，在则续期
                String lua = "if redis.call('hexists', KEYS[1], ARGV[1]) == 1 " +
                    "then return redis.call('pexpire', KEYS[1], ARGV[2]) " +
                    "else return 0 end";
                // 执行续期...
            }
        }, RENEWAL_INTERVAL, RENEWAL_INTERVAL);
    }
}
```

### 3.3 锁续期 vs 固定过期

| 方案 | 优点 | 缺点 |
|------|------|------|
| 固定过期时间 | 简单，无额外开销 | 业务时间难预估，锁可能提前释放或长期占用 |
| Watch Dog 自动续期 | 业务时间不固定时安全 | 额外网络开销，客户端崩溃时最多 30s 后释放 |

## 四、一致性哈希

### 4.1 为什么需要一致性哈希？

Redis Cluster 使用哈希槽方式分片，但很多客户端（如 Jedis、ShardedJedis）使用**一致性哈希**。一致性哈希解决的是：**增加或减少节点时，尽可能少地影响已有数据的映射关系**。

### 4.2 原理

```
        哈希环
    ┌───────────────┐
    │    Node A      │
    │     ●          │
    │                │
    │   ●            │
    │  Node B        │
    │                │
    │          ●     │
    │       Node C   │
    └───────────────┘

数据 key 的哈希值落在环上，顺时针找到第一个节点即为目标节点。
```

**虚拟节点**：每个物理节点映射到多个虚拟节点（如 Node A 映射为 A1、A2、A3...），使数据分布更均匀，节点增减时影响范围更小。

### 4.3 一致性哈希 vs Redis Cluster 哈希槽

| 对比 | 一致性哈希 | 哈希槽（Redis Cluster） |
|------|-----------|----------------------|
| 数据分布 | 依赖虚拟节点，概率分布 | 固定 16384 槽，精确分配 |
| 节点增减 | 影响相邻节点，数据迁移量小 | 需要重新分配槽位，迁移数据 |
| 实现复杂度 | 客户端实现，较简单 | 服务端实现，较复杂 |
| 缓存场景 | 推荐（增减节点影响小） | 所有场景通用 |

### 4.4 面试关键点

> **一致性哈希和普通哈希的区别？**
> 普通哈希取模（`hash(key) % N`）在节点数变化时，绝大多数 key 的映射会改变，导致缓存雪崩。一致性哈希只有少量 key 的映射改变。

> **为什么需要虚拟节点？**
> 物理节点少时，一致性哈希在环上分布不均匀，虚拟节点让每个物理节点在环上多点分布，使数据分布更均匀。
