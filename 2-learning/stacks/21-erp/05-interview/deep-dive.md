# ERP 面试深挖题（15 题 · L3-L4）

---

## 一、业务建模深挖

### 1. 为什么 ERP 强调"数据闭环"？闭环断裂会怎样？
**追问背景**：考察对 ERP 本质的理解。

**参考答案**：
ERP 的本质是"围绕流程设计，让数据闭环流转"。闭环意味着每笔业务从发生到财务入账全程可追溯、自动流转，无需人工重复录入。

闭环断裂的后果：
1. **信息孤岛**：销售知道卖了货，但库存没扣减，导致超卖
2. **账实不符**：仓库实际有 100 件，系统显示 120 件，月末对账差异巨大
3. **成本失真**：领料没关联工单，产品成本算不准，报价失误
4. **效率低下**：每个环节人工传递数据，重复录入、易出错

所以 ERP 设计的核心是"单据驱动 + 自动流转"：销售订单自动生成发货任务、发货自动扣库存、开票自动生成应收、收款自动核销。

**考察点**：是否理解 ERP 是"流程驱动的数据系统"，而非一堆 CRUD 表。

### 2. 移动加权平均 vs 先进先出，ERP 为什么常用移动加权平均？
**追问背景**：考察成本核算的业务理解。

**参考答案**：
两种成本计算方法：
- **先进先出（FIFO）**：假设先入库的先出库，期末库存是最近的价格。适合价格波动大、有保质期的商品（食品、药品）。
- **移动加权平均**：每次入库重新计算均价，出库按当前均价。计算简单，平滑价格波动。

ERP 常用移动加权平均的原因：
1. **计算简单**：每次入库更新一次均价，出库直接用，无需维护批次成本队列
2. **平滑波动**：原材料价格波动时，均价法平滑了成本曲线，利润更稳定
3. **符合多数行业**：制造业、零售业大多用均价法

但 ERPNext 同时支持两种（在 Item 上配置 valuation method），因为：
- 有保质期/批次管理的商品（食品、电子元件）需要 FIFO 精确追溯成本
- 财务合规要求某些行业必须用特定方法

**考察点**：是否理解成本方法背后的业务逻辑，而非只会背概念。

### 3. 借贷记账法在 ERP 中如何自动实现？
**追问背景**：考察财务模块的技术实现。

**参考答案**：
ERP 通过"业务事件→会计分录模板→自动生成凭证"实现借贷记账自动化。

核心机制：
1. **科目映射表**：预定义每类业务对应的会计科目。如"采购入库"→ 借：库存商品 / 贷：应付账款
2. **分录模板引擎**：每类业务单据配置借贷模板，触发时自动填充金额
3. **平衡校验**：生成凭证时强制校验"借方合计 = 贷方合计"，不平则拒绝入账

```java
// 采购入库自动生成会计分录
public void onGoodsReceipt(GoodsReceipt gr) {
    List<JournalEntry> entries = new ArrayList<>();
    // 借：库存商品
    entries.add(new JournalEntry("库存商品", gr.getAmount(), 0));
    // 贷：应付账款
    entries.add(new JournalEntry("应付账款", 0, gr.getAmount()));
    // 平衡校验
    Assert.isTrue(sumDebit(entries) == sumCredit(entries), "借贷不平");
    glService.post(entries);
}
```

**考察点**：是否理解财务自动化的"模板+校验"机制。

## 二、MRP 深挖

### 4. MRP 计算时，为什么"已分配量"要加回净需求？
**追问背景**：考察 MRP 逻辑的严谨性。

**参考答案**：
净需求公式：`净需求 = 毛需求 - 现有库存 - 在途 + 已分配`

"已分配量"是已经被其他订单预留、但还没出库的库存。这部分库存虽然物理上还在仓库，但已经被"占用"了，不能用于新订单。

举例：
- 仓库有 100 件（现有库存）
- 其中 30 件已被 A 订单预留（已分配）
- 新订单 B 需要 80 件
- 如果不加回已分配：净需求 = 80 - 100 = -20（认为够用）→ 错误！实际可用只有 70 件
- 加回已分配：净需求 = 80 - 100 + 30 = 10（需采购 10 件）→ 正确

所以"已分配"必须加回，否则会重复分配同一批库存，导致超卖。

**考察点**：是否真正理解 MRP 每个变量的业务含义。

### 5. BOM 循环引用（A→B→A）在 MRP 展开时如何处理？
**追问背景**：考察递归算法的健壮性。

**参考答案**：
BOM 循环引用是数据错误（正常产品结构不会有环），但系统必须防御，否则递归展开会死循环。

处理方案：
1. **深度限制**：递归 CTE 加 `WHERE depth < 10`，超限自动终止
2. **访问标记**：展开时记录已访问节点，遇到重复立即报错
3. **录入校验**：BOM 保存时做环检测（拓扑排序），有环则拒绝保存
4. **告警**：展开遇到环时记录异常日志并告警，而非静默返回错误结果

推荐"录入校验 + 展开防御"双保险：录入时挡住大部分错误，展开时的深度限制和访问标记兜底。

**考察点**：是否有防御性编程意识。

## 三、集成深挖

### 6. ERP 和 MES 的库存同步，如果两边数量不一致怎么办？
**追问背景**：考察分布式一致性实战。

**参考答案**：
ERP 和 MES 库存不一致是常见问题（网络延迟、消息丢失、并发操作）。

保障机制：
1. **事件驱动 + 幂等**：每次出入库发事件，消费端幂等处理，避免重复扣减
2. **单一数据源**：明确谁是库存主数据。通常 ERP 是财务库存主源，MES 是执行库存主源，两者口径不同但通过事件对齐
3. **日终对账**：每日批量比对两边库存，差异生成对账报告，人工核实调整
4. **库存快照**：关键时点（月末）冻结库存快照，作为对账基准

不一致的根因排查：
- 消息丢失 → 检查 Outbox 状态
- 重复消费 → 检查幂等日志
- 并发冲突 → 检查锁机制

**考察点**：是否有处理分布式数据不一致的完整方案。

### 7. 为什么 ERP 的成本归集用批量而非实时？
**追问背景**：考察架构权衡。

**参考答案**：
成本归集涉及大量数据聚合（一个工单可能有几十次领料、上百次报工），实时计算代价高且没必要。

用批量的原因：
1. **成本是事后核算**：财务成本本来就是月末/日终结算，不需要秒级实时
2. **数据量大**：一个工单的成本要汇总所有领料+报工+分摊，实时算会拖慢 MES 完工响应
3. **可重算**：成本核算允许重算（如发现领料错误后重新归集），批量更适合
4. **解耦**：批量任务在业务低峰期（夜间）跑，不影响白天生产

实时性要求高的场景（如库存数量）用事件驱动，事后核算场景（如成本）用批量，这是合理的分工。

**考察点**：是否能根据业务特性选择实时/批量方案。

## 四、架构深挖

### 8. ERP 用模块化单体还是微服务？
**追问背景**：考察架构决策能力。

**参考答案**：
大多数企业用模块化单体（如 Spring Modulith），理由：
1. **业务耦合度高**：销售→库存→财务是紧密链路，拆微服务会导致大量跨服务事务
2. **数据一致性**：库存扣减 + 生成会计分录需要强一致，同库本地事务最简单
3. **团队规模**：多数企业 ERP 团队 < 20 人，微服务治理成本过高

微服务适合的场景：
- 超大型企业（多事业部、多工厂独立运营）
- 某些模块负载差异极大（如报表查询 vs 交易处理）
- 团队规模大，需要独立部署节奏

推荐路径：单体起步 → Spring Modulith 保持模块边界 → 按需拆分热点模块。

**考察点**：是否能做务实的架构决策，而非盲目微服务。

---

### 9. Spring Modulith 如何保证模块间不违规依赖？
**追问背景**：考察对模块化架构的理解。

**参考答案**：
Spring Modulith 提供架构测试能力：
1. **模块边界验证**：`ApplicationModules.of(Application.class).verify()` 自动检测跨模块的内部类访问
2. **显式接口**：模块只暴露 `internal` 包外的 API，其他模块只能调用公开接口
3. **事件解耦**：模块间通过 ApplicationEvent 通信，而非直接方法调用
4. **CI 集成**：把架构验证写成单元测试，纳入 CI，违规依赖直接构建失败

这让"模块化"从口头约定变成可执行的架构约束。

**考察点**：是否了解 Modulith 的架构守护能力。

## 五、AI 深挖

### 10. AI BI 生成 SQL 如何防止 SQL 注入和误删数据？
**追问背景**：考察 AI 落地的安全意识。

**参考答案**：
LLM 生成 SQL 有两大风险：注入攻击和误操作（删库）。

防护方案：
1. **只读账号**：AI BI 用只读数据库账号，物理上无法执行 DDL/DML
2. **SQL 白名单校验**：解析生成的 SQL，只允许 SELECT，拒绝 INSERT/UPDATE/DELETE/DROP
3. **意图约束**：Prompt 明确"只查询不修改"，并限制表范围
4. **结果行数限制**：强制 LIMIT，防止全表扫描拖垮数据库
5. **审计日志**：所有 AI 生成的 SQL 记录审计，可追溯
6. **沙箱执行**：查询走只读副本，不影响主库

核心原则：不信任 LLM 的输出，用数据库权限层做最后一道防线。

**考察点**：是否有 AI 工程化的安全意识。
