## 1. Embedding 模型对比

### 1.1 主流 Embedding 模型详细对比

| 维度 | OpenAI text-embedding-3-large | BGE-m3 | Cohere Embed v3 | text2vec-large |
|------|------------------------------|--------|----------------|---------------|
| 向量维度 | 3072（可降维） | 1024 | 1024 | 1024 |
| 最大输入 | 8191 tokens | 8192 tokens | 512 tokens | 512 tokens |
| 多语言 | 英文为主 | 多语言（中英日韩） | 多语言 | 中文 |
| 检索精度 (MTEB) | 64.6 | 64.0 | 62.6 | 61.2 |
| 速度 | API 调用，延迟依赖网络 | 本地，GPU 约 10ms/条 | API 调用 | 本地，GPU 约 5ms/条 |
| 成本 | $0.13/1M tokens | 免费自部署 | 按量付费 | 免费自部署 |
| 适用场景 | 国际通用场景 | 中文为主的多语言 | 企业级多语言 | 中文场景，预算敏感 |

**选型原则**：
- 中文场景优先 BGE 系列（bge-m3 或 bge-large-zh-v1.5）
- 不在乎成本选 OpenAI（精度最高）
- 资源受限选 M3E 或 bge-small（384维，速度快）

### 1.2 双编码器 vs 交叉编码器

```
双编码器（Bi-Encoder）：
query → [Encoder] → 向量 q
doc   → [Encoder] → 向量 d
score = cos(q, d)

特点：独立编码，可预计算，适合大规模检索，速度快
精度：中

交叉编码器（Cross-Encoder）：
[query; doc] → [Encoder] → score

特点：拼接编码，看到完整交互，精度高，速度慢
精度：高
```

**典型配合**：Bi-Encoder 用于召回（top-30），Cross-Encoder 用于精排（top-5）。

## 2. 向量索引原理

### 2.1 HNSW（Hierarchical Navigable Small World）

HNSW 是目前最主流的 ANN（近似最近邻）索引算法。

```
核心思想：分层图结构
- 顶层：少量节点（粗粒度，快速定位区域）
- 中间层：逐步细化
- 底层：完整节点（细粒度，精确搜索）

搜索过程类似"跳表"：从顶层开始，逐层细化到最底层。
```

**HNSW 参数**：

| 参数 | 说明 | 推荐值 | 效果 |
|------|------|--------|------|
| M | 每个节点的最大连接数 | 16~64 | 越大精度越高，索引越大 |
| efConstruction | 构建时的动态列表大小 | 100~200 | 越大构建越慢，索引质量越高 |
| efSearch | 搜索时的动态列表大小 | 100~500 | 越大精度越高，查询越慢 |

**HNSW 优劣势**：
- 优点：高精度（>95% recall），查询速度快（毫秒级）
- 缺点：内存占用大，构建慢，不适合频繁更新

### 2.2 IVF（Inverted File Index）

```
核心思想：聚类 + 倒排
1. 将所有向量聚为 N 个簇（类似 K-means）
2. 检索时只查最近的几个簇
3. 簇内暴力搜索

搜索过程：
query → 找到最近的 nprobe 个簇 → 簇内线性搜索
```

**IVF 参数**：

| 参数 | 说明 | 推荐值 | 效果 |
|------|------|--------|------|
| nlist | 聚类数 | 100~4096 | 越大索引越大，搜索越精确 |
| nprobe | 搜索时探查的簇数 | 1~20 | 越大精度越高，查询越慢 |

**IVF 优劣势**：
- 优点：内存占用低，构建快，适合大规模数据
- 缺点：精度低于 HNSW，需要调参

### 2.3 索引选型

| 场景 | 推荐索引 | 原因 |
|------|---------|------|
| 10万级数据，高精度 | HNSW | 精度高，速度快 |
| 百万级数据，内存敏感 | IVF+PQ | 量化压缩，内存省 |
| 亿级数据，分布式 | DiskANN | 支持磁盘存储 |
| 频繁更新 | IVF | 重建快，HNSW 增量更新成本高 |

## 3. RRF 变体

### 3.1 标准 RRF

```
score(doc) = Σ 1 / (k + rank_i)
```

- k=60 是原论文的推荐值
- 所有检索器等权，仅依赖排名

### 3.2 加权 RRF

```
score(doc) = Σ w_i / (k + rank_i)

w_i 为第 i 个检索器的权重
```

**适用场景**：当某个检索器效果明显优于其他时，可给予更高权重。

### 3.3 归一化 RRF

```
score(doc) = Σ 1 / (k + rank_i) / Σ 1 / (k + i)

分子：实际 RRF 分数
分母：理论最大分数（所有排名都排第一）
结果：归一化到 [0, 1]
```

**优点**：分数有明确的语义（0~1），便于设定阈值。

### 3.4 扩展 RRF

```
score(doc) = Σ 1 / (k + rank_i) + α × score_i(doc)

加入原始分数信息，弥补纯排名融合的信息损失。
α 为原始分数的权重，通常很小（0.01~0.1）。
```

## 4. Reranker 原理

### 4.1 交叉编码器的工作机制

```
输入：[CLS] query [SEP] doc [SEP]
      ↓
Transformer 编码器（如 BERT）
      ↓
[CLS] 位置的输出向量
      ↓
线性层 → 分类/回归分数
```

**为什么比双编码器更准？**

```
双编码器：query 和 doc 独立看，丢失了"query 中的关键词在 doc 中出现的位置和上下文"
交叉编码器：能直接看到 query 词与 doc 词的 attention 交互，捕捉细粒度匹配
```

### 4.2 主流 Reranker 模型

| 模型 | 特点 | 延迟（单条） | 精度 |
|------|------|-------------|------|
| BAAI/bge-reranker-v2-m3 | 多语言，1024 tokens | ~50ms (GPU) | 高 |
| BAAI/bge-reranker-large | 英文，512 tokens | ~80ms (GPU) | 最高 |
| cross-encoder/ms-marco-MiniLM-L6-v2 | 轻量，512 tokens | ~10ms (GPU) | 中 |
| Cohere Rerank | API 调用，不限长度 | 依赖网络 | 高 |

### 4.3 Reranker 延迟优化

```python
# 优化策略
strategies = {
    "批量推理": "一次传入多个 pair，利用 GPU 并行",
    "模型量化": "INT8 量化，推理速度提升 2x，精度损失 <1%",
    "截断输入": "只取 query+doc 前 512 tokens（超过部分截断）",
    "级联重排": "先用轻量级模型粗排 top-50 → 再用大模型精排 top-5",
```

## 5. 高级话题

### 5.1 上下文窗口与 RAG 的关系

| 模型 | 上下文窗口 | RAG 影响 |
|------|-----------|---------|
| GPT-4 | 128K | 可一次放入大量检索片段，但"大海捞针"问题 |
| GPT-4o-mini | 128K | 同上，成本更低 |
| Claude 3 | 200K | 大窗口下检索精度更重要 |
| 国产模型 | 4K~128K | 窗口小的模型分块要更精细 |

**大海捞针问题**：上下文越长，LLM 越难找到关键信息。检索质量 > 检索数量。
