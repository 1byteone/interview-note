# 企业平台整合面试深挖题（15 题 · L3-L4）

---

## 一、架构深挖

### 1. 三域为什么要用事件驱动而不是直接 REST 调用？
**追问背景**：考察集成架构的权衡。

**参考答案**：
REST 直接调用的问题：
1. **强耦合**：MES 挂了，ERP 完工回报就失败，影响生产
2. **同步阻塞**：MES 完工要等 ERP 入库成功才能返回，延迟高
3. **事务难题**：跨系统 REST 调用无法用本地事务保证一致性

事件驱动的优势：
1. **解耦**：生产者只管发消息，不关心消费者是否在线
2. **异步**：MES 完工后立即返回，ERP 异步消费
3. **削峰**：MQ 缓冲突发流量，消费者按自己的速度处理
4. **可靠性**：Outbox 模式保证消息不丢，失败可重试

但事件驱动也有代价：最终一致性（有延迟）、排查链路复杂（需要链路追踪）、消费顺序难保证。

**考察点**：是否理解事件驱动 vs 同步调用的 trade-off，而非只说"事件驱动好"。

### 2. 三域如果各自独立部署，服务发现怎么做？
**追问背景**：考察微服务治理能力。

**参考答案**：
三域独立部署时的服务发现方案：

方案一：Spring Cloud Gateway + Nacos（轻量）
- 三域各自注册到 Nacos
- Gateway 根据路由规则转发
- OA 调 ERP/MES 通过 Gateway 路由

方案二：服务网格 Istio（K8s 场景）
- 三域作为 K8s Pod 部署
- Istio sidecar 自动管理服务发现和负载均衡
- 无需改代码

推荐中小团队用 Nacos，大团队用 Istio。

**考察点**：是否有实际的服务发现和部署经验。

---

### 3. Spring Modulith 和微服务的核心区别是什么？
**追问背景**：考察架构理解深度。

**参考答案**：
| 维度 | Spring Modulith | 微服务 |
|------|-----------------|--------|
| 部署单元 | 一个 JAR | 每个服务独立 JAR |
| 进程 | 同一进程 | 不同进程 |
| 通信 | 方法调用 / ApplicationEvent | HTTP / RPC / MQ |
| 数据库 | 共享（或分 Schema） | 独立数据库 |
| 事务 | 本地事务 | 分布式事务或最终一致 |
| 运维 | 简单 | 复杂（K8s + 链路追踪） |

Modulith 的核心价值：**保持模块边界的同时享受单体的简单性**。代码层面模块自治（包隔离 + 接口通信），部署层面还是单体。

演进路径：单体 → Modulith（保持模块边界）→ 按需拆分热点模块为独立服务 → 微服务（多工厂场景）。

**考察点**：是否理解架构演进的务实路径，而非跳跃式上微服务。

### 4. 如果 MQ 消息丢失了，怎么发现和修复？
**追问背景**：考察消息可靠性的运维能力。

**参考答案**：
发现机制：
1. **Outbox 监控**：PENDING 状态超过 5 分钟的记录 → 告警
2. **死信队列**：DLQ 积压数 > 0 → 告警
3. **日终对账**：MES 工单 vs ERP 生产订单数量不一致 → 告警
4. **业务反馈**：用户报告"审批通过了但 ERP 没收到" → 人工检查

修复方案：
1. **重发**：找到 PENDING 的 Outbox 记录，手动重新投递
2. **补偿**：ERP 侧检查是否有遗漏的工单，手动创建
3. **根因排查**：检查 MQ 集群状态、网络、消费者日志

**考察点**：是否有消息可靠性的运维实战意识。

## 二、数据一致性深挖

### 5. 三域数据不一致的典型场景有哪些？
**追问背景**：考察分布式系统实战。

**参考答案**：
| 场景 | 原因 | 检测方式 | 修复方式 |
|------|------|---------|---------|
| MES 完工但 ERP 未入库 | MQ 投递失败 | 对账 | 重发消息 |
| ERP 库存扣减但 MES 领料未记录 | 消息乱序 | 对账 | 手动补录 |
| OA 审批通过但 ERP 未创建 PO | 消费者异常 | 死信队列 | 重发 + 手动创建 |
| 三方库存数量不一致 | 并发操作 | 日终对账 | 以 ERP 为准调整 |

核心原则：**不追求强一致，保证最终一致 + 对账兜底**。

---

### 6. 对账发现数据不一致，以谁为准？
**追问背景**：考察数据治理策略。

**参考答案**：
按域确定数据权威源：

| 数据类型 | 权威源 | 理由 |
|---------|--------|------|
| 财务数据 | ERP | 财务合规要求 |
| 生产执行数据 | MES | 车间实时性要求 |
| 审批状态 | OA | 审批记录不可篡改 |
| 库存数量 | ERP（财务视角） | 月末对账以 ERP 为准 |
| 批次追溯 | MES | 车间追溯最准确 |

对账不一致时，以权威源为准，生成调整单据，记录审计日志。

**考察点**：是否有数据治理的全局视角。

## 三、业务深挖

### 7. 紧急插单时三域如何协同处理？
**追问背景**：考察跨域业务协同能力。

**参考答案**：
```
1. ERP 接收紧急订单（优先级=URGENT）
2. ERP 重新计算排产：识别可延迟的工单
3. ERP 通知 MES：暂停可延迟工单，插入紧急工单
4. MES 调整排产：紧急工单优先分配设备
5. ERP 通知 OA：原订单交期变更，通知客户
6. OA 发送通知：相关方知晓交期调整
```

关键：三域需要共享一个"排产视图"，ERP 做宏观调整，MES 做微观执行。

---

### 8. 月末结账时三域如何协同？
**追问背景**：考察财务视角的跨域协作。

**参考答案**：
```
月末结账流程（T日）：
1. ERP 冻结当月业务（截止过账日期）
2. MES 汇总当月完工数据 → 发送给 ERP
3. ERP 成本归集：材料+人工+制造费用 → 生成成本凭证
4. ERP 损益结转：收入-成本-费用 → 生成利润凭证
5. ERP 生成报表：资产负债表/利润表
6. 对账：ERP vs OA vs MES 数据一致性校验
7. 关账：锁定当月凭证
```

---

### 9. 三域如何支持多工厂场景？
**追问背景**：考察架构扩展性。

**参考答案**：
多工厂方案：
1. **数据隔离**：每个工厂独立 Schema 或独立数据库
2. **组织架构**：sys_dept 支持多级工厂→车间→产线
3. **数据权限**：工厂经理只看本工厂数据
4. **MRP 分工厂**：每个工厂独立计算 MRP
5. **MES 独立部署**：每个工厂一套 MES 实例
6. **ERP 统一**：ERP 一套，多工厂共享主数据和财务

## 四、AI 深挖

### 10. AI 在三域中最大的价值是什么？
**追问背景**：考察 AI 落地的业务判断力。

**参考答案**：
最大的价值不是"炫技"，而是**减少人工重复劳动**：
- OA：RAG 知识问答 → HR 重复咨询减少 60%
- ERP：AI BI → 管理者不用等报表，自助查数据
- MES：智能排产 → 排产员从 2 小时缩短到 15 分钟

AI 增强的正确姿态是"嵌入现有业务"，而非"独立的 AI 系统"。

## 五、场景设计深挖

### 11. 设计"客户退货→三域协同处理"流程
**参考答案**：
```
1. ERP 创建退货单（Sales Return）
2. 仓库收货 → ERP 入库（库存 +）
3. ERP 通知 MES：质量检查退货品
4. MES 质检 → 判定：返工/报废
5. 如果返工 → MES 创建返工工单
6. 如果报废 → ERP 财务核销
7. OA：异常审批（如果是系统性问题）
8. ERP：更新客户信用 / 退款
```

---

### 12. 三域如何保证审计合规（ISO 9001）？
**参考答案**：
ISO 9001 要求"所有操作可追溯、可审计"：
- OA：审批记录不可修改（append-only）
- ERP：单据状态变更日志（who/when/what）
- MES：工单流转日志 + 追溯记录
- 三域：操作审计日志（全量记录）

### 13. 如何用三域架构支撑"工业互联网平台"？
**参考答案**：
在三域基础上增加 IoT 层：
- 设备层：PLC/传感器 → MQTT → 时序库
- 边缘层：边缘计算网关 → 本地预处理
- 平台层：三域平台 + IoT 数据融合
- 应用层：预测性维护 + 数字孪生 + 能耗优化
