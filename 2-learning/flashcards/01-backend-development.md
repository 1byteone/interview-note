### Card 1: RESTful 规范
**维度**: 📝速记 | **难度**: ⭐

> **Q: RESTful API 中 HTTP 方法如何对应 CRUD 操作？幂等性和安全性如何区分？**

**A:** GET（查询，幂等安全）、POST（创建，非幂等非安全）、PUT（全量更新，幂等）、DELETE（删除，幂等）。安全性指不改变资源状态；幂等性指多次执行结果相同。PUT 和 DELETE 幂等，POST 非幂等（每次创建新资源）。

### Card 2: HTTP 状态码分类
**维度**: 📝速记 | **难度**: ⭐

> **Q: HTTP 状态码的 5 大类分别代表什么？各举 2 个常见例子。**

**A:** 1xx 信息（101 Switching Protocols），2xx 成功（200 OK，201 Created），3xx 重定向（301 永久，302 临时），4xx 客户端错误（400 Bad Request，404 Not Found，429 Too Many Requests），5xx 服务端错误（500 Internal，502 Bad Gateway，503 Service Unavailable）。

### Card 3: CAP 定理
**维度**: 🔬深挖 | **难度**: ⭐⭐

> **Q: 什么是 CAP 定理？分布式系统中如何取舍？**

**A:** CAP 指一致性（Consistency）、可用性（Availability）、分区容错性（Partition Tolerance），三者不可兼得。网络分区（P）必然发生，实际在 C 和 A 之间权衡：ZooKeeper 选 CP（强一致），Eureka 选 AP（高可用），Nacos 支持 CP/AP 切换。AP 场景可接受最终一致性。

### Card 4: BASE 理论
**维度**: 📝速记 | **难度**: ⭐

> **Q: BASE 理论是什么？与 ACID 的区别是什么？**

**A:** BASE = Basically Available（基本可用）+ Soft State（软状态）+ Eventually Consistent（最终一致性）。ACID 追求强一致，适合单体数据库；BASE 追求最终一致，适合分布式系统。BASE 牺牲强一致换可用性，是 CAP 中 AP 权衡的实践体现。

### Card 5: 分布式 ID 生成方案
**维度**: 🔬深挖 | **难度**: ⭐⭐

> **Q: 分布式 ID 需满足哪些要求？主流方案有哪些？**

**A:** 要求：全局唯一、趋势递增、高可用、高吞吐。方案：① UUID（无序、太长，不适合做索引）；② 数据库自增步长（扩展难）；③ 雪花算法（64bit，1bit 符号+41bit 时间戳+10bit 机器+12bit 序列，时钟回拨有隐患）；④ 号段模式（Leaf 方案，预取号段到内存）。

### Card 6: 秒杀系统设计
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: 设计秒杀系统要考虑哪些问题？如何应对高并发？**

**A:** ① 前端限流（按钮置灰、验证码、CDN 静态化）；② 后端分层削峰（Nginx 限流 → 网关限流 → Redis 令牌桶 → 消息队列排队）；③ 库存扣减用 Redis Lua 脚本保证原子性；④ 异步落单（MQ 削峰，最终库存扣减走 DB）；⑤ 防刷（用户维度限流、设备指纹）。

### Card 7: 短链系统设计
**维度**: 🎯场景 | **难度**: ⭐⭐

> **Q: 设计短 URL 系统的核心思路是什么？如何处理冲突？**

**A:** 核心：发号器生成唯一 ID → 62 进制编码（数字+大小写字母）→ 映射出短链接。冲突处理：① 预生成号段（发号器提前分配 batch）；② 用布隆过滤器判断短链是否存在；③ 数据库唯一索引兜底。重定向用 301 可缓存，302 可追踪点击数。

### Card 8: DDD 与三层架构区别
**维度**: 🔬深挖 | **难度**: ⭐⭐

**Q: DDD 与传统的三层架构有何本质区别？**

**A:** 三层架构（Controller → Service → DAO）以数据为中心，业务逻辑散落在 Service 中，容易变成"贫血模型"。DDD 以领域为中心，用聚合根封装业务规则，强调充血模型（实体包含行为），通过限界上下文划分领域边界。DDD 适合复杂业务，三层架构适合简单 CRUD。

### Card 9: API 版本管理策略
**维度**: 📝速记 | **难度**: ⭐

> **Q: API 版本管理有哪些方式？推荐哪种？**

**A:** ① URL 路径版本 `/api/v1/orders`（最常用，直观；缺点：URL 污染）；② 请求头版本 `Accept: application/vnd.myapp.v1+json`（优雅，但调试不便）；③ 查询参数 `?version=1`（简单，但易忘记）。推荐 URL 路径版本，破坏性变更加版本号，6-12 个月过渡期后废弃旧版。

### Card 10: 限流算法对比
**维度**: 🔬深挖 | **难度**: ⭐⭐

> **Q: 令牌桶与漏桶算法有什么区别？分别适用于什么场景？**

**A:** 令牌桶：以固定速率生成令牌，桶满则丢弃，允许突发流量（有令牌就消费），适合接口限流。漏桶：以固定速率流出，超出桶容量则丢弃，平滑流量零突发，适合流量整形保护下游。滑动窗口：精确统计时间窗口内请求数，解决了固定窗口的边界突刺问题。

### Card 11: 熔断与降级
**维度**: 📝速记 | **难度**: ⭐

> **Q: 熔断和降级有什么区别？熔断的三个状态是什么？**

**A:** 熔断是应对**下游故障**：当错误率达到阈值时切断调用，防止级联故障（雪崩）；降级是**主动放弃**非核心功能，保证核心功能可用。熔断三状态：Closed（正常）→ Open（熔断开启）→ Half-Open（半开试探恢复），Half-Open 成功后回到 Closed。

### Card 12: 负载均衡算法
**维度**: 📝速记 | **难度**: ⭐

> **Q: 常见的负载均衡算法有哪些？各有什么优缺点？**

**A:** ① 轮询（依次分发，简单但忽略服务器差异）；② 加权轮询（按权重分配，适合异构集群）；③ 最小连接数（分给活跃连接最少的，适合长连接场景）；④ IP Hash（同一 IP 固定到同一台，解决 Session 问题）；⑤ 一致性 Hash（缓存场景，减少节点增减时的 rehash 量）。

### Card 13: 接口幂等方案
**维度**: 🎯场景 | **难度**: ⭐⭐

> **Q: 如何保证接口的幂等性？具体实现方案有哪些？**

**A:** ① 唯一索引/唯一约束（DB 层防重复插入）；② 幂等 Token（先获取 token，请求时携带，处理一次后删除）；③ 状态机幂等（利用业务状态判断，如"已支付"不可重复支付）；④ 去重表（建立去重流水表，唯一键防重）；⑤ 乐观锁（version 字段，CAS 更新）。

### Card 14: 数据一致性方案
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: 分布式系统中如何保证数据最终一致性？**

**A:** ① 本地消息表（业务操作 + 消息表在同一个本地事务，定时任务扫表发送）；② 事务消息（RocketMQ 半消息 + 回查机制）；③ TCC（Try-Confirm-Cancel，两阶段补偿，业务侵入大）；④ Saga（长事务拆成子事务 + 补偿，适合跨服务编排）；⑤ Seata AT（自动代理 SQL，无侵入）。

### Card 15: 系统设计方法论
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: 面试中系统设计题的通用解题框架是什么？**

**A:** 四步法：① 场景确认（功能需求 + 非功能需求，QPS/数据量/延迟要求）；② 存储设计（数据库选型、表结构、索引策略）；③ 架构设计（分层架构、模块划分、核心流程时序）；④ 扩展优化（缓存、分库分表、多级缓存、CDN）。要点：先确定边界，再逐步细化，最后关注瓶颈和容错。
