### Card 1: 单线程模型与高性能
**维度**: 🔬深挖 | **难度**: ⭐⭐

> **Q: Redis 单线程为什么还能如此高性能？**

**A:** ① 纯内存操作（内存访问速度是磁盘的 10 万倍）；② 非阻塞 IO 多路复用（epoll，单线程管理大量连接）；③ 避免上下文切换和锁竞争（单线程天然无锁）；④ 数据结构简单高效（跳表、压缩列表等）。Redis 6.0+ 在网络 IO 引入多线程，命令执行仍是单线程。瓶颈通常在内存和网络，而非 CPU。

### Card 2: 5 大数据结构底层编码
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: Redis 的 5 种基本数据结构底层分别是什么编码？何时发生转换？**

**A:** String：int（整数）、embstr（<44B）、raw（长字符串）。Hash：ziplist（字段 <512 且值 <64B）→ hashtable。List：quicklist（ziplist 节点双向链表）。Set：intset（整数且 <512 个）→ hashtable。ZSet：ziplist（成员少且值小）→ skiplist + dict（跳表存 score 排序，dict 存 member→score 映射）。阈值由 `hash-max-ziplist-entries` 等配置控制。

### Card 3: 持久化 RDB vs AOF
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: RDB 和 AOF 持久化的区别是什么？生产环境如何选择？**

**A:** RDB：fork 子进程生成全量二进制快照，恢复极快，但可能丢分钟级数据。AOF：追加写命令日志，`everysec` 每秒 fsync，最多丢 1 秒数据。AOF 体积大，恢复慢。Redis 4.0+ 推荐混合持久化：RDB 头 + AOF 增量，结合 RDB 恢复快和 AOF 数据安全。恢复优先级：AOF 开启则加载 AOF，否则加载 RDB。

### Card 4: 缓存穿透
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: 什么是缓存穿透？如何解决？**

**A:** 缓存穿透指查询不存在的数据，请求绕过缓存直接打到数据库。解决方案：① 布隆过滤器（拦截所有不存在 key 的请求，Redis Bitmap 实现，说"不存在"一定不存在，说有误判）；② 缓存空对象（查询不存在的数据也缓存，设置短 TTL，如 30 秒）；③ 参数校验（非法参数直接拒绝，如 id < 0）。布隆过滤器无法删除，可用计数布隆过滤器（CBF）或 Redis 4.0+ Bloom Module。

### Card 5: 缓存击穿
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: 缓存击穿和缓存穿透有什么区别？如何解决缓存击穿？**

**A:** 缓存击穿是热点 key 失效瞬间，高并发全部打到数据库。缓存穿透是查询不存在的数据。解决方案：① 互斥锁（SETNX 加锁，只允许一个线程回源查 DB，其他等待）；② 逻辑过期（缓存中不设置 TTL，而是存一个逻辑过期时间，发现过期时启动异步线程更新缓存，其他线程返回旧数据）；③ 热点 key 永不过期（不设 TTL，后台定时更新）。

### Card 6: 缓存雪崩
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: 缓存雪崩的原因和解决方案是什么？**

**A:** 缓存雪崩指大量 key 同时过期或 Redis 宕机，大量请求打到数据库。解决方案：① 过期时间加随机值（`TTL + random(1-300)`），避免同时过期；② 多级缓存（本地 Caffeine → Redis → MySQL）；③ 互斥锁（回源时加锁，降低 DB 压力）；④ 缓存预热（系统上线前提前加载缓存）；⑤ 高可用（Redis Sentinel/Cluster，防止宕机）；⑥ 限流降级（Nginx 限流，返回降级数据）。

### Card 7: 分布式锁实现
**维度**: 💻代码 | **难度**: ⭐⭐⭐

> **Q: 如何用 Redis 实现可靠的分布式锁？**

**A:** 加锁：`SET key uuid NX EX 30`（原子操作，UUID 标识持有者）。解锁：Lua 脚本 `if redis.call("get",KEYS[1])==ARGV[1] then return redis.call("del",KEYS[1]) else return 0 end`（原子性，防止误删其他线程的锁）。Redisson 可重入锁：Hash 结构记录重入次数，`hincrby` 加锁，`hincrby -1` 解锁。Watch Dog：默认 30 秒过期，每 10 秒自动续期，客户端崩溃时停止续期，避免死锁。

### Card 8: Redisson 原理
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: Redisson 的 Watch Dog 机制是如何实现的？**

**A:** Watch Dog 是 Redisson 实现的自动续期机制。客户端获取锁后，后台启动一个定时任务（Netty 的 Timeout），每 10 秒执行一次 Lua 脚本，检查锁是否存在且持有者是自己，如果是则重置过期时间为 30 秒。如果客户端崩溃，Netty 的 EventLoop 停止，定时任务不再执行，锁自动过期释放。Watch Dog 默认关闭（`lockWatchdogTimeout` 参数控制），在通过 `lock()` 方法（无参）时自动开启，`tryLock(10, TimeUnit.SECONDS)` 指定过期时间时不开启。

### Card 9: RedLock 算法
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: RedLock 解决的是什么问题？它的加锁步骤是什么？**

**A:** RedLock 解决 Redis 主从切换时锁丢失的问题：在主节点写入锁后，主节点宕机，从节点未同步，新主节点没有锁信息，其他线程可获取锁。步骤：① 获取当前时间；② 依次在 N 个独立节点加锁（N=5 个，设置超时时间）；③ 计算获取锁的总耗时；④ 如果大多数节点（N/2+1）加锁成功且总耗时 < 锁 TTL，则加锁成功；⑤ 加锁失败则向所有节点发送解锁。争议：RedLock 不能保证绝对的强一致性，且需要独立部署的节点，集群中不适用。

### Card 10: Lua 脚本原子性
**维度**: 💻代码 | **难度**: ⭐⭐

> **Q: Redis 为什么支持 Lua 脚本？Lua 脚本的原子性如何保证？**

**A:** Redis 使用内置 Lua 解释器，整个脚本作为单个命令执行，期间不会被其他命令打断（原子性）。`EVAL` 命令执行脚本，`SCRIPT LOAD` 缓存脚本返回 SHA1，`EVALSHA` 用 SHA 执行。局限：脚本执行期间阻塞其他命令，不能执行长时间脚本（`lua-time-limit` 5000ms，超时后日志记录但不停止）。CAS 操作（如分布式锁解锁）通过 Lua 脚本保证原子性，避免竞态条件。

### Card 11: Redis Cluster 哈希槽
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: Redis Cluster 的哈希槽是如何分配的？数据如何路由？**

**A:** 16384 个哈希槽：`CRC16(key) % 16384` 计算槽位。槽位均匀分配到主节点（如 3 节点：0-5460、5461-10922、10923-16383）。客户端请求的 key 不在当前节点时，返回 MOVED 重定向（告知正确节点）或 ASK 重定向（迁移中）。`CLUSTER ADDSLOTS` 手动分配槽。`hash tag`（`{user1001}`）强制多个 key 进入同一槽，支持多 key 操作。Cluster 要求至少 3 主 3 从。

### Card 12: 哨兵模式
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: Redis Sentinel 的高可用原理是什么？故障转移的过程是怎样的？**

**A:** Sentinel 监控主节点，发现不可达时标记 sdown（主观下线），多个 Sentinel 都确认后标记 odown（客观下线），触发故障转移。选举新主节点：① 从从节点中过滤掉宕机的、断开连接的、优先级低的；② 按 replica-priority 优先级选择，优先选复制偏移量最大的从节点。Sentinel 至少 3 个节点，避免"脑裂"。哨兵是 Client 发现主节点的方式（客户端通过哨兵获取当前主节点地址）。

### Card 13: 大 Key 排查与处理
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: 如何发现和处理 Redis 大 Key？大 Key 有什么危害？**

**A:** 大 Key 标准：String > 10MB，集合 > 5000 个元素。危害：① 阻塞 Redis 单线程（操作大 key 耗时）；② 网络延迟（传输大数据）；③ 数据倾斜（集群中某些节点内存占满）；④ 过期删除阻塞（`DEL` 删除大 key 阻塞）。发现：`redis-cli --bigkeys` 扫描，`MEMORY USAGE key` 查看内存。处理：① 拆分（hash 分桶，`key:{hash}`）；② 分页操作（`LRANGE 0 99`）；③ 异步删除（`UNLINK` 非阻塞删除）。

### Card 14: 热 Key 处理
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: 如何发现和处理 Redis 热 Key？**

**A:** 发现：① `redis-cli --hotkeys`（需要 `maxmemory-policy` 为 LFU）；② `MONITOR` 命令（生产慎用，增加负载）；③ 客户端统计（记录访问频率）；④ 代理层（如 Twemproxy）统计。处理：① 本地缓存（Caffeine，最有效）；② 散列打散（key 加随机后缀，如 `product:123:{rand}`，分散到多个节点）；③ 读写分离（从节点分担读）；④ 限流（热点 key 触发限流保护）。

### Card 15: 过期策略与内存淘汰
**维度**: 🔬深挖 | **难度**: ⭐⭐

**Q: Redis 的过期删除策略和内存淘汰策略分别是什么？**

**A:** 过期删除：惰性删除（访问时检查过期，过期则删）+ 定期删除（每秒 10 次，每次随机检查 20 个 key，删除过期 key，超过 25% 重复）。内存淘汰策略（`maxmemory-policy`）：`noeviction`（默认，不淘汰，写失败）、`allkeys-lru`（最常用，淘汰最久未使用的）、`allkeys-lfu`（淘汰最少使用的，适合热点场景）、`volatile-lru`（仅淘汰设置了 TTL 的 key）、`volatile-ttl`（淘汰 TTL 最短的）。LRU 在 Redis 中近似实现（采样 5 个 key 淘汰最久未使用的）。

### Card 16: Pipeline 批量操作
**维度**: 💻代码 | **难度**: ⭐⭐

> **Q: Redis Pipeline 和普通操作的性能差异有多大？使用时需要注意什么？**

**A:** Pipeline 将多个命令打包一次性发送，减少网络 RTT（Round-Trip Time）。批量 1000 条命令：普通操作约 1000ms（网络延迟 1ms），Pipeline 约 1ms（一次发送）。注意：① Pipeline 不是原子性的（服务器仍逐条执行）；② 返回结果按顺序对应；③ 不要 Pipeline 过多命令（避免内存堆积，建议 100-500 条一批）；④ Pipeline 中的命令执行结果暂存在内存中，全部执行完才返回。

### Card 17: 缓存一致性方案
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: 如何保证数据库和缓存的一致性？**

**A:** 推荐方案：先更新数据库，再删除缓存（Cache-Aside 模式）。原因：先删缓存再更新 DB 在并发下会有脏数据（读请求把旧数据写入缓存）。更新 DB 后删除缓存，下次读取时回填新数据，最终一致。如果删除缓存失败：① 延迟双删（先删缓存→更新 DB→延迟再删缓存）；② 消息队列（MQ 异步重试删除）；③ Canal 监听 binlog 变更（订阅 MySQL binlog 变更，自动刷新缓存）。强一致性场景：读请求也走分布式锁，读时加锁写时加锁（性能差，不推荐）。

### Card 18: Redis 单线程模型细节
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: Redis 6.0 的多线程 IO 是如何工作的？为什么命令执行仍然单线程？**

**A:** Redis 6.0 引入多线程处理网络 IO（读/写），但命令执行仍然是单线程。多线程 IO 流程：主线程 accept 连接 → 将就绪的 fd 分配给 IO 线程（轮询）→ IO 线程并行读取请求 → 主线程串行执行命令 → IO 线程并行写回响应。`io-threads` 配置线程数（默认 4），`io-threads-do-reads yes` 开启读线程。多线程 IO 只解决网络瓶颈，命令执行单线程保证无锁和原子性。
