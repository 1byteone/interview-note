# RAG — 面试抽认卡

> 来源：`learn/15-rag/05-interview/`

---

### Card 1: RAG vs 微调
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: RAG 和微调的区别是什么？什么场景选择 RAG？**

**A:** RAG 外挂知识库，检索相关文档后生成回答，知识更新只需更新向量库，成本低，可解释（可溯源到原文）。微调更新模型参数，让模型学习领域风格和格式，成本高，更新慢，幻觉无法消除。选型：知识密集型（产品文档、FAQ、政策法规）→ RAG；风格/格式学习（客服话术、邮件模板）→ 微调；两者可结合（RAG 检索 + 微调优化输出风格）。

### Card 2: 分块策略对比
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: 文档分块策略有哪些？如何选择最佳分块大小？**

**A:** 固定大小分块（最简单，但破坏语义边界，相邻块可能不相关）；递归字符分块（推荐，按 `\n\n` → `\n` → `.` → ` ` 递归分割，语义连贯）；语义分块（按 Embedding 语义边界切分，精度高但计算量大）；特定文档分块（Markdown 按标题、代码按函数、HTML 按标签）。分块大小：256-1024 tokens 为常见范围。太小→上下文不足；太大→噪声多、检索精度下降。重叠（chunk overlap）：相邻块重叠 10-20%，避免信息被截断丢失。

### Card 3: 向量库选型
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: 主流向量数据库对比和选型建议？**

**A:** Milvus：分布式，支持千亿级向量，功能丰富（混合检索、多索引），适合大规模生产。Pinecone：托管 SaaS，零运维，按量付费，适合快速验证。Weaviate：内置向量化模块（开箱即用），支持 GraphQL，适合中小规模。Qdrant：Rust 实现，性能高，支持过滤和分组。FAISS：Meta 开源库，本地运行，适合小规模/原型。Chroma：轻量级，嵌入应用，适合开发测试。选型建议：原型用 FAISS/Chroma，生产小规模用 Qdrant/Weaviate，大规模用 Milvus/Pinecone。

### Card 4: Embedding 模型对比
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: 主流 Embedding 模型有哪些？如何选择？**

**A:** 国外：OpenAI text-embedding-3-small（1536 维，性价比高）、text-embedding-3-large（3072 维，精度高）、Cohere Embed（支持多语言）。国产：BGE（bge-m3，1024 维，中英双语）、M3E（中文优化）、text2vec（中文）。选择因素：① 语义匹配精度（在 MTEB 榜单上对比）；② 维度（高维度精度高但存储大）；③ 语言支持（中文场景优先国产模型）；④ 向量维度一致性（训练和推理用同一模型）；⑤ 延迟和成本（API 调用 vs 本地部署）。

### Card 5: 混合检索
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: 为什么需要混合检索？BM25 和向量检索如何互补？**

**A:** 向量检索擅长语义匹配（"苹果手机"→"iPhone 15 Pro"），BM25 擅长精确匹配（"型号 A2634"→"A2634"）。混合检索取长补短：向量检索召回语义相关但可能忽略精确关键词，BM25 召回精确匹配但可能遗漏同义词。BM25 基于词频（TF）和逆文档频率（IDF），参数 k1（饱和度，默认 1.2）和 b（长度归一化，默认 0.75）。混合检索流程：向量检索 + BM25 检索 → RRF 或加权融合 → 排序输出。

---

### Card 6: RRF 融合
**维度**: 🔬深挖 | **难度**: ⭐⭐

> **Q: RRF（Reciprocal Rank Fusion）融合公式是什么？为什么不用加权平均？**

**A:** RRF 公式：`score(doc) = Σ 1 / (k + rank_i)`，其中 k=60 为平滑参数，`rank_i` 是文档在第 i 个检索器中的排名。RRF 对排名敏感、对分数不敏感（只关心排名，不管检索器给出的具体分数）。不同检索器分数尺度不同（余弦相似度 0-1，BM25 0-100），直接加权平均无意义。RRF 实现简单，效果稳定，不依赖调参。k=60 是经验值（排名 60 之后的文档影响很小）。

### Card 7: Reranker 原理
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: Reranker 的工作原理是什么？为什么在检索后使用 Reranker？**

**A:** Reranker 使用交叉编码器（Cross-Encoder），将 query 和 doc 拼接为 `[CLS] query [SEP] doc [SEP]` 输入模型，计算相关性分数。双编码器（Bi-Encoder，如 BGE）将 query 和 doc 各自编码，内积计算相似度，速度快但无法看到 query 和 doc 的完整交互。Reranker 精度更高，但计算量大（O(n) 次推理），所以放在检索后（top-30 → Reranker → top-5），作为精排阶段。典型流程：向量检索 top-30 → Reranker 重排 → top-5 送入 LLM。

### Card 8: HyDE 查询转换
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: HyDE（Hypothetical Document Embeddings）的原理是什么？**

**A:** HyDE 先用 LLM 基于用户查询生成一个假设文档（假设的完美回答），然后用这个假设文档的 Embedding 去检索真实文档。原理：假设文档与真实文档在语义空间上更接近（都是文档），而用户查询与文档在语义空间上存在差距（查询 vs 文档）。优点：提升检索质量，特别是当查询简短或表达不完整时。缺点：依赖 LLM 生成质量，增加一次 LLM 调用。HyDE 适合查询与文档表达差异大的场景（如"怎么修手机"→"屏幕碎裂维修步骤"）。

---

### Card 9: Multi-Query 检索
**维度**: 🔬深挖 | **难度**: ⭐⭐

> **Q: Multi-Query 是什么？它与 HyDE 有什么不同？**

**A:** Multi-Query 将用户的一个问题扩展为多个不同角度的查询（如"RAG 的优缺点"扩展为"RAG 的优点是什么""RAG 的局限性""RAG vs 微调""RAG 应用场景"），分别检索后合并去重。HyDE 先生成假设文档再用文档 Embedding 检索，只检索一次。Multi-Query 检索多次（N 次），增加召回率但增加检索成本。两者可以组合：Multi-Query 生成多个查询，每个查询用 HyDE 生成假设文档再检索，最后合并结果。

### Card 10: Graph RAG
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: Graph RAG 的原理是什么？相比纯向量检索有什么优势？**

**A:** Graph RAG = 知识图谱 + 向量检索。构建方式：从文档中抽取实体（Entity，如"苹果公司""iPhone 15"）和关系（Relation，如"发布""生产"），构建知识图谱。查询时，图检索处理结构化推理（多跳关系："苹果发布了什么产品"→"iPhone 15"），向量检索处理语义相似。RRF 融合结果。优势：支持多跳推理（"A 公司的 CEO 曾任职于哪家公司"）、关系理解（"A 和 B 是什么关系"）。缺点：构建成本高、关系抽取可能不完整。微软 GraphRAG 是最流行的开源实现。

### Card 11: 幻觉控制
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: RAG 系统中如何控制幻觉？有哪些有效方法？**

**A:** ① 证据门控（检索质量低于阈值则返回"无法回答"而非猜测）；② 引用溯源（回答中标注来源段落编号，用户可验证）；③ 领域守卫（拦截非领域问题，避免模型"编造"）；④ Prompt 约束（"仅基于提供的文档回答，不要添加自己的知识"）；⑤ 自我反思（Self-RAG：检查是否需检索、文档是否相关、回答是否完整）；⑥ 多轮验证（LLM 自我校验回答是否忠于原文）；⑦ 温度控制（temperature=0 减少随机性）。

### Card 12: 证据门控
**维度**: 🎯场景 | **难度**: ⭐⭐

> **Q: 什么是证据门控？如何在 RAG 中实现？**

**A:** 证据门控是检索质量控制机制：检索结果的相关性分数低于阈值时，不送入 LLM，而是返回预设回复（如"我无法从知识库中找到相关信息"）。实现：① 计算检索文档与查询的相似度分数；② 设置阈值（如余弦相似度 < 0.7 则门控）；③ 门控触发时，可选择降级（如使用 LLM 自身知识）或拒绝回答。门控策略：strict（严格，拒绝回答）、moderate（降级）、flexible（全部送 LLM 但 Prompt 提醒"文档可能不相关"）。

### Card 13: RAGAS 评估
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: RAGAS 的四个核心评估指标是什么？**

**A:** Faithfulness（忠实度）：回答是否忠于检索到的文档，不包含未在文档中提到的信息。Answer Relevancy（答案相关性）：回答是否与问题相关，不答非所问。Context Precision（上下文精确度）：检索到的文档中，有多少是真正相关的（排序质量）。Context Recall（上下文召回率）：所有相关文档中，有多少被检索出来了（召回质量）。RAGAS 使用 LLM 作为评估器，无需人工标注。`pip install ragas`，`RagasScore` 量化指标。

### Card 14: 在线评估
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: 如何对生产环境中的 RAG 系统进行在线评估？**

**A:** ① 用户反馈（点赞/点踩，直接反馈回答质量）；② 隐式反馈（用户是否复制回答、是否继续追问，间接反映质量）；③ 日志分析（回答长度、响应时间、检索文档数）；④ A/B 测试（对比不同分块策略/检索算法/模型的效果）；⑤ 自动监控（P95 延迟、忠实度分数、缓存命中率、检索失败率）；⑥ 定期人工抽检（随机抽取 100 条对话，人工评分）；⑦ 回放测试（线上请求记录回放，离线评估改进效果）。

### Card 15: 生产化要点
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: RAG 系统生产化部署的关键点有哪些？**

**A:** ① 延迟优化（HNSW 索引加速、结果缓存、流式输出、预加载模型）；② 检索优化（混合检索 + RRF + Reranker 多级流水线）；③ 知识更新（增量更新策略：定时全量重建 + 实时增量更新）；④ 监控告警（P95 延迟、忠实度分数、缓存命中率、检索失败率、Token 消耗）；⑤ 安全（Prompt 注入防护、敏感信息过滤、内容审核）；⑥ 成本控制（缓存常见问题、使用低配模型处理简单查询、Embedding 批量处理）；⑦ 可观测性（全链路追踪、检索日志、用户反馈记录）。

### Card 16: 知识更新策略
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: RAG 知识库如何更新？增量更新和全量重建的权衡？**

**A:** 全量重建：重新处理所有文档，生成 Embedding 并重建索引，保证一致性但耗时（大型知识库可能数小时）。增量更新：只处理新增/修改的文档，更新向量数据库，速度快但可能有碎片。策略：① 定时全量重建（如每天凌晨）+ 实时增量更新；② 监控增量更新的碎片率，达到阈值时触发全量重建；③ 文档版本管理（每个文档带版本号，增量更新时自动替换旧版本）；④ 双索引切换（并行构建新索引，构建完成后切换）。

### Card 17: 缓存优化
**维度**: 🎯场景 | **难度**: ⭐⭐

> **Q: RAG 系统的缓存优化策略有哪些？**

**A:** ① 查询缓存（缓存常见问题的检索结果和 LLM 回答，LRU 淘汰）；② Embedding 缓存（缓存文档 Embedding，避免重复计算，文档更新时失效）；③ 检索结果缓存（缓存相同查询的检索结果，TTL 控制过期时间）；④ LLM 响应缓存（相同输入直接返回缓存结果，适合确定性查询）；⑤ 多级缓存（本地 Caffeine → Redis → 向量数据库）；⑥ 语义缓存（语义相似查询共享缓存，如"苹果手机价格"和"iPhone 价格"命中同一缓存）。缓存命中率是 RAG 系统成本控制的关键指标。

---

### Card 18: 延迟优化
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: 如何优化 RAG 系统的端到端延迟？**

**A:** ① 向量索引优化（HNSW 图索引，搜索参数 `ef_search` 调节召回精度 vs 速度的平衡）；② 混合检索并行化（向量检索和 BM25 检索并行执行，RRF 融合）；③ Reranker 批处理（多个 doc 合并为一个 batch 推理，利用 GPU 并行）；④ 流式输出（LLM 生成时立即流式返回，减少用户感知延迟）；⑤ 预加载模型（Embedding 模型和 LLM 预热，避免冷启动延迟）；⑥ 连接池（数据库/Redis/向量库连接复用）；⑦ 结果缓存（常见查询缓存，跳过检索和生成步骤）；⑧ 降级策略（缓存未命中时，用快速检索替代完整检索流程）。
