### Card 1: B+Tree 索引原理
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: 为什么 MySQL 使用 B+Tree 而不是 B-Tree 或红黑树作为索引结构？**

**A:** B+Tree 非叶子节点只存 key（不存数据），一个节点可存更多 key，树高更矮。InnoDB 页大小 16KB，3-4 层 B+Tree 可支撑亿级数据。叶子节点存数据+链表指针，范围查询时直接从链表遍历，无需回根节点。B-Tree 非叶子节点也存数据，相同高度存储量少。红黑树是二叉树，深度太大，磁盘 IO 次数多。

### Card 2: 聚簇索引 vs 非聚簇索引
**维度**: 📝速记 | **难度**: ⭐

> **Q: 聚簇索引和非聚簇索引有什么区别？什么是回表？**

**A:** 聚簇索引：叶子节点存完整行数据，每张表只有一个（主键索引）。非聚簇索引（二级索引）：叶子节点存主键值，查询需要先找到主键值，再回聚簇索引查完整数据。回表指通过二级索引查到主键后，再走聚簇索引查整行数据。覆盖索引（查询列都在索引中）可避免回表。

### Card 3: 最左前缀原则
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: 联合索引 (a, b, c) 在哪些查询条件下能用到索引？哪些会失效？**

**A:** 能用到：`WHERE a=1`（全匹配）、`WHERE a=1 AND b=2`、`WHERE a=1 AND b=2 AND c=3`、`WHERE a=1 ORDER BY b`（索引排序）。失效：`WHERE b=2`（没用到 a，不走索引）、`WHERE a=1 AND c=3`（b 跳过，只用到 a 列的索引，c 无法走索引）。结论：查询从最左列开始连续匹配，跳过中间列后面的列无法使用索引。

### Card 4: 索引失效场景
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: 列举 5 种以上索引失效的场景及优化方案。**

**A:** ① 函数操作：`WHERE LEFT(name,3)='abc'` → 改为 `WHERE name LIKE 'abc%'`；② 隐式类型转换：`WHERE phone=123`（phone 是 varchar）→ 改为 `WHERE phone='123'`；③ LIKE 前模糊：`LIKE '%abc'` → 考虑全文索引或 ES；④ OR 非索引列：`WHERE a=1 OR b=2`（b 无索引）→ 改为 UNION 或给 b 建索引；⑤ 运算操作：`WHERE age+1=20` → 改为 `WHERE age=19`；⑥ 不等于操作：`!=` / `<>` 通常不走索引。

### Card 5: EXPLAIN 解读
**维度**: 💻代码 | **难度**: ⭐⭐

> **Q: EXPLAIN 输出中 type 和 Extra 字段分别代表什么？如何判断 SQL 是否高效？**

**A:** type 从好到差：system > const > eq_ref > ref > range > index > ALL。`ALL` 全表扫描需优化。Extra 重要信息：`Using index`（覆盖索引，好）、`Using filesort`（文件排序，需优化）、`Using temporary`（临时表，需优化）、`Using where`（索引后过滤）。`rows` 表示扫描行数，理想情况应远小于表总行数。`key` 显示实际使用的索引。

### Card 6: MVCC 原理
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: MVCC 是如何实现读不阻塞写、写不阻塞读的？**

**A:** MVCC 核心组件：隐藏字段（`DB_TRX_ID` 记录最近修改的事务 ID，`DB_ROLL_PTR` 指向 Undo Log 版本链）+ Read View。Read View 结构：`creator_trx_id`（当前事务 ID）、`m_ids`（活跃事务列表）、`min_trx_id`、`max_trx_id`。可见性规则：`TRX_ID < min_trx_id` 可见；`TRX_ID >= max_trx_id` 不可见；`TRX_ID` 在 `m_ids` 中不可见。RR 级别只在第一次 SELECT 创建 Read View，实现可重复读；RC 每次 SELECT 都创建新 Read View。

### Card 7: 隔离级别对比
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: 四种隔离级别分别解决了什么问题？MySQL 默认用哪个？**

**A:** RU（读未提交）：可能脏读、不可重复读、幻读。RC（读已提交）：解决脏读，仍有不可重复读和幻读。RR（可重复读）：解决脏读和不可重复读，MySQL 通过间隙锁解决幻读。Serializable（串行化）：解决全部，但并发最低。MySQL 默认 RR（通过间隙锁解决幻读）；Oracle 默认 RC。RR 比 RC 多间隙锁开销，但 InnoDB 的 RR 不会像其他数据库那样频繁出现幻读。

### Card 8: 行锁/间隙锁/临键锁
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: InnoDB 的行锁、间隙锁、临键锁有什么区别？加锁规则是什么？**

**A:** 行锁（Record Lock）：锁住索引记录行。间隙锁（Gap Lock）：锁住索引值之间的间隙，防止幻读，RR 级别生效。临键锁（Next-Key Lock）= 行锁 + 间隙锁，RR 级别默认锁策略。加锁规则：唯一索引等值查询命中时退化为行锁；范围查询或普通索引加临键锁。`SELECT ... FOR UPDATE` 加 X 锁，`SELECT ... LOCK IN SHARE MODE` 加 S 锁。

### Card 9: 死锁排查与预防
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: 如何排查死锁？如何预防死锁？**

**A:** 排查：`SHOW ENGINE INNODB STATUS` 查看最近死锁，包括死锁事务的 SQL、锁等待资源。`information_schema.INNODB_TRX` 查看当前事务。开启 `innodb_print_all_deadlocks` 将死锁记录到日志。预防：① 固定顺序访问（如都按 id 升序操作）；② 缩短事务时间；③ 降低隔离级别（RC 无间隙锁，死锁少）；④ 合理使用索引（减少锁范围）；⑤ 避免大事务。

### Card 10: 慢 SQL 优化
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: 一条慢 SQL 的优化步骤是什么？**

**A:** ① 开启慢查询日志，设置 `long_query_time=1` 记录超过 1 秒的 SQL；② 找到慢 SQL，用 `EXPLAIN` 分析执行计划；③ 检查 `type`（ALL 全表扫描需优化）、`Extra`（Using filesort/temporary 需优化）；④ 优化索引（加索引/改联合索引/覆盖索引/索引下推）；⑤ 改写 SQL（拆分大查询、避免函数操作、小表驱动大表）；⑥ 验证效果（重新 Explain 对比 rows）；⑦ 考虑业务层优化（缓存、异步、分页）。

### Card 11: 分页优化
**维度**: 🎯场景 | **难度**: ⭐⭐

> **Q: 大表分页时 LIMIT 100000, 20 为什么慢？如何优化？**

**A:** `LIMIT 100000, 20` 慢的原因是 MySQL 需要扫描 100020 行，然后丢弃前 100000 行。优化：① 游标分页（覆盖索引延迟关联）：`SELECT * FROM t INNER JOIN (SELECT id FROM t WHERE ... LIMIT 100000, 20) AS tmp USING(id)`；② 游标分页（基于索引）：`WHERE id > last_id ORDER BY id LIMIT 20`（适合连续翻页，不能跳页）；③ 子查询方式：`WHERE id >= (SELECT id FROM t ORDER BY id LIMIT 100000, 1) LIMIT 20`。

### Card 12: 分库分表策略
**维度**: 🔬深挖 | **难度**: ⭐⭐⭐

> **Q: 分库分表有哪些策略？如何选择分片键？**

**A:** 垂直分库：按业务拆到不同库（订单/用户/商品库）。水平分表：按分片键拆分。分片策略：① 范围分片（按时间/ID 范围，扩展简单，可能有热点）；② Hash 分片（`user_id % 16`，数据均匀，扩展需迁移）；③ 一致性 Hash（减少扩展时数据迁移量）。分片键选择：选查询频率最高的字段（如 `user_id`、`order_id`）。跨分片查询（如排序、聚合）需在应用层合并。

### Card 13: 主从延迟与解决方案
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: 主从延迟的原因是什么？如何解决？**

**A:** 原因：主库写压力大、从库配置低、大事务（如一次 UPDATE 全表）、DDL 操作。解决方案：① 强制读主：关键数据（支付结果）从主库读取；② 并行复制：MySQL 5.7+ 并行回放（`slave_parallel_workers`）；③ 缓存补偿：写后缓存数据，读从库无数据时读缓存或主库；④ 分库分表：减少单个库的压力；⑤ 监控延迟：`SHOW SLAVE STATUS` 的 `Seconds_Behind_Master` 指标告警。

### Card 14: 读写分离
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: 读写分离的实现方式有哪些？ShardingSphere 如何实现？**

**A:** 应用层：代码中配置两个数据源，`@Transactional(readOnly=true)` 路由到从库。中间件层：ShardingSphere-JDBC（轻量级，嵌入应用）、ShardingSphere-Proxy（独立代理，兼容 MySQL 协议）。ShardingSphere 读写分离：主库写操作，从库读操作，支持负载均衡（轮询/随机/权重），支持从库 HA（自动摘除不可用从库）。写操作后读一致性：通过 `hint` 强制读主。

### Card 15: SQL 注入防护
**维度**: 💻代码 | **难度**: ⭐⭐

> **Q: SQL 注入的原理是什么？MyBatis 和 JPA 如何防护？**

**A:** SQL 注入：攻击者在输入参数中嵌入 SQL 代码，如 `' OR 1=1; --`。MyBatis 防护：`#{}` 使用 PreparedStatement 参数化（自动转义），`${}` 直接拼接（有注入风险，仅用于表名/列名等动态 SQL）。JPA 防护：`@Query` 中 `?1` 或 `:name` 参数化查询，`Criteria API` 类型安全预防。安全原则：永远不拼接用户输入到 SQL 字符串，使用参数化查询。

### Card 16: 事务注解失效场景
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: @Transactional 在哪些情况下会失效？**

**A:** ① 非 public 方法（Spring 默认只代理 public 方法）；② 自调用（同类中方法 A 调方法 B，B 有 `@Transactional`，实际走的 this.B() 而非代理）；③ 异常被 catch（事务默认回滚 RuntimeException/Error，自定义异常需指定 `rollbackFor`）；④ 不同数据源（需配置分布式事务）；⑤ 方法中使用了 `try-catch` 吞掉异常；⑥ 数据库引擎不支持事务（MyISAM 而非 InnoDB）。

### Card 17: 乐观锁 vs 悲观锁
**维度**: 📝速记 | **难度**: ⭐⭐

> **Q: 乐观锁和悲观锁分别适用于什么场景？如何实现？**

**A:** 悲观锁：认为每次操作都会冲突，操作前先加锁（`SELECT ... FOR UPDATE`），适合写冲突多的场景（如库存扣减）。乐观锁：认为冲突少，更新时检查版本（`version` 字段 `UPDATE ... SET version=version+1 WHERE version=old_version`），适合读多写少的场景（如商品信息更新）。CAS 失败时重试。悲观锁有死锁风险，乐观锁有 ABA 问题（通过 version 或时间戳解决）。

### Card 18: 大表设计原则
**维度**: 🎯场景 | **难度**: ⭐⭐⭐

> **Q: 设计亿级数据量的 MySQL 表有哪些原则？**

**A:** ① 字段精简（能用 INT 不用 BIGINT，能用 VARCHAR(50) 不用 TEXT）；② 合适的索引（高频查询字段建索引，索引数 < 5 个）；③ 分表分库（水平拆分，按 user_id/order_id 分片）；④ 冷热分离（热数据 3 个月，冷数据归档到历史表或 TiDB）；⑤ 时间分区（按天/月分区，方便删除历史数据）；⑥ 读写分离（主库写，从库读）；⑦ 避免大事务（批量操作分批次提交）；⑧ 使用自增主键（B+Tree 顺序写入，减少页分裂）。

### Card 19: 冷热分离
**维度**: 🎯场景 | **难度**: ⭐⭐

> **Q: 冷热分离的常见实现方案有哪些？**

**A:** ① 同库分表：按时间拆分，热表（最近 3 个月）用小表，冷表（历史数据）归档。② 不同存储：热数据在 MySQL，冷数据在 TiDB/ClickHouse/ES（查询少、存储便宜）。③ 数据迁移：定时任务（如每天凌晨）将 3 个月前的数据迁移到冷存储。④ 业务透明：通过数据路由层（如 ShardingSphere）自动路由到热/冷库。⑤ 归档策略：删除、压缩、归档到 HDFS。

### Card 20: 全局 ID 方案
**维度**: 🎯场景 | **难度**: ⭐⭐

> **Q: 分库分表后，如何生成全局唯一 ID？**

**A:** ① 雪花算法（Snowflake）：64bit，1bit 符号+41bit 时间戳+10bit 机器 ID+12bit 序列号，趋势递增，性能高。注意时钟回拨问题。② 号段模式（Leaf）：预取号段到内存，批量分配，减少 DB 压力。③ Redis INCR：简单但网络开销大，RDB 持久化可能丢失导致 ID 重复。④ UUID：唯一但无序且太长（36 字符），不适合做 MySQL 索引。⑤ 美团 Leaf：支持号段和雪花两种模式，完善的时钟回拨处理。
