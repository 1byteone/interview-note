## 题库说明与项目 Goal

- **项目定位**：`[源码已确认]` FastAPI AI 搜索服务从 MySQL `sku_info` 读取 `deleted=0` 商品，构造文档、分片并经 OpenAI-compatible Embedding 写入 Redis `RedisVectorStore`；查询时由 LangChain/LangGraph Agent 调用向量工具，返回结构化商品推荐。传统分页搜索和 Java/Gateway 的完整映射仍需联调确认。
- **适用岗位**：Java 后端、Spring Cloud 微服务、Python/FastAPI AI 应用、RAG/Agent 应用工程师。
- **阅读方式**：先掌握 1-12 的事实，再用 13-30 解释执行机制，31-44 练排障，45-56 练项目深挖，57-60 练架构设计。回答每题都先说当前实现，再说风险/验证，再说规划方案。
- **证据等级**：源码已确认 > Word描述；架构规划是建议；待验证必须明确验证手段。源码路径与行号见事实文件 S1-S13。
- **实现边界声明**：当前材料没有证明 Elasticsearch、独立 Rerank、消息队列、业务缓存、Redis 持久 checkpoint 或生产级多实例高可用已存在；它们只能作为规划或设计题方案。Java/Gateway/OpenFeign 只有 Word/待验证整合证据，不能补写不存在的 Java 源码。
- **答题策略**：用“事实—机制—缺口—方案—指标”五步回答；不要把 `k=10` 说成前端展示 5 条，不要把 Pydantic 格式校验说成商品真实性校验，不要把 body `code=500` 说成 HTTP status 已是 500。

### 题目 1：一句话说明项目的输入、处理和输出
**难度**：Level 1
**类型**：事实复述
**题型形式**：选择题
**考察点**：业务定位、RAG 主链路、边界意识
**项目证据**：S1-S6；分析文件第 2、4.1 节 `[源码已确认]`；Java/传统搜索整合为 `[待验证]`。

**问题**：以下哪项最准确地描述当前一次商品同步和一次推荐请求的主链路？

A. MySQL `sku_info` → `lazy_load`/`page_content`/`metadata` → 分片与 Embedding → Redis `RedisVectorStore`；推荐由 `/api/v1/recommend` 进入 Agent/tool，召回后返回结构化结果。
B. MySQL → Elasticsearch → Rerank → MQ，推荐只返回前端已经过滤的 5 条。
C. 前端直接调用 OpenAI API，Java 服务负责把商品字段写入 Redis，Python 只做展示。
D. `/api/v1/recommend` 只调用价格数据库，不经过向量检索或结构化 Schema。

**正确答案**：A。

**解析**：源码确认同步从 MySQL `sku_info` 查询 `deleted=0`，构造 `page_content`/`metadata`，按 256 token、25 overlap 切分，经 OpenAI-compatible Embedding 批量写入 Redis；推荐由 FastAPI 接收 query 和 `thread_id`，配置/注册 `vector_search_tool`，实际运行调用仍需集成验证，以 `similarity_search(query,k=10)` 召回，再按 `ProductRecommendResponse` 返回摘要、商品列表和理由。ES、Rerank、MQ 以及 Java/Gateway 完整映射不是当前源码已确认能力。

**深入解析**：这是“商品数据—向量—工具—Agent—结构化响应”的当前 Python 链路；前端 AI 模式还并行调用条件提取，提取结果用于传统分页接口。点击率、真实连通性、Java/Gateway 映射和业务收益均未由事实文件证明。

**面试官追问**：当前推荐有没有价格硬过滤？为什么不能只看 Schema？

**优秀回答应包含**：指出没有价格/库存/上下架硬过滤；Pydantic 只校验字段类型；说明 ES、Rerank、MQ、生产高可用不是当前实现。

**常见误答**：说系统当前用 Elasticsearch、Rerank 和 MQ；说推荐一定返回真实在售商品；把 Word 示例当运行结果。

### 题目 7：同步批次和文档 ID 如何生成
**难度**：Level 1
**类型**：代码走读
**题型形式**：简答题
**考察点**：批处理、MD5 ID  规范
**项目证据**：S1:46-50、80-101 `[源码已确认]`。

**问题**：向量同步如何批量写入？文档 ID 如何计算？

**标准答案**：`lazy_load` 逐步得到文档，切分后每累计 100 个 chunk 调用一次 `RedisVectorStore.add_documents`，循环结束再写入不足 100 的尾批。ID 是 `sku id + chunk 文本` 的 MD5；内容变化会得到新 ID。

**深入解析**：批次降低单次内存和调用粒度；MD5 让相同 SKU/相同分片内容可复现，但不负责删除旧分片、增量同步、锁、断点或失败恢复。

**面试官追问**：同一 SKU 改价后，旧向量一定会被清理吗？

**优秀回答应包含**：不一定，当前代码主动删除未实现；需要版本/映射表和删除任务的规划。

**常见误答**：说 MD5 ID 自动完成全量幂等和旧数据清理。

### 题目 9：vector_search_tool 召回多少条
**难度**：Level 1
**类型**：代码走读
**题型形式**：选择题
**考察点**：Top-K、后端与前端口径
**项目证据**：S2:24-36、S9:604-610 `[源码已确认]`。

**问题**：关于后端 Top-K 与前端展示条数，以下哪项正确？

A. 后端调用 `similarity_search(query, k=10)`，前端再 `slice(0,5)`，两者是不同阶段。
B. 后端只召回 5 条，前端把它扩展为 10 条。
C. `k=10` 表示系统已经引入独立 Rerank。
D. 前端展示 5 条意味着 Redis 索引只能存 5 个候选。

**正确答案**：A。

**解析**：源码确认工具最多按 `k=10` 召回，前端展示层最多取前 5 条；Top-K 影响候选覆盖、上下文和成本，不能把展示截断说成后端 top5，也不能据此声称已有 Rerank。

**深入解析**：后端召回数量影响候选覆盖、模型上下文和成本，前端截断只影响展示；当前没有独立 Rerank 的源码证据。

**面试官追问**：如何判断应该改 k？

**优秀回答应包含**：建立 Recall@K、NDCG/相关性、P95、token 和成本基线，而不是凭感觉。

**常见误答**：说后端只查询 5 条；说改 k 就等于加了 Rerank。

### 题目 12：OpenFeign 基础：声明式 HTTP 调用是什么
**难度**：Level 1
**类型**：接口契约
**题型形式**：简答题
**考察点**：OpenFeign 基础、声明式客户端、契约边界
**项目证据**：Word 第 9.2 节提到 Java/Gateway/Feign 适配方案 `[Word描述]`；本次指定范围无 Java 源码 `[待验证]`。

**问题**：在 Java 微服务中，`@FeignClient` 主要解决什么问题？写出一个面向搜索服务的最小声明式客户端应关注哪些契约字段。

**标准答案**：OpenFeign 用接口和注解描述 HTTP 调用，由客户端代理完成请求构造、参数绑定和响应反序列化，减少手写 HTTP 模板代码。最小客户端至少要明确服务名或 URL、HTTP 方法与路径、query/body 参数、请求/响应 DTO、超时和错误映射；例如搜索适配层要明确 `/recommend`、`/extract` 的版本路径及 `threadId`/`thread_id` 转换边界。当前材料只证明 Word 描述了该整合方向，不能说项目已有可运行的 Feign 客户端。

**深入解析**：Feign 只是调用方式，不自动解决服务发现、重试、幂等、鉴权或业务正确性。Java/Gateway 是否实际完成路径重写、DTO 映射和超时策略，必须通过 Java 源码、网关日志和端到端契约测试验证。

**面试官追问**：OpenFeign 的超时、重试和错误解码为什么不能只用默认值？

**优秀回答应包含**：区分连接/读取 timeout，按幂等性和错误类型设计有限重试，统一错误码与 HTTP status，并明确当前实现待验证。

**常见误答**：说 `@FeignClient` 会自动保证服务高可用；把 Word 方案当成已有 Java 源码；忽略 DTO 和版本化路径。

### 题目 13：从 lazy_load 到批量入库的执行顺序

### 题目 31：代码题——为向量同步增加批次失败统计
**难度**：Level 3
**类型**：安全可靠性
**考察点**：批处理、异常边界、可观测性
**项目证据**：S1:80-101 `[源码已确认]`；逐批恢复和统计为 `[架构规划]`。

**问题**：在不改变“每 100 个 chunk 写一次”的事实前提下，写出最小伪代码统计成功/失败批次，并返回可追踪结果。

**最小可读代码**：
```python
import asyncio


async def write_batches(store, chunks, batch_size=100):
    success_batches = 0
    failed_batches = 0
    failed_ranges = []
    batch = []
    start = 0

    async def flush(current, offset):
        nonlocal success_batches, failed_batches
        try:
            # add_documents 是同步 I/O，不能直接阻塞 async 事件循环。
            await asyncio.to_thread(store.add_documents, current)
            success_batches += 1
        except Exception as exc:
            failed_batches += 1
            failed_ranges.append({"start": offset, "size": len(current),
                                  "error_type": type(exc).__name__})
            # 生产方案：记录任务 ID，按有限退避策略重试或标记待补偿。

    for chunk in chunks:
        batch.append(chunk)
        if len(batch) == batch_size:
            await flush(batch, start)
            start += len(batch)
            batch = []
    if batch:
        await flush(batch, start)

    status = ("failed" if failed_batches and not success_batches
              else "partial" if failed_batches else "succeeded")
    return {"status": status, "success_batches": success_batches,
            "failed_batches": failed_batches, "failed_ranges": failed_ranges}
```

这里将同步 `add_documents` 放入 `asyncio.to_thread`，避免在异步请求线程直接阻塞事件循环；批次状态和安全失败记录仍由调用方持久化。示例的 `chunks` 是可迭代的同步输入；若上游是异步流，应由异步生成器/队列收集到 100 条再调用 `flush`，不要在 `flush` 中一次性把无限流转成 list。

**标准答案**：统计应按批次而不是按请求总成功判断；失败批次记录任务 ID、起始位置、数量和安全错误类型，最后状态应能区分成功、部分失败和失败。是否重试要有上限、退避和幂等保证，不能简单无限重跑。

**深入解析**：当前 `/sync` 没有逐批异常恢复；代码是规划示例。若中途失败，必须避免把“部分写入”报告为全量成功，并设计断点/补偿。

**面试官追问**：失败重试会不会产生重复向量？

**优秀回答应包含**：依赖 ID/upsert 语义验证；以稳定文档 ID、任务幂等键和结果核对控制重复，不能仅靠 MD5 声称已解决。

**常见误答**：捕获异常后继续并返回 code=200；无限重试；把统计当作一致性保证。

### 题目 57：设计亿级商品的增量向量同步平台
**难度**：Level 5
**类型**：测试验证
**考察点**：大规模同步、一致性、成本、可恢复性
**项目证据**：当前 S1 是 MySQL 全量 `deleted=0`、lazy load、100 批写 Redis `[源码已确认]`；源码未发现增量、删除、队列或高可用能力 `[源码已确认]`；以下为 `[架构规划]`。

**问题**：在亿级商品规模下，设计增量向量同步平台，并清楚区分当前实现与演进方案。

**标准答案**：
- **目标**：只处理商品新增/变更/删除，保证索引最终一致、可恢复、可审计，控制 Embedding 成本并支持版本切换。
- **约束**：当前 `/sync` 是同步全量扫描，`lazy_load` 和 100 批次不能承受亿级；外部 Embedding 有延迟/配额；不能假设当前已有 MQ、业务缓存或生产高可用。需要保护 MySQL、Redis 和模型供应商。
- **架构**：规划变更捕获/任务表产生带 SKU、版本、操作类型的任务；调度器分片领取，worker 按租约和幂等键执行；Embedding 批处理写入版本化向量索引，元数据状态表记录 pending/ready/deleted；校验后切换 alias/可见版本；对账与补偿任务清残留。
- **数据流**：MySQL 变更 → 任务记录 → 读取商品快照 → page_content/metadata → token splitter → Embedding → Redis Vector index → 批次校验 → 版本发布；删除走 tombstone 和旧 chunk ID 删除。
- **接口**：`POST /vector-sync/jobs` 返回 task ID，`GET /vector-sync/jobs/{id}` 查状态，内部 worker/对账接口带版本、游标、失败批次；保留 `/sync` 兼容入口但转任务，不在 HTTP 内长阻塞。
- **存储**：MySQL 任务/版本/映射表；Redis 向量索引按 embedding 版本隔离；对象存储/日志保存批次审计（具体基础设施待选型）。不把 Redis checkpoint 或业务缓存写成当前已有能力。
- **故障处理**：批次有限退避；失败可重放；锁/租约过期可接管；Provider 4xx 暂停并告警；Redis 写失败不发布版本；乱序事件按版本丢弃；对账发现旧向量执行补偿删除。
- **指标**：事件延迟、吞吐、成功/失败批次、重试率、积压、残留率、向量版本覆盖率、Embedding token/费用、Redis 写入 P95、发布耗时和恢复时间。
- **容量估算思路**：以 SKU 数 N、平均文本 token T、平均 chunk 数 C、日变更率 r、batch B、Embedding 吞吐 E、Redis 每向量存储 S 估算：日向量数约 N×r×C，Embedding 请求约 ceil(日向量/B)，存储约向量数×S×版本保留数；用峰值变更率和重试倍数预留。
- **取舍**：事件驱动降低全量成本但引入乱序/丢失治理；双版本切换提高一致性但占用存储；更强实时性增加 Embedding 费用；先做任务表+定时增量可作为低复杂度过渡。所有这些是规划。

**深入解析**：当前可复述的只有 MySQL→lazy_load→分片→Redis 写入；不能声称亿级平台已实现。架构验收应做故障注入、断点恢复、重复事件、删除和版本切换演练。

**面试官追问**：如何处理同一 SKU 的变更乱序？如何估算 Redis 存储与 Embedding 费用？新索引未完成时能否发布？删除事件丢失如何发现？

**优秀回答应包含**：版本序列/幂等、公式化容量、不可发布闸门、对账补偿、成本与一致性的取舍。

**常见误答**：把当前 `/sync` 说成增量平台；直接加入 MQ/ES 并说已部署；只谈吞吐不谈删除、版本和失败恢复。

### 题目 58：设计传统关键词 + 向量召回 + Rerank 的混合搜索
**难度**：Level 5
**类型**：一致性幂等
**考察点**：混合检索、排序、精确约束、评估
**项目证据**：当前 Redis `similarity_search(k=10)`、无 ES/Rerank `[源码已确认]`；混合方案 `[架构规划]`。

**问题**：为“品牌/型号精确、属性语义、价格约束”设计混合搜索，不能把 ES/Rerank 写成当前能力。

**标准答案**：
- **目标**：兼顾型号/品牌精确命中和自然语言语义召回，保证价格/上下架等业务约束，提升 Recall/NDCG 并控制延迟/成本。
- **约束**：当前只有 Redis 向量检索 k=10；未发现 ES 客户端、独立 Rerank 或消息队列；商品实时状态要以业务库/服务为准；模型调用可能超时。
- **架构**：查询规范化/条件提取 → 关键词召回（既有商品搜索能力或规划的倒排组件）与 Redis 向量召回并行 → ID 合并去重 → 结构化硬过滤/业务回查 → 可选 Rerank → Schema 响应。Rerank 不可用时回退融合分数排序。

- **接口**：对外版本化 `/v2/search/recommend`，参数 query、thread_id、可选 filter；内部召回接口返回候选 ID/score/source；Rerank 接口设置 deadline；响应保留来源/降级标志和稳定错误码。
- **存储**：Redis Vector index 保留当前语义候选；关键词索引可由既有商品服务或新倒排组件承载，具体 ES 只是候选方案；MySQL/商品服务是状态回查源；评估集和索引版本独立保存。
- **故障处理**：任一召回分支超时可用另一分支；Rerank 失败回退；业务回查失败不展示未经验证商品；索引版本不一致告警；对空 query/恶意 query 限流和拒绝。
- **指标**：分支召回率、合并后 Recall@K、NDCG/MRR、型号命中率、硬过滤违规率、Rerank 覆盖率、各分支 P95、总 P95、token/费用和降级率。
- **容量估算思路**：按 QPS、关键词/向量分支并发、候选数 K、Rerank batch、索引大小、更新率估算 CPU/Redis/模型吞吐；总延迟近似并行分支最大耗时+合并/回查+Rerank，成本按 query 候选和 token 估算。
- **取舍**：混合提高精确词召回但增加索引和一致性复杂度；Rerank 提质但增加外部调用和 P95；先做候选合并和硬过滤，再用离线评估决定 Rerank 灰度，不宣称现有组件已上线。

**深入解析**：前端传统 `/search/product/page` 只能证明存在外部/既有接口，不能证明本 Python 模块内有 ES；设计必须以指标和灰度验证而非组件堆叠。

**面试官追问**：两路分数不可比怎么办？为什么不让 Rerank 直接看全库？如果关键词分支失败如何保证型号查询？如何避免过滤后没有候选？

**优秀回答应包含**：分数归一化/学习权重、候选集边界、降级、硬约束和空结果语义。

**常见误答**：说当前已经是混合检索；把前端截取 5 条说成 Rerank；没有质量和延迟指标。

**标准答案**：
- **目标**：让用户追问“换成更便宜/只看在售”时保持会话上下文，首 token 快速到达，结果可中断，且每租户可控成本、无越权和幻觉商品。
- **约束**：当前是 `InMemorySaver`、GET `/recommend` 非 SSE，前端随机 threadId 无用户绑定；Agent 只有向量工具；无 Redis 持久会话、业务回查和生产 HA 证据。必须兼容已有 FastAPI/前端，并保护 query、商品数据和 Provider key。
- **架构**：Gateway 鉴权/限流 → SSE session endpoint → 会话存储/检查点 → query 校验与意图/条件抽取 → 向量召回与业务过滤 → Agent 流式事件（工具开始/结束、候选、结构化结果）→ 业务回查 → SSE done/error；checkpoint 工厂规划使用 Redis，Agent 仍受工具白名单约束。
- **数据流**：请求携带用户绑定 thread ID 和 last-event-id；加载历史并裁剪摘要 → 校验 query/预算 → Redis Vector `k` 候选 → 结构化条件硬过滤/商品回查 → 模型按事件流输出受控 token → 校验完整 `ProductRecommendResponse` 后发送最终结果；断线按 event ID 恢复或返回可重试状态。
- **接口**：`POST /v2/search/sessions/{threadId}/events` 或明确 SSE GET/POST 语义，参数 query、预算/过滤条件；事件类型 `meta/tool/progress/result/error/done`，每事件带 request ID、序号和降级标志；同步任务另用 task API。前端与 Python/Gateway 统一 camel/snake 映射和版本契约。
- **存储**：规划 Redis checkpoint（TTL、用户/租户隔离、加密/脱敏）；Redis Vector 存候选；MySQL/商品服务做实时事实回查；成本账单表记录 provider、model、token、请求和租户；不把当前内存 checkpoint说成持久存储。
- **故障处理**：SSE 心跳、断线重连、取消传播和 deadline；checkpoint 失败时拒绝恢复历史而不串会话；模型/Redis 超时可返回结构化错误/传统搜索降级；预算超限裁剪历史、降低候选或拒绝；工具空召回直接空结果，禁止模型自由造商品；敏感错误只回 request ID。
- **指标**：首 token/完成时延、断线率、重连成功率、token 与单次/租户成本、历史 token 裁剪率、tool call 成功率、空召回率、无效 SKU 率、P95/P99、SSE 连接数和 SLO。
- **容量估算思路**：按并发 SSE 连接 C、心跳周期 H、峰值 query QPS、平均输入/输出 token、每会话状态大小/TTL、Redis ops、模型并发和重连倍数估算；连接层与模型 worker 隔离，预算按租户峰值和日额度计算。
- **取舍**：SSE改善感知延迟但增加连接管理和代理配置；持久会话支持多实例但有隐私/成本；历史摘要降低 token 但可能丢上下文；严格回查增加尾延迟但保障可信；优先安全和正确性，再做体验优化。所有新增能力是规划。

**深入解析**：流式输出不能绕过最终 Schema 和业务回查；中途展示的候选也应标注未完成，不能把模型 token 当最终可信商品。需做断线、并发、预算、Prompt 注入、越权 thread、上游超时和敏感日志测试。

**面试官追问**：SSE 已输出部分文本后发现商品回查失败怎么办？如何阻止用户读取别人的 thread？预算是在网关还是模型层扣减？断线重连如何避免重复扣费？

**优秀回答应包含**：事件状态机、最终结果闸门、鉴权绑定、统一预算账本、幂等 event ID 和安全降级。

**常见误答**：说当前已经支持 SSE/Redis 会话；把流式 token 直接当最终商品结果；只谈体验不谈鉴权、成本和回查。

## 项目表达与答题评分

### 30 秒项目表达

这是一个面向电商的 AI 商品搜索微服务：它从 MySQL `sku_info` 读取有效 SKU，将商品名称、属性、品牌、类目和价格构成文档，经 256 token/25 overlap 分片和 OpenAI-compatible Embedding 写入 Redis 向量库；查询时 LangChain Agent 调用向量工具，以 `k=10` 召回并按 Pydantic Schema 返回摘要、商品和理由。当前亮点是把同步、语义召回、结构化输出和前端 AI/传统搜索协作串起来；边界是没有价格/库存硬过滤和商品二次回查，checkpoint 是 InMemorySaver，增量删除、生产高可用、ES/Rerank/MQ 都不能说已具备。

### 3 分钟架构表达

1. **业务**：自然语言请求同时支持 AI 推荐解释和传统分页兜底；收益目标来自 Word 描述，点击率/转化率尚无实测。
2. **同步**：`/sync` 查 `sku_info WHERE deleted=0`，五个字段进入 page_content，整行查询字段进入 metadata；lazy load 后按 256/25 分片，每 100 个 chunk 写 Redis。
3. **推荐**：`/recommend` 接收 query/thread_id，每次构建含已配置/注册 vector tool 的 Agent（实际运行调用仍需集成验证），Redis similarity search `k=10`，输出 ProductRecommendResponse；前端最多显示 5 条。
4. **提取与整合**：`/extract` 当前只有 keyword/min/max price，前端把结果给传统分页；推荐并不消费 extract。前端路径/命名与 Python 不一致，Java/Gateway/Feign 映射需要联调证明。
5. **边界与路线**：当前没有硬过滤、ID 白名单、实时回查、增量/删除/断点、持久会话、完整外部 timeout/retry 和全链路测试；规划补正确性、安全、任务可靠性、评估、观测和降级。

### 10 分钟深挖策略

先用 3 分钟讲清事实主链路，再按“现状—证据—风险—方案—验收”深挖：同步用增量/删除/幂等/断点解决一致性；检索用结构化过滤和离线评估决定混合召回/Rerank；推荐用 ID 白名单、实时商品回查解决幻觉和过期；会话用 Redis checkpoint 规划多实例隔离；接口修正 HTTP status、路径/命名和错误脱敏；外部模型按 deadline、有限退避、熔断和成本预算降级；复习时不要遗漏题 30 的测试覆盖边界；最后给 P95、Recall/NDCG、有效 SKU 率、token/费用、同步积压等指标。任何 ES、Rerank、消息队列、业务缓存、Redis checkpoint、生产高可用都要明确说“规划/待验证”，不能冒充当前实现。
