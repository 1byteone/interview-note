## 一、索引数据结构：B+Tree 详解

### 1.1 为什么不用二叉树或哈希？

| 数据结构 | 查询复杂度 | 磁盘 IO 次数（百万级数据） | 范围查询 |
|----------|------------|---------------------------|----------|
| 二叉树 | O(log n) | 20 次 | 差 |
| 红黑树 | O(log n) | 20 次 | 差 |
| 哈希表 | O(1) | 1 次 | 不支持 |
| B-Tree | O(log n) | 3-4 次 | 一般 |
| **B+Tree** | **O(log n)** | **3-4 次** | **优秀** |

**B+Tree 的核心优势：**

1. **矮胖结构**：一个节点可存上千个 key，3 层就能存 2000^3 = 80 亿条记录
2. **叶子节点链表**：叶子节点通过指针串联，范围查询只需遍历链表
3. **非叶子节点只存 key**：每页可存更多 key，降低树高
4. **磁盘友好**：每个节点大小 = 一个 page（16KB），一次 IO 读取完整节点

### 1.2 B+Tree 结构图示

```
                     ┌──────────────┐
                     │  [50, 100]   │   ← 非叶子节点（只存 key）
                     └──────┬───────┘
                            │
            ┌───────────────┼───────────────┐
            │               │               │
     ┌──────┴──────┐  ┌────┴────┐  ┌───────┴───┐
     │ [10, 30, 50]│  │[70, 100]│  │[150, 200] │
     └──────┬──────┘  └────┬────┘  └───────┬───┘
            │               │               │
      ┌─────┼──────┐  ┌────┼────┐    ┌─────┼──────┐
      │     │      │  │    │    │    │     │      │
    ┌─┴─┐ ┌─┴─┐ ┌─┴┐ ┌┴─┐ ┌┴─┐ ┌┴┐ ┌┴─┐ ┌┴─┐ ┌─┴──┐
    │10 │ │20 │ │30│ │50│ │60│ │70│ │100│ │150│ │200 │  ← 叶子节点（存数据/主键）
    │...│ │...│ │..│ │..│ │..│ │..│ │.. │ │.. │ │..  │     双向链表
    └───┘ └───┘ └──┘ └──┘ └──┘ └──┘ └───┘ └───┘ └────┘
      ←────────────────────────────────────────────────→
```

### 1.3 B+Tree 层数计算

**InnoDB 页大小**：16KB（默认）

**估算公式：**
- 非叶子节点一个 key 占约 8 字节（BIGINT）+ 6 字节指针 = 14 字节
- 一页可存 key 数 ≈ 16KB / 14B ≈ 1170 个
- 叶子节点一行数据约 1KB，一页存 16 行
- **3 层 B+Tree**：1170 * 1170 * 16 ≈ 2190 万行
- **4 层 B+Tree**：1170 * 1170 * 1170 * 16 ≈ 256 亿行

所以百万级数据 B+Tree 高度为 3，千万级为 3-4，亿级为 4。

## 二、聚簇索引 vs 非聚簇索引

### 2.1 聚簇索引（Clustered Index）

InnoDB 中，**主键就是聚簇索引**。

| 特性 | 说明 |
|------|------|
| 数据存储 | 叶子节点存储完整行数据 |
| 数量 | 每张表只有一个 |
| 默认 | 主键作为聚簇索引 |
| 回表 | 不需要，数据就在索引中 |

**没有主键怎么办？**
1. 找第一个 NOT NULL UNIQUE 列
2. 没有则自动生成隐藏的 `ROW_ID`（6 字节）

### 2.2 非聚簇索引（Secondary Index）

也叫辅助索引或二级索引，叶子节点存储的是**主键值**。

```sql
-- name 上的二级索引
CREATE INDEX idx_name ON product(name);
```

查询过程：
```
SELECT * FROM product WHERE name = 'iPhone 15';
               ↓
    二级索引 idx_name 找到 name='iPhone 15'
               ↓
    叶子节点存储主键 id = 1
               ↓
    通过主键回表查询聚簇索引
               ↓
    获取完整行数据
```

### 2.3 覆盖索引

如果查询所需的列都在二级索引中，就**不需要回表**，这叫覆盖索引。

```sql
-- 以下查询只需要 name 和 price，如果 idx_name_price 包含这两列，则无需回表
CREATE INDEX idx_name_price ON product(name, price);
SELECT name, price FROM product WHERE name = 'iPhone 15';
```

## 三、联合索引与最左前缀原则

### 3.1 联合索引的结构

联合索引 `(a, b, c)` 先按 a 排序，a 相同再按 b 排序，b 相同再按 c 排序。

```
(a, b, c) 在 B+Tree 中的存储顺序：
(1, 1, 1) → (1, 1, 2) → (1, 2, 1) → (1, 2, 3) → (2, 1, 1) → (2, 2, 1)
```

### 3.2 最左前缀原则

```sql
CREATE INDEX idx_a_b_c ON t(a, b, c);

-- 走索引的查询
WHERE a = 1                    -- 用到了 a
WHERE a = 1 AND b = 2          -- 用到了 a, b
WHERE a = 1 AND b = 2 AND c = 3 -- 用到了 a, b, c
WHERE a IN (1, 2) AND b = 2    -- 用到了 a, b
WHERE a = 1 ORDER BY b         -- 用到了 a, b（排序）

-- 不走索引的查询
WHERE b = 2                    -- 跳过了 a，不走索引
WHERE c = 3                    -- 跳过了 a, b，不走索引
WHERE a = 1 AND c = 3          -- 只用到了 a，c 跳过了 b 不走索引
```

### 3.3 联合索引设计原则

1. **区分度高的列放前面**：性别（区分度低）放前面会导致索引效果差
2. **经常查询的列放前面**：`WHERE a = ? AND b = ?` 频率高，a 放前面
3. **排序的列放后面**：`ORDER BY b` 可以利用索引，b 放在最后
4. **尽量用覆盖索引**：减少回表

## 四、索引失效场景

以下 10 种场景会导致索引失效，面试高频考点：

| 场景 | 错误示例 | 正确写法 |
|------|----------|----------|
| 1. 索引列使用函数 | `WHERE DATE(create_time) = '2024-01-01'` | `WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'` |
| 2. 隐式类型转换 | `WHERE phone = 13800138000`（phone 是 VARCHAR） | `WHERE phone = '13800138000'` |
| 3. 非最左前缀 | `WHERE b = 1`（联合索引 a,b,c） | 加 b 的独立索引 |
| 4. LIKE 前模糊 | `WHERE name LIKE '%phone'` | `WHERE name LIKE 'phone%'` |
| 5. OR 两边不全有索引 | `WHERE a = 1 OR b = 2`（b 无索引） | 改为 UNION |
| 6. 索引列参与运算 | `WHERE price * 1.1 > 100` | `WHERE price > 100 / 1.1` |
| 7. NOT IN / NOT EXISTS | `WHERE id NOT IN (1,2,3)` | 看数据量是否可用 EXISTS |
| 8. IS NULL / IS NOT NULL | `WHERE name IS NOT NULL` | 视情况，有时全表扫描更快 |
| 9. 数据分布不均 | `WHERE status = 1`（99% 数据 status=1） | 优化器认为全表扫描更快 |
| 10. 联合索引中间断 | `WHERE a = 1 AND c = 3` | 重建索引 (a, c) |

## 五、Explain 执行计划分析

### 5.1 使用方式

```sql
EXPLAIN SELECT * FROM product WHERE name = 'iPhone 15'\G
```

### 5.2 关键字段详解

| 字段 | 含义 | 重要程度 |
|------|------|----------|
| type | 访问类型 | ★★★★★ |
| key | 实际使用的索引 | ★★★★★ |
| rows | 扫描行数估计值 | ★★★★☆ |
| Extra | 额外信息 | ★★★★☆ |
| possible_keys | 可能使用的索引 | ★★★☆☆ |

### 5.3 type 字段详解（从好到差）

| type | 说明 | 示例 |
|------|------|------|
| system | 表只有一行 | 系统表 |
| const | 主键或唯一索引等值查询 | `WHERE id = 1` |
| eq_ref | 联表查询，主键关联 | JOIN ON 主键 |
| ref | 普通索引等值查询 | `WHERE name = 'iPhone'` |
| range | 索引范围查询 | `WHERE id > 100` |
| index | 扫描整个索引树 | 比 ALL 好但有成本 |
| ALL | 全表扫描 | 大表必须避免 |

### 5.4 Extra 字段详解

| Extra | 含义 | 优化方向 |
|-------|------|----------|
| Using index | 覆盖索引，无需回表 | 理想状态 |
| Using where | 回表后用 where 过滤 | 尝试覆盖索引 |
| Using index condition | 索引下推（ICP） | MySQL 5.6+ 自动优化 |
| Using filesort | 文件排序（性能差） | 加索引消除排序 |
| Using temporary | 使用临时表 | 优化 GROUP BY |
| Using MRR | 多范围读取 | 好现象 |

### 5.5 实战分析

```sql
-- 慢查询分析
EXPLAIN SELECT *
FROM order_info
WHERE DATE(create_time) = '2024-01-15'
ORDER BY amount DESC
LIMIT 10;
```

结果分析：
```
type: ALL（全表扫描）
key: NULL（没有使用索引）
Extra: Using where; Using filesort（回表过滤 + 文件排序）

优化方案：
1. 创建覆盖索引 (create_time, amount)
2. 将 DATE() 函数改为范围查询
```

## 六、索引设计最佳实践

### 6.1 索引设计 Checklist

- [ ] 主键使用自增 BIGINT（页分裂少，写入性能好）
- [ ] 每张表索引数控制在 5 个以内
- [ ] 联合索引不要超过 3 个字段
- [ ] 长字符串用前缀索引（`INDEX(name(10))`）
- [ ] 频繁查询的列优先建索引
- [ ] 频繁更新的列谨慎建索引
- [ ] 区分度低（性别、状态）不单独建索引
- [ ] 用覆盖索引减少回表

### 6.2 索引监控

```sql
-- 查看索引使用情况
SELECT * FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE OBJECT_NAME = 'order_info';

-- 查看索引基数（区分度）
SHOW INDEX FROM order_info;
-- Cardinality 越大，区分度越好
```

### 6.3 常见误区

```sql
-- 误区 1：索引越多越好 → 每个索引维护有成本，影响写入性能
-- 误区 2：主键用 UUID → UUID 无序，页分裂严重，写入性能差
-- 误区 3：VARCHAR(255) 全建索引 → 浪费空间，用前缀索引
-- 误区 4：索引一定能加速查询 → 数据量小（<1000 行）时全表扫描更快
```

## 总结

- B+Tree 是 MySQL 索引的核心数据结构，3-4 层支撑亿级数据
- 聚簇索引存储完整行数据，二级索引需要回表
- 联合索引遵循最左前缀原则，设计时区分度高的列放前面
- 索引失效有 10 种常见场景，面试高频
- Explain 是 SQL 优化利器，重点关注 type、key、rows、Extra
