# 网络基础 — OSI / TCP/IP / HTTP / DNS / CDN

## OSI 七层模型

| 层 | 名称 | 作用 | 典型协议/设备 |
|----|------|------|--------------|
| 7 | 应用层 | 为用户提供网络服务接口 | HTTP, HTTPS, FTP, DNS, SMTP |
| 6 | 表示层 | 数据格式转换、加密、压缩 | SSL/TLS, JPEG, ASCII |
| 5 | 会话层 | 建立、管理、终止会话 | RPC, NetBIOS |
| 4 | 传输层 | 端到端通信、可靠传输 | TCP, UDP |
| 3 | 网络层 | 路由选择、逻辑寻址 | IP, ICMP, ARP, 路由器 |
| 2 | 数据链路层 | 帧封装、MAC 寻址、差错检测 | Ethernet, PPP, 交换机 |
| 1 | 物理层 | 比特流传输、电气信号 | 网线、集线器、中继器 |

## TCP/IP 四层模型

| 层 | 对应 OSI 层 | 核心协议 |
|----|-------------|----------|
| 应用层 | 5~7 | HTTP, DNS, FTP, SMTP |
| 传输层 | 4 | TCP, UDP |
| 网络层 | 3 | IP, ICMP, IGMP |
| 网络接口层 | 1~2 | Ethernet, ARP |

> 面试高频：OSI 是理论模型（7层），TCP/IP 是事实标准（4层）。回答时先说清楚分层，再结合具体协议展开。

## HTTP / HTTPS 协议

### HTTP 请求方法

| 方法 | 用途 | 幂等 | 安全 |
|------|------|------|------|
| GET | 获取资源 | 是 | 是 |
| POST | 提交资源 | 否 | 否 |
| PUT | 更新资源（全量替换） | 是 | 否 |
| PATCH | 部分更新资源 | 否 | 否 |
| DELETE | 删除资源 | 是 | 否 |
| HEAD | 获取响应头（无 Body） | 是 | 是 |
| OPTIONS | 查询支持的请求方法 | 是 | 是 |

### 常见状态码

- **1xx** — 信息性：`101 Switching Protocols`（WebSocket 升级）
- **2xx** — 成功：`200 OK`、`201 Created`、`204 No Content`
- **3xx** — 重定向：`301 Moved Permanently`、`302 Found`、`304 Not Modified`
- **4xx** — 客户端错误：`400 Bad Request`、`401 Unauthorized`、`403 Forbidden`、`404 Not Found`、`429 Too Many Requests`
- **5xx** — 服务端错误：`500 Internal Server Error`、`502 Bad Gateway`、`503 Service Unavailable`、`504 Gateway Timeout`

### HTTPS 握手过程

1. Client Hello — 客户端发送支持的 TLS 版本、加密套件列表、随机数
2. Server Hello — 服务端选定 TLS 版本与加密套件，返回证书（含公钥）+ 随机数
3. 客户端验证证书（CA 链校验），生成预主密钥，用公钥加密后发送
4. 服务端用私钥解密，得到预主密钥，双方各自计算出会话密钥
5. 双方发送 Change Cipher Spec + Finished，此后使用对称加密通信

> 核心要点：非对称加密传输密钥，对称加密传输数据。

## DNS 解析流程

以访问 `www.example.com` 为例：

```
浏览器 → 本地 DNS 缓存 → 系统 hosts 文件
    ↓（未命中）
本地 DNS 服务器（通常是 ISP 提供的）
    ↓（递归查询）
根 DNS 服务器 → 返回 .com 顶级域服务器地址
    ↓
.com 顶级域服务器 → 返回 example.com 权威服务器地址
    ↓
example.com 权威服务器 → 返回 www.example.com 的 IP 地址
    ↓
本地 DNS 服务器缓存结果并返回给客户端
```

**递归查询**：客户端只发送一次请求，DNS 服务器负责完成全部查询。
**迭代查询**：DNS 服务器返回下一级服务器的地址，由客户端逐级查询。

## TCP 三次握手与四次挥手

### 三次握手（建立连接）

```
客户端                         服务端
  │                              │
  │───── SYN (seq=x) ──────────→│ ① SYN_SENT
  │                              │
  │←── SYN-ACK (seq=y, ack=x+1)─│ ② SYN_RCVD
  │                              │
  │───── ACK (seq=x+1, ack=y+1)→│ ③ ESTABLISHED
  │                              │
```

- 第一次握手：客户端发送 SYN，表示请求建立连接
- 第二次握手：服务端回复 SYN-ACK，确认收到请求并同意连接
- 第三次握手：客户端发送 ACK，确认收到服务端的同意，连接建立

> 为什么是三次而不是两次？防止已失效的 SYN 请求突然传到服务端，导致资源浪费。

### 四次挥手（关闭连接）

```
客户端                         服务端
  │                              │
  │───── FIN (seq=x) ──────────→│ ① FIN_WAIT_1
  │                              │
  │←── ACK (seq=y, ack=x+1)────│ ② CLOSE_WAIT
  │                              │
  │←── FIN (seq=z) ────────────│ ③ LAST_ACK
  │                              │
  │───── ACK (ack=z+1) ────────→│ ④ TIME_WAIT (2MSL)
```

- 第一次挥手：客户端发送 FIN，表示不再发送数据
- 第二次挥手：服务端回复 ACK，表示知道客户端要关闭，但服务端可能还有数据要发
- 第三次挥手：服务端数据发送完毕，发送 FIN
- 第四次挥手：客户端回复 ACK，进入 TIME_WAIT 状态，等待 2MSL 后关闭

> TIME_WAIT 持续 2MSL（约 2 分钟），确保最后一个 ACK 能被服务端收到，同时让旧连接的所有报文在网络中消失。

## CDN 原理

### 核心概念

- **边缘节点** — 部署在全球各地的缓存服务器，用户就近访问
- **源站** — 存放原始内容的服务器（如阿里云 OSS、自建服务器）
- **回源** — 边缘节点未命中缓存时，向源站请求内容

### 工作流程

1. 用户请求 `cdn.example.com/image.png`，DNS 解析到 CDN 的负载均衡系统
2. 负载均衡根据用户 IP 地理位置，返回最近的边缘节点 IP
3. 边缘节点检查本地缓存：命中则直接返回；未命中则向源站发起回源请求
4. 边缘节点缓存内容并返回给用户，后续相同请求直接命中缓存

### 缓存策略

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| TTL 过期 | 设置 Cache-Control: max-age=3600 | 静态资源（图片、CSS、JS） |
| 版本号 | 资源 URL 带版本号，强制更新 | 前端构建产物 |
| 预热 | 提前将热点资源推送到边缘节点 | 大促活动、新品上线 |
| 刷新 | 主动清除指定 URL 的缓存 | 内容更新后立即生效 |

### CDN 在 AI 商城的应用

- 商品图片、用户头像等静态资源通过 CDN 加速，降低源站带宽压力
- AI 推荐结果的封面图使用 CDN 分发，提升用户端加载速度
- 前端 SPA 构建产物（HTML/CSS/JS）托管 CDN，配合版本号实现秒级更新
