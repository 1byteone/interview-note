# 02 · 请求生命周期

> 本文跟踪两个核心请求的完整生命周期：**AI 智能搜索** 和 **用户下单**。通过时序图展示每个请求如何穿越接入层、网关层、服务层、中间件层，最终返回结果。

### 1.2 各阶段耗时分析

| 阶段 | 估算耗时 | 占比 | 瓶颈分析 |
|------|---------|------|---------|
| 前端网络传输 | 20ms | 1% | 取决于用户网络 |
| 网关路由+鉴权 | 10ms | 0.5% | 低延迟，可忽略 |
| Agent 初始化 | 50ms | 2% | 首次创建 Agent 的开销 |
| 向量检索 | 210ms | 10% | 其中 Embedding 200ms，HNSW 搜索 10ms |
| LLM 推理 | 1600ms | 76% | **最大瓶颈**，取决于模型大小和推理服务 |
| 响应解析 | 50ms | 2% | Pydantic 校验结构化输出 |
| 前端渲染 | 50ms | 2% | Vue3 响应式更新 |
| **总计** | **~2.1s** | **100%** | 主要瓶颈在 LLM 推理 |

**关键结论：** AI 搜索的瓶颈不在检索，而在生成。向量检索仅占 ~10%，LLM 推理占 ~76%。优化方向应优先考虑 LLM 推理速度（模型量化、推理加速、流式输出）。

### 2.2 下单流程中的关键设计

| 环节 | 设计 | 目的 |
|------|------|------|
| **库存扣减** | 订单服务发起 Seata 全局事务，调用库存服务扣减 | 保证订单和库存的一致性 |
| **Seata AT 模式** | 自动生成镜像、自动回滚，业务无侵入 | 降低分布式事务开发成本 |
| **RocketMQ 延迟消息** | 下单时发送 30 分钟延迟消息，超时检查订单状态 | 订单超时自动取消，无需轮询 |
| **支付回调** | 异步 HTTP 回调，更新订单状态 | 支付成功通知业务系统 |
| **幂等设计** | 支付回调 ID 去重，防止重复处理 | 保证支付结果只处理一次 |

## 三、两条核心链路的对比

| 对比维度 | AI 搜索链路 | 下单链路 |
|---------|------------|---------|
| **核心模式** | 同步 HTTP + 异步 Agent 循环 | 同步事务 + 异步消息 |
| **一致性要求** | 最终一致性（推荐结果可接受微调） | 强一致性（库存不能超卖） |
| **延迟敏感度** | 中等（2s 以内可接受） | 极低（需毫秒级响应） |
| **瓶颈** | LLM 推理（~76%） | 数据库写入 + 分布式事务 |
| **容错策略** | 降级展示（推荐失败可兜底到传统搜索） | 事务回滚 + 消息补偿 |
| **Java 服务** | 网关路由到 Python AI 服务 | 网关路由到 Java 微服务 |
| **Python 服务** | Agent + 向量检索 + LLM 生成 | 不参与 |
