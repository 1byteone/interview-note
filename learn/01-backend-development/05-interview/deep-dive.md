# 深挖题 — 分布式理论、一致性、分布式 ID、架构演进

> 考察对基础理论的深度理解，死记硬背过不了面试官的下一个问题。多问自己"为什么"。

## 1. CAP 定理

### 概念

分布式系统中的三个特性最多只能同时保证两个：

| 性质 | 全称 | 含义 |
|------|------|------|
| C | Consistency（一致性） | 所有节点同一时刻看到相同的数据 |
| A | Availability（可用性） | 任何请求都能得到响应（不保证正确） |
| P | Partition Tolerance（分区容错性） | 节点间网络分区时，系统仍能继续运行 |

**关键结论**：网络分区（P）在分布式环境中不可避免，所以分布式系统实际是在 **CP 和 AP 之间二选一**，而 CA 在分布式系统中不存在（CA 只存在于单机）。

### 面试追问

**Q1：为什么 P 不能放弃？**
P 是所有分布式系统的前提——网络可能随时出现分区和延迟，无法人为控制。所以在"分区发生的那一刻"系统必须在 C 和 A 之间做抉择：选择 CP（拒绝服务保证一致性）还是 AP（保证可用性，允许短暂不一致）。

**Q2：CP 和 AP 各举一个例子？**
- **CP**：Zookeeper、etcd、Consul 注册中心——服务注册要求强一致，宁可短暂不可用也不允许注册错误。
- **AP**：Eureka 注册中心、Redis 集群哨兵模式、缓存系统——允许短暂的不一致，保证可用性优先。

**Q3：CAP 是不是说三个特性只能选两个，和应用里两者兼得？**
CAP 是针对**分布式系统在分区时的行为**。在正常无分区时，C 和 A 可以同时满足。一个系统可以设计为：正常时段强一致，分区时段牺牲 A 或 C（如 MySQL 主从 + 半同步复制就是正常抓一致，分区降级）。

## 2. BASE 理论

### 概念

BASE 是 "Basically Available, Soft state, Eventually Consistent" 的缩写：

| 组成部分 | 含义 | 例子 |
|----------|------|------|
| Basically Available（基本可用） | 系统在故障时仍能响应，允许降级 | 秒杀时关闭部分非核心功能（评论、搜索）只保留核心下单链路 |
| Soft state（软状态） | 允许系统中的数据存在中间状态 | 订单状态"支付中"，最终会落到"已支付"或"已关闭" |
| Eventually Consistent（最终一致性） | 数据经过一段时间后最终达到一致 | 转账后余额短暂不一致，最终一致 |

### 面试追问

**Q：如何实现最终一致性？**
1. **本地消息表**：业务操作和消息写入在同一事务中，投递失败则重试，配合定时任务扫描补偿
2. **事务消息（RocketMQ 事务消息 / Kafka 事务）**：先发半事务消息，业务成功提交后确认消息，失败则回滚
3. **消息重试 + 幂等消费**：消费者重复消费要有幂等机制（主键去重、状态机）
4. **对账系统**：定期对账发现不一致的数据，人工或自动补偿

**Q：最终一致性有哪些实现模式？**
- 异步确保型（消息队列）
- 定期校对型	（对账）
- 可靠消息最终一致性（RocketMQ 事务消息）
- TCC（Try-Confirm-Cancel）——严格说是"尽力而为"，接近最终一致性

## 3. 分布式 ID 方案对比

### 需求
全局唯一、单调递增（或趋势递增）、高性能、高可用、尽量短的位数（减少索引开销）。

### 方案对比

| 方案 | 生成原理 | 优点 | 缺点 | 适用场景 |
|------|----------|------|------|----------|
| **UUID** | 128 位随机 | 生成简单、无中心、天然唯一 | 无序（索引性能差）、太长（36 字符） | 非主键场景（文件名、消息 traceId） |
| **数据库自增** | DB auto_increment | 简单、有序 | 单点性能瓶颈，泄露业务量 | 单库场景 |
| **号段模式** | 一次取一段 ID 缓存到内存 | 性能高、有序性尚可 | 依赖数据库，重启丢失号段 | 中低并发 |
| **雪花算法（Snowflake）** | 时间戳 + 机器 ID + 序列号（64 位） | 高性能、趋势递增、无中心依赖 | 时钟回拨问题 | 大规模分布式最常用 |
| **Redis 自增** | INCR/INCRBY | 高潮发、趋势递增 | 依赖 Redis，需要考虑持久化 | 会丢失 ID 的场景、中并发 |
| **美团 Leaf / 百度 UidGenerator** | 号段 + 雪花改进 | 高可用、高性能 | 需要部署专用服务 | 大规模业务 |

### 雪花算法详解

```
64 位 Long
├── 1 bit（符号位，固定 0）
├── 41 bit（时间戳，毫秒，可支持约 69 年）
├── 10 bit（工作机器 ID，可支持 1024 台机器）
└── 12 bit（序列号，同一毫秒内可生成 4096 个 ID）
```

```java
// 简化版雪花算法核心逻辑
public synchronized long nextId() {
    long now = System.currentTimeMillis();
    if (now < lastTimestamp) {
        // 时钟回拨：要么抛异常，要么等待时间追上
        throw new RuntimeException("时钟回拨，拒绝生成 ID");
    }
    if (now == lastTimestamp) {
        sequence = (sequence + 1) & 0xFFF;  // 4095 掩码
        if (sequence == 0) {
            // 当前毫秒序列号用完，等待下一毫秒
            now = waitNextMillis(lastTimestamp);
        }
    } else {
        sequence = 0;
    }
    lastTimestamp = now;
    return ((now - EPOCH) << 22) | (machineId << 12) | sequence;
}
```

### 面试追问

**Q：雪花算法的缺点？** 时钟回拨——机器时间被往前调整时，会生成重复 ID。解决方案：等待时间追上、用备用时钟、或闭区间拒绝生成。

**Q：你项目里用的什么？**（结合项目答）"我们订单 ID 用的是美团 Leaf 号段模式，因为要保证趋势递增以便数据库索引，同时支持高并发。Trace ID 用 UUID，因为只要求唯一不要求有序。"

## 4. 单体拆分微服务的评估框架

### 面试追问

**Q：如何评估一个单体要不要拆成微服务？** 用"三有原则"：
1. 有流量压力需要独立扩缩容
2. 有组织边界需要独立发布
3. 有技术异构需求

**Q：如何控制拆分风险？** 分阶段演进（Strangler Fig 模式——绞杀者模式）：先在单体边缘新增微服务，逐步把流量从单体迁移到新服务，最后彻底下线单体功能。每个阶段都有独立交付和回滚计划。

**Q：拆了之后，又是单点怎么办？** 微服务的难点从"拆分"转移到"治理"：注册发现（Nacos/Eureka）、配置中心、网关路由、限流熔断（Sentinel/Hystrix）、链路追踪（SkyWalking/Zipkin）、分布式事务（Seata）、监控告警（Prometheus）。这些问题本身是复杂的系统工程。

## 5. 高并发下的数据一致性

### 面试追问

**Q：下单链路的超卖问题怎么办？**
1. 数据库层面：**悲观锁**（`SELECT ... FOR UPDATE`）或**乐观锁**（`WHERE stock >= n`）
2. Redis 预扣库存：先扣 Redis，异步落库，Redis 扣减失败直接返回售罄
3. SQL 原子扣减：`UPDATE t_product SET stock = stock - 1 WHERE id = ? AND stock > 0`——判断影响行数

**Q：库存扣减和订单创建的最终一致性怎么保证？**
- 方案 A：RocketMQ 事务消息（扣库存和发送消息同一分布式事务，消息最终通知订单服务）
- 方案 B：本地消息表（扣库存事务中插入本地消息表，异步投递+重试）
- 两种方案都要求消费端**幂等**（订单号唯一索引，重复消费时跳过）

## 6. 架构演进的历史脉络（祖宗篇）

**Q：从单体到微服务，人类是怎么演进的？**
1. **单体** → 所有代码一个进程
2. **SOA** → 服务化 + ESB 总线（重的中心化集成）
3. **去中心化微服务** → 轻量 RPC/HTTP + 注册发现 + 网关（Spring Cloud / Dubbo）
4. **Service Mesh**（服务网格）→ 把治理能力下沉到边车（Sidecar）代理，业务代码零侵入（Istio）

每个阶段都是**对前一个阶段痛点的回应**：SOA 解决单体重，微服务解决 SOA 重，Service Mesh 解决微服务侵入。

> **总结**：深挖题的核心是把概念连成体系——CAP 解释"为什么分布式要妥协"，BASE 解释"怎么妥协"，分布式 ID、消息事务、库存扣减都是妥协后具体怎么落地的技术方案。
