# 单体 vs SOA vs 微服务 vs DDD — 架构演进路线

## Situation（情境）

创业初期，你是一个 5 人团队，要尽快上线一个电商 MVP：注册登录、商品浏览、下单支付、订单查询。工期只有 3 个月。此时姑且把架构做得多复杂？另一面，两年后业务增长，日活过百万，团队扩张到 80 人，原来的单体代码库开始互相踩踏：一次促销活动引发的慢查询拖垮了整个下单链路，改一个库存字段要同时回归支付、物流、统计十几个模块。这时候要不要拆？怎么拆？

这就是架构演进的核心矛盾：**单体快速迭代 vs 业务扩张后的拆分需求**。

## Task（任务）

理解四种主流架构形态（单体、SOA、微服务、DDD）各自的适用范围、优缺点与演进路径，并能在面试中结合具体业务回答"你们为什么选这个架构？"

## Action（行动）

### 1. 单体架构（Monolith）

一个应用、一个进程、一个数据库，所有模块（用户、商品、订单）编译打包在一起部署。

| 优点 | 缺点 |
|------|------|
| 开发简单，没有网络开销，事务好做 | 体积膨胀后编译慢、启动慢 |
| 部署简单，一个包一个容器 | 模块边界模糊，代码互相纠缠 |
| 调试方便，链路清晰 | 技术栈锁定，无法局部替换 |
| 性能好（本地调用） | 扩展只能整体扩展（Scale Up） |

### 2. SOA（面向服务架构）

以**服务**为粒度，通过 ESB（企业服务总线）集成。强调服务复用，但 ESB 容易成为单点和性能瓶颈。SOA 的核心规则是"服务只通过契约交互"，**服务间独立部署，共享数据库**是其常见形态。

### 3. 微服务架构（Microservices）

每个服务独立进程、独立数据库、独立部署，通过 HTTP/RPC 通信。本质是 SOA 的演进：去掉了 ESB，改用轻量级协议 + 服务注册发现。

| 优点 | 缺点 |
|------|------|
| 独立部署、独立扩展，弹性伸缩 | 分布式事务复杂，最终一致性替代强一致 |
| 故障隔离：一个服务挂了不影响整体 | 运维成本高（注册中心、网关、链路追踪）|
| 技术异构：不同服务可用不同语言 | 跨服务调试困难，接口契约需严格维护 |
| 团队自治：小团队拥有全生命周期 | 网络延迟与调用链复杂度上升 |

### 4. 领域驱动设计（DDD，Domain-Driven Design）

DDD 不是架构"形态"，而是一种**建模方法论**：以业务领域为思考中心，用**限界上下文（Bounded Context）**划分系统边界，用**子域（核心域/支撑域/通用域）**判断投资优先级。在微服务实践中，DDD 常被用来回答"**服务边界划在哪里**"——每个限界上下文对应一个或多个服务，这种方法叫 DDD 结合微服务的"两个维度"打法。

### 5. 演进路径与选型决策

```
单体 ──业务复杂化──► SOA ──轻量化──► 微服务
  │                    │
  └──── DDD 建模贯穿始终，决定边界 ────┘
```

**何时选单体**：团队 < 10 人、业务模式未验证、需要 3 个月上线验证市场。此时拆微服务是**预支复杂度**。

**何时拆微服务**（至少满足 2-3 条信号）：
- 团队规模 > 足够多，一个代码库并行开发冲突严重
- 不同模块扩缩容需求差异大（如商品搜索扛高流量，订单低频）
- 部门职责清晰，需要独立发布节奏
- 技术栈异构需求出现

**何时用 DDD**：核心业务逻辑复杂、规则多变（如信贷风控、电商促销引擎），需要专家与开发深度协作；且系统生命周期足够长，建模投资有回报空间。

### 6. 面试 STAR 示例

> **S**：我们团队从 6 人增长到 40 人，单体商城出现发布冲突和故障放大。
> **T**：评估是否拆分，拆分粒度以什么为准。
> **A**：先做 DDD 事件风暴梳理出 6 个限界上下文（用户、商品、订单、支付、库存、营销），按"团队自治"和"故障隔离"优先级分批拆分；第一批只拆出商品与支付两个高频变动的服务，订单仍在单体停留一个迭代，用 2 周时间验证发布与监控流程。
> **R**：发布频率从每周 1 次升到每天 4 次，下单链路 P99 从 800ms 降到 250ms，且支付服务故障不再拖垮商品浏览。

## Result（结果）

架构选型的判断句式：**在业务复杂度明确之前不要引入架构复杂度**；拆分以 DDD 边界为依据，渐进式演进；微服务是为团队组织和流量结构服务的，不是技术炫耀。

## 附：AI 商城为什么选择微服务？

回到本系列的项目背景——AI 商城，它比传统电商多出几类明显不同的流量特征：

1. **AI 推荐服务与主流程流量差异巨大**：秒杀活动时订单服务 QPS 可能到 1 万，而 AI 推荐服务需要 GPU 推理、响应要求分钟级；如果混在一个单体里，一次大促就能把推荐链路打挂。
2. **独立的扩缩容维度**：商品搜索可以开 20 个实例，但支付服务受清算风控约束只需要 4 个，微服务允许按需伸缩。
3. **技术异构必要**：AI 商城需要 Python/GPU 做模型推理，而 Java 做订单核心链路更稳妥，微服务天然支持异构。
4. **独立发布节奏**：推荐算法每周迭代，支付合规一年只动几次。

用 DDD 划分后，AI 商城拆成：`用户服务 / 商品服务 / 订单服务 / 支付服务 / 库存服务 / AI 推荐服务 / 搜索服务 / 网关` —— 这就是 04-projects/mall-integration.md 里那张架构图的来由。

> 一个反直觉的提醒：即使选了微服务，**核心下单路径也可以先保留在单体**或做"模块化单体"（Modular Monolith），等真正的痛点出现再拆。微服务不是终点，而是应对痛点的工具。
