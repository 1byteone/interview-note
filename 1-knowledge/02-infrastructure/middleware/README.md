# 中间件面试题

## 📚 知识点概览

中间件是微服务架构的重要组成部分，包括缓存、数据库、搜索引擎、消息队列等。

## 🎯 面试题分类

### Level 1: 基础题

#### Redis 基础
1. **Redis 核心特性**
   - 问题：Redis 的核心特性有哪些？它为什么这么快？
   - 答案：Redis 是基于内存的键值存储系统，核心特性包括高性能（单机 QPS 可达 10 万+）、丰富的数据结构、持久化、主从复制、高可用集群和 Lua 脚本支持。其高性能源于纯内存操作、单线程模型避免竞态、IO 多路复用（epoll）以及高效的数据结构设计。
   - 解析：Redis 的快是多方面因素共同作用的结果。首先，数据全部存储在内存中，读写速度远快于磁盘 IO。其次，采用单线程模型处理命令，避免了上下文切换和锁竞争带来的开销。IO 多路复用机制使单线程能高效处理大量并发连接。底层数据结构如跳表、压缩列表等针对不同场景做了极致优化。此外，Redis 6.0 后引入的多线程 IO 仅用于网络读写，命令执行依然是单线程，兼顾了性能和简单性。

2. **数据结构**
   - 问题：Redis 支持哪些数据结构？各自的使用场景是什么？
   - 答案：Redis 支持 String（缓存、计数器）、Hash（对象存储）、List（消息队列、最新列表）、Set（去重、交集并集运算）、ZSet（排行榜、延时队列）、Bitmap（签到统计）、HyperLogLog（UV 统计）、Geo（地理位置）、Stream（消息队列）和 Bitfield。
   - 解析：String 是最基础的类型，可用于缓存任何序列化数据，INCR 命令天然适合计数器场景。Hash 适合存储对象，可以单独操作某个字段。List 基于双向链表，LPUSH+BRPOP 组合实现阻塞队列。Set 支持交并差运算，适合标签系统。ZSet 的 score 排序特性使其成为排行榜和延时队列的理想选择。Stream 是 Redis 5.0 引入的持久化消息队列，支持消费者组和消息确认，弥补了 Pub/Sub 不持久化的缺陷。

3. **缓存策略**
   - 问题：什么是缓存穿透、缓存击穿、缓存雪崩？如何解决？
   - 答案：缓存穿透指查询不存在的数据导致请求直达数据库，解决方法是布隆过滤器和缓存空对象。缓存击穿指热点 key 过期导致高并发请求穿透到数据库，解决方法是互斥锁和逻辑过期。缓存雪崩指大量 key 同时过期或 Redis 宕机导致数据库崩溃，解决方法是过期时间加随机值、多级缓存和集群高可用。
   - 解析：三种场景的根因和影响不同。缓存穿透的攻击性较强，恶意查询不存在的 key 可能拖垮数据库，布隆过滤器能在 O(k) 时间内判断元素一定不存在，但存在误判率。缓存击穿针对单一热点 key，在失效瞬间大量请求涌入，互斥锁保证只有一个线程去重建缓存，其他线程等待。缓存雪崩的破坏力最大，过期时间均匀打散（基础时间+随机偏移）可有效避免同时过期。实际生产中应组合使用多种策略，例如本地缓存（Caffeine）作为 Redis 的降级方案。

#### MySQL 基础
4. **索引原理**
   - 问题：MySQL 索引的原理是什么？B+ 树有什么优势？
   - 答案：MySQL InnoDB 使用 B+ 树作为索引结构，叶子节点存储完整行数据或主键值，非叶子节点仅存储索引键和指针。B+ 树的优势在于：树高较低（通常 2-4 层），减少磁盘 IO；叶子节点形成有序双向链表，支持高效的范围查询和排序；所有数据都在叶子节点，查询效率稳定。
   - 解析：B+ 树相比 B 树的关键区别在于非叶子节点不存数据，只存索引，使得每页能容纳更多索引项，从而降低树高。以 3 层 B+ 树为例，若每页存储 1000 个索引项，可容纳 10 亿条记录，查找任意记录仅需 3 次磁盘 IO。叶子节点的双向链表使范围查询不需要回溯到父节点，直接遍历即可。InnoDB 的主键索引是聚簇索引，叶子节点直接存行数据，二级索引叶子节点存主键值，回表查询时通过主键索引找到完整行。

5. **事务特性**
   - 问题：MySQL 事务的四大特性是什么？什么是 ACID？
   - 答案：ACID 是事务的四个特性：原子性（Atomicity）指事务要么全部成功要么全部回滚；一致性（Consistency）保证事务前后数据完整性约束不被破坏；隔离性（Isolation）使并发事务互不干扰；持久性（Durability）确保提交后数据永久保存。MySQL 通过 undo log 保证原子性，redo log 保证持久性，锁和 MVCC 保证隔离性。
   - 解析：原子性由 undo log 实现，事务回滚时利用 undo log 中记录的反向操作恢复数据。持久性由 redo log 实现，采用 WAL（Write-Ahead Logging）策略，先写日志再刷盘，即使宕机也可通过 redo log 恢复。隔离性通过锁机制和 MVCC 实现，MySQL 提供四种隔离级别：读未提交、读已提交（RC）、可重复读（RR，默认）、可串行化。RR 级别通过间隙锁解决幻读。一致性是 ACID 的最终目标，前三个特性共同保证一致性。

6. **SQL 优化**
   - 问题：如何优化 SQL 查询？有哪些常用的方法？
   - 答案：SQL 优化方法包括：合理使用索引（覆盖索引、复合索引最左前缀原则）、避免 SELECT * 只查必要字段、避免索引列上使用函数或隐式类型转换、使用 EXPLAIN 分析执行计划、优化 JOIN 顺序（小表驱动大表）、分页优化（游标分页代替 OFFSET）、合理使用慢查询日志定位问题。
   - 解析：EXPLAIN 是 SQL 优化的核心工具，重点关注 type（ALL 需优化）、key（实际使用的索引）、rows（扫描行数）、Extra（Using filesort/Using temporary 需优化）。覆盖索引避免回表查询，效率最高。复合索引遵循最左前缀原则，如 (a,b,c) 索引可匹配 (a)、(a,b)、(a,b,c) 查询。分页深度问题（OFFSET 大时）可通过子查询先定位 ID 再 JOIN 优化。使用慢查询日志（long_query_time 设为 1 秒）和 Performance Schema 持续监控。避免在 WHERE 中对索引列使用函数，如 WHERE DATE(create_time) = '2024-01-01' 应改为范围查询。

#### Elasticsearch 基础
7. **倒排索引**
   - 问题：什么是倒排索引？Elasticsearch 如何实现全文搜索？
   - 答案：倒排索引是以词条为键、文档 ID 列表为值的数据结构，记录每个词条在哪些文档中出现及位置信息。Elasticsearch 基于 Lucene，将文档经过分词器（Analyzer）拆分为词条（Term），构建倒排列表。搜索时对查询语句分词，在倒排索引中查找匹配的文档，结合 TF-IDF 或 BM25 算法计算相关性评分并排序返回。
   - 解析：倒排索引的构建过程包括：文档经字符过滤（HTML 标签去除等）、分词（Tokenization）、词项过滤（转小写、去停用词、词干提取）后得到 Term Dictionary。Term Dictionary 按字典序排序，配合 Term Index（FST 结构）实现快速定位。倒排列表记录文档 ID、词频（TF）和位置信息（Position），支持短语查询。ES 7.x 默认使用 BM25 算法，相比 TF-IDF 引入饱和度和长度归一化，避免长文档得分虚高。搜索时先查 Term Dictionary 定位 Term，再遍历倒排列表收集文档，最后评分排序。

8. **基本操作**
   - 问题：Elasticsearch 的基本操作有哪些？
   - 答案：Elasticsearch 的基本操作包括：索引管理（创建/删除索引、设置分片和映射）、文档 CRUD（Index/Create/Update/Delete/Get）、搜索（Query DSL 的 term/match/bool/range 查询）、聚合分析（Terms/Cardinality/Date Histogram 等 Bucket 和 Metric 聚合）、以及批量操作（Bulk/MultiGet/MultiSearch）。
   - 解析：查询 DSL 是 ES 的核心交互语言。term 查询用于精确匹配，match 查询用于全文搜索（会分词）。bool 查询组合 must/should/filter/must_not 子句，filter 子句不计算评分，适合精确过滤，性能优于 must。聚合分析分为 Bucket（分组桶）、Metric（指标计算，如 avg/sum/cardinality）、Pipeline（对聚合结果再聚合）。Mapping 定义字段类型和分析器，Dynamic Mapping 自动推断类型但可能不准确，生产环境建议显式定义。Bulk API 批量操作大幅提升写入性能，但需注意批次大小（通常 5-15MB）。

#### RocketMQ 基础
9. **消息模型**
   - 问题：RocketMQ 的消息模型是怎样的？
   - 答案：RocketMQ 采用 Producer（生产者）、Consumer（消费者）、NameServer（注册中心）、Broker（消息服务器）的四层架构。消息按 Topic 分类，Topic 下分多个 Message Queue（消息队列），每个 Queue 在 Broker 上存储。NameServer 提供路由发现，Broker 集群部署实现高可用。消费模式支持集群消费（一条消息只被一个消费者消费）和广播消费（所有消费者都收到）。
   - 解析：RocketMQ 的消息模型设计借鉴了 Kafka 的分区思想但做了改进。Topic 是逻辑概念，Message Queue 是物理存储单元，实现水平扩展。NameServer 是轻量级路由注册中心，无状态可集群部署，Broker 启动时向所有 NameServer 注册，Producer/Consumer 定时从 NameServer 拉取路由信息。Broker 主从架构支持同步双写和异步复制两种模式。CommitLog 是消息的物理存储文件，ConsumeQueue 是逻辑队列文件，基于 CommitLog 构建，这种设计实现了顺序写 CommitLog 的高性能和逻辑多队列的灵活性。

10. **消息类型**
    - 问题：RocketMQ 支持哪些消息类型？各自的使用场景是什么？
    - 答案：RocketMQ 支持普通消息（常规异步/同步发送）、顺序消息（全局顺序和分区顺序，用于订单流程）、延时消息（预设 18 个延时级别，用于超时关单）、事务消息（分布式事务最终一致性）、批量消息（批量发送提高吞吐量）。还支持定时消息（精确到秒级）和请求-应答消息（RPC 模式）。
    - 解析：顺序消息通过将相同业务 key（如订单 ID）的消息发送到同一 Message Queue，消费者端使用单线程消费来保证严格顺序，但会牺牲部分并行度。事务消息的实现分两阶段：先发送半消息，执行本地事务后提交或回滚，Broker 通过回查机制保证最终一致性。延时消息的 18 个级别从 1s/5s/10s/30s/1m 到 2h，消息体不存储延时信息，而是通过 Broker 的定时任务扫描延期队列。RocketMQ 5.0 支持基于时间轮的精确延时/定时消息，弥补了固定级别的不足。

### Level 2: 进阶题

#### Redis 进阶
11. **持久化机制**
    - 问题：Redis 的持久化机制有哪些？RDB 和 AOF 的区别是什么？
    - 答案：Redis 支持 RDB（快照持久化）和 AOF（追加文件持久化）两种机制。RDB 通过 fork 子进程生成全量数据快照，文件紧凑恢复快，但可能丢失最后一次快照后的数据。AOF 记录每条写命令，数据安全性高，支持三种刷盘策略（always/everysec/no），但文件体积大、恢复慢。Redis 4.0 引入混合持久化，结合 RDB 和 AOF 的优劣势。
    - 解析：RDB 通过 save（同步阻塞）和 bgsave（异步 fork 子进程）触发，fork 时采用 copy-on-write 机制，子进程共享父进程内存页，父进程继续处理请求，只有被修改的页才会复制，因此内存开销较小。AOF 的 everysec 策略是生产推荐方案，每秒刷盘一次，最多丢失 1 秒数据。AOF 文件会随写入增长，需通过 BGREWRITEAOF 重写压缩。混合持久化在 AOF 重写时将当前内存快照以 RDB 格式写入 AOF 文件开头，后续增量命令以 AOF 格式追加，兼顾了 RDB 的快速恢复和 AOF 的数据安全。

12. **集群部署**
    - 问题：Redis Cluster 的原理是什么？如何实现高可用？
    - 答案：Redis Cluster 采用无中心化架构，通过虚拟槽（16384 个哈希槽）实现数据分片，每个节点负责一部分槽位。使用 Gossip 协议进行节点间通信和状态同步，自动发现新节点和检测故障。通过主从复制实现高可用，主节点故障时从节点自动提升为主。客户端直接连接任意节点，通过 MOVED/ASK 重定向找到正确节点。
    - 解析：Redis Cluster 的键通过 CRC16 算法计算哈希值对 16384 取模决定归属的槽，槽到节点的映射关系存储在 Cluster 状态中。Gossip 协议使用 PING/PONG 消息定期交换节点状态，每个节点维护集群视图。故障检测分两步：节点标记 PFAIL（疑似故障）和集群确认 FAIL（下线），当半数以上持有槽的主节点都认为某节点 PFAIL 时标记为 FAIL。从节点选举通过 Raft 算法实现，只有持有最新数据的从节点才能竞选。客户端在 MOVED 重定向时缓存槽位信息，ASK 重定向用于迁移中的临时路由。

13. **分布式锁**
    - 问题：如何使用 Redis 实现分布式锁？有哪些注意事项？
    - 答案：Redis 分布式锁的核心命令是 SET NX EX（或 SETNX+EXPIRE 原子化），通过 SET key value NX EX 30 实现加锁。释放锁时使用 Lua 脚本确保原子性：先校验锁持有者再删除，防止误删。注意事项包括：设置合理过期时间防止死锁、使用唯一标识（如 UUID）区分锁持有者、加锁和设置过期时间必须原子操作、考虑 Redlock 算法在极端场景下的必要性。
    - 解析：单机 Redis 锁的问题在于主从切换时可能丢失锁。Redlock 算法在 N 个独立 Redis 节点上获取锁，超过半数成功才算加锁成功，但存在时钟漂移和性能开销问题，业界争议较大。实际生产中使用 Redisson 库，它提供看门狗（Watch Dog）机制自动续期，避免业务执行超时锁被释放。锁粒度应尽量细化，避免大锁影响并发。对于高一致性要求的场景，建议使用 ZooKeeper 的临时顺序节点实现分布式锁，虽性能低于 Redis，但 CP 特性更可靠。Redis 锁适合允许少量锁冲突的 AP 场景。

#### MySQL 进阶
14. **锁机制**
    - 问题：MySQL 的锁机制有哪些？行锁和表锁的区别是什么？
    - 答案：MySQL 锁按粒度分为表锁（Table Lock）、行锁（Row Lock）和页锁。InnoDB 支持行锁和表锁，行锁通过索引实现，分为共享锁（S Lock）和排他锁（X Lock）。表锁包括意向锁（IS/IX）和 AUTO-INC 锁。行锁又分为记录锁（Record Lock）、间隙锁（Gap Lock）和临键锁（Next-Key Lock），用于不同隔离级别下的并发控制。
    - 解析：行锁和表锁的核心区别在于锁定粒度。行锁锁住单行记录，并发度高但锁管理开销大；表锁锁住整张表，开销小但并发度低。InnoDB 的行锁是基于索引实现的，若查询不走索引则会升级为表锁。间隙锁在 RR 级别下防止幻读，锁定索引记录之间的间隙，阻止其他事务插入。Next-Key Lock 是记录锁+间隙锁的组合，锁定一个左开右闭区间。意向锁是表级别的锁，表明事务即将对行加锁，避免逐行检查表锁冲突。死锁检测通过 wait-for graph 算法，InnoDB 自动回滚代价较小的事务。

15. **MVCC 原理**
    - 问题：什么是 MVCC？它是如何实现的？
    - 答案：MVCC（多版本并发控制）是 MySQL InnoDB 实现高并发读的关键机制，通过维护数据行的多个版本，使读操作不阻塞写操作、写操作不阻塞读操作。实现依赖三个核心组件：隐藏字段（DB_TRX_ID、DB_ROLL_PTR、DB_ROW_ID）、undo log 版本链和 ReadView（一致性视图）。ReadView 根据活跃事务列表决定可见性规则。
    - 解析：每个数据行有两个隐藏字段：DB_TRX_ID 记录最近修改的事务 ID，DB_ROLL_PTR 指向 undo log 中上一个版本。当 UPDATE 产生新版本时，旧版本数据保留在 undo log 中，通过回滚指针串联形成版本链。ReadView 包含 m_ids（活跃事务 ID 列表）、min_trx_id（最小活跃事务 ID）、max_trx_id（下一个分配的事务 ID）。可见性判断：trx_id < min_trx_id 可见；trx_id > max_trx_id 不可见；trx_id 在 m_ids 中不可见，否则可见。RC 级别每次查询生成新 ReadView，RR 级别只在事务首次查询时生成 ReadView，从而实现可重复读。

16. **分库分表**
    - 问题：什么时候需要分库分表？有哪些分片策略？
    - 答案：当单表数据量达到千万级（InnoDB B+ 树深度超过 3 层）或单库连接数、IO 成为瓶颈时，需要考虑分库分表。分片策略包括：水平分表（按 ID 取模/时间范围分表）、水平分库（按业务维度分库）、垂直拆分（按字段拆分宽表）、以及混合拆分。常用分片键选择频繁查询条件字段，如用户 ID 或订单 ID。
    - 解析：分库分表引入分布式事务、跨节点查询、全局主键、数据迁移等复杂问题。ShardingSphere 和 MyCat 是主流中间件。分片策略选择：取模分片数据均匀分布但扩展困难（需重新哈希），一致性哈希可减少迁移量；范围分片（按时间）便于分区裁剪但数据可能倾斜。全局主键可用雪花算法（Snowflake）或 Leaf 方案。跨分片查询（如 ORDER BY 和 JOIN）需要中间件聚合，性能较差。分库分表是最后的手段，优先考虑索引优化、读写分离、缓存等方案。建议在业务初期预留分片字段和扩展能力。

#### Elasticsearch 进阶
17. **集群架构**
    - 问题：Elasticsearch 的集群架构是怎样的？
    - 答案：ES 集群由多个节点组成，节点角色包括 Master（管理集群元数据）、Data（存储数据）、Ingest（预处理文档）、Coordinating（路由请求）、Machine Learning 等。索引分为多个分片（Primary Shard）和副本分片（Replica Shard），分片分布在不同的 Data 节点上。Master 节点通过 Zen Discovery 或选主算法选举产生，保证集群一致性。
    - 解析：ES 7.x 后推荐节点角色分离，Dedicated Master 节点不存数据，负责集群状态管理，建议 3 个奇数节点。Data 节点是集群的容量和性能核心，按冷热分层部署：Hot 节点 SSD 存储近期数据，Warm 节点 HDD 存储历史数据，Cold 节点只读归档。分片数量在索引创建时确定，调整需要重建索引。副本分片提供高可用和读扩展。ES 的选主算法基于 Bully 算法的变体，候选节点按照集群状态版本号投票，新版本优先。脑裂问题通过 minimum_master_nodes 避免，7.x 后默认配置为 (master 候选节点数/2)+1。

18. **性能优化**
    - 问题：如何优化 Elasticsearch 的查询性能？
    - 答案：ES 查询性能优化包括：合理设计分片大小（每分片 20-50GB）、使用过滤器（Filter）代替 Query 减少评分计算、利用 routing 机制避免广播查询、使用字段数据（Doc Values）代替 Fielddata、开启索引排序（Index Sorting）优化范围查询、使用 search_after 代替深度分页、避免过度使用通配符和正则查询、定期 force_merge 合并段。
    - 解析：分片过多会导致小文件过多和 GC 压力增大，分片过少则影响并行度。Filter 查询不计算相关性评分且结果可缓存，性能优于 Query。Routing 使查询路由到指定分片而非广播到所有分片，对于按用户 ID 查询的场景效果显著。Doc Values 是列式存储，优化排序和聚合性能，默认开启。Index Sorting 在索引时按指定字段排序，可大幅提升范围查询和排序性能。搜索时面对深度分页（from+size 超过 10000），建议使用 search_after 配合 PIT 实现无偏移分页。Segment 合并可减少查询时需要扫描的段数量，建议在低峰期执行 force_merge。

#### RocketMQ 进阶
19. **消息可靠性**
    - 问题：如何保证 RocketMQ 消息的可靠性？
    - 答案：RocketMQ 从四个层面保证消息可靠性：生产端通过同步发送（同步阻塞等待 Broker 确认）或事务消息确保消息不丢失；Broker 端使用同步刷盘（FlushDiskType=SYNC_FLUSH）和同步主从复制确保消息持久化；消费端通过消费确认机制（ConsumeStatus 返回 SUCCESS）和重试机制确保至少消费一次；消息轨迹追踪用于定位丢失问题。
    - 解析：生产端同步发送返回 SendStatus.SEND_OK 才表示消息发送成功，失败时需重试或记录到本地表。事务消息保证本地事务和消息发送的原子性，半消息对消费者不可见，本地事务执行成功后提交，Broker 回查机制兜底。Broker 端同步刷盘性能较差但安全性最高，生产环境通常选择异步刷盘+同步复制，兼顾性能和安全。消费端消息确认是自动或手动 ACK，手动 ACK 更可控，业务处理完再提交位点。消费失败后消息进入重试队列，重试 16 次（间隔递增）后进入死信队列。死信队列需人工处理或配置死信转发策略。

20. **消息堆积处理**
    - 问题：RocketMQ 消息堆积了怎么办？有哪些解决方案？
    - 答案：RocketMQ 消息堆积的解决方案包括：水平扩展消费者实例（增加 Consumer 数量，不超过 Queue 数）、增加 Topic 的 Queue 数量（需重置消费位点）、优化消费逻辑（批量处理、异步化）、使用线程池提升消费并行度、启用消息轨迹定位堆积原因。对于瞬时堆积，可临时拉取消息到本地文件处理，或使用 SLOW 降级策略。
    - 解析：消息堆积的根本原因是生产速度大于消费速度。RocketMQ 的消费能力由 Queue 数决定，一个 Queue 最多被一个消费者实例消费，因此增加消费者实例的前提是 Queue 数足够。消费端优化是最直接的方案：批量消费（Consumer 设置 consumeMessageBatchMaxSize）减少网络开销；异步处理将消息先写入本地队列或内存，后台线程批量提交；业务逻辑优化，如减少 DB 操作、使用缓存。对于持久化堆积，可创建临时 Topic 分流消息，或使用 RocketMQ 的 retry 机制控制消费速度。Broker 端监控堆积量（Broker 的积压指标），设定告警阈值，实现自动弹性伸缩。

### Level 3: 高级题

#### Redis 高级
21. **缓存设计模式**
    - 问题：有哪些经典的缓存设计模式？各自的特点是什么？
    - 答案：经典缓存设计模式包括：Cache-Aside（旁路缓存，应用同时维护缓存和数据库，先读缓存后读库，更新时先更新库再删除缓存）、Read-Through（缓存层负责读库，应用只与缓存交互）、Write-Through（缓存层负责写库，先写缓存再写库）、Write-Behind（异步写库，先写缓存立即返回，后台批量写库）。还有单飞模式（Singleflight）防止缓存击穿。
    - 解析：Cache-Aside 是最常用的模式，读时缓存未命中则从 DB 加载并设置缓存，写时先更新 DB 再删除缓存。注意删除缓存而非更新缓存，避免并发写导致数据不一致。Read-Through 和 Write-Through 将缓存与 DB 的操作封装在缓存中间件中，简化应用代码，适合一致性要求较高的场景。Write-Behind 通过合并写操作提升吞吐量，但存在数据丢失风险。单飞模式适用于热点 key 重建，同一时刻只有一个请求去加载数据，其他请求等待结果，可通过 Redis 的 SET NX 或 Go 的 singleflight 包实现。实际应用中常组合使用多种模式，如 Cache-Aside + 单飞 + 布隆过滤器。

22. **内存优化**
    - 问题：如何优化 Redis 的内存使用？
    - 答案：Redis 内存优化方法包括：使用合适的数据类型（如 ziplist 编码的 Hash/List/ZSet 在数据量小时更省内存）、设置过期时间（TTL）及时清理无用数据、使用 Redis 5.0 的 Stream 代替 List 做消息队列、启用内存淘汰策略（LRU/LFU/volatile-ttl）、使用压缩（Redis 6.2 的 RESOURCE 模块）、对大 key 进行拆分、使用 Redis 的 RDB 持久化降低内存碎片。
    - 解析：Redis 对不同数据类型有多个编码方式。Hash 在 field 数小于 512 且 value 长度小于 64 字节时用 ziplist 编码，可节省 60% 以上内存。ZSet 的 ziplist 编码同样省内存。内存淘汰策略根据业务选择：allkeys-lru 适合缓存场景，淘汰最近最少使用的 key；volatile-ttl 淘汰即将过期的 key。内存碎片由 jemalloc 分配策略和频繁的 key 增删引起，可通过 info memory 查看 mem_fragmentation_ratio，大于 1.5 时考虑重启或使用 ACTIVEDEFRAG 在线整理。大 key（超过 10MB）不仅占用内存，还会阻塞网络 IO，应通过拆分或压缩处理。使用 Redis 的 bigkeys 命令扫描大 key。

#### MySQL 高级
23. **性能调优**
    - 问题：如何进行 MySQL 性能调优？有哪些关键指标？
    - 答案：MySQL 性能调优从四个维度入手：SQL 层面（慢查询日志、EXPLAIN 分析、索引优化）、参数层面（innodb_buffer_pool_size 设为可用内存的 70%-80%、innodb_log_file_size 设为 1-4GB、max_connections 合理设置）、架构层面（读写分离、分库分表、缓存层）、硬件层面（SSD 磁盘、内存扩容、CPU 升级）。关键指标包括 QPS/TPS、慢查询数、InnoDB 行锁等待、连接数、IO 延迟和 Buffer Pool 命中率。
    - 解析：Buffer Pool 命中率是关键指标，低于 95% 说明内存不足或存在大量全表扫描，通过 show engine innodb status 查看。慢查询日志分析是定位问题的第一步，pt-query-digest 工具可自动分析慢查询并给出建议。参数调优中，innodb_flush_log_at_trx_commit 设为 1 保证数据安全，设为 2 提升性能（适合允许丢失 1 秒数据的场景）。InnoDB 的日志文件大小对写入性能影响大，太小会导致频繁的日志切换和 checkpoint 刷盘。线程池（thread_pool）在短连接场景下提升并发。连接数不是越高越好，每个连接消耗内存，建议使用连接池控制。定期使用 OPTIMIZE TABLE 回收碎片空间。

24. **高可用架构**
    - 问题：如何设计 MySQL 的高可用架构？
    - 答案：MySQL 高可用架构方案包括：主从复制（异步/半同步复制，实现读写分离）、MHA（Master High Availability，自动故障切换）、InnoDB Cluster（Group Replication，官方高可用方案）、Orchestrator（自动故障检测和恢复）、MySQL Proxy（中间件层路由）。核心是保证主库故障时秒级切换，数据零丢失或接近零丢失。
    - 解析：主从复制的瓶颈在于异步复制可能丢数据，半同步复制（semisync）保证至少一个从库收到 binlog 后才返回成功，但会增加延迟。MHA 是经典方案，监控主库健康，故障时选择数据最新从库提升为主，并通知其他从库重新指向新主，切换时间通常在 10-30 秒。InnoDB Cluster 使用 Group Replication，基于 Paxos 协议保证强一致性，官方支持但配置复杂。Orchestrator 提供更友好的管理和故障恢复能力，支持跨机房部署。高可用方案还需配合：健康检查（3 次失败后切换）、VIP 漂移或 DNS 更新、自动恢复脚本、数据一致性校验（pt-table-checksum）。异地多活方案需考虑延迟和冲突处理，通常采用单元化架构。

#### Elasticsearch 高级
25. **数据建模**
    - 问题：Elasticsearch 的数据建模有哪些最佳实践？
    - 答案：ES 数据建模最佳实践包括：避免大宽表，使用扁平化而非关联（ES 不擅长 JOIN）；合理选择字段类型（keyword 用于精确匹配、text 用于全文搜索、integer/long 用于范围查询）；控制 mapping 字段数量（避免超过 1000 个字段）；使用 nested 类型处理数组对象的独立查询；使用 parent-child（join 类型）谨慎处理关联；为时间序列数据设计滚动索引（Rollover Index）；使用 alias 简化索引切换。
    - 解析：ES 的 JOIN 操作（nested 和 parent-child）性能较差，建议在应用层做数据关联。nested 类型将数组对象单独存储为独立文档，查询时保证内部对象字段的关联性，但查询性能比普通字段差 5-10 倍。对于日志和时间序列数据，使用 ILM（Index Lifecycle Management）自动管理索引生命周期：hot 阶段写入，warm 阶段只读，cold 阶段压缩，delete 阶段删除。字段数过多会增大 mapping 开销，禁用 dynamic mapping 的 dynamic: false 或 dynamic: strict。使用 doc_values 控制聚合和排序的性能，关闭不需要的 doc_values 和 norms 可节省存储空间。对于超长文本，使用 ignore_above 截断 keyword 字段。

26. **集群运维**
    - 问题：如何进行 Elasticsearch 集群的运维和监控？
    - 答案：ES 集群运维监控包括：健康状态（Green/Yellow/Red）、节点指标（JVM 堆内存使用率、GC 频率和耗时、磁盘使用率、CPU 和 Load）、集群指标（未分配分片数、Pending 任务数、搜索和索引吞吐量及延迟）。常用工具：Elasticsearch Monitoring（X-Pack）、Cerebro（集群管理）、Elastic HQ。关键操作：滚动重启、分片分配策略、慢查询日志（Search Slow Log/Index Slow Log）。
    - 解析：JVM 堆内存是 ES 运维的核心指标，堆内存使用率超过 75% 需关注，超过 85% 可能触发并发 GC 导致 JVM 暂停。GC 方面，Young GC 频繁（每秒超过 1 次）或 Full GC 超过 1 秒需排查。磁盘使用率超过 85% 需处理，超过 90% 触发分配器限制，超过 95% 进入只读模式。集群 Yellow 状态表示有未分配副本，Red 状态表示主分片丢失。滚动重启是零停机升级的关键操作：先停用分片分配（cluster.routing.allocation.enable=none），逐节点重启，再恢复分配。分片分配策略可设置基于磁盘水位线的自动均衡。慢查询日志配置慢于 1 秒的搜索和 500ms 的索引请求记录，结合 Kibana 分析。

#### RocketMQ 高级
27. **消息架构设计**
    - 问题：如何设计 RocketMQ 的消息架构？有哪些注意事项？
    - 答案：RocketMQ 消息架构设计需考虑：Topic 划分原则（按业务领域而非技术维度拆分，一个 Topic 对应一个业务场景）、Queue 数规划（根据消费并行度和吞吐量需求，通常 8-16 个 Queue）、消息体设计（轻量化，仅包含业务关键字段，大对象通过引用存储）、消费幂等设计（业务表唯一索引或分布式 ID 去重）、消息优先级（不同 Topic 实现不同优先级）。架构上需考虑 Producer 和 Consumer 的容错和重试策略。
    - 解析：Topic 不宜过多，过多 Topic 导致 Broker 上产生大量文件，增加磁盘寻道开销，建议单个集群 Topic 数控制在 1000 以内。Queue 数决定消费并行度，设置后一般不可变，需提前规划。消息体应控制在 1MB 以内，超过 4MB 的消息会被 Broker 拒绝，大消息可通过 OSS 存储引用。消费幂等是消息架构的核心难点，RocketMQ 的 At Least Once 语义要求消费端自行去重，常见方案：数据库唯一约束、Redis 分布式锁+业务主键、本地消息表状态机。消息顺序性要求严格的场景需将相关消息路由到同一个 Queue，且使用单线程消费。事务消息的二阶段提交和回查机制给接口设计带来复杂度，需合理设置回查间隔和最大回查次数。

28. **消息治理**
    - 问题：如何进行 RocketMQ 的消息治理？
    - 答案：RocketMQ 消息治理包括：消息轨迹（TraceTopic 记录消息全生命周期）、消息查询（按 Key 和时间范围查询消息）、消息回溯（重置消费位点）、死信队列处理（DLQ 消息告警和自动重投）、消息 TTL（过期消息清理）、消费组管理（消费进度监控、消费延迟告警）、流量控制（Broker 流控、客户端限流）。治理工具包括 RocketMQ Dashboard 和 Admin CLI。
    - 解析：消息轨迹通过开启 trace 采集，记录消息从生产到消费的完整路径，包括发送时间、Broker 地址、消费状态、重试次数等，对排查消息丢失和延迟问题至关重要。消息回溯是治理的重要手段，当消费逻辑出现 bug 时，可重置消费位点到指定时间点重新消费，但需注意消息积压可能触发下游系统压力。死信队列是消息治理的兜底机制，重试 16 次仍失败的消息进入 %DLQ% 开头的死信队列，需配置告警通知，人工处理后重新投递。消费延迟监控是日常运维的核心，使用 RocketMQ Dashboard 的 Consumer 页面查看消费延迟量，设置延迟超过 1000 条的告警。Broker 流控在页缓存写满或磁盘使用率过高时触发，可通过调整 TransientStorePool 和磁盘预留空间缓解。

### Level 4: 专家题

#### 中间件架构
29. **中间件选型**
    - 问题：如何进行中间件选型？有哪些评估标准？
    - 答案：中间件选型的评估标准包括：功能匹配度（是否满足核心业务需求）、性能指标（吞吐量、延迟、并发能力）、高可用特性（集群部署、故障切换、数据一致性保障）、社区活跃度（GitHub Star 数、Issue 响应速度、版本更新频率）、运维复杂度（部署难度、监控体系、调优成本）、团队技术储备（学习曲线、人才市场）、以及商业支持（付费版 SLA 和生态兼容性）。
    - 解析：选型是技术决策也是风险决策，需平衡短期需求和长期演进。功能匹配度是第一优先级，例如消息队列选择：Kafka 适合日志采集和流处理，吞吐量最高但功能较简单；RocketMQ 适合金融级可靠消息，功能丰富但兼容性不如 Kafka；RabbitMQ 适合低延迟路由，但吞吐量有限。性能测试应在真实业务场景下进行，关注 P99 延迟而非平均延迟。高可用方面需评估 RPO（恢复点目标）和 RTO（恢复时间目标）。社区活跃度影响问题解决速度和生态发展，Apache 基金会项目通常更成熟。运维复杂度常被低估，如 Redis Cluster 的运维成本远高于单机 Redis Sentinel。建议在选型后做 POC（概念验证），验证关键场景并评估团队上手成本。

30. **中间件集成**
    - 问题：如何设计中间件的集成架构？有哪些最佳实践？
    - 答案：中间件集成架构设计最佳实践包括：统一抽象层（封装中间件 API，业务代码不直接依赖具体实现）、配置中心管理（Nacos/Apollo 管理连接池、超时、重试等配置）、连接池统一管理（HikariCP 连接池参数调优）、健康检查和优雅上下线（K8s Readiness/Liveness 探针配合中间件心跳）、链路追踪集成（SkyWalking 或 Zipkin 追踪全链路调用）、熔断降级（Sentinel 保护中间件调用）。
    - 解析：统一抽象层是中间件集成的核心原则，以缓存为例：定义 Cache 接口，分别实现 RedisCache、LocalCache、多级缓存，业务代码注入接口即可，切换缓存实现无需改动业务逻辑。配置中心使中间件参数可动态调整，如 Redis 连接池大小可在流量高峰前动态扩容。连接池参数中，最小空闲连接数（minimumIdle）和最大连接数（maximumPoolSize）需根据并发量计算，超时时间（connectionTimeout）不宜过长。健康检查应检测中间件的真实可用性，如 Redis 的 PING、MySQL 的 SELECT 1、ES 的 /_cluster/health。优雅上下线保证服务重启时先摘除流量再关闭连接池，避免请求中断。链路追踪记录每条中间件调用的耗时和状态，是排查性能瓶颈的利器。

#### 性能优化
31. **性能瓶颈分析**
    - 问题：如何分析和解决中间件的性能瓶颈？
    - 答案：分析中间件性能瓶颈遵循"观测-定位-优化"三步法：观测阶段监控系统指标（CPU、内存、IO、网络）和中间件指标（QPS、延迟、连接数、GC）；定位阶段使用火焰图、Arthas、Profiling 工具定位热点；优化阶段针对瓶颈点实施优化，如 Redis 增大连接池、MySQL 加索引、ES 调整分片数、RocketMQ 增加 Queue。持续压测验证优化效果。
    - 解析：性能瓶颈分析需体系化方法。CPU 瓶颈看 user/sys 比例，user 高说明业务计算密集，sys 高说明系统调用频繁（如锁竞争）。内存瓶颈关注堆使用率和 GC 频率，GC 频繁导致 STW（Stop-The-World）影响延迟。IO 瓶颈分磁盘 IO（慢查询和大量写入）和网络 IO（带宽限制和大量小包）。不同中间件的典型瓶颈不同：Redis 是网络 IO 和内存，MySQL 是磁盘 IO 和锁，ES 是 CPU（查询和索引）和磁盘，RocketMQ 是磁盘 IO（刷盘）和内存（页缓存）。压测是发现瓶颈的核心手段，使用 JMeter 或 Locust 模拟真实流量，逐步增加并发直到系统达到性能拐点。优化后需再次压测验证，避免负优化。

32. **容量规划**
    - 问题：如何进行中间件的容量规划？
    - 答案：中间件容量规划步骤包括：业务流量预测（基于历史数据和业务增长预估未来 QPS 和峰值）、性能基线测试（通过压测确定单机吞吐量和延迟拐点）、资源换算（根据预估流量计算所需节点数和规格）、冗余设计（预留 30%-50% 余量应对突发流量和故障）、弹性伸缩（K8s HPA 配合中间件 Metrics 实现自动扩缩容）。定期复核容量规划，根据实际数据修正模型。
    - 解析：容量规划是保障系统稳定性和成本控制的关键。业务流量预测需考虑日常流量、促销峰值（如双 11 的 10 倍流量）、灰度发布和新功能上线带来的流量增长。性能基线是通过压测获取的，例如单机 Redis 可承载 10 万 QPS 读操作，MySQL 单表可支撑 5000 QPS 写入。资源换算举例：若预估 QPS 为 20 万读 + 2 万写，Redis 集群需 3 个节点（20 万/10 万 × 1.5 余量），MySQL 读写分离需 1 主 2 从。冗余设计中，网络带宽常被忽略，需计算每个请求的响应体大小乘以 QPS 得到带宽需求。Kubernetes 环境中，HPA 基于 CPU/内存或自定义 Metrics（如 Redis 连接数、Kafka 消费延迟）实现自动扩缩。定期容量复核建议每季度一次，对比实际流量和规划值，及时调整。
