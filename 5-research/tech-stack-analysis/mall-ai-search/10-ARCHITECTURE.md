### 1.2 全链路延迟分解

> 以下为估算值，实际取决于网络、模型、数据量。仅供理解"延迟分布"。

```
链路阶段              延迟 (估算)   占比    说明
────────────────────────────────────────────────────
前端网络传输            20ms        8%     HTTP 请求/响应序列化
FastAPI 路由分发         5ms        2%     APIRouter + Pydantic 校验
/extract LLM 调用     600ms       24%     阿里云通义千问一次推理
/recommend LLM 调用   600ms       24%     Agent 执行 + 推理
向量检索 (Embedding)   200ms        8%     查询 Embedding + Redis HNSW
向量检索 (Redis)        10ms        <1%     HNSW 近邻搜索
LLM 结构化输出生成      800ms       32%     response_format 强制输出
前端渲染                20ms        8%     Vue3 响应式更新
────────────────────────────────────────────────────
总计                   ~2.2s      100%
```

**关键认知：** 延迟大头在 LLM 推理（~2s），向量检索本身仅 ~10ms。**AI 搜索的瓶颈不是检索，而是生成。**

## 三、核心架构决策复盘

### 决策 1: Python + FastAPI 而不是 Java Spring Boot

| 考量 | 结论 |
|------|------|
| AI 生态成熟度 | Python 完胜，LangChain/LangGraph 等 AI 框架仅有 Python 完整版 |
| 团队技术栈 | 如果团队 Java 为主，可以用 Spring AI 但生态远不如 Python |
| 性能 | 两者差距不大，瓶颈在 LLM 推理而非框架本身 |
| 正确性 | ✓ 选择 Python，因为 AI 应用的核心价值在模型集成而非框架性能 |

**面试话术：** "AI 应用的瓶颈在 LLM 推理延迟和模型能力，不在框架性能。Python 拥有最完善的 AI 生态，LangChain/LangGraph 等框架仅在 Python 中完整可用。技术选型要服务于业务价值，而非技术偏好。"

### 决策 2: Redis 做向量库而不是 Milvus/Pinecone

| 考量 | 结论 |
|------|------|
| 复用现有基础设施 | 已有 Redis，学习成本零 |
| 数据规模 | 当前量级 < 100 万 SKU，Redis 足够 |
| 功能完备性 | 支持 HNSW 索引、ANN 搜索、文档过滤 |
| 运维复杂度 | 单实例，零额外运维负担 |
| 正确性 | ✓ 适合当前阶段，但需要预留迁移路径 |

**面试话术：** "选择 Redis 做向量库是业务规模驱动的决策。当前数据量下 Redis 完全够用，且复用现有基础设施降低运维成本。但我们也预留了迁移路径——LangChain 的 VectorStore 抽象让切换向量库只需改一行代码。如果数据量增长到百万级以上，可以平滑迁移到 Milvus。"

### 决策 3: Agent 而不是 Chain 做推荐

| 考量 | 结论 |
|------|------|
| 需要外部信息获取 | Agent 可通过 tool 调用向量库 |
| 需要循环决策 | Agent 可自主判断"是否需要检索→检索到什么→是否足够回答" |
| 需要结构化输出 | Agent 的 response_format 强制最严格的结构化 |
| 正确性 | ✓ 推荐场景复杂度需要 Agent，提取场景简单用 Chain 即可 |

**面试话术：** "Agent 和 Chain 不是二选一，而是按需使用。提取场景（原文→结构化）是线性映射，Chain 够用。推荐场景需要'检索→判断→生成'的循环，Agent 更适合。好的架构是在正确的地方引入正确的复杂度。"

### 决策 4: InMemorySaver 而不是 RedisSaver

| 考量 | 结论 |
|------|------|
| 项目阶段 | 开发/演示阶段，不需要持久化 |
| 电商搜索场景 | 用户通常不会连续搜索，记忆非核心需求 |
| 正确性 | ✓ 当前合理，但生产环境需切换为 RedisSaver |

**面试话术：** "当前阶段用 InMemorySaver 是合理的权衡——简化部署、快速迭代。但我也清楚它的局限性，代码中预留了 langgraph-checkpoint-redis 依赖，生产环境切换到 RedisSaver 只需改一行代码。"

## 五、面试题集

### 5.1 项目架构类

**Q1: 讲一下你这个 AI 搜索项目的整体架构。**

> **回答思路（2 分钟版）：** 这是一个电商智能搜索系统，分四层：前端 Vue3 双模式搜索 → FastAPI 网关 → LangChain Agent 决策层 → Redis 向量检索层。用户输入自然语言后，前端并行调用两个接口：`/extract` 用 LLM 提取结构化搜索条件，`/recommend` 用 Agent 调用向量检索工具召回 TOP-10 商品，再由 LLM 生成推荐理由。数据通过离线同步链路从 MySQL 流式读取、切片、Embedding 后写入 Redis 向量库。
>
> **加分项：** 画图说明（架构图）、每个层次的关键决策、技术选型理由。

**Q2: 这个项目最大的技术挑战是什么？**

> **回答思路：** 三个挑战：1) **多供应商统一接入**——不同 LLM 供应商有自己的 base_url、model、参数，项目通过策略模式 + 工厂方法 + OpenAI 兼容协议统一了接入；2) **Agent 结构化输出**——LLM 自由输出容易偏离 JSON 格式，通过 create_agent 的 response_format 强制结构化输出，零解析烦恼；3) **数据一致性**——MySQL 更新后 Redis 向量索引可能过时，通过幂等 ID + 批量同步保证最终一致性。

**Q3: 为什么这个项目用 Python 而不是 Java？**

> **回答思路：** 核心原因：AI 生态。LangChain、LangGraph、LangChain-Core 等 AI 框架仅在 Python 中有完整实现。Spring AI 虽然也在发展，但生态成熟度远不如 Python。AI 应用的瓶颈在模型能力和推理延迟，不在框架性能。Python 的 FastAPI 也能提供足够的性能。

### 5.2 LLM/Agent 类

**Q4: LangChain Agent 的 create_agent 底层是怎么工作的？**

> **回答思路：** 底层是 LangGraph 驱动的有状态图执行。`create_agent(model, tools, response_format)` 做了四件事：1) 将 tools 绑定到 model（bind_tools）；2) 构建 Agent 状态图（StateGraph），包含 Agent 节点和 Tool 节点；3) 添加条件边——Agent 判断是否需要调用工具，需要则进入 Tool 节点，不需要则直接输出；4) response_format 通过 tool_strategy 将 Pydantic 模型注册为强制工具调用，保证输出严格符合 schema。

**Q5: 你是怎么防止 LLM 编造不存在的商品的？**

> **回答思路：** 四层防护：1) **Prompt 层**——系统提示词明确"严禁编造不存在的商品信息"+"仅使用上下文存在的数据"；2) **上下文约束**——只把向量库召回的 TOP-10 商品作为上下文传入，LLM 没有编造的数据基础；3) **低温度**——temperature=0.1，减少随机创作空间；4) **结构约束**——response_format 强制字段结构，空数据时要设置兜底值（summary="暂无相关信息"，product_list=[]）。

**Q6: 什么是 Agent 的 Tool 调用？工具定义质量如何影响效果？**

> **回答思路：** Tool 是 Agent 获取外部信息的手段。`@tool` 装饰器将函数转为 Tool 对象，自动提取 name、description、args_schema。LLM 通过 description 判断"要不要调用这个工具"，通过 args_schema 知道"怎么调用"。工具定义质量直接影响 Agent 执行效果——name 要清晰，description 要准确描述场景，args 要简化。一个差定义的 tool 会导致 LLM 调错工具或填错参数。

**Q7: 为什么 /extract 用 Chain 而 /recommend 用 Agent？**

> **回答思路：** 复杂度匹配原则。提取是"一篇文章→结构化字段"的线性映射，Chain 足够。推荐需要"检索→判断→生成"的循环，Agent 更适合。如果提取也用 Agent，增加了不必要的复杂度和延迟。好的架构是在正确的地方引入正确的复杂度。

### 5.3 向量检索类

**Q8: 向量检索和传统 ES 关键词搜索的区别？**

> **回答思路：** 本质区别：ES 匹配"字面"，向量匹配"意思"。ES 基于倒排索引做关键词精确匹配，用户搜"手机"能匹配到"手机"但匹配不到"移动设备"；向量检索将文本转为高维向量，语义相似的文本在向量空间中距离近，用户搜"续航强的手机"能匹配到"5000mAh大电池的产品"。实际项目中两者互补——ES 做精确匹配和属性过滤，向量做语义召回，最后通过 RRF 融合排序。

**Q9: HNSW 索引的原理是什么？为什么比暴力搜索快？**

> **回答思路：** HNSW（分层可导航小世界图）构建多层图结构，高层节点稀疏（长距离跳跃），低层节点稠密（精确细分）。搜索时从高层随机入口，贪心搜索到局部最近邻，然后下降到下一层继续搜索，逐步逼近全局最近邻。时间复杂度 O(log n) vs O(n) 暴力搜索。召回率约 95%，是速度与精度的权衡。

**Q10: 为什么选择 BGE-M3 作为 Embedding 模型？**

> **回答思路：** 电商场景的多维度需求：1) **中文为主**——BGE 系列中文 SOTA；2) **中英混合**——商品名含英文，BGE-M3 支持 100+ 语言；3) **长文本**——商品属性描述长，BGE-M3 支持 8192 token；4) **成本可控**——1024 维向量，质量和存储平衡；5) **开源可自部署**——降低对外部 API 的依赖。

### 5.4 数据工程类

**Q11: 数据同步链路中，为什么用 tiktoken 计算 token 长度而不是字符数？**

> **回答思路：** 中英文 token 密度差异大。中文 1 个 token 约 1.5 字符，英文 1 个 token 约 4 字符。用字符数切片会导致中文 chunk 语义密度远高于英文 chunk。tiktoken 使用 OpenAI 的 `cl100k_base` 编码，精确计算每个文本的 token 数，保证每个 chunk 的语义密度一致。

**Q12: 幂等 ID 怎么设计的？解决了什么问题？**

> **回答思路：** `md5(sku_id + chunk_content)` 生成唯一 ID。解决了重复同步产生重复文档的问题。同一商品同一切片内容，多次同步产生相同 ID，Redis 内部覆盖写入而非新增。产品更新后只有变更的切片会生成新 ID，未变更的切片保持不变。

**Q13: 如果 MySQL 有百万级 SKU，同步方案怎么优化？**

> **回答思路：** 三个优化方向：1) **增量同步**——基于 `updated_at` 时间戳只同步变更数据，减少全量同步频率；2) **CDC 实时同步**——Canal 监听 MySQL binlog，实时捕获变更事件，单条 Embedding 后写入 Redis；3) **并发加速**——用 asyncio + 信号量控制 Embedding 并发度，避免 API 限速。百万级数据全量同步可接受，但增量同步才能保证实时性。

### 5.5 配置与架构类

**Q14: 多 Provider 配置架构是怎么设计的？** 

> **回答思路：** 策略模式 + 工厂模式 + 环境变量驱动。定义 `EMBED_PROVIDER` 和 `LLM_PROVIDER` 两个枚举开关，通过 `active_embedding_config` / `active_llm_config` 两个属性动态选择当前激活的配置。业务代码只面向"当前激活的配置"编程，切换供应商只需改 `.env` 文件中的一行配置。API Key 采用三层回填：.env 占位符 → 系统环境变量 → 代码默认值，保证安全不泄漏。

**Q15: 如果要在 Spring Boot 里实现这个项目，你会怎么做？**

> **回答思路：** 用 Spring AI 的 ChatClient 代替 LangChain、对应 EmbeddingClient 代替 OpenAIEmbeddings、JdbcTemplate 流式读取代替 SQLAlchemy lazy_load。但 Agent 部分（create_agent + Tool + Checkpointer）在 Java 生态中不如 Python 成熟，可以用 LangChain4j 或手动实现 ReAct 循环。向量库部分用 Spring Data Redis + FT.SEARCH 命令。整体架构模式不变，只是实现语言不同。

### 5.6 业务场景类

**Q16: 这个 AI 搜索和传统搜索比，用户体验上有什么提升？**

> **回答思路：** 三个核心提升：1) **语义理解**——用户可以用自然语言描述需求，如"5000元以下续航强的华为手机"，系统自动理解"续航强=电池容量大"；2) **智能推荐**——基于语义相似度召回商品，不局限于关键词匹配，能发现传统搜索"搜不到"的商品；3) **推荐理由**——LLM 生成的可读性推荐理由，帮助用户理解"为什么推荐这个商品"。

**Q17: 如果用户搜索"电视"，系统应该推荐什么？**

> **回答思路：** 向量检索会召回语义相似的商品——"电视"的向量可能接近"显示器"、"投影仪"、"智能屏"等。但这不是问题，因为 LLM 会基于召回结果重新排序和过滤，只推荐实际是"电视"的商品。如果召回结果中没有电视，LLM 的兜底策略是返回"暂无相关信息"。

**Q18: 如何评估这个 AI 搜索的效果？**

> **回答思路：** 三个维度：1) **检索质量**——Recall@K、Precision@K、MRR（Mean Reciprocal Rank），评估向量召回的相关性；2) **推荐质量**——用户点击率、推荐转化率、A/B 测试对比不同模型/供应商；3) **系统性能**——P50/P95/P99 延迟、QPS、错误率。
