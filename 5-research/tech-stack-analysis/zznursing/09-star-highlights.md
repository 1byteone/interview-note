## 亮点一：百度千帆 AI 大模型与养老场景深度融合

### S（情境）

养老机构中，家属对老人的健康状况高度关注，但护工人数有限，无法及时回答每个家属的健康咨询。传统方案是建 FAQ 知识库，但问题千变万化，维护成本极高。产品侧希望引入 AI 能力，让家属通过小程序直接咨询健康问题，系统结合老人实时数据生成个性化建议。

### T（任务）

设计并实现 AI 智能问答系统，要求：
- 家属在小程序输入问题，AI 结合老人健康数据做出个性化回答
- 回复需要在 3 秒内开始展示，支持流式逐字输出
- 控制 API 调用成本，日均 5000 次调用，月成本不超过 1000 元
- 确保医疗建议的安全性和合规性

### A（行动）

1. **模型选型与分级**：选择百度千帆文心一言 4.0 作为主模型（中文理解强），简单问答降级到 3.5（成本更低），通过问题复杂度分类器自动路由
2. **Prompt 工程**：设计系统 Prompt 定义 AI 角色为"健康顾问"，限制回答范围在健康建议内，涉及用药时强制加入"请遵医嘱"免责声明
3. **流式输出架构**：千帆 SSE → Spring WebFlux Flux → WebSocket → 微信小程序，实现 1 秒内开始展示回复
4. **上下文管理**：Redis 缓存最近 10 轮对话，控制 Prompt 长度，降低 Token 消耗
5. **数据增强**：AI 回答前自动拼接老人最近 7 天的健康数据摘要，让回复个性化

### R（结果）

- 家属满意度提升 40%，健康咨询响应时间从平均 2 小时（人工回复）缩短到 3 秒
- 日均调用 4500 次，月成本约 800 元，符合预算
- 护工从重复性咨询中解放出来，专注于护理工作
- 流式输出体验良好，用户留存率提升 25%

## 亮点二：华为 IoTDA 平台大规模设备接入与数据治理

### S（情境）

养老院有 300 多位老人，每人佩戴心率手环、跌倒检测器、定位胸牌等多台设备，总计约 1000 台 IoT 设备。这些设备每 5 秒上报一次数据，每天产生约 1728 万条数据。原来使用自建 MQTT 服务器，但设备管理、OTA 升级、安全认证等功能缺失，运维成本高。

### T（任务）

重构设备接入层，要求：
- 支持 1000+ 设备并发接入，峰值 200 次/秒数据上报
- 设备数据零丢失，端到端延迟 < 5 秒
- 支持远程 OTA 升级、设备状态监控、故障诊断
- 统一管理多种设备类型（心率手环、跌倒检测器、定位胸牌等）

### A（行动）

1. **平台选型**：评估自建 vs 华为 IoTDA，选择 IoTDA 平台，利用其设备影子、数据转发规则、OTA 开箱即用能力
2. **架构设计**：IoTDA 数据转发 → HTTP 回调 → Controller → RocketMQ → 批量写入 MySQL，实现三层削峰
3. **设备影子**：利用 IoTDA 设备影子模式，应用层与设备解耦，设备离线时配置仍可下发
4. **消息队列**：引入 RocketMQ 削峰填谷，消费端批量写入，每 100 条或 1 秒 flush 一次
5. **分层存储**：Redis 热数据（1 小时）→ MySQL 当月表（30 天）→ 历史聚合表（90 天），兼顾性能与成本
6. **监控告警**：设备离线 5 分钟自动告警，心率异常实时推送，跌倒检测秒级响应

### R（结果）

- 单日处理 1500 万+ 条设备数据，系统稳定运行，无数据丢失
- 设备管理效率提升 60%，OTA 升级从 1 天缩短到 30 分钟
- 告警延迟控制在 3 秒内，跌倒检测推送成功率 99.9%
- 存储成本降低 40%（分层存储 + 数据聚合）

## 亮点三：微信小程序 + Spring Boot 全栈架构设计与性能优化

### S（情境）

产品需要同时服务两类用户：老人家属（关注健康监测、告警通知）和养老机构运营人员（关注设备管理、数据分析）。家属端使用微信小程序，运营端使用 Vue3 管理后台。两类用户共用一套后端服务，但接口能力和数据权限不同。

### T（任务）

设计双端统一的后端架构，要求：
- 家属端小程序和管理后台共用一套后端 API
- 接口级别权限控制，家属只能查看绑定老人的数据
- 小程序首屏加载 < 2 秒，AI 问答流式展示
- 支持微信订阅消息推送告警通知

### A（行动）

1. **统一 API 网关**：Spring Cloud Gateway 统一入口，根据请求来源（小程序/管理后台）路由到不同服务
2. **双端鉴权**：小程序使用微信登录 Token 鉴权，管理后台使用 JWT 鉴权，拦截器统一处理
3. **接口粒度控制**：家属端接口按"老人维"授权，管理后台接口按"角色维"（RBAC）授权
4. **小程序性能优化**：
   - 分包加载：主包仅包含首页和核心页面，AI 问答等放在分包
   - 数据预加载：页面跳转前预拉取数据
   - setData 合并：减少频繁更新，只更新变化的数据路径
   - 图片优化：WebP 格式 + CDN 加速 + 懒加载
5. **WebSocket 流式推送**：AI 问答使用 WebSocket 长连接接收流式回复，实现打字机效果
6. **消息推送**：使用微信订阅消息推送告警通知，跌倒检测、心率异常立即推送

### R（结果）

- 小程序首屏加载时间 1.5 秒，符合性能目标
- 双端共用一套后端 API，代码复用率 70%，开发效率提升 30%
- 告警推送成功率 99.5%，家属满意度提升 35%
- 系统上线 6 个月，服务 5 家养老机构，300+ 老人，1000+ 家属

## 亮点四：设备时序数据存储架构设计（备选亮点）

### S（情境）

1000 台设备每 5 秒上报一次数据，每天产生约 1728 万条时序数据。初期使用单表存储，3 个月后单表数据量超过 1.5 亿条，查询性能急剧下降，健康趋势图表加载需要 10 秒以上。

### T（任务）

重构数据存储方案，要求：
- 单表数据量控制在 5000 万以内
- 趋势查询响应时间 < 2 秒
- 数据保留 90 天，存储成本可控
- 支持实时数据查询（毫秒级）和历史趋势查询（秒级）

### A（行动）

1. **按月分表**：`device_data_record_yyyyMM` 按月创建新表，控制单表数据量
2. **分层存储**：Redis 热数据（1 小时）→ MySQL 当月表（30 天）→ 历史聚合表（90 天）
3. **数据聚合**：定时任务每天凌晨执行，将 30 天前的原始数据按 1 分钟粒度聚合（平均值/最大值/最小值），存储量减少 90%
4. **索引优化**：`(device_id, collect_time)` 联合索引覆盖大部分查询场景
5. **批量写入**：RocketMQ 消费端批量写入，每 100 条或 1 秒 flush 一次
6. **缓存穿透防护**：布隆过滤器 + 缓存空值

### R（结果）

- 查询性能提升 10 倍，趋势图表加载从 10 秒降到 1 秒
- 存储成本降低 60%，每天新增数据量从 2GB 降到 800MB
- 系统稳定运行 6 个月，无性能瓶颈
- 方案被其他项目复用，成为团队 IoT 数据存储的标准方案
