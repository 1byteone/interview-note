成果验收 · 时序图
成果从提交到验收闭环的详细交互序列 — 聚焦证据链与决策分支
Step 1 · 员工准备成果
员工 确认执行完成 — 日计划状态自动流转到「待提交成果」
员工 准备验收证据 — 收集代码 PR、测试报告、压测数据、截图、文档链接
📎 证据链结构（以"支付回调异常监控优化"为例）
P
计划目标：降低发现时间 + 建立可追踪告警
R
实际成果：新增 3 项指标 + P1/P2 告警 + 10 万次压测
E
验收证据：压测报告.pdf + 监控截图.png + PR #1842
A
员工自评：失败率从 0.42% 降至 0.06%，建议纳入 SLO
员工 提交成果 — 关联计划 → 上传证据 → 撰写自评 → 提交验收
系统 通知领导 — 推送待验收提醒，显示关联的计划目标
Step 2 · 领导验收
领导 查看待验收成果 — 打开验收详情页，看到完整证据链
领导 逐项核对证据 — 对照验收标准，查看 PR / 报告 / 截图 / 文档，评估交付质量
领导 做出验收决策 —
alt · 验收决策分支
验收通过
填写质量评分（1-5 星）
填写主管评语
状态：待验收 → 验收通过
成果关联的计划标记「已闭环」
系统通知员工"成果已通过"
退回补充
填写退回原因（必填）
说明需要补充什么
状态：待验收 → 退回补充
员工补充后重新提交
循环直至通过或驳回
退回驳回
填写驳回原因（必填）
说明目标未达成的具体原因
状态：待验收 → 退回驳回（终态）
员工需重新制定计划
在绩效统计中单独记录
Step 3 · 闭环
系统 更新统计指标 — 重新计算：完成率、按期交付率、返工率、验收通过率
系统 生成操作日志 — 记录：who / when / what / before / after，支撑审计和绩效
员工 查看验收结果 — 查看评分、评语、退回原因（如有），形成个人工作档案
设计要点：成果验收的核心不是"通过/不通过"的二元判断，而是证据链的核对过程。"退回补充"和"退回驳回"是两种不同的退回——前者是"证据不够"，后者是"目标未达成"，两者在绩效统计中权重不同。领导验收时看到的不是一句"已完成"，而是完整的证据链：计划目标 → 实际成果 → 证据附件 → 员工自评。这让验收从主观判断变成客观验证。
