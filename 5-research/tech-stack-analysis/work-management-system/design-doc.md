# 日/月计划与成果验收系统 · 设计文档

> **文档性质**：开卷考察交付物——聚焦系统设计思路，不涉及代码实现。
>
> **核心立场**：这道题考的不是"能不能做 CRUD"，而是能不能把一个表面简单的管理场景，拆解成一套真正可用、能防伪、能沉淀数据的企业工作管理系统。

---

## 一、我为什么这么理解这道题

拿到这道题的第一反应不是"画页面"，而是问自己一个问题：

**如果我真的是一家 50 人研发团队的技术负责人，这套系统上线后，我希望它解决什么问题？**

答案不是"计划录入"——那是 Excel 能干的事。

真正的痛点是三件事：

| # | 痛点 | 表现 | 系统该怎么回应 |
|---|------|------|----------------|
| 1 | **目标漂移** | 员工月初写的目标，月底翻出来发现跟实际做的完全不一样 | 月计划必须能拆解成日计划，日计划必须关联到具体产出，形成"战略→执行"的可追溯链路 |
| 2 | **成果不可验证** | 员工报"已完成"，领导只能选择信或不信 | 成果必须携带证据链——代码 PR、测试报告、截图、文档链接——验收是对照证据打分，不是审批一句"同意" |
| 3 | **管理滞后** | 到月底才发现延期，没有干预窗口 | 系统必须有实时看板：谁延期了、谁在等审批、哪些成果卡住了——领导打开系统第一眼看到的是"我需要处理什么"，而不是"所有数据" |

所以，我把这道题定义为**一个以"计划→执行→成果→验收"为业务闭环的工作管理系统**，而不是一个"计划审批工具"。

---

## 二、两种角色，两种完全不同的工作台

### 2.1 员工视角："我今天该干什么"

员工打开系统，不应该看到一张空白表单等着填。他应该看到的是：

```
┌─────────────────────────────────────────────────┐
│  本月计划完成率  78%  │  今日待办  3 项  │  待提交成果  2 项  │
├─────────────────────────────────────────────────┤
│                                                 │
│  今日计划                                        │
│  ┌─────────────────────────────────────────────┐│
│  │ 09:00  支付回调异常监控开发  [执行中]  6h P1  ││
│  │ 14:00  压测报告撰写        [未开始]  3h P2  ││
│  │ 16:00  PR #1842 代码 Review [未开始]  1h P2  ││
│  └─────────────────────────────────────────────┘│
│                                                 │
│  待提交成果                                      │
│  · 8/29 订单幂等改造 → 等待提交验收证据          │
│  · 8/27 Redis 缓存优化 → 已提交，等待领导验收     │
│                                                 │
│  领导退回意见                                    │
│  · 库存压测报告（退回）→ "请补充压测数据来源说明"  │
│                                                 │
└─────────────────────────────────────────────────┘
```

核心设计原则：**计划必须有"成果出口"**。

每个日计划创建时就预设"预期交付物"（DoD），执行完成后，员工不是填一句"已完成"，而是对照预期交付物提交具体的成果证据。这让"做没做"从主观判断变成了客观验证。

### 2.2 领导视角："谁需要我处理"

领导打开系统，最关心的不是"所有人的所有计划"，而是一个问题：

**今天我需要做什么决策？**

```
┌─────────────────────────────────────────────────┐
│  待审批计划  4 项  │  待验收成果  3 项  │  团队完成率  73%  │
├─────────────────────────────────────────────────┤
│                                                 │
│  待我处理                                        │
│  员工     事项              类型    状态          │
│  陈晨     订单中心幂等改造   计划审批  待审批      │
│  李明     回调监控优化       成果验收  待验收      │
│  赵宇     库存服务压测       成果验收  需补充      │
│  周敏     8月客户问题闭环     成果验收  退回中      │
│                                                 │
│  团队月度看板                                     │
│  按期交付率 82%  │  延期事项 3 项  │  返工率 12%   │
│                                                 │
│  延期预警                                        │
│  · 张三：本周日计划 2/5 未完成（连续 3 天）       │
│  · 王五：月计划 #3 已延期 5 天，无进展更新        │
│                                                 │
└─────────────────────────────────────────────────┘
```

这里有个关键区分：**计划审批**和**成果验收**是两个独立的决策场景，不能混在一起。领导审批计划时关注的是"方向对不对"；验收成果时关注的是"交付质量够不够"。把它们混成一个列表，决策效率会大幅下降。

## 三、两台独立的状态机

这是整个系统设计的核心骨架。很多"简单"的做法是把计划和成果塞进一张表，用一个 status 字段管全生命周期——这在真实业务中会制造大量混乱。

### 3.1 计划审批状态机

```
草稿 ──→ 待审批 ──→ 审批通过 ──→ 执行中 ──→ 待提交成果
              ↑  │                ↑
              │  ↓                │
              │ 退回修改 ─────────┘
              │
              └───── 再次提交 ──→ 待审批
```

**关键设计决策：**

- **"退回修改"和"待审批"形成循环**：领导退回不是终点，员工修改后重新提交，形成迭代。但系统必须记录每次退回的原因和修改历史——这是后续复盘"为什么这个计划反复被退回"的数据基础。
- **"审批通过"不等于"开始执行"**：计划审批通过后进入"执行中"，但真正开始执行可能因为资源排期等原因延迟。系统应支持"计划通过但未开始"的状态，避免数据失真。
- **"待提交成果"是从"执行中"自然流转的**：当执行时间到达或员工标记执行完成，计划自动流转到"待提交成果"状态。

### 3.2 成果验收状态机

```
待提交 ──→ 待验收 ──→ 验收通过
              │
              ├─→ 退回补充 ──→ 待验收（再次提交）
              │
              └─→ 退回驳回（终态）
```

**关键设计决策：**

- **"退回补充"和"退回驳回"是两种不同的退回**：退回补充意味着"方向对但证据不够"，员工补充材料后重新验收；退回驳回意味着"成果质量不达标或目标未达成"，是一个更严重的信号。两者在后续的绩效统计中权重不同。
- **成果必须强关联计划**：不能孤立地提交成果——每条成果必须挂在一个具体的日计划或月计划下。一个计划可以分多次提交成果（长周期任务），一个成果也可以关联多个计划（跨任务产出）。
- **证据链是验收的唯一依据**：验收界面不是点"通过"按钮，而是逐项核对证据——压测报告、PR 链接、截图、文档——然后给出评价。

## 四、系统架构

### 4.1 总体分层

```
┌───────────────────────────────────────────┐
│              前端展示层                     │
│  员工工作台 │ 领导工作台 │ 管理后台         │
├───────────────────────────────────────────┤
│            统一接入层 (BFF)                │
│  计划 API │ 成果 API │ 审批 API │ 通知 API  │
├───────────────────────────────────────────┤
│              业务服务层                     │
│  用户服务 │ 计划服务 │ 成果服务             │
│  审批引擎 │ 通知服务 │ 统计分析服务          │
├───────────────────────────────────────────┤
│              基础设施层                     │
│  MySQL │ Redis │ 文件存储(OSS) │ 消息队列   │
└───────────────────────────────────────────┘
```

### 4.2 核心设计决策

**为什么不做成微服务？**

这道题考察的不是微服务拆分能力，而是业务建模能力。一个 50 人团队用的工作管理系统，单体 + 模块化就够了。强行拆微服务反而引入分布式事务、服务发现等与业务无关的复杂度。如果面试官追问演进方向，可以回答：随着团队规模扩大和跨部门接入，计划服务和审批引擎会是最先需要拆出去的两个模块。

**审批引擎为什么独立于计划服务和成果服务？**

因为审批是一个可复用的通用能力。计划审批和成果验收的流程不同，但审批动作（提交、通过、退回、评论、历史记录）是相同的。把审批逻辑抽成独立模块，未来新增"需求评审""技术方案评审"等场景时，不需要重复开发。

## 五、数据模型与业务规则

### 5.1 核心实体关系

```
组织(Org)
 └── 部门(Dept)
      └── 用户(User)
           ├── 月计划(MonthlyPlan)
           │    ├── 审批记录(ApprovalRecord) × N
           │    └── 日计划(DailyPlan) × N
           │         ├── 审批记录(ApprovalRecord) × N
           │         └── 成果(Result) × N
           │              ├── 验收记录(VerificationRecord)
           │              ├── 证据附件(Evidence) × N
           │              └── 员工自评(SelfEvaluation)
           └── 操作日志(OperationLog) × N
```

### 5.2 关键业务规则

| # | 规则 | 理由 |
|---|------|------|
| 1 | 日计划创建时必须填写"预期交付物"和"预计工时" | 没有 DoD 的计划是空话；没有工时预估无法做负荷分析 |
| 2 | 日计划总工时上限 8 小时，超出系统预警 | 防止员工把计划当流水账，倒逼优先级取舍 |
| 3 | 计划一旦审批通过即形成基线，修改需走变更流程 | 基线是"计划偏差率"计算的前提，没有基线就没有复盘 |
| 4 | 成果必须关联至少一个计划，不能独立存在 | 防止成果脱离目标变成"做了什么"的流水账 |
| 5 | 每个业务动作记录操作日志（who/when/what/before/after） | 支撑审计、绩效统计和问题追责 |
| 6 | 退回时必须填写退回原因，不能为空 | 空退回既不专业也无法指导员工改进 |

### 5.3 "计划偏差率"的计算逻辑

这是这套系统最有管理价值的指标之一，但很多系统忽略了它：

```
计划偏差率 = |实际完成内容 - 计划目标| / 计划目标 × 100%

其中：
- 计划目标 = 月计划审批通过时的基线版本
- 实际完成内容 = 该月所有已验收通过的成果汇总
- 偏差率 < 15% → 正常
- 15%-30% → 关注
- \> 30% → 预警（触发领导复盘）
```

这个指标的意义在于：**区分"计划不准"和"执行不力"**。如果一个团队偏差率长期很高，问题可能出在计划制定环节（目标不切实际），而不是执行环节。

## 六、管理看板设计

### 6.1 员工看板指标

| 指标 | 含义 | 颜色规则 |
|------|------|---------|
| 本月计划完成率 | 已验收通过的成果 / 本月计划总数 | >80% 绿色，60-80% 黄色，<60% 红色 |
| 今日待办 | 今日日计划中未完成的任务数 | 数字越大越紧急 |
| 待提交成果 | 执行已完成但未提交成果的计划数 | 鼓励及时提交 |
| 本月验收通过率 | 一次验收通过的成果 / 总提交数 | 反映交付质量 |
| 连续未完成天数 | 连续 N 天有日计划未完成 | >3 天触发预警 |

### 6.2 领导看板指标

| 指标 | 含义 | 决策支撑 |
|------|------|---------|
| 团队月完成率 | 团队整体计划完成率 | 评估团队整体执行力 |
| 按期交付率 | 按时提交成果的计划占比 | 评估时间管理能力 |
| 延期事项数 | 超过截止时间仍未闭环的计划 | 识别风险项 |
| 返工率 | 被退回补充的成果占比 | 评估一次交付质量 |
| 待审批/待验收数 | 领导自己的待办积压 | 督促领导及时处理 |
| 员工维度完成率分布 | 每个员工的完成率分布 | 识别高绩效和需要辅导的员工 |

### 6.3 看板的数据来源

看板不是装饰，它的每个数字都必须能下钻：

```
团队完成率 73%
  └── 点击下钻 →
      ├── 李明 100% (5/5)  ← 全部通过
      ├── 陈晨 80%  (4/5)  ← 1项延期
      ├── 赵宇 60%  (3/5)  ← 2项被退回
      └── 周敏 40%  (2/5)  ← 3项未提交成果
```

领导看到"73%"这个数字时，下一步动作应该是点进去看谁拖了后腿，而不是去看所有人的所有计划。

## 七、容易被忽略的"坑"

### 7.1 通知疲劳

员工每天收到 10 条"计划提醒"、"成果提交提醒"、"审批结果通知"——两周后他就会关掉所有通知。

**解法**：通知分级。只有"被退回"和"截止时间还剩 1 天"才推送到手机/IM；其余通知只出现在系统内待办列表。

### 7.2 计划补录

真实场景中，员工经常是"先干活再补计划"。如果系统强制"先有计划才能提交成果"，员工会为了提交成果而编造一个假计划。

**解法**：允许"事后补录计划"，但系统会标记"该计划为补录"，并在统计中区分"按计划执行"和"事后补录"。领导看板上能看到"补录率"——这个数字本身就是一个管理质量指标。

### 7.3 月计划的"锚定效应"

一旦计划完成率直接挂钩绩效，员工下个月就会把计划定得极低以确保 100% 完成。

**解法**：引入"计划挑战度"系数。系统根据历史数据自动评估计划难度（工时、复杂度、跨团队依赖），给出挑战度评分。最终绩效 = 完成率 × 挑战度系数。这倒逼员工敢于定有挑战的目标。

## 八、MVP 边界

如果第一版只能做 3 个页面，我会做：

| 页面 | 核心功能 | 为什么优先做 |
|------|---------|------------|
| **员工工作台** | 今日计划 + 待提交成果 + 领导反馈 | 解决"打开系统不知道干什么"的问题 |
| **领导审批/验收** | 待审批 + 待验收 + 团队完成率 | 解决"领导不知道该处理什么"的问题 |
| **成果验收详情** | 证据链展示 + 通过/退回 + 评语 | 这是系统价值的核心差异化点 |

**不做**的（但我知道该做）：
- 通知推送系统（接入飞书/钉钉 webhook 即可）
- 统计报表导出（数据已经有了，导出是锦上添花）
- 审批流自定义配置（MVP 阶段固定两种审批流就够）

## 九、这套设计的面试表达逻辑

如果我在面试中讲这套方案，我的叙述线是：

```
"这个系统表面是计划审批，本质是目标管理的数字化载体。
 我的设计围绕三个核心问题展开：
  1. 怎么让员工的目标不漂移？→ 月计划拆日计划，日计划关联成果
  2. 怎么让领导的信任有依据？→ 成果证据链，验收对照 DoD
  3. 怎么让管理从被动变主动？→ 实时看板 + 异常预警

 这三个问题对应三组独立的状态机、两种差异化的工作台、和一套可下钻的指标体系。"
```

这句话不超过 30 秒，但能清晰传达：**我理解这不是 CRUD，这是一个管理工具**。
