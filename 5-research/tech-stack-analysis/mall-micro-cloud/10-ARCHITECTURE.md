## 三、架构决策复盘

### 决策 1: Spring Cloud Alibaba 而不是 Eureka + Feign

| 考量 | 结论 |
|------|------|
| 国内生态 | Nacos 支持注册+配置中心二合一 |
| Sentinel | 比 Hystrix 更活跃的限流熔断 |
| Seata | 分布式事务标准实现 |
| 版本兼容 | Spring Boot 3.3 + Spring Cloud 2023.0.1 + Alibaba 2023.0.1.0 |
| **正确性** | ✓ 国内主流电商微服务标准技术栈 |

### 决策 2: MongoDB 做购物车而不是 Redis

| 考量 | 结论 |
|------|------|
| 持久化 | 购物车数据不能丢，MongoDB 落盘 |
| 查询能力 | 按 userId + 商品名 + 价格范围多条件查询 |
| 分页 | MongoDB 原生支持 |
| **正确性** | ✓ 购物车是"结构化文档数据"，不是"缓存数据" |

### 决策 3: Redis 预扣库存 + MQ 双写而不是直接数据库扣减

| 考量 | 结论 |
|------|------|
| 性能 | Redis 内存操作百万 QPS vs 数据库行锁数百 QPS |
| 一致性 | MQ 最终一致性 + 幂等消费兜底 |
| **正确性** | ✓ 秒杀场景的行业标准方案 |

### 决策 4: Seata AT 模式而不是 TCC

| 考量 | 结论 |
|------|------|
| 开发效率 | AT 无侵入，只需 @GlobalTransactional |
| 回滚能力 | 自动 undo log 回滚 |
| 灵活性 | 秒杀/支付等高定制场景才需要 TCC |
| **正确性** | ✓ 下单场景 AT 模式足够 |

## 五、面试题集

### 5.1 微服务架构类

**Q1: 你们为什么拆分这么多微服务？拆分原则是什么？**

> **回答思路：** 按**业务域**拆分：商品、用户、订单、购物车、秒杀、支付独立部署升级。每个服务有独立的数据库，互不影响。拆分原则：1) **单一职责**——每个服务做一件事；2) **独立部署**——服务间通过 API 通信；3) **数据隔离**——每个服务独立数据库；4) **团队独立**——不同团队负责不同服务。

**Q2: 微服务的优缺点分别是什么？**

> **回答思路：** 优点：独立部署、技术异构（订单用 MySQL + 购物车用 MongoDB）、故障隔离（A 服务挂了不影响 B）、易于扩展。缺点：分布式复杂度（事务、一致性、调用链追踪）、运维成本高、服务调用有网络开销。**不是所有项目都适合微服务，中小项目单体更合适。**

### 5.2 网关与安全类

**Q3: Spring Cloud Gateway 里自定义过滤器的完整流程？**

> **回答思路：** 继承 `AbstractGatewayFilterFactory<Config>`，实现 `apply(Config)` 返回 `GatewayFilter`，在 `filter()` 中实现逻辑。使用 `shortcutType()` 和 `shortcutFieldOrder()` 实现短格式配置。项目中的 `AuthGatewayFilterFactory` 就是自定义过滤器——通过 `Auth=/api/v1/**,/api/user/login,...` 短格式配置白名单路径，实现 JWT 鉴权。

**Q4: JWT 和 Session 的区别？为什么选择 JWT？**

> **回答思路：** Session 在服务端存储，JWT 在客户端存储。JWT 无状态（服务端不需要存），天然支持水平扩展和跨域。缺点是无法主动失效、体积较大。项目通过网关无感知续期解决过期问题。

### 5.3 分布式事务类

**Q5: Seata AT 模式的工作原理？**

> **回答思路：** AT 模式三个角色：TC（协调器）、TM（事务管理器）、RM（资源管理器）。流程：TM 开启全局事务 → RM 执行本地事务并生成 undo log → 所有 RM 成功后 TM 提交 → 任一 RM 失败则根据 undo log 回滚。**对业务代码无侵入，只加 @GlobalTransactional 注解。**

**Q6: 下单流程中，库存扣减失败怎么处理？**

> **回答思路：** 通过 Feign 调用扣库存，返回失败则抛出 `BusinessException`，Seata 捕获到异常自动回滚整个全局事务——订单不保存、购物车不清空、其他分支也回滚。

### 5.4 高并发类

**Q7: 你们秒杀是怎么做的？**

> **回答思路：** 四层防护：1) **静态化**——商品页预生成 HTML；2) **布隆过滤器**——拦截不存在的商品请求，防缓存穿透；3) **Redisson 分布式锁**——同一商品扣减串行化，防超卖；4) **Redis 原子扣减 + MQ 异步双写**——Redis 扛瞬时流量，MQ 异步同步到 MySQL，保证最终一致性。

**Q8: Redisson 的看门狗机制是什么？**

> **回答思路：** 获取锁后后台线程每 10 秒检测，如果业务还在执行就自动续期锁的过期时间（默认 30 秒）。防止"业务执行时间 > 锁过期时间"导致锁提前释放、其他线程趁机进入。业务结束释放锁，看门狗自动停止。

**Q9: 怎么防止超卖？**

> **回答思路：** 三层：1) **Redis 原子操作**——`decrement()` 返回扣减后剩余量，小于 0 回滚；2) **Redisson 分布式锁**——同商品扣减串行化；3) **MySQL 条件更新兜底**——`UPDATE SET stock=stock-1 WHERE stock > 0`，数据库层再次兜底。

### 5.5 消息队列类

**Q10: 支付成功后的一系列操作怎么保证最终一致性？**

> **回答思路：** 支付成功 → 发送 RocketMQ 消息 → 各消费者异步处理（清购物车/更新订单/同步ES）。通过 RocketMQ 的**重试机制**保证消息最终被消费，通过**幂等设计**保证重复消费无副作用。如果消费多次失败，存入死信队列人工处理。

### 5.6 缓存与搜索类

**Q11: 布隆过滤器原理是什么？解决什么问题？**

> **回答思路：** 布隆过滤器用 bit 数组和多个哈希函数判断元素是否存在。插入时用 k 个哈希函数计算位置并置 1，查询时检查这 k 个位置是否全为 1。解决**缓存穿透**——大量不存在 key 的请求直接打到数据库。
