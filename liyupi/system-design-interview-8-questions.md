# Q1. 设计一个 AI 代码生成平台

## 1.1 题目（中文）

> 请设计一个 AI 代码生成平台：用户输入一句自然语言需求（如"生成一个 AI 塔罗牌应用"），平台自动完成需求分析 → 架构选型 → 代码生成 → 代码审查 → 一键部署，全程可见、可干预。系统需支持可视化编辑、实时预览、模型可选（DeepSeek / Qwen / Claude）、多用户并发（预计 1000 并发）、按 Token 计费。请给出整体架构、关键模块设计、AI 编排方案与可靠性保障。

## 1.2 难度

⭐⭐⭐⭐⭐（大厂 P6/P7 级 AI 业务系统设计题）

## 1.3 时间分配（面试中）

- 需求澄清 & 明确约束（functional / non-functional）：2 分钟
- 画架构图 & 讲模块划分：5 分钟
- 深挖 AI 编排（LangGraph4j / SSE / Tool Calling）：6 分钟
- 可靠性 / 限流 / 计费追问：4 分钟
- 电梯陈述收尾：3 分钟

**总计控制在 20 分钟内。**

## 1.5 核心技术选型（附理由）

| # | 选型 | 理由 |
|---|------|------|
| 1 | **Spring Cloud Alibaba 微服务**（Gateway + Nacos + Sentinel + Seata） | AI 生成是 CPU/成本密集型长任务，必须与服务治理解耦：Nacos 做注册/配置（AP 满足发现，动态刷新模型 Key），Sentinel 对生成接口做 QPS+热点参数限流、慢调用熔断（LLM 超时是常态），Seata 处理"扣费 + 生成记录落库 + 额度扣减"的跨服一致性 |
| 2 | **LangChain4j + LangGraph4j 编排多步工作流** | 需求→架构→生成→审查是天然的状态机流程，LangGraph4j 的 StateGraph 天然支持节点、条件边、人工介入（Human-in-the-loop）；LangChain4j 的 `@AiService` 声明式接口封装 LLM 调用，`@Tool` 注解注册工具，比手写 HTTP 调用低耦合、可测试 |
| 3 | **SSE（Server-Sent Events）+ 异步任务池** | 大模型生成是分钟级长任务：SSE 单向流式推送 token 成本最低、断线自动重连；配合线程池 + 任务表（status: 排队→生成中→完成/失败）支撑断点续传和失败重试，WebSocket 在此场景不需要双向实时性 |
| 4 | **模型网关（Model Gateway）+ 统一计费层** | 屏蔽 DeepSeek/Qwen/Claude 的 API 差异（适配器模式），内置超时、重试（指数退避）、熔断、多 Key 轮换；Token 计量在网关统一埋点，写入 MQ 异步记账，避免阻塞生成主链路 |
| 5 | **Docker 沙箱 + 对象存储承载预览/部署** | 生成代码不可信，必须隔离执行：preview-service 用 Docker 容器（内存/CPU 配额 + 网络隔离 + 超时回收）跑实时预览；产物上传 COS/OSS，deploy-service 通过 K8s/Docker 一键发布，天然支持版本回滚 |

## 1.6 鱼皮项目佐证

- **yu-ai-code-mother（1,892⭐）**：完全对应的案例。微服务拆分（gateway / user / ai / code / preview / deploy / monitor 七服务）、LangChain4j AiService + `@Tool`、LangGraph4j StateGraph（analyze→design→generate→review + 条件边 needsReview）、SseEmitter 流式推送都是现成模板。
- **ai-guide（19,013⭐）**：佐证"多步骤生成工作流"是 2025-2026 主流的 Plan-and-Execute Agent 模式；其项目实战章节证明"生成 AI 应用"（塔罗牌/翻译器）是经市场验证的真实需求。
- **interview-value-guide**：提供了现成 STAR 话术——"AI 应用开发周期从 2 周缩短到 1 天，准确率 85%+，可用性 99.9%"。

**面试话术锚点**：*"我做的是大厂级 AI 应用生成平台，七服务微服务架构，用 LangGraph4j 编排『需求分析→架构设计→代码生成→代码审查』状态机，SSE 流式输出每步进度，Tool Calling 让 LLM 能查表结构、执行 SQL、触发部署。"*

## 1.7 常见陷阱（面试官追问）

| 陷阱 | 正确应对 |
|------|---------|
| **「为什么不用 WebSocket 用 SSE？」** | 单向推送场景，SSE 无双向开销、心跳断线重连、EventSource 原生支持，天然适配流式 token；WebSocket 留给"可视化协同编辑"这类双向需求 |
| **「生成到一半模型挂了怎么办？」** | 双保险：任务表持久化节点状态（LangGraph4j checkpoint），重启可从断点续跑；token 级幂等 + 模型网关自动重试 |
| **「如何防止生成代码被恶意利用（SQL 注入/挖矿）？」** | 只做静态产物生成 + Docker 沙箱隔离执行（无网络出站/限 CPU 内存/超时强杀）；部署环境独立命名空间；对生成的 SQL/脚本做白名单校验 |
| **「多模型怎么切换？成本怎么控？」** | 模型网关适配器 + 路由策略（按任务复杂度/用户等级/价格）；计费用令牌桶 + MQ 异步扣费；支持"廉价模型先生成、贵模型再审"的分级流水线 |
| **「1000 并发下 LLM Rate Limit 怎么办？」** | 网关层做令牌桶限流 + 队列削峰 + 多账号 Key 轮换 + 结果缓存（相同 Prompt 命中 Redis 缓存）；高峰期退化为排队模式（任务表 + 前端轮询） |
| **「分布式事务怎么解决扣费与生成记录不一致？」** | Seata AT 模式（两阶段提交，符合 ACID 场景）或本地消息表 + RocketMQ 最终一致；生成主链路不阻塞在扣费上，异步对账兜底 |

## 1.8 5 分钟电梯陈述

> "我想设计的是一个『需求一句话，应用一键出』的 AI 代码生成平台。整体是 Spring Cloud Alibaba 七服务微服务架构，核心是独立的 AI 编排服务——我们用 LangGraph4j 把『需求分析 → 架构选型 → 代码生成 → 代码审查 → 一键部署』编排成带状态和条件回退的工作流，每个节点通过 LangChain4j 的 `@AiService` 声明式调 LLM，通过 `@Tool` 注册表结构查询、SQL 执行、Git 提交、容器部署这些外部能力，让大模型真正『动手』。用户体验上我们用 SSE 流式推送每一步进度，生成产物进 Docker 沙箱实时预览。
> 可靠性上，生成任务全部落库成任务表，支持断点续跑；模型层做了一层网关，多模型可切换、统一计费、超时自动重试、Rate Limit 时排队削峰；Sentinel 对生成接口做限流熔断，扣费走 Seata + MQ 保证最终一致。
> 结果量化为：单次生成从 2 周的开发周期压缩到约 1 天，代码生成准确率 85%+。为了控制成本，我们支持『轻量任务走廉价模型、复杂任务走高端模型』的模型分级路由，这也是后期最大的优化点。"

# Q2. 设计一个在线 SQL 学习系统

## 2.1 题目（中文）

> 请设计一个面向初学者的在线 SQL 学习系统：用户在线写 SQL、实时看到执行结果，系统自动判题（答对过关），支持 50+ 关卡、社区贡献关卡、闯关进度记录。约束：目标用户量大（DAU 10 万级），期望**成本极低甚至免费**，且要防恶意 SQL（删表/注入）。请给出判题引擎、执行环境、关卡体系与防攻击设计。

## 2.2 难度

⭐⭐⭐⭐（中高难度，重点考察"架构取舍"与"成本意识"）

## 2.3 时间分配

- 澄清与关键取舍（浏览器执行 vs 服务端执行）：3 分钟
- 判题引擎设计：5 分钟
- 关卡/进度体系 & 防攻击：5 分钟
- 扩展方案（在线评测 OJ 化）：4 分钟
- 电梯陈述：3 分钟

## 2.4 架构图（ASCII）

```
│                      浏览器                              │
│  Monaco Editor (SQL 编辑器, 语法高亮/补全)               │
│        │                                                │

│        │                                                │

│  sql-wasm.wasm (SQLite 引擎跑在内存里, 每关独立重建)     │

│        ├─► 判题：用户结果 JSON vs 标准答案 JSON 对比      │

用户 SQL ─► API ─► 判题服务 ─► 数据库沙箱(每用户一个容器/实例)
                 │              ├─► 临时库执行 + 超时强杀
                 │              └─► 结果序列化返回
                 └─► 扣费/配额 (SQL 引擎即算力)
```

## 2.5 核心技术选型（附理由）

| # | 选型 | 理由 |
|---|------|------|
| 1 | **WebAssembly 前端执行引擎（sql.js）** | 核心杀手锏：SQL 在浏览器内存里执行，服务端只为进度付费——DAU 10 万近乎零服务器成本；Wasm 沙箱天然隔离，删表只删浏览器里的临时库，没有注入攻击面；切关卡重建内存库，零状态残留、判题结果天然确定性 |
| 2 | **"执行结果对比"而非"SQL 文本对比"判题** | 允许 `SELECT * FROM student` 和 `SELECT name, age FROM student` 等不同写法得同一正确答案——这是教学系统的灵魂；判题实现：分别执行用户 SQL 与答案 SQL，`JSON.stringify(columns)` 必须一致 + `values` 完全一致即通过；避免正则匹配 SQL 文本的脆弱与误伤 |
| 3 | **关卡元数据目录化（每关一个目录）** | `level1/index.ts(答案+hint) + createTable.sql(建表+数据) + README.md(教程)`——关卡即代码，社区贡献只需提 PR 加目录，大幅度降低扩展门槛；答案与初始化 SQL 分离，保证判题基准可复用 |
| 4 | **教程内容 Markdown 化 + 静态托管** | 每个关卡内嵌 README 教程，学习内容与判题逻辑同目录聚合；配合前端框架（Vue 3）客户端路由，冷启动快、CDN 成本可忽略 |
| 5 | **（扩展/商用）重型判题走服务端容器沙箱** | 当需要支持复杂数据库（PG/MySQL 方言）、大数据量评测时，前端 Wasm 不适用：改为每个判题请求在独立 Docker 容器（或 MySQL 实例秒级重建）执行，加超时(如 5s)强杀 + 只读账号 + 资源配额，按执行次数计费 |

## 2.6 鱼皮项目佐证

- **sql-mother（4,326⭐）**：直接对应。30 主线关卡 + 16 社区关卡，纯前端 Wasm SQLite + 结果对比判题算法，"没有后端数据库，SQL 完全在浏览器内执行"是它的招牌。
- **sql-father-backend（2,098⭐）+ sql-generator（3,427⭐）**：佐证 SQL 生态的两翼——sql-father 提供后台管理/题目 CRUD；sql-generator 用 JSON 模板 DSL + 递归展开（`@ruleName(param)` 语法、嵌套括号计数匹配）自动生成教学 SQL 数据，大幅降低题目生产成本。
- **learning-roadmap**：把 sql-mother 定位为"MySQL 索引 / B+树 / SQL 执行引擎"的教学载体，说明该设计天然服务教育场景。

**面试话术锚点**：*"我实现了一个让用户写 SQL、系统自动判题的闯关平台。核心决策是放弃服务端数据库——用 WebAssembly 把整个 SQLite 编译进浏览器，每个关卡独立内存库，判题不比对 SQL 文本、而是比对执行结果。这样 10 万 DAU 的服务端成本几乎为零，还天然免疫恶意 SQL。"*

## 2.7 常见陷阱

| 陷阱 | 正确应对 |
|------|---------|
| **「判题只比结果，那 `SELECT 1+1` 和 `SELECT 2` 算对吗？」** | 这正是设计意图（等价性），但需分层：初级关卡比结果集，高级关卡可增加"执行计划对比"或"必须使用某语法（如必须用 JOIN）"的额外标记，用元数据标注约束 |
| **「Wasm 里不能连真实数据库，复杂场景怎么办？」** | 承认边界：前端 Wasm 只覆盖教学级 SQL（CRUD/JOIN/GROUP BY）；企业级场景切换服务端容器沙箱方案 B，二者以题目难度阈值自动路由 |
| **「如何防用户执行 `DROP TABLE` 导致判题环境崩？」** | 每关重建内存库是天然防护；即便删库也只影响该用户本地会话；服务端方案则用只读账号 + 临时库 + 超时强杀 + 白名单（禁用多语句/事务） |
| **「进度同步与并发写怎么办？」** | 进度表以 `userId + levelId` 为唯一键 UPSERT；服务端只保存通过记录，不保存执行中间态 |
| **「题目判定有歧义（列顺序不同）？」** | 决定性：要求列名集合一致 + 行数据有序比对；用 JSON 序列化对比避免手写深层比较，且可排序后对比保证确定性 |
| **「为什么不用在线编辑器 + 后端真数据库的最常见方案？」** | 3 个理由：成本（10 万 DAU 的 DB 连接数会打死任何后端）、安全（注入面消失）、体验（无网络延迟秒级反馈）——技术选型紧跟业务批量与成本约束 |

## 2.8 5 分钟电梯陈述

> "我要设计的是一个让零基础用户闯关学 SQL 的平台，核心约束是『DAU 很大、成本必须极低、还要防恶意 SQL』。三个约束让我做了一个反直觉的决定：**不在服务端跑数据库，把整个 SQLite 用 Emscripten 编译成 WebAssembly 放进浏览器**。用户在 Monaco 编辑器写 SQL，浏览器内的 sql.js 直接执行，判题引擎同时跑用户 SQL 和标准答案 SQL，比对两边的列名和行数据——注意我们拒绝比 SQL 文本，因为要包容『不同写法、同一答案』的教学宽容度。
> 架构上，每个关卡是一个独立目录（关卡定义 + 建表脚本 + Markdown 教程 + 隐藏答案），社区贡献者提 PR 就能加关卡；服务端只保留一个轻量进度接口。这样 10 万 DAU 的服务器几乎只承担登录和写进度。
> 成本数据：方案 A 的服务端成本趋近于零，是我们领先同类产品（服务端真库方案）的最大壁垒。如果未来要做企业 SQL 训练（真实 PG/大数据量），我会在判题服务上加一层 Docker 沙箱执行，用只读账号 + 超时强杀 + 按次计费，这是成本模型里唯一的例外。"

# Q3. 设计一个自研 RPC 框架

## 3.1 题目（中文）

> 假设所在团队微服务改用自研 RPC（不用 Dubbo/Spring Cloud OpenFeign），请设计一个 RPC 框架：服务注册发现、可插拔序列化、负载均衡、重试容错、Spring Boot 注解驱动、监控埋点。要求 QPS 10,000+，并说明自定义协议、粘包半包处理、注册中心选型。

## 3.2 难度

⭐⭐⭐⭐⭐（考察底层原理深度的经典框架设计题）

## 3.3 时间分配

- 自定义协议（17 字节头）& 粘包半包：5 分钟

- 负载均衡/重试/容错策略：4 分钟

## 3.5 核心技术选型（附理由）

| # | 选型 | 理由 |
|---|------|------|
| 1 | **自定义 17 字节定长 TCP 协议而非 HTTP** | HTTP/1.1 文本头开销大、每次请求冗余传输；TCP 自定义协议 17 字节头搞定寻址（魔数 1B + 版本 + 序列化类型 + 消息类型 + 状态 + 雪花 requestId 8B + bodyLength 4B），长连接复用高吞吐；魔数防串包、version 支持协议演进、requestId 支撑异步配对与链路追踪 |
| 2 | **Vert.x 非阻塞 TCP + RecordParser 解粘包半包** | 非阻塞 EventLoop 天然支撑高并发长连接（对比阻塞 BIO 每连接一线程）；RecordParser 天然支持"先读定长头→根据 bodyLength 切 fixedSizeMode→读满 body 复位"的分帧模式，优雅解决 TCP 粘包/半包 |
| 3 | **自研 SPI（key→class 映射，双目录覆盖）而非 Java SPI** | 序列化器/注册中心/负载均衡/重试/容错五大扩展点全部组件化：`META-INF/rpc/system/` 内置 + `META-INF/rpc/custom/` 用户覆盖；Java SPI 只能全量加载、无 key 寻址，自研 SPI 支持 `kryo=com.xx.KryoSerializer` 按名称单例加载，按需实例化 |
| 4 | **etcd 为主 / ZooKeeper 为备的注册中心双实现** | etcd（Raft 强一致 + Leaner watch + K8s 原生生态）适合云原生；ZK（ZAB 强一致 + 临时节点免心跳）在 Java 生态成熟；通过 Registry 接口 SPI 化实现二者可一键切换，Watch 机制驱动本地缓存失效 |
| 5 | **一致性哈希 + 虚拟节点负载均衡（默认策略）** | 相比 random/轮询，一致性哈希保证相同请求参数落到相同节点，天然支持服务端缓存 & 有状态场景（后续 RPC 扩展到图库/共享会话的基石）；100 虚拟节点/真实节点解决节点少时分布不均 |

## 3.7 常见陷阱

| 陷阱 | 正确应对 |
|------|---------|
| **「为什么不直接用 gRPC / Dubbo？」** | 自研价值在教育与可控性（学习动机）+ 特定场景裁剪（协议更精简、无 gRPC 的 HTTP/2 建连开销）；同时承认生产多用成熟框架，自研版作为团队内部教学基座 |
| **「粘包半包到底怎么发生的？怎么解？」** | 粘包：多个小包被合并（Nagle/内核缓冲）；半包：大包被拆成多段（MSS 限制）。解法：定长头 + bodyLength 分帧（RecordParser / Netty LengthFieldBasedFrameDecoder 是同一思想） |
| **「TCP 相比 HTTP/2 还有优势吗？」** | HTTP/2 多路复用已缩小差距，但自定义协议仍赢在：头部极简、二进制紧凑、无 TLS 握手开销（内网可明文）、完全掌控流控与编解码 |
| **「一致性哈希的坑？节点变化怎么办？为什么虚拟节点？」** | 节点增减只影响环上邻近节点的 key 映射（最小化重哈希）；虚拟节点解决数据倾斜；生产实现应缓存 TreeMap 而非每次 select 重建（教学版简化） |
| **「服务端线程模型？BIO vs NIO？」** | NIO/EventLoop（Vert.x/Netty）避免每连接一线程，10 万连接只需数百线程；配合 Future/回调或虚拟线程（Java 21）管理异步链路 |
| **「如何做全链路监控？」** | requestId（雪花）贯穿请求，接入 OpenTelemetry/SkyWalking trace；Provider 侧记录方法级耗时、序列化耗时、错误率埋点上报 Prometheus |
| **「注册中心挂了会怎样？」** | 本地缓存 RegistryServiceMultiCache 保证存量节点可用（降级但仍服务）；Watch 断线重连 + 全量对账兜底同步 |

## 3.8 5 分钟电梯陈述

> "目标很明确：造一个够快、可插拔、能教学的 RPC 框架。整体分四块——通信、协议、注册发现、扩展策略，全部 SPI 化。
> 通信层我们没有用 HTTP，而是自定义 17 字节定长二进制头：魔数、版本、序列化类型、消息类型、状态、8 字节雪花 requestId、4 字节 bodyLength，配合 Vert.x 的 RecordParser 先读头再按 bodyLength 读体，优雅解掉粘包半包。相比 HTTP，同样一次调用省掉几百字节文本头，长连接复用得 QPS 过万。
> 序列化支持 JDK/JSON/Kryo/Hessian 四种，通过自研 SPI 按 key 加载、system/custom 双目录让用户覆盖内置实现。注册中心实现 Etcd 和 ZooKeeper 两套——Etcd 走 30 秒租约加心跳续约、前缀 Watch 清缓存；ZK 走临时节点断开自动删除。负载均衡默认一致性哈希、每个节点 100 个虚拟节点，保证节点增减只影响局部 key 并且分布均匀。
> 最后我用 Spring Boot Starter 收了尾：`@RpcService` 发布服务、`@RpcReference` 注入代理、`@EnableRpc` 一键启停，BeanPostProcessor 扫描装配。重试（固定间隔 3 次）和容错（failFast/failSafe/failOver）也做了策略化。
> 一句话总结：协议极端精简 + 全链路扩展点 SPI 化 + 工程化的 Starter 体验，这套设计同时让我把序列化、网络分帧、分布式一致性这些底层原理全部打通了。"

## 4.5 核心技术选型（附理由）

| # | 选型 | 理由 |
|---|------|------|
| 1 | **ShardingSphere 按 spaceId 动态分表** | 千万级图片按空间维度天然聚合，`picture_{spaceId}` 分表让单表数据量可控、查询走分片键避免跨库扫描；同一空间的数据热聚合，符合业务访问模式；相比按时间分片，更贴合"个人空间"的隔离语义 |
| 2 | **对象存储（COS/OSS）存二进制 + MySQL 存元数据** | 图片本质是不可变二进制，对象存储自带 CDN 加速、分块上传、版本/回收站；MySQL 只存 URL、尺寸、格式、主色调、标签等结构化元数据；上传时服务端同步提取这些特征一次入库，搜索零二次 IO |
| 3 | **WebSocket + LMAX Disruptor 无锁队列承载协同编辑** | 多人同图编辑的高频鼠标/画笔事件（每秒数百条）不适合落 DB，先入 Disruptor RingBuffer（1024×256=262,144 槽位无锁环形队列）异步批量广播+持久化；Disruptor 比阻塞队列吞吐高一个量级（GC-free、缓存行填充），保证低延迟广播 |
| 4 | **多级缓存：Caffeine (L1) → Redis (L2) → MySQL (L3)** | 热门图片元数据走本地缓存，热点突变时 L1 未布立即回源 Redis；配合 Sa-Token 做空间级 RBAC 权限（图可见性 = 空间成员关系），权限判断也进缓存 |
| 5 | **AI 能力异步化：DashScope 扩图/向量化走异步任务** | AI 扩图是秒级-分钟级任务，异步任务队列（MQ）+ 状态轮询/WebSocket 推送结果；以图搜图的生产级方案用 CLIP/embedding 模型把图片向量化，存向量库（Milvus/PgVector）做相似度检索（鱼皮教学版用 Jsoup 爬取简化，生产应升级向量检索） |

## 4.7 常见陷阱

| 陷阱 | 正确应对 |
|------|---------|
| **「为什么 DDD？不是过度设计吗？」** | 承认两版对比的价值：传统三层适合快速迭代，DDD 适合边界复杂的聚合（Picture/Space/User 三大聚合各自维护不变量）——面试里说清楚"什么场景选什么"才是加分项 |
| **「协同编辑冲突怎么解决？」** | 分层策略：轻量场景服务端广播（后写覆盖 + 版本号），重场景用 OT（操作转换）/CRDT；鱼皮实现是 Disruptor 异步广播 + 版本比对，面试可补充说明冲突合并的演进方向 |
| **「动态分表的坑？跨空间查询怎么办？」** | 分片键缺失的查询会广播到所有分片（性能差）——设计约束：所有查询必须带 spaceId；表过多时需定期归档或平滑扩容；事务尽量限制在单分片内 |
| **「以图搜图为什么爬虫方案不行？」** | Jsoup 爬虫只能搜"外部网页里的图"，无法对库内图片做真实特征相似度；生产必须走向量化（embedding 模型 → 向量库 ANN 检索），面试要主动指出教学简化与生产方案的差距 |
| **「对象存储的图片被恶意替换怎么办？」** | 内容寻址（hash 命名）+ 上传签名（STS 临时凭证）+ 回源校验 + 图片处理管道防 SSRF（禁用内网 URL） |
| **「多人同时编辑同一张图怎么保证一致性？」** | 房间概念：同图用户加入同一 WS 房间；事件带 version/seq，服务端按序广播；落库走 Disruptor 单线程消费者，天然串行化写库 |

## 4.8 5 分钟电梯陈述

> "我设计的是一个千万级的云图库，四个关键词：分片存储、特征化搜索、异步 AI、协同编辑。
> 存储上，图片二进制全部交给对象存储（COS），自带 CDN 和回收站；MySQL 只存元数据，而且按 spaceId 动态分表——每个用户空间的数据天然聚合在一张表里，单表数据量可控。关键设计是上传时就把尺寸、格式、主色调这些特征一次提取入库，搜索时零二次 IO。
> 搜索三路并行：按色搜图用主色调 RGB 欧氏距离最近邻；以图搜图生产方案是 embedding 向量化 + 向量库相似检索；标签描述走 ES 全文。AI 扩图这种秒级任务全部异步化，走 MQ 队列推结果。
> 协同编辑是技术亮点：多人的画笔事件通过 WebSocket 进到 LMAX Disruptor 无锁环形队列，单消费者串行广播和落库，避免锁竞争，事件吞吐和延迟都远好于直接写数据库；正常路径是『事件改的是 Redis 里的画布状态 + 定期落盘』，保证响应快、可恢复。

## 5.5 核心技术选型（附理由）

| # | 选型 | 理由 |
|---|------|------|
| 1 | **三模块终端架构：Terminal UI ⇄ Executor ⇄ Commands 插件集** | 终端 UI 只管渲染输入输出流，Executor 只做解析分发，Commands 每个命令独立实现 `CommandType` 协议（func/name/alias/params/options/subCommands/action）——职责分离让"加一个命令 = 加一个模块 + 注册"，天然插件化，新人贡献命令零成本 |

| 4 | **空闲/首屏性能优先：静态资源 + 懒加载命令** | 起始页要求秒开：核心命令打包进主包，重型命令（如音乐、爬热搜）动态 import 按需加载；全站无首屏图片依赖，减少 DOM 节点数量，SSR 非必需（纯客户端渲染冷启动更快） |
| 5 | **轻后端仅做云同步与第三方 API 代理** | 收藏夹快照按用户加密/压缩上传 MySQL，多端登录拉取合并（以时间戳/版本号做冲突合并）；网易云/百度翻译等跨域 API 一律走后端代理解决 CORS 与防盗链 |

## 5.7 常见陷阱

| 陷阱 | 正确应对 |
|------|---------|
| **「为什么不用现成 xterm.js / 真实 shell？」** | 关键技术决策：这里只需命令式 UI 唤起，不需要真实进程与 ANSI 终端协议——自研三模块比引入 xterm.js 轻一个量级；与"真终端模拟"是两种不同产品场景（对比讲清楚即可） |
| **「命令多了以后性能怎么办？解析器会不会成为瓶颈？」** | 命令查找用 Map 索引（func/alias 双索引），解析只处理当前行文本，复杂度 O(命令数)；执行动作多为 `window.open` / 状态变更，无重计算——瓶颈不在解析在外部 API |
| **「虚拟文件系统的路径计算怎么处理 `..`、符号链接、重名？」** | 路径规约（split + 栈处理 `..`/`.`）、重名报错/追加序号、读操作只读快照保证幂等；扁平存储（DB 表/Map 的 key 即绝对路径）天然规避目录树一致性问题 |
| **「云同步冲突：两台设备都改了收藏夹？」** | 乐观更新 + 版本号：冲突时按"文件级 last-write-wins + 目录级合并"，极端情况生成冲突副本交由用户确认（类 Dropbox 策略），不引入分布式锁 |
| **「多端场景 localStorage 不够用怎么办？」** | 升级 IndexedDB 存大体积快照；同步接口增量上传（diff 而非全量），用哈希对比分片 |
| **「安全：收藏链接 XSS？」** | 所有外部 URL 一律白名单协议（http/https）+ 跳转前二次确认；渲染小组件（如热搜）内容走 Vue 模板转义，杜绝 v-html |

## 6.5 核心技术选型（附理由）

| # | 选型 | 理由 |
|---|------|------|
| 1 | **单体应用 + 企业级中间件组合（Sa-Token/Sentinel/HotKey/ES）** | 相比 Q1 的微服务，刷题平台核心链路读写模型简单（题目读多写少、无 AI 长任务编排），单体初期交付最快、无分布式事务成本；企业级组件以库/中间件形式嵌入，为未来的垂直拆分（题库服务/模拟面试服务/搜索服务）留好模块边界——"先单体后微服务"本身就是架构决策 |

## 6.7 常见陷阱

| 陷阱 | 正确应对 |
|------|---------|
| **「缓存击穿/穿透/雪崩怎么区分怎么解？」** | 击穿=热点 Key 过期瞬间打爆 DB → 互斥锁/逻辑过期/HotKey 本地缓存；穿透=查询不存在的数据绕过缓存 → 布隆过滤器/缓存空值；雪崩=大批 Key 同时过期 → 过期时间加随机抖动/多级缓存。三连问必须能脱口而出 |
| **「HotKey 是中间件，自己实现原理是什么？」** | 本质是"本地滑动窗口计数 + 阈值上报 + 事件驱动写本地缓存"；要把核心思想说出来：热点不能靠静态缓存解决，要靠"动态探测 + 就近缓存"，这是中间件设计能力的体现 |
| **「ES 和 MySQL 数据不一致怎么办？」** | 三层保障：定时全量对账（diff 补任务）+ 增量同步（MQ/定时）+ 主动刷新接口；最终一致符合搜索语义。不要承诺强一致，清晰划出一致性边界 |
| **「游标分页为什么不用 offset？」** | 深分页 offset 深了会全表扫描（limit 100000,10 要扫 10 万行）；游标分页 `WHERE (appId, createTime) < 游标 ORDER BY ... LIMIT 10` 走复合索引，恒定快，且并发下数据变动不会导致重复/跳页 |
| **「同端互斥登录怎么实现？」** | Sa-Token `StpUtil.login(userId, device)`：同设备新登录挤掉旧登录（is-concurrent=false），Redis 存会话与设备维度绑定——讲清楚多端/同端策略差异 |
| **「模拟面试对话随便发怎么办？」** | Token 配额 + 大模型调用走独立限流阈值；对话存 JSON 字段防表爆炸；状态机 0→1→2 控制生命周期 |
| **「Redis 里存题库 JSON，更新了怎么办？」** | 版本 + 主动失效（更新时删 Key）+ 兜底 TTL；热点题库更新频率低，主动失效成本可忽略 |

## 6.8 5 分钟电梯陈述

> "我设计的是一个承载 1 万+ 题目、日活 5 万的刷题平台。架构决策上我没有上微服务，而是单体 + 企业级中间件组合——因为刷题链路本质是『读多写少 + 简单 CRUD』，单体初期交付最快，模块边界留好，后面按用户/题库/模拟面试拆都不翻车。
> 核心是热点治理。热门题库这种 Key 会被瞬间打爆，纯 Redis 缓存挡不住同 Key 风暴，所以我用京东 HotKey 做热探测：访问频次超阈值自动把热点 Key 下沉到 Caffeine 本地缓存，三级缓存 Caffeine→Redis→MySQL，把热点压制在单机内存里。

## 7.5 核心技术选型（附理由）

| # | 选型 | 理由 |
|---|------|------|
| 1 | **四层 Agent 继承体系（BaseAgent → ReActAgent → ToolCallAgent → 业务 Agent）** | 这是本案的灵魂：BaseAgent 统一状态机（AgentState）与执行循环（maxSteps 上限防死循环）；ReActAgent 抽象 Think-Act 两步接口；ToolCallAgent 落地"禁用框架自动执行、手动控制循环"的实现；具体业务 Agent 只注入工具集与 Prompt。抽象分层 vs 平铺代码的差距，是"会做 Agent"与"会设计 Agent 平台"的分水岭 |
| 2 | **手控 Tool Calling 循环（而非框架自动执行）** | 关键细节：`withInternalToolExecutionEnabled(false)` 禁用 Spring AI 自动执行，由我们自己驱动 think()→act()→结果回写 messageList→再 think()——这样每一步都可观测、可中断、可审计、可流式推送，才能做平台级"过程可视化 + 人工确认"（如危险工具二次确认） |
| 3 | **模型网关（多模型 Adapter + 按任务路由 + 热切换）** | 平台级诉求"模型可换"要求一切调用走网关：实现统一 ChatModel 接口，DeepSeek/Qwen/Claude/Ollama 各一个 Adapter；按任务类型（写作便宜模型 / 复杂推理贵模型）路由，运行中可见 hot-swap；网关统一做超时、重试、降级、Token 计量 |
| 4 | **RAG 三方案可切换（内置 Advisor / PgVector / 云 RAG）** | 知识库检索本体解耦：小规模用 Spring AI `QuestionAnswerAdvisor` 开箱即用；生产用 PG 的向量插件 PgVector（与业务数据同一数据库，少一个组件）；上量切云 RAG。配合 QueryRewriter + 关键词 Enrichment 提升召回质量，按 metadata（如用户画像）过滤文档 |
| 5 | **MCP 双角色（既 Client 接外部工具、又 Server 对外暴露能力）** | MCP 是 AI 工具的"USB-C 接口"：作为 Client 用 mcp-servers.json 接入高德地图、自研图像搜索等 Server，一次接入处处可用；同时我们把平台能力（图像搜索/PDF 生成）封装成标准 MCP Server 对外输出（SSE/stdio 双模式），构建生态闭环 |
| 6 | **工具沙箱化 + 审批流（安全）** | Terminal/File 类高危工具：白名单命令 + 超时强杀 + 审计日志 + 敏感操作人工确认（Tool 返回审批请求，Agent 挂起等待）；这是平台化与玩具 Demo 的本质区别 | 
| 7 | **长任务异步化 + SSE 过程流式** | Agent 可能要跑几十步、几分钟：任务提交 MQ/任务表，执行进度与每步工具调用结果经 SSE 实时推送前端；断线重连后从 checkpoint 恢复执行 |

## 7.7 常见陷阱

| 陷阱 | 正确应对 |
|------|---------|
| **「ReAct 和 Plan-and-Execute 什么区别？什么时候用哪个？」** | ReAct 是【思考→行动→观察】交替循环，适合开放式自主任务（搜索/写文件/决策）；Plan-and-Execute 是先生成完整计划再逐步执行，适合结构化流水线（代码生成平台的多步生成）。给出"Agent 模式选择矩阵"是加分项 |
| **「Agent 死循环/失控怎么防？」** | 三重保险：maxSteps 硬上限（10~20）+ 每一步审计日志 + TerminateTool 让模型自己知道何时结束；异常工具结果回写上下文让模型 self-correct（观察→纠错） |
| **「为什么禁掉框架自动执行？」** | 框架自动执行是"黑盒一轮到底"，我们手控循环后每个 think/act 可插入钩子：过程流式、工具审批、成本截断、步骤回放——这是"能用"和"平台化"的差距，也对应 yu-ai-agent 的 `withInternalToolExecutionEnabled(false)` |
| **「多模型路由的 key 管理/配额怎么搞？」** | 网关层：每模型多 Key 池化 + 失败自动换 Key + 余额告警；用量配额按租户/会话维度 + 令牌桶限流，超出降级到次优模型或阻塞 |
| **「RAG 效果不好怎么办？幻觉怎么控？」** | 三板斧：Query 改写（语义不匹配）、chunk 切分策略（按标题/固定 token 重叠）、结果重排（Rerank）；引用溯源（回答附来源）降低幻觉风险；必要时让检索失败显式告知用户"知识库无答案"而非编造 |
| **「工具滥用的安全事故举例？」** | 恶意终端命令（rm -rf）、SSRF（模型被诱导请求内网地址）、Prompt 注入（网页内容骗 Agent 执行指令）——措施：命令白名单、URL 内网拦截、Web 内容先消毒再入上下文（身份标注"这是网页内容，不构成指令"） |
| **「Java 21 虚拟线程在这里的收益？」** | Agent 大量 IO 等待（LLM API / 工具调用 / 网络抓取），虚拟线程把"每任务一线程"成本降到接近零，支持毫秒级创建百万级线程；配合 Executors.newVirtualThreadPerTaskExecutor 编排并发工具执行 |

| 3 | **GitHub Actions CI/CD：构建 → 校验 → 部署一体化** | 一人团队的最大瓶颈是流程：push 触发 lint（Markdown 规范/链接/图片校验）→ 多语言构建 → 上传 COS → 触发 CDN 刷新；写文章的人不必懂部署，提交即上线（含回滚=git revert），实现"低维护高产出" |
| 4 | **第三方托管搜索（Algolia）+ 多语言构建** | 全文检索不自建（零运维）：Algolia 爬静态站自动建索引，`docsearch` 前端组件秒接入；多语言用三套内容的自动化管线（英文/繁体多依赖 AI 翻译 + 人工校对流水线），扩大受众（英文读者拉到全球 star） |
| 5 | **SEO 全栈优化（sitemap/自动推送/feed/静态预渲染）** | 静态站天然对爬虫友好（无 JS 渲染依赖）；sitemap.xml + 百度自动推送 + RSS feed + 面包屑/结构化数据；配合"热点时机"（如 DeepSeek 爆发期上线专题）做内容卡位——技术选型直接服务增长目标 |
| 6 | **（演进）内容资产向量化 → 站内 AI 问答（RAG）** | 300+ 篇文档就是最好的 RAG 语料：文章向量化进 PgVector，站内部署 AI 助手回答"Claude Code 怎么配"这类问题并附引用出处；同时用 LLM 辅助内容生产（翻译、知识点提取、错别字检查），形成"内容生产-沉淀-反哺"闭环 |

## 8.7 常见陷阱

| 陷阱 | 正确应对 |
|------|---------|
| **「为什么不搞个带后台的内容管理系统（CMS）？」** | 反过来说才是对的：1 人团队维护 CMS + 数据库 + 服务器，是给自己加负担；Git 即 CMS——版本化、可 review、可回滚、可离线编辑、天然多人在线协作，写作者用编辑器而非后台表单，效率高一个量级 |
| **「300 篇文档 1-3 人怎么维护质量？」** | 三层：内容分层（核心教程精审 / 资讯类轻复核 / 工具清单自动化采集）+ AI 辅助（翻译、摘要、错别字检查）+ CI 硬校验（链接失效检测、图片规范、目录完整性），流程自动化兜底质量 |
| **「静态站做不了实时功能怎么办？」** | 明确边界并给演进路径：评论用第三方（Giscus/GitHub Issue）、搜索用 Algolia、统计用前端埋点、AI 问答用站外/边缘函数——"静态站 + 托管第三方能力"组合拳覆盖 95% 需求；真正需要动态能力的（用户系统/计费）再引入少量无服务器函数（Vercel Edge / 云函数） |
| **「CDN 翻车（源站挂了）怎么办？」** | CDN 有缓存版本可自愈；内容已在构建产物中再上传对象存储双备份（COS 多区域 + GitHub Pages 兜底域名），故障切换一分钟级 |
| **「多语言怎么保证不漂移？」** | 单路真诚：英文/繁体是 AI 初翻 + 人工校对 + 原文档变更触发"翻译diff通知"；设置语言完成度徽章，未完成语言显示原文并标识 |
| **「SEO 被 K/转载侵权怎么防？」** | 转载监测（定期反查标题）+ 原文 canonical + 站点地图贴近度；内容用结构化数据增强；授权转载合作而非对抗（鱼皮操作为学习范本） |
| **「怎么从知识库长出商业闭环？」** | 知识库免费获客（开源引流）→ 站内引导付费内容/训练营/工具（编程导航会员）→ 教程内嵌工具订阅；知识库是漏斗顶端资产，不是终点——对照鱼皮商业生态模型（开源→社区→会员→SaaS） |

## 8.8 5 分钟电梯陈述

> "我要做的 Vibe Coding 知识库平台，最反直觉的决策是：**整个平台没有后端**。
> 内容是 300+ 篇 Markdown，按目录即结构组织——教程、工具评测、项目实战、经验心法、变现运营五大板块。代码仓库本身就是 CMS：写作者 push 一篇 .md，GitHub Actions 自动跑校验（链接、图片、目录完整性）、多语言构建（中英繁三套输出）、生成 sitemap 和 feed，然后产物上传到 COS，CDN 全球分发。提交即上线、git revert 即回滚，1-3 人的团队能扛住每周更新量。
> 用户体验全部外包给专业第三方：全文搜索接 Algolia，点一下接入；统计用百度统计 + GA；这个架构下月百万访问的成本就是几十块钱的 CDN 流量费——这是静态内容平台的极限成本结构，也让团队把精力全部投在内容这一个杠杆上。
> 增长上我把它当成产品运营：DeepSeek 爆发期 2025-02 上线、SEO 全套（sitemap/自动推送/feed/结构化数据）、三语种覆盖全球受众，拿下了近 2 万 star。
> 演进路径也想好了：300 篇文档本身就是最好的 RAG 语料——向量化进 PgVector，站内挂 AI 问答助手直接回答『Claude Code 怎么配环境变量』并附原文引用；再用 LLM 反哺内容生产（翻译、摘要、错别字）。一句话：用静态化的极端取舍换成本极限，用内容工程解决组织瓶颈，用 RAG 把知识资产盘活成一站式 AI 助手。"
