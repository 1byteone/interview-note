## Part 1: sql-mother — SQL 之母 (4,326⭐)

### Q1. 为什么用 sql.js/Wasm 在浏览器执行 SQL，不搭后端数据库？
> **架构设计 ⭐⭐⭐** — 核心权衡是"零后端、零部署"的教学场景。sql.js 是 SQLite C 代码通过 Emscripten 编译成 Wasm，浏览器内运行真实 SQL 引擎。价值：① 省去数据库服务、SQL 执行接口、判题服务；② 无网络延迟、无并发问题；③ Wasm 沙箱化运行。代价：内存数据库无法持久化、单机无高并发。类比 Java：**Wasm 内存 ≈ 堆外 DirectBuffer，必须手动管理**。
>
> **追问**：用户量变大后，如何平滑迁移到前后端分离？

### Q2. 判题机制为什么"比执行结果"而非"比 SQL 文本"？
> **架构设计 ⭐⭐⭐** — 比 SQL 文本会导致"写法不同但语义等价"的答案被误判。分别执行用户 SQL 和答案 SQL，对比列名+数据行，所有等价写法都判对。实现用 `JSON.stringify` 字符串比较，约 30 行代码。类比：**接口契约测试——关注输出而非内部实现**。每次切关卡重建内存数据库，零状态残留。
>
> **追问**：如何防止用户执行死循环或超大数据量的危险 SQL？

### Q3. 每关一个目录的设计好在哪？如何扩展到 50+ 关？
> **前端工程化 ⭐⭐** — "约定优于配置 + 内容与代码分离"。新增关卡 = 新增目录，零业务代码改动。README.md 同时是教程文档。扩展：动态 `import()` 按需加载、用户自定义关卡提交前做校验、量级上来后可抽成后端配置表。类比 Java：**模板数据与渲染逻辑解耦 + SPI 插件化扩展**。

## Part 2: sql-generator — SQL 生成器 (3,427⭐)

### Q4. JSON 模板 DSL + 递归展开引擎的整体设计？
> **架构设计 ⭐⭐⭐⭐** — 把"重复片段抽出复用"。`@ruleName(params)` 引用 SQL 模板，`#{var}` 参数占位符，`"main"` 入口。引擎约 180 行：`doGenerateSQL` → `generateSQL`（递归）→ `replaceParams` + `replaceSubSql`。同步构建调用树实现可视化。类比 Java：**Freemarker/Velocity 模板引擎 + 编译器语义展开**。哲学："重逻辑轻页面"——复杂度收敛在纯函数引擎，UI 只做展示。
>
> **追问**：模板出现循环引用（A调B、B调A）时如何检测和兜底？

### Q5. 嵌套调用 @a(xx = @b(yy = 1)) 为什么标准正则不能解决？
> **前端工程化 ⭐⭐⭐⭐** — 正则 `/@name\((.*?)\)/` 非贪婪匹配会在**第一个右括号**提前截断。本质：**括号配对不是正则文法能表达的**。解法："正则定位 + 手工配对"——正则找到 `@name(` 起始位，然后逐字符扫描用括号计数器找到真正闭合位置。类比 Java：**手写表达式解析器 / 栈做括号配对**——面试常考的"用栈做括号匹配"的实战版。

### Q6. 调用树可视化（InvokeTreeNode）怎么实现？
> **创意设计 ⭐⭐** — 递归展开时同步创建树节点，记录节点名、参数、替换前/后 SQL。前端用树控件渲染，点击节点可对比替换前后。类比 Java：**分布式追踪的 span 树 / Jaeger 调用谱系图**——在链路里埋点产出可视化依赖关系。

## Part 3: yuindex — 极客浏览器主页 (2,124⭐)

### Q7. 命令式插件架构（CommandType 协议）怎么设计？
> **架构设计 ⭐⭐⭐⭐** — 三模块：YuTerminal（UI）+ Executor（引擎）+ Commands（插件集）。每个命令实现统一协议：func 唯一标识、alias 别名、params/options 参数、subCommands 递归子命令、action 执行函数。用 getopts 标准化解析。类比 Java：**SPI + 策略模式 + 命令模式**——核心只做解析与调度，新命令注册即用。
>
> **追问**：两个插件注册相同 func 时冲突怎么处理？

### Q8. 浏览器内文件系统"扁平化存储 + 路径计算"怎么评价？
> **创意设计 ⭐⭐⭐** — 扁平化存储（Map + parentId）比树形存储简单得多：O(n) 读写、序列化简单、插入删除无递归。路径计算按需推导目录树。类比后端：**关系数据库"父子外键+递归查询" vs 嵌套文档**——扁平化更易索引和扩展。

### Q9. "search 程序员鱼皮 -f github" 从输入到开网页的完整流程？
> **前端工程化 ⭐⭐⭐** — ① 捕获回车输入；② getopts 解析 `{_:["程序员鱼皮"], from:"github"}`；③ 命令注册表匹配 searchCommand；④ 按 from 找搜索引擎 URL 模板，`encodeURIComponent` 编码后 `window.open`。解析与执行分离，新增搜索引擎只注册 URL 模板。类比：**Spring Cloud Gateway 按 predicate 路由到不同下游**。

## Part 4: yu-picture — 智能协同云图库 (1,033⭐)

### Q10. 传统三层 vs DDD 双版本架构对比？
> **架构设计 ⭐⭐⭐⭐** — 三层（Controller→Service→Mapper）简单直接，适合 CRUD。DDD 把核心业务下沉 domain 层：picture/space/user 三个聚合封装领域规则；application 做用例编排；interfaces 用 Assembler 转换防 DTO 泄露；infrastructure 隔离存储细节。收益：边界清晰、规则可单测、技术可替换。代价：样板代码多、需要建模功底。**取舍原则**：核心业务复杂才上 DDD。
>
> **追问**：空间配额扣减这类跨聚合一致性怎么保证？

### Q11. ShardingSphere 按 spaceId 动态分表的动机与坑？
> **架构设计 ⭐⭐⭐⭐⭐** — 动机：查询高度按"空间"维度，分表后单表数据量可控，同一空间查询路由到单张表。路由：SQL 解析→分片键计算→表名改写→执行。**五个坑**：① 跨空间聚合退化为全分片路由；② 自增主键冲突（换雪花 ID）；③ 再分片成本极高；④ 分布式事务复杂度上升；⑤ DDL 需对所有分片执行。
>
> **追问**：空间被删除后分片表怎么回收？跨分片 count/分页怎么做？

### Q12. WebSocket + Disruptor 无锁队列协同编辑？
> **性能优化 ⭐⭐⭐⭐⭐** — WebSocket 是接入层，高吞吐核心是 Disruptor 环形缓冲区（262,144 槽位）+ 无锁并发（CAS+内存屏障替代锁）。Disruptor 四个核心：**环形缓冲区、序列号、无锁、伪共享防护（cache-line 填充）**。类比 Java：Disruptor 是高频面试点，能讲清 ring buffer + 序列号 + 无锁 + 伪共享就是高分。
>
> **追问**：ring 写满时背压/丢弃策略怎么配？协同编辑如何保证事件顺序？

### Q13. 多级缓存 + 按色搜图 + 以图搜图的设计取舍？
> **性能优化 ⭐⭐⭐⭐** — 多级缓存：Caffeine L1（微秒）→ Redis L2（毫秒）→ MySQL L3，Cache-Aside + 短 TTL。按色搜图：RGB 欧氏距离，低维向量朴素检索，量小时讨巧。以图搜图：Jsoup 三步链式爬取，低成本 hack。演进：量大后升级为颜色直方图+倒排索引，以图搜图换 pHash 或深度学习特征向量。
>
> **追问**：缓存击穿怎么防（singleflight/布隆过滤器）？RGB 对"人眼感知相似"不准怎么改进？

## 使用建议

- **后端主战场**：Q10(DDD)、Q11(分表)、Q12(Disruptor) 必须优先过熟
- **差异化亮点**：Q1(Wasm)、Q5(嵌套括号)、Q9(命令引擎) 是"前端工程师做不到、你能讲透"的题
