# A 组 · AI 大模型基础（10 题）

### Q1：什么是大模型（LLM）？它和传统机器学习模型的核心区别是什么？
**参考回答：** 大语言模型是基于 Transformer 架构、以海量文本预训练的深度学习模型，核心能力是通过"预测下一个 token"学会语言理解和生成。和传统模型的核心区别有三点：① 通用性——传统模型是"任务专用"（一个分类器只能分一类），LLM 一个模型可做翻译、总结、问答、代码等；② 涌现能力——参数规模足够大后出现少样本学习、推理、思维链等小模型不具备的能力；③ 交互范式——通过自然语言 Prompt 驱动，而非固定的输入输出 schema。

**关键点解析：**
- **面试官意图**：JD 写"了解基础 ML/DL 理论"，考察你是否有底层认知，而非只会调 API。
- **怎么答**：先一句话下定义（Transformer + 预测下一个 token），再给"任务专用 vs 通用 + 涌现 + 提示词驱动"三点对比。
- **深挖方向**：追问"为什么能涌现"——可答"大模型在训练中学习到海量知识的统计规律，注意力机制让长程依赖建模成为可能"。

**结合项目：** 智颐养老里我用百度千帆大模型做体检报告语义分析，本质就是"通用模型 + 领域场景化 Prompt"，不用为每个科室单独训练分类器；灵犀写作里不同智能体共用一个大模型底座，靠不同的角色 Prompt 分化能力。

**常见扣分项：** 只答"很厉害的大模型"；把 GPT 和 Transformer 混为一谈；说不出"预测下一个 token"这个本质。

### Q2：主流的 OpenAI / 文心一言 / 通义千问大模型 API 调用流程是怎样的？
**参考回答：** 通用流程五步：① 申请 API Key 并配置鉴权（多数走 HTTP Bearer / 服务商自定义 Header）；② 构造请求体，核心字段是 model（模型名）、messages（消息数组，含 role: system/user/assistant）、temperature/top_p（采样参数）、stream（是否流式）；③ 发起 HTTP 调用（REST / OpenAI 兼容协议）；④ 解析响应——非流式拿 choices[0].message.content，流式按 SSE 逐块拼装 delta.content；⑤ 错误处理——限流 429、超时、鉴权 401，配合指数退避重试。

**关键点解析：**
- **面试官意图**：JD 明确要求"了解主流大模型 API 调用流程"，这是硬考核点，必须能讲出 messages 结构和流式。
- **怎么答**：按"鉴权 → 请求体 → 调用 → 解析 → 容错"五步讲，重点突出 messages 三元组和 stream 字段。
- **深挖方向**：追问"为什么通义/文心接口长得像 OpenAI"——因为各家都在做 OpenAI 兼容协议，迁移成本低。

**结合项目：** 实习中我按统一契约封装 AI 调用层，把百度千帆（智颐养老）和通义系模型（实习）统一成同一个接口，上层业务不感知厂商差异；SSE 流式在灵犀写作里前端直接对接 delta 增量渲染。

**常见扣分项：** 说不出 messages 里的 role；只会说"传个 key 就能调"；不知道 stream 参数的作用。

### Q3：Token 是什么？为什么说它是大模型的"计费单位"和"上下文窗口单位"？
**参考回答：** Token 是大模型处理文本的最小单元，不是单词也不是字符——英文约 1 token≈0.75 个单词，中文约 1 个汉字≈1~2 个 token。计费按输入+输出 token 总量；上下文窗口（context window）限制了一次能放进去的 token 数，超出会被截断或报错。控制 token 的核心手段：精简 Prompt、限制 max_tokens、缓存历史、摘要压缩。

**关键点解析：**
- **面试官意图**：JD 综合素质强调"成本意识"，HR/技术面都会问 token 与成本。
- **怎么答**：定义 + 中文/英文换算 + "计费与窗口双身份" + 四个控制手段。
- **深挖方向**：追问"长文档怎么塞进窗口"——分块 + 检索只取相关片段（即 RAG 的动机之一）。

**结合项目：** 简历自我评价提到"控制 AI 调用的 Token 消耗与响应延迟"——实习里我把系统 Prompt 从逐条拼接改为模板化精简，长对话只保留最近 N 轮 + 历史摘要，实测单会话 token 消耗降低明显。

**常见扣分项：** 说 token 就是"字"；不知道输出也要计费；没想过成本控制。

### Q4：什么是 Prompt 工程？写出一个好的 Prompt 通常包含哪些要素？
**参考回答：** Prompt 工程是通过设计输入文本引导大模型稳定输出符合预期内容的实践。一个好 Prompt 常包含：① 角色设定（你是资深 Java 工程师）；② 明确任务（请做 X）；③ 输入数据；④ 约束条件（不要编造、限定字数、只返回 JSON）；⑤ 输出格式（给出 schema 或示例）；⑥ 示例（few-shot，给 1~3 个输入输出对）。进阶技巧有思维链（Let's think step by step）、分隔符隔离上下文、负面指令（禁止…）。

**关键点解析：**
- **面试官意图**：JD 明确要求"掌握基础 Prompt 工程，能根据业务场景优化提示词"，必考题。
- **怎么答**：六要素顺序背出 + 给出一个"角色+任务+约束+格式"的现场示例，比空谈强很多。
- **深挖方向**：追问"为什么 few-shot 有用"——大模型具备上下文学习（in-context learning）能力，示例是最强的引导信号。

**结合项目：** 灵犀写作我封装了 Prompt 模板引擎，标题/大纲/正文三个智能体共用模板骨架、差异化填充角色与约束；结构化输出要求模型只返回 JSON，配合错误重试兜底。

**常见扣分项：** 只会说"写清楚点"；举不出具体 Prompt 例子；不知道 few-shot 和约束的作用。

### Q5：什么是 RAG（检索增强生成）？它解决什么问题？完整流程是什么？
**参考回答：** RAG = 检索增强生成，先从外部知识库检索相关内容，再把检索结果拼进 Prompt 让大模型基于它回答。解决三类问题：① 知识时效性（模型训练截止后的事实）；② 私有/领域知识（企业内部文档）；③ 幻觉（模型凭空编造）。流程五步：文档加载 → 解析预处理 → 文本分块（chunking）→ 向量化（Embedding）入库 → 查询时向量检索 Top-K → 拼 Prompt → 生成并给出引用来源。

**关键点解析：**
- **面试官意图**：JD 写"了解 RAG 检索增强生成技术者优先"，而且你有知识库实习经历，必问且会深挖。
- **怎么答**：动机（时效/私有/幻觉）→ 五步流程 → 强调"引用来源"是 RAG 相对裸调模型的关键差异。
- **深挖方向**：追问"检索不准怎么办"——分块策略、混合检索、重排（rerank）、阈值过滤（见 B 组）。

**结合项目：** 实习中我参与企业 RAG 知识库问答：负责 PDF/Markdown 预处理、文本分块、向量化入库和素材标准化；用 LangChain + LCEL 验证调用路径，补来源约束、结构化输出和兜底策略。

**常见扣分项：** 把 RAG 说成"把文档喂给模型"（那是微调/超长上下文）；流程漏掉分块或向量化任一步；说不出引用来源的意义。

### Q6：RAG 和微调（Fine-tuning）有什么区别？什么场景该选哪个？
**参考回答：** RAG 是"检索外挂知识 + 现场拼接"，不改模型参数；微调是"用领域数据继续训练模型权重"，改变模型行为。选型：① 知识型（文档、FAQ、私有资料、经常更新）→ RAG，成本低、可溯源、更新即时；② 风格/能力型（模仿某文风、固定输出结构、让模型学会特定任务格式）→ 微调；③ 多数场景两者可结合——微调定"人设/格式"，RAG 供"事实"。

**关键点解析：**
- **面试官意图****：考察你是否理解两种技术边界，能否在真实业务中做选型判断。
- **怎么答**：先给一句话对比（改不改参数），再给选型判据（知识 vs 能力、更新频率、可解释性），最后说"可组合"。
- **深挖方向**：追问"RAG 有什么缺陷"——检索质量决定上限、有检索延迟、知识冲突时可能仍幻觉。

**结合项目：** 实习的知识库问答选 RAG 因为资料是私有且频繁更新、需要引用来源；没有选微调是因为成本高且无法即时反映资料变化。

**常见扣分项：** 说"微调更高级所以更好"；不清楚微调能改什么（行为/风格）不能改什么（事实库）。

### Q7：文本分块（Chunking）有哪些策略？分块大小怎么定？
**参考回答：** 常见策略：① 固定长度分块（按 token 数切，带重叠 overlap 避免切断语义）；② 按结构分块（按 Markdown 标题/段落/PDF 章节切，语义完整性最好）；③ 语义分块（按语义边界切，效果好成本高）。分块大小权衡：块太小——上下文不足、检索片段零碎；块太大——向量语义稀释、混入无关内容、Token 成本高。一般中文场景 300~800 token 加 10~20% 重叠是常见起点，最终靠评测集调。

**关键点解析：**
- **面试官意图**：JD 有"数据整理"职责，分块质量直接影响检索效果，考察工程细节。
- **怎么答**：先给三种策略，重点讲"按结构切优先、固定长度兜底、必须有重叠"。
- **深挖方向**：追问"分块太差会怎样"——检索回不到正确片段 → 回答错误；这也是实习中我"检查分块质量、完成检索素材标准化"的意义。

**结合项目：** 实习中 PDF/Markdown 材料预处理我优先按文档标题层级切块，配合固定长度 + 重叠兜底，保证一个块尽量是一个完整知识点，并抽查样例格式与来源。

**常见扣分项：** 只提"按字数切"；不知道要重叠；不考虑块内语义完整性。

### Q8：什么是向量化 / Embedding？向量数据库解决什么问题？
**参考回答：** Embedding 是把文本（或其他模态）映射成高维稠密向量，语义相近的文本向量距离近（余弦相似度高）。向量数据库（如 ChromaDB、Milvus、FAISS、pgvector）解决的是"海量向量高效近邻检索"问题——用 ANN 索引（HNSW、IVF）替代全量暴力比对，支持千万级向量的毫秒级召回。RAG 里文本被 Embedding 模型向量化后入库，查询时把问题也向量化做 Top-K 相似检索。

**关键点解析：**
- **面试官意图**：JD 加分项写"熟悉向量数据库、LangChain、LlamaIndex"，是加分考核点。
- **怎么答**：Embedding=语义向量化；向量库=ANN 近邻检索 + 元数据过滤；一句话点出"语义检索 vs 关键词检索"的差异。
- **深挖方向**：追问"关键词 vs 向量检索各适合什么"——专有名词/精确 ID 用关键词（ES），语义泛化用向量，实际混合。

**结合项目：** 实习中文本分块后向量化入库，检索时先语义召回再叠加业务筛选；智颐养老的知识建议场景本质也是"高频命中 + 语义理解"。

**常见扣分项：** 把 Embedding 和词向量/One-Hot 混为一谈；说不清向量库和普通数据库的区别。

### Q9：什么是 AI Agent？它和"直接调大模型"有什么区别？工具调用（Function Calling）是什么？
**参考回答：** Agent = 大模型 + 规划（Planner）+ 工具（Tools）+ 记忆（Memory）+ 反馈循环（Loop）。区别：直接调模型是"一问一答"，Agent 是"模型自主决定调用什么工具、拆解步骤、根据工具返回结果继续行动直到完成目标"。Function Calling 是让模型输出一个结构化的"工具调用意图"（函数名+参数），由程序执行后把结果回填给模型继续推理——它是 Agent 能力落地的关键机制。

**关键点解析：**
- **面试官意图**：JD 加分项"Agent 实战经验"；简历写了 StateGraph 多智能体编排，必问。
- **怎么答**：先拆 Agent 五要素，再用"用户问天气 vs Agent 查天气"的对比讲清"谁在做决定"。
- **深挖方向**：追问"Agent 的核心难点"——工具选择准确性、错误恢复、无限循环、上下文爆炸。

**结合项目：** 灵犀写作的 StateGraph 工作流就是 Agent 思想：标题/大纲/正文是"规划节点"，配图服务是"工具"，任务状态是"记忆"，失败重试是"反馈循环"。

**常见扣分项：** 把 Agent 说成"会聊天的机器人"；不知道 Function Calling 是结构化输出的一种形式；讲不清"规划-执行-反馈"闭环。

### Q10：SSE（Server-Sent Events）是什么？和 WebSocket 有什么区别？为什么 AI 流式输出用 SSE？
**参考回答：** SSE 是浏览器通过 HTTP 建立的单向服务端推送协议，服务端可持续发送文本事件，前端用 EventSource API 接收。和 WebSocket 区别：① 单向 vs 双向；② 基于 HTTP 复用 vs 独立 TCP 长连接；③ SSE 自动重连、文本友好；WebSocket 支持二进制。AI 流式输出用 SSE 因为：只需服务端往客户端推 token，单向即可；基于 HTTP 兼容性好、无需额外握手协议、断线自动重连。

**关键点解析：**
- **面试官意图**：简历写了 SSE 流式输出，JD 有"AI 接口联调"，且这是 AI 应用的标志性技能，高频考点。
- **怎么答**：定义 + 与 WebSocket 三点对比 + "单向、HTTP、自动重连"三个用 SSE 的理由。
- **深挖方向**：追问"SSE 的坑"——连接数限制、代理缓冲、断线续传、心跳保活。

**结合项目：** 灵犀写作整合 SSE 实现毫秒级首字上屏；实习中基于 FastAPI 异步接口 + SSE 做逐 Token 展示、多会话访问和异常中断恢复。

**常见扣分项：** 说"SSE 是双向的"；不知道 EventSource 只能 GET 不能带 header（鉴权要 query 或 cookie）；分不清 SSE 和 WebSocket 适用场景。

# B 组 · AI 效果优化与落地（8 题）

### Q11：如何评估一个 RAG 问答系统的效果？有哪些关键指标？
**参考回答：** 分层评估：① 检索层——召回率（Top-K 内是否包含正确答案）、命中率、检索时延；② 生成层——回答准确率/正确率（人工或 LLM 打分）、引用正确率、幻觉率、拒答率；③ 体验层——首字时延、端到端时延、用户满意度。工程上要建"评测集"（问题 + 标准答案 + 对应知识片段），回归测试防止改了检索反而变差。

**关键点解析：**
- **面试官意图**：JD 有"数据整理、测试验证、效果优化"职责，简历写了 35% 提升，这里考你是否"有评估意识"。
- **怎么答**：检索/生成/体验三层指标 + 强调"评测集 + 回归测试"的工程闭环。
- **深挖方向**：追问"效果不好先查哪一层"——先用"是否检索到正确片段"定位问题在检索还是生成。

**结合项目：** 实习中"内部测试集验证召回效果提升约 35%"，就是先建固定测试集，统计 Top-K 命中率，再对比优化前后的数据，而不是凭感觉说"变好了"。

**常见扣分项：** 只会说"效果挺好的"；没有指标分层概念；不知道要控制变量。

### Q12：模型回答不准 / 产生幻觉（编造事实）怎么排查和兜底？
**参考回答：** 排查思路：① 定位在检索还是生成——打印检索片段看是否包含答案；② 看 Prompt 约束是否生效——是否明确"只能基于给定资料回答，资料中没有就说不知道"；③ 看分块质量——相关内容是否被切断或没被召回。兜底手段：来源约束（要求带引用编号）、结构化输出（固定字段含 source）、阈值过滤（相似度低于阈值拒答）、兜底策略（命中失败时返回"未找到"或转通用知识查询）。

**关键点解析：**

### Q20：缓存穿透、缓存击穿、缓存雪崩分别是什么？怎么解决？
**参考回答：** ① 穿透——查一个不存在的 key，缓存和 DB 都没有，请求直接打 DB。解决：缓存空值 + 短过期；布隆过滤器；参数校验。② 击穿——某个热点 key 过期瞬间大量并发打到 DB。解决：互斥锁重建缓存（setnx）；逻辑过期 + 后台线程异步更新；热点 key 永不过期。③ 雪崩——大量 key 同一时间失效或 Redis 宕机，DB 被压垮。解决：过期时间加随机值分散；多级缓存；Redis 高可用（哨兵/集群）+ 限流降级。

**关键点解析：**
- **面试官意图**：简历技能线明确写"熟悉缓存穿透与缓存雪崩等基本概念"，必考，且会问"你项目里怎么防的"。
- **怎么答**：三个概念 + 各自 2~3 个方案，讲清"穿透=查不存在、击穿=单个热点、雪崩=批量/整体"。
- **深挖方向**：追问"互斥锁重建缓存的坑"——要防死锁、防缓存击穿连锁，用 Redisson 锁 + 双检。

**结合项目：** 智颐养老早高峰 2000+ 并发查询健康建议，我用 Redis 多级缓存 + 热点保护；实习中 Redis 缓存场景同样考虑了三类风险。

**常见扣分项：** 三个概念混淆（尤其是击穿和雪崩）；方案说不全；不结合自己场景。

### Q21：什么是多级缓存？你项目里是怎么设计的？缓存和数据库一致性怎么保证？
**参考回答：** 多级缓存 = 本地缓存（Caffeine/Caffeine+内存）+ Redis 分布式缓存 + DB，逐级回源。访问流程：本地缓存 → 命中返回，未命中查 Redis → 未命中查 DB → 回填两级缓存。一致性方案：① 主动失效——写库后删缓存（Cache Aside），关键场景用"延迟双删"或"先删缓存再写库 + 延迟删除"；② 消息异步更新——写库后发 MQ 通知清缓存/重建；③ Canal 监听 binlog 同步（解耦但引入组件）。一致性要按业务容忍度选，热点读多写少场景 Cache Aside 足够。

**关键点解析：**
- **面试官意图**：简历写了"设计 Redis 多级缓存策略"，这是项目亮点，必深挖"为什么多级 + 怎么保一致"。
- **怎么答**：三级链路 + Cache Aside 为主，指出本地缓存解决"Redis 网络开销"、Redis 解决"本地多实例不一致"。
- **深挖方向**：追问"为什么是删缓存不是更新缓存"——更新有并发写覆盖旧值的风险，删除让下次读重建。

### Q22：什么是幂等性？接口幂等怎么设计？
**参考回答：** 幂等 = 同一个请求执行一次和多次结果一致。常见实现：① 唯一 ID + 去重表（每次请求带唯一标识，处理前查是否已处理，用唯一索引兜底）；② Redis setnx 占位（key=业务ID，设置成功才处理，过期时间防死锁）；③ 数据库乐观锁/版本号（更新时带版本）；④ 状态机（订单状态只允许正向流转，重复请求命中已处理状态直接返回）。要覆盖"重复提交、重试、消息重复消费"三种来源。

**关键点解析：**

- **深挖方向**：追问"setnx 幂等的坑"——要设过期时间防宕机死锁；要先查再写的竞态要靠唯一索引兜底。

**结合项目：** 实习中针对活动重复提交问题，用 Redis setnx 做请求幂等，配合 RocketMQ 异步处理，降低重复下单和超卖风险。

### Q23：Redisson 分布式锁的原理？看门狗、可重入、主从切换问题是什么？
**参考回答：** Redisson 基于 Redis 实现分布式锁：① 加锁——SET key value NX PX（key=锁名，value=线程唯一标识，过期时间防死锁）；② 看门狗——默认 leaseTime 30s，若业务未完成，后台线程每 10s 续期，防止业务没执行完锁就过期；③ 可重入——value 存线程标识 + 重入计数，同一线程可重入；④ 释放——Lua 脚本原子校验"是自己的锁才删除"，防止误删他人锁；⑤ 主从问题——主节点加锁后未同步就宕机，从节点升主会丢锁，严格场景用 RedLock 或 Zookeeper/ETCD。

**关键点解析：**
- **面试官意图**：简历写了 Redisson，且锁在"幂等、防超卖、缓存重建"中都用，深挖点。
- **怎么答**：加锁/续期/重入/释放四步 + 主动提主从问题展示深度。
- **深攻方向**：追问"误删锁怎么发生"——业务超时锁过期，另一线程拿到锁，原线程回来删掉了别人的锁，所以删除前必须校验标识（Lua 原子操作）。

**结合项目：** 实习中防超卖/幂等用 Redisson 锁保证同一商品/同一订单的并发操作互斥；智颐养老热点缓存重建也考虑过互斥锁方案。

**常见扣分项：** 只会"setnx"三个字母；不知道看门狗；不知道要校验标识防误删。

### Q24：RocketMQ 的核心概念？你们用消息队列解决了什么问题？
**参考回答：** 核心概念：Producer/Consumer（生产消费）、Topic（主题）、MessageQueue（队列，并行与有序的最小单位）、Broker（存储转发）、ConsumerGroup（消费组，组内竞争、组间广播）、Tag（二级过滤）、Offset（消费位点）。解决的问题：① 异步解耦——下单后发消息，短信/积分/库存扣减异步执行，主流程只回成功；② 削峰填谷——大促瞬间请求先进 MQ，下游按能力消费；③ 可靠投递——消息持久化 + 重试 + 死信。

**关键点解析：**
- **面试官意图**：简历实习职责写"使用 Redis、Redisson 和 RocketMQ 完成异步处理、失败重试与异常补偿"，MQ 必考。
- **怎么答**：概念挑核心几个讲 + 落到"你们解决什么"（异步、削峰、补偿）。
- **深挖方向**：追问"消息不丢"——生产端同步发送+重试，Broker 持久化，消费端手动 ack + 消费失败重投。

### Q25：消息消费失败怎么办？死信队列、失败重试、异常补偿分别是什么？

**结合项目：** 实习中针对"同步写库压力"用 MQ 异步化后，配套了失败重试（瞬时错误自动重试）和异常补偿（对账/补单），并通过并发压测验证。

### Q28：ThreadPoolTaskExecutor 和 @Async 有哪些容易踩的坑？
**参考回答：** 常见坑：① 不自定义线程池——Spring 默认用 SimpleAsyncTaskExecutor，每个任务新建线程、不复用，高并发直接线程爆炸，必须显式声明 ThreadPoolTaskExecutor Bean；② 线程复用 + ThreadLocal 脏数据——异步线程池复用线程，ThreadLocal 不清理会串数据（结合我们 ThreadLocal 上下文要 remove）；③ @Async 异常丢失——默认由线程池吞掉（SimpleAsyncTaskExecutor 会打日志但调用方感知不到），要配 AsyncUncaughtExceptionHandler；④ @Async 和 @Transactional 同方法失效——自调用（this.xxx()）不走代理，异步/事务都不生效，必须注入代理对象调用；⑤ 线程池被其他模块覆盖——要命名 Bean 避免冲突。

**关键点解析：**
- **面试官意图**：这是从"会背参数"到"真用过"的分水岭，简历写 @Async 一定会被追问坑。

- **深挖方向**：追问"自调用为什么失效"——Spring 异步/事务基于 AOP 代理，this 调用不经过代理。

**结合项目：** 灵犀写作的异步任务体系里，我显式配置了 ThreadPoolTaskExecutor，任务状态 tracking 记录每个任务的执行结果，异常由统一处理器记录到状态表——相当于天然解决了"异常丢失"问题。

**常见扣分项：** 说"我用了 @Async 没问题"；不知道自调用失效；不处理异常。

### Q30：SSE 在高并发下有哪些实现细节和坑？（SseEmitter / FastAPI StreamingResponse）

### Q31：ThreadLocal 是什么？你项目里用 ThreadLocal 存登录用户，怎么防内存泄漏？
**参考回答：** ThreadLocal 是线程局部变量，每个线程有独立的副本，通过 ThreadLocalMap 存储（key 是 ThreadLocal 弱引用）。常见用法：传递请求级上下文（登录用户、traceId）。内存泄漏原因：ThreadLocalMap 的 value 是强引用，若 key 的弱引用被 GC 回收而线程还活着（线程池复用线程），value 永远无法被访问但也不释放。防泄漏：① 使用后必须 remove()（finally 块中）；② 用 ThreadLocal.withInitial 或自定义包装类统一清理；③ 拦截器 afterCompletion 统一 remove。

**关键点解析：**
- **面试官意图**：简历写"拦截器 + ThreadLocal 实现无感登录上下文传递，零内存泄漏"，这是深挖点。
- **怎么答**：定义 + 存储结构 + 泄漏成因（线程池复用 + 强引用 value）+ remove 三招。
- **深挖方向**：追问"为什么线程池下特别危险"——线程复用意味着 ThreadLocal 数据会残留给下一个任务，既泄漏又串数据。

**结合项目：** 智颐养老统一鉴权：拦截器解析微信小程序 token → 存 ThreadLocal → 业务里取用户上下文 → 请求结束 finally remove，支撑日均 2000+ 次访问稳定运行。

**常见扣分项：** 只知道"存一下取一下"；不知道弱引用与泄漏关系；不用 remove。

### Q32：华为云 IoTDA 对接怎么做的？增量同步如何保证数据一致性？
**参考回答：** 对接要点：① 鉴权——IoTDA 用 AK/SK 签名或设备接入凭证；② 拉取数据——调用平台接口（分页）获取产品、设备列表；③ 增量同步——记录同步游标（lastSyncTime / 上次设备 ID），只拉取更新数据；④ 异步线程池——拉取+落库是 IO 密集，用线程池并发处理提升吞吐；⑤ 一致性保障——按"设备-位置"绑定关系做 upsert（存在更新、不存在插入）；⑥ 防重防丢——本地记录同步批次 + 幂等写入；⑦ 失败处理——单设备失败重试，整批失败记录待重跑。

- **深挖方向**：追问"为什么从 3 分钟到 10 秒"——改全量拉取为增量 + 并发，瓶颈在网络往返和串行写库。

**结合项目：** 智颐养老 IoT 模块：华为云 IoTDA 对接 + 异步线程池增量同步 + "设备-位置"绑定一致性，列表同步 3min→10s，支撑 500+ 设备实时监控。

**常见扣分项：** 只讲"调接口拿数据"；没有增量与一致性概念；说不出性能优化依据。

### Q34：多级缓存的 Key 怎么设计？缓存与数据库数据不一致怎么处理？
**参考回答：** Key 设计规范：业务前缀 + 维度 + 唯一标识，如 `health:suggestion:{userId}:{reportId}`；多级缓存 Key 前缀统一，本地缓存和 Redis 用不同前缀区分（如 `L1:`、`L2:`）。一致性处理（Cache Aside）：① 读——缓存未命中查 DB 后回填；② 写——先更新 DB，再删除缓存（不是更新缓存），下次读重建；③ 高一致性场景用"延迟双删"或"先删缓存再写库 + 延迟删除"；④ 批量/低频更新可用消息异步删缓存。评估：健康建议是"读多写少 + 允许秒级短暂不一致"，Cache Aside 足够。

**结合项目：** 智颐养老健康建议缓存：读多写少场景，Cache Aside 模式 + 按报告版本号失效，保证早高峰命中的同时不一致窗口可控。

**常见扣分项：** 说不清"删缓存 vs 更新缓存"；没有一致性方案。

### Q36：养老系统的整体架构是什么？微信小程序的"无感登录"是怎么实现的？

- **深挖方向**：追问"为什么不用 session"——小程序端无 cookie 环境，自定义 token/JWT 更适合跨端。

**结合项目：** 智颐养老统一鉴权：拦截器 + ThreadLocal 实现无感登录与上下文传递，零内存泄漏，支撑日均 2000+ 次访问。

**常见扣分项：** 说不清项目整体结构；鉴权只说"存了个 token"；不知道 ThreadLocal 清理。

### Q37：IoT 设备同步怎么处理增量、去重和失败重试？
**参考回答：** 增量：记录游标（同步时间/自增 ID/分页 marker），只拉增量。去重：以平台设备唯一 ID 为主键做 upsert（INSERT ... ON DUPLICATE KEY UPDATE），天然幂等，重复拉取不产生脏数据。失败重试：单设备失败记录错误重试几次，批量失败标记批次状态可重跑；同步任务本身可被定时任务触发（全量兜底 + 增量高频）。性能：拉取与落库解耦，拉取线程 + 消费线程（线程池），DB 批量插入。

**关键点解析：**
- **面试官意图**：IoT 是养老项目第二亮点（3min→10s），会问数据可靠性细节。
- **怎么答**：增量游标 + upsert 幂等 + 分级重试 + 定时兜底四件套。

**常见扣分项：** 没有去重幂等概念；只做全量同步没有增量；失败直接丢。

### Q38：灵犀写作为什么用 StateGraph 工作流引擎而不是线性调用多个模型？
**参考回答：** 线性调用问题：① 各步骤强耦合、串行，改动一处要动整条链；② 无法表达"并行"（如大纲完成后正文和配图并行）、"条件分支"（根据大纲长度选择不同策略）、"失败回退"；③ 不可视化、不可观测。StateGraph 把任务建模成"状态节点 + 边（条件转移）"，每个智能体是一个节点，节点间显式定义流转条件：串行（标题→大纲→正文）、并行（正文∥配图）、失败重试（节点失败回退到重试节点）。收益：新增一种生成模式只需新增节点和边，可扩展性大幅提升。

**关键点解析：**
- **面试官意图**：这是灵犀写作的技术核心亮点，考察你是否真的理解"为什么用工作流而不是 if-else 串调用"。
- **怎么答**：线性调用的三个痛点 → StateGraph 的节点/边建模 → 串并行/分支/重试举例。
- **深挖方向**：追问"和 LangGraph 的关系"——StateGraph 借鉴图编排思想，与 LangGraph 同模式，简历写的是自研版本。

**结合项目：** 灵犀写作：标题生成、大纲构建、正文撰写等多智能体串行/并行灵活编排，新增生成模式仅需配置新节点。

**常见扣分项：** 说不清"为什么不用线性"；没有并行/分支/回退的例子；把 StateGraph 说成玄学。

### Q39：多智能体编排里，各智能体之间的上下文是怎么传递的？并行怎么保证互不干扰？
**参考回答：** 上下文传递：① 共享状态对象（State）——所有节点读写同一个结构化 State（如 {title, outline, content, images, taskId}），节点只更新自己负责的字段；② 显式依赖——下游节点消费上游节点的输出字段，通过 State 的字段级更新保证顺序；③ 并行安全——并行节点只读写各自独立的字段（如"正文"节点与"配图"节点互不写对方字段），避免共享可变字段的竞争；④ 失败隔离——单节点失败只回退该节点，不影响其他已完成节点。

**关键点解析：**
- **面试官意图**：简历写了"串行/并行灵活编排"，面试官会追问"怎么并行的、状态怎么共享"。
- **怎么答**：共享 State + 字段级隔离 + 显式依赖三点，说明"并行安全靠字段隔离"。
- **深挖方向**：追问"配图和正文并行但正文要引用配图怎么办"——设计成大纲→(正文∥配图)→汇总节点再合并。

**结合项目：** 灵犀写作的 StateGraph 状态对象承载各节点产出，并行节点各写各的字段，汇总节点合并。

**常见扣分项：** 只有"一个 List 存所有结果"；没有字段隔离意识；说不清依赖关系。

### Q40：文章生成任务的状态机是怎么设计的？用户怎么知道任务进度？
**参考回答：** 状态机：PENDING（提交）→ RUNNING（执行中，含子阶段 progress）→ SUCCESS（成功，存结果）或 FAILED（失败，存 errorMsg）→ 支持 RETRY（失败重试）/ CANCEL。用户感知：① 前端提交任务拿到 taskId → 轮询（或 SSE）查状态；② 返回 progress 和当前阶段文案（"正在生成大纲 60%"）；③ 成功返回文章详情页，失败返回可重试按钮；④ 中断恢复——任务表里未完成的任务重启后标记失败或重跑。

**关键点解析：**
- **面试官意图**：简历"任务状态 tracking 机制"的直接体现，考察异步任务的完整闭环。
- **怎么答**：状态枚举 + 前端轮询交互 + 失败恢复，讲"可追踪、可重试、可恢复"。
- **深挖方向**：追问"进度怎么算"——按智能体阶段数（如 5 个节点各 20%）或按输出长度估算。

**结合项目：** 灵犀写作异步任务体系 + 任务状态 tracking + 进度管理 + 结果回调。

**常见扣分项：** 没有状态字段；前端拿不到进度；失败任务不可重试。

### Q41：SSE 前端怎么对接？断线重连、心跳怎么处理？
**参考回答：** 前端用 EventSource API：`new EventSource('/api/article/stream?taskId=xx')`，监听 message（数据）/ open（连接建立）/ error（异常）。断线重连：EventSource 默认自动重连（浏览器自带），但业务要处理——重连后由后端用 taskId 恢复未输出完的流（带断点），或前端提示重新生成；手动重连可 close 后重建。心跳：后端定期发注释行（`:\n\n` 或 `event: ping`）维持连接，防代理超时；前端收到 ping 重置超时计时。自定义事件：后端可发 `event: title` / `event: content` 区分类型，前端 addEventListener 分别处理。注意 EventSource 只能 GET，鉴权放 query/cookie。

**关键点解析：**
- **面试官意图**：简历写"SSE 流式输出 + 前端对接"，前端交互细节是加分深挖点。
- **怎么答**：EventSource 用法 + 自动重连 vs 业务断点 + 心跳 + 自定义事件四块。
- **深挖方向**：追问"为什么不用 fetch + ReadableStream"——EventSource 更简单但有局限（GET/无自定义 header），fetch 流可控性更强。

**结合项目：** 灵犀写作 SSE 对接前端，首字毫秒级上屏；实习中完成前后端验证，支持逐 Token 展示、多会话访问和异常中断恢复。

**常见扣分项：** 不知道 EventSource 自动重连；不做心跳；鉴权放 header 结果被浏览器限制。

### Q42：StructuredOutputConverter / 结构化输出是怎么保证大模型返回稳定 JSON 的？
**参考回答：** 思路：① Prompt 明确要求只输出 JSON 并给 schema 示例；② 用框架的结构化输出能力（LangChain with_structured_output / Spring AI StructuredOutputConverter）——它会自动把 schema 注入 Prompt 并解析响应；③ 关键兜底——大模型偶发返回非 JSON（带解释文字、截断、JSON 转义错误），要：先做清洗（截取首个 { 到最后一个 }），再解析失败重试（重新调用 1~2 次，可附错误信息让模型修正）；④ 解析层封装——统一 Converter，把成功/失败、重试、降级（返回默认结构）收敛在一处。

**关键点解析：**
- **面试官意图**：简历明确写了 StructuredOutputConverter，考察"结构化输出的可靠性工程"。
- **怎么答**：Prompt schema + 框架工具 + 清洗重试兜底三层，突出"不能假设模型永远听话"。
- **深挖方向**：追问"重试会重复计费吗"——会，所以重试次数限制 + 用上次错误提示让模型修正，比盲目重试高效。

**结合项目：** 灵犀写作统一大模型输出格式（标题/大纲/正文/配图结构化），保证 99%+ 生成成功率。

**常见扣分项：** 只会"让模型输出 JSON"；没有解析兜底；不知道重试修正技巧。

### Q43：策略模式 + 多源配图的降级切换是怎么设计的？

### Q44：两个项目技术选型对比：Spring Boot 2.7 vs 3.0、MyBatis-Plus vs MyBatis Flex、LangChain vs Spring AI，你怎么选？

### Q46：慢 SQL 怎么优化？执行计划（EXPLAIN）怎么看？

### Q49：实习/项目里遇到的最大挑战是什么？你是怎么解决的？（行为面）
**参考回答：** 建议讲"多智能体编排"或"SSE 高并发流式"或"召回提升 35%"任一个，用 STAR 结构：S（背景）——灵犀写作长文生成串行耗时、体验差；T（任务）——要把生成做成可编排、可流式、高可用的工作流；A（行动）——调研后引入 StateGraph 建模多智能体、配置线程池 + 任务状态 tracking、整合 SSE 并做异常恢复；R（结果）——首字毫秒级上屏、吞吐提升 50%、99%+ 成功率。强调"先调研选型 → 小步验证 → 迭代优化 → 数据验证"的解决问题路径。

**关键点解析：**
- **面试官意图**：几乎必问的行为面问题，考察真实经历、解决问题能力和表达结构。
- **怎么答**：STAR 结构，行动要有"调研/选型/验证"过程，结果要有数字。
- **深挖方向**：追问"如果重来一次哪里会改进"——答"更早做基准评测、SSE 连接管理更早关注"等，体现复盘能力。

**结合项目：** 可讲灵犀写作（个人主导，最能体现独立能力）或实习（体现团队协作与稳定性）。

**常见扣分项：** 没有结构流水账；功劳全在自己或全在别人；结果没有量化。

### Q50：你为什么选择 AI 应用开发方向？你的职业规划是什么？为什么能长期实习？
**参考回答：** 为什么选 AI 应用：① 价值感——AI 应用把大模型能力落到真实业务（知识库、智能写作、健康服务），看得见用户价值；② 技术契合——我有 Java 后端工程能力 + AI 实战（RAG/Agent/SSE），正好是"懂业务、能落地的 AI 工程师"的定位；③ 趋势——AI 应用是持续增长的赛道，且更新快适合爱钻研的性格。职业规划：短期——在实习中完整走通"需求→开发→联调→测试→上线"闭环，夯实 AI 应用落地能力；中期——成长为能独立负责 AI 功能模块、能选型能优化效果的全栈 AI 应用工程师；长期——深耕特定行业（知识库/Agent 方向）的工程专家。长期实习理由：在校课程相对灵活、可安排充足时间；且 AI 应用项目周期长，希望能完整经历从需求到上线的全过程。

**关键点解析：**
- **面试官意图**：JD 最后强调"愿意深耕 AI 应用领域、长期实习者优先"，这题决定"稳定性与意愿"评分。
- **怎么答**：兴趣（真实）+ 能力匹配（Java+AI 组合）+ 规划（短期落地/中期独立/长期深耕）+ 长期实习承诺，逻辑自洽。
- **深挖方向**：追问"Java 和 Python 你更倾向哪个"——答"Java 做后端工程、Python 做 AI 原型，两者都会，按项目选"，不要贬低任何一方。

**结合项目：** 三个经历正好构成"工程（养老）→ AI 落地（实习）→ 全栈 AI 创作（灵犀）"的成长主线，非常契合 JD 画像。

**常见扣分项：** 只说"因为 AI 火"；规划空洞；对"长期实习"含糊其辞。
