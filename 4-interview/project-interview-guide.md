## 1.2 完整项目介绍

### 项目背景

这个项目是我大学期间投入精力最大的一个实训项目。起因很简单：我学了一堆分布式的技术栈——Spring Cloud Alibaba、Redis、RocketMQ、Elasticsearch，但没有一个完整项目把它们串起来。于是我决定做一个"麻雀虽小五脏俱全"的电商平台，真正跑通微服务全链路。

项目定位是面向百万用户级交易场景，核心涉及商品、订单、用户、支付、搜索等 8 个微服务模块。技术选型上采用 Spring Boot 3 + Spring Cloud Alibaba 全家桶：Nacos 做服务注册发现和配置中心，Gateway 做统一路由和鉴权，Sentinel 做流量控制和熔断降级，OpenFeign 做服务间远程调用。数据层用 MySQL 8.0 做主存储，Redis/Redisson 做缓存和分布式锁，RocketMQ 做异步消息解耦，Elasticsearch 8 做全文检索，Elastic-Job 做定时任务调度，Seata 做分布式事务。

整个项目我主导了核心后端架构设计和关键模块实现，包括秒杀链路、搜索/RAG 双检索体系、分布式一致性保障和团队研发规范建立。

### 核心技术实现

**第一块：秒杀链路——这是面试最常被问的。**

秒杀场景的核心矛盾是：瞬时高并发请求 + 库存有限 + 不能超卖。我的方案是三层防护：

第一层是 Redis 预扣库存。活动开始前把库存从 MySQL 加载到 Redis，用 Lua 脚本原子执行"判断-扣减"，直接在内存层拦截绝大部分请求。这里有一个关键细节：Lua 脚本必须保证原子性，我最初用的是两条 Redis 命令分开执行，压测发现并发下会超卖，改成 Lua 脚本后问题解决。

第二层是 Redisson 可重入锁。当同一用户尝试重复下单时，用 Redisson 的 RLock 加锁，锁的粒度是 userId + productId，既防止了重复下单，又不会过度串行化。锁的超时时间我设了 5 秒，用看门狗机制自动续期，避免业务没执行完锁就过期的问题。

第三层是 RocketMQ 异步落库。用户下单成功后，不是直接写 MySQL，而是发一条延迟消息到 RocketMQ，30 分钟后自动检查支付状态，未支付则取消订单、回滚库存。这层异步解耦把数据库写入压力从同步降到了异步，吞吐量相比原生乐观锁方案提升了 5 倍。

还有一个兜底机制：用 Elastic-Job 做定时校对任务，每 10 分钟跑一次 Redis 和 MySQL 的库存对账，发现不一致就自动补偿。这保证了即使 Redis 宕机恢复后，库存数据也能最终一致。

**第二块：搜索检索双体系——这是技术亮点。**

项目的商品搜索我设计了两套检索方式：

关键词检索基于 Elasticsearch 8 + IK 中文分词器。我配置了 ik_max_word 模式做索引，ik_smart 模式做搜索，支持多条件筛选（分类、价格区间、库存状态）和权重排序（标题匹配 > 描述匹配 > 销量）。商品搜索响应从 MySQL 的 2 秒降到了 ES 的 20 毫秒以内。

语义检索我独立搭建了一个 RAG 微服务。商品详情和用户评论经过文本清洗、分块后，用 Embedding 模型向量化存入 RedisStack 的向量检索能力（基于 RediSearch 的 VECTOR 类型）。搜索时先做余弦相似度召回，再用 MMR（Maximal Marginal Relevance）去重排序，避免返回重复或高度相似的商品。语义召回准确率相比纯关键词提升了 35%，而幻觉率——就是返回不相关商品的比例——降低了 90%。

两套检索通过一个搜索路由层统一对外暴露 API，前端可以根据场景选择"关键词搜索"或"智能推荐"，后端也可以做混合排序。

**第三块：分布式一致性——这是工程深度。**

微服务架构下最头疼的问题之一是跨服务数据一致性。我用了三种机制配合：

一是 Seata AT 模式处理核心事务。比如创建订单需要同时扣库存、扣余额、创建支付记录，这三个操作分散在不同微服务的数据库里。Seata AT 通过全局事务协调器 + undo log 实现分布式事务的 ACID 特性。AT 模式的优点是业务代码无侵入，缺点是性能开销，所以只用在核心交易链路上。

二是 RocketMQ 事务消息处理非核心但必须最终一致的场景。比如订单创建后需要同步积分、发送通知、更新统计，这些用事务消息保证"要么都发，要么都不发"。配合本地消息表 + 定时扫描，实现了最终一致性。

三是重试 + 死信队列兜底。MQ 消费失败自动重试 3 次，超过次数进死信队列，由人工或告警处理。这个机制把故障发现时间从"用户投诉"缩短到了"实时监控"。

### 团队协作与规范

除了技术实现，我还负责建立了团队研发规范。包括：统一建表规范（字段命名、索引命名、注释规范）、SQL Review 流程（上线前必须走 EXPLAIN 检查）、Git 分支策略（feature/develop/master 三分支模型 + PR 必须至少一人 Review）、接口文档规范（统一用 Knife4j 生成 Swagger 文档）。这些规范推行后，联调 Bug 率下降了 60%，数据库压力降低了 70%。

### 成果

最终项目通过 Docker 单机集群压测，验证了万级并发下的稳定运行。秒杀链路 QPS 达到 5000+，搜索响应 20ms 以内，跨服务事务成功率 99.9%。

## 1.3 高频追问与回答

**Q: 为什么选 Seata AT 而不是 TCC？**
AT 模式对业务代码零侵入，适合我们项目阶段快、团队对分布式事务经验不深的情况。TCC 虽然性能更好，但需要每个参与者手写 Try/Confirm/Cancel 三个接口，开发成本高。AT 模式通过 undo log 自动回滚，我们只需要在方法上加 `@GlobalTransactional` 注解。未来如果性能瓶颈出现，核心链路可以升级为 TCC。

**Q: Redis 预扣库存如果宕机了怎么办？**
有三层保障。第一，Redis 启用 AOF 持久化 + 主从同步，宕机后自动恢复。第二，Elastic-Job 定时对账任务每 10 分钟校验 Redis 和 MySQL 库存一致性，发现差异自动补偿。第三，降级方案：Redis 完全不可用时，流量直接走 MySQL 库存表的悲观锁扣减，性能会下降但不会超卖。

**Q: 为什么不用 Redisson 分布式锁直接做库存扣减？**
Redisson 锁是单个请求级别的，高并发下大量请求排队等锁，吞吐量上不去。预扣库存方案把库存判断从锁内移到了 Lua 脚本的原子操作里，减少了锁持有时间。我测试过，纯 Redisson 锁方案 QPS 约 1000，预扣 + Lua 方案 QPS 可以到 5000。

**Q: Seata AT 模式的性能开销怎么优化？**
核心优化三点。第一，缩小事务范围，只把最关键的写操作放进全局事务，读操作和非核心操作剥离。第二，数据源代理的连接池配置调优。第三，AT 模式的 undo log 表做定期清理，避免历史数据堆积影响性能。

**Q: RAG 检索的幻觉率怎么降低 90% 的？**
三个手段。第一，严格的来源约束——检索结果必须关联到具体的商品 ID 和信息源，不允许"自由发挥"。第二，Prompt 中加入"如果没有找到相关信息，请明确说明"的指令。第三，用 Pydantic 结构化输出约束返回格式，字段不全或不符合 schema 的直接拦截重试。

1. **秒杀全链路设计**：Redis 预扣 + Lua + Redisson + RocketMQ 延迟消息 + 定时对账，QPS 5000+，吞吐量比乐观锁方案提升 5 倍

# 二、农业知识库问答智能体

> **角色**: 独立完成 | **时间**: 2026.01 - 2026.04

## 2.1 一句话定位

一个独立开发的农业病害问答 Agent，从 PDF 农技手册的文档预处理、向量检索到 FastAPI 接口闭环，实现了"私有知识库优先、通用知识兜底"的智能问答系统，解决了农技手册不可读和 AI 幻觉两大痛点。

---

## 2.2 完整项目介绍

### 项目背景

这个项目的灵感来自一个真实需求：农村地区有很多纸质的农业病害防治手册，农民遇到问题时翻书效率极低，而通用大模型对地方性、专业性的农技知识回答又不够准确，经常出现"幻觉"——也就是一本正经地胡说八道。

所以我决定做一个农业病害问答 Agent，把农技手册电子化后导入私有知识库，让 AI 先从这些权威资料里找答案，找不到时再用通用农业知识兜底。这样既保证了专业性，又不会因为知识库覆盖不全而回答不了问题。

整个项目我一个人从头到尾独立完成，从 PDF 文档预处理、文本分块、向量化入库，到 LangChain Agent 工具调度、会话记忆管理、FastAPI SSE 流式接口，全部自己搞定。

### 技术架构

系统分为四层：

**文档处理层**：PDF 农技手册经过文本提取、清洗（去掉页眉页脚、水印）、按语义分块（chunk size 512，overlap 50），然后用 Embedding 模型向量化，存入向量数据库。分块策略我做了多次实验——按固定长度分块简单但容易切断语义，按段落分块保留语义但 chunk 大小不均。最终我用 LangChain 的 RecursiveCharacterTextSplitter，先按段落切，再用递归分隔符（`\n\n` → `\n` → ` `）保证每个 chunk 在 512 token 以内。

**检索调度层**：这是系统的核心。我基于 LangChain Agent + LCEL（LangChain Expression Language）封装了两套工具——私有 PDF 检索工具和通用农业知识查询工具。调度策略是"知识库优先、无匹配兜底"：先用私有知识库检索，如果返回结果的相似度得分低于阈值（我设的 0.6），再切换到通用知识工具。

这里有一个关键的设计决策：为什么不用 Rerank 而是用相似度阈值？因为农业问答的场景比较特殊——农民问的问题往往很具体（"我家番茄叶子发黄怎么办"），如果私有库里有相关信息，相似度得分通常会很高（0.8+）；如果没找到，得分往往低于 0.4。所以用阈值做路由比 Rerank 更简单高效，减少了不必要的计算开销。

**会话管理层**：使用 LangChain 的 InMemorySaver 做多轮对话记忆，用 `thread_id` 隔离不同用户的上下文。这里有个坑：InMemorySaver 是内存存储，重启就丢。在生产环境应该换 PostgreSQL 或 Redis 持久化，但作为实验项目，InMemory 够用。我用 thread_id 做隔离是因为它天然适配 FastAPI 的异步请求模型——每个请求带上 thread_id，服务端就能找到对应的会话历史。

**接口层**：FastAPI + SSE（Server-Sent Events）流式输出。这个是用户体验的关键——农民用手机问问题，如果要等 5 秒才能看到回答，体验很差。SSE 让 AI 的回答逐 Token 返回，前端可以做打字机效果，首字延迟控制在 200ms 以内。FastAPI 的 `astream` 方法原生支持 async generator，配合 `StreamingResponse` 就能实现 SSE。

### 关键技术细节

**工具调度的实现**：LangChain Agent 的核心是一个 ReAct（Reasoning + Acting）循环。Agent 收到用户问题后，先"思考"应该用哪个工具，然后"执行"工具调用，拿到结果后再"思考"是否需要更多信息。我在 Prompt 里明确告诉 Agent："你是一个农业病害防治助手，先查私有知识库，查不到再用通用知识。"

**结构化输出**：为了防止 AI 返回格式混乱的答案，我用 Pydantic 定义了输出 schema——必须包含作物名称、病害名称、风险等级、防治方案、信息来源。LLM 返回的自然语言经过 StructuredOutputConverter 转换为结构化 JSON，格式不对就重试。这个机制把回答的"可控性"从 60% 提升到了 95% 以上。

**可靠性保障**：我做了 20+ 组并发压测，模拟多用户同时提问。过程中定位并修复了 7 类故障：向量召回超时（调大超时阈值 + 加缓存）、工具调用失效（Prompt 中增加工具描述）、会话内存溢出（加 LRU 淘汰）、Embedding 模型冷启动（预热加载）、PDF 解析特殊字符异常（正则清洗）、SSE 连接中断（前端自动重连）、并发下 thread_id 冲突（UUID 生成策略）。

### 成果

最终系统稳定支持多用户并发访问，回答准确率在测试集上达到 85%+，幻觉率控制在 5% 以内（对比纯 LLM 直接回答的 40%+ 幻觉率，降低了 90%）。首字响应时间 200ms，完整回答平均 2-3 秒。

## 2.3 高频追问与回答

**Q: 为什么选 LangChain 而不是 Spring AI？**
项目主要用 Python 技术栈，LangChain 在 Python 生态中的 Agent/RAG 能力最成熟，工具调度、记忆管理、流式输出都有现成组件。Spring AI 更适合 Java 微服务场景，如果这个 Agent 需要嵌入到商城项目的 Java 后端里，我会选 Spring AI。

**Q: 分块策略怎么选的？为什么 overlap 50？**
chunk size 512 是经验值——太小会丢失上下文（一句话被切成两半），太大检索噪声多。overlap 50 是为了保证相邻 chunk 之间的语义连续性——同一个段落被切到两个 chunk 时，overlap 能让检索命中任一 chunk 都能拿到完整信息。我对比过 overlap 0/25/50/100，50 是准确率和存储成本的最佳平衡点。

**Q: "知识库优先、无匹配兜底"的阈值 0.6 怎么定的？**
用 20 组测试问答手动标注。相似度 0.8+ 的结果我判断为"高度相关"，0.6-0.8 为"可能相关"，0.6 以下为"不相关"。实际测试中，0.6 阈值的召回率约 82%，精确率约 90%——也就是说 90% 被阈值放行的结果确实是正确的。阈值设太高（0.8）会漏掉一些相关但表述不同的结果，设太低（0.4）会引入噪声。

**Q: SSE 流式输出在并发下的性能问题怎么处理？**
SSE 是长连接，占用服务器连接资源。我的方案是 FastAPI 的 async 模型——每个 SSE 连接是一个 async task，不占用线程，所以单机能支持 100+ 并发 SSE 连接。如果连接数进一步增长，可以加 Nginx 做反向代理，利用 Nginx 的 epoll 模型分担连接压力。

**Q: 这个项目和商城项目的 RAG 有什么区别？**
本质区别在于场景复杂度。商城 RAG 面向商品数据，检索对象是结构化的商品信息（标题、描述、属性），分块相对简单。农业问答 RAG 面向非结构化的 PDF 文档，需要处理表格、图片、公式等复杂格式，分块策略更讲究。另外农业问答需要多轮对话记忆，商城搜索通常是单次查询。

2. **"知识库优先 + 兜底"的智能路由**：幻觉率从 40%+ 降到 5%，准确率 85%+
3. **工程可靠性**：20+ 组压测定位修复 7 类故障，多用户并发稳定运行

## 3.2 完整项目介绍

### 项目背景

这个项目是一个团队协作的养老院管理系统。之所以做这个项目，是因为养老行业数字化转型是国家重点推进的方向，而市面上的养老管理系统要么太贵、要么功能不匹配。我们团队 6 个人，用一个学期的时间做了一个轻量级但功能完整的版本。

我负责三个核心模块：健康评估引擎、IoT 设备同步服务、微信小程序统一鉴权。这三个模块分别对应了 AI 应用、IoT 对接和安全认证三个技术方向，对我的技术广度和深度都有很大锻炼。

### 模块一：健康评估引擎

这是项目中技术含量最高的模块。业务场景是：护理人员把老人的体检报告（纸质 PDF）录入系统后，系统自动分析各项指标，给出健康评估报告和护理建议。

最初的设计是纯规则引擎——把每项指标和正常范围做对比，超出就标记。但这种方式太粗糙：比如血压 140/90 算"轻度高血压"，但如果是 75 岁以上的老人，这个值其实是可接受的。规则引擎无法理解这种上下文。

所以我引入了百度千帆 AI 大模型做语义分析。把体检数据结构化后传给大模型，Prompt 里告诉它："你是一个资深老年科医生，请根据以下体检数据分析老人的健康状况，给出风险等级和护理建议。"大模型返回的结果经过 Pydantic 校验后存入数据库。

性能优化是这个模块的重点。大模型调用本身慢（2-3 秒），加上体检数据的重复查询，用户体验不好。我的方案是 Redis 多级缓存：第一级用 Redis 缓存高频查询的健康建议（用体检报告的 hash 做 key），TTL 设 24 小时；第二级用本地 Caffeine 缓存热点数据（比如最近录入的 100 份报告）。加上两级缓存后，单次分析响应时间从 8 秒降到了 1 秒以内，护理人员查阅效率提升约 30%。

早高峰期间（每天上午 8-10 点）是查询高峰，多科室同时查看报告。我用 Sentinel 做了限流，QPS 上限 200，超过的请求排队等待，而不是直接拒绝。这保证了系统不会被瞬间流量压垮。

### 模块二：IoT 设备同步服务

养老院有 500+ 台设备（体温计、血压仪、智能床垫、摄像头等），对接华为云 IoTDA 平台。我的任务是实现设备数据的本地同步——设备上报的数据要同步到我们自己的数据库里，前端才能展示实时状态。

最初的方案是全量同步——每隔 1 分钟把华为云的设备列表拉下来对比。但 500 台设备全量拉取要 3 分钟，而且大部分设备状态没变化，浪费带宽。

我改成了增量同步：维护一个本地的设备状态版本号（类似 ETag），每次请求带上版本号，华为云只返回变化的设备。对于没变化的设备，直接返回 304 Not Modified。同时用异步线程池（ThreadPoolTaskExecutor）并发拉取不同类型的设备，线程池核心 8 线程、最大 16 线程。改造后同步耗时从 3 分钟缩短到了 10 秒。

数据一致性方面，我设计了"设备-位置"绑定逻辑。每台设备必须绑定到具体的房间和床位，一个位置只能绑一台设备。这个用数据库唯一索引 + Redis 分布式锁双重保证——先查 Redis 锁，再写数据库索引，防止并发绑定冲突。

### 模块三：统一鉴权体系

C 端家属通过微信小程序访问，需要实现"无感登录"。方案是：用户首次打开小程序时引导授权，拿到 openid 后调用后端登录接口，后端生成 JWT token 存入 Redis，返回给前端。后续请求前端自动带上 token，后端拦截器校验 token 有效性。

这里的关键是 ThreadLocal 上下文传递。用户信息解析出来后存入 ThreadLocal，在 Service 层可以直接获取当前用户 ID，不用每个方法都传参。但必须注意：用完之后要 remove，否则在线程池复用线程时会导致数据泄露。我写了一个拦截器在请求结束时清理 ThreadLocal，保证零内存泄漏。

这个鉴权体系支撑了小程序端日均 2000+ 次的稳定访问。

**Q: 千帆大模型调用失败怎么办？**

设备本地缓存最近一次上报的数据，恢复网络后批量上报。我们的同步服务支持批量写入，不会因为数据堆积导致超时。华为云 IoTDA 本身也有离线消息缓存能力。

**Q: ThreadLocal 的内存泄漏是怎么避免的？**
三个措施。第一，拦截器 finally 块里必须 remove。第二，线程池用自定义的 ThreadFactory，每次执行完任务后清理 ThreadLocal。第三，代码 Review 时重点检查 ThreadLocal 的使用——这是我给团队定的规范之一。

## 4.2 完整项目介绍

### 项目背景

这个项目的起因是我在使用 ChatGPT 写长文时的一个痛点：AI 生成长文时，要么等待时间太长（10 秒以上才出结果），要么生成的内容结构松散、缺少配图、质量不稳定。我想做一个更专业的 AI 写作工具，把长文生成拆成多个步骤——先生成标题，再生成大纲，再逐段撰写正文，最后配上合适的图片——每一步用不同的 Prompt 和策略，最终拼成一篇完整的高质量文章。

技术选型上我选了 Spring Boot 3 + Spring AI Alibaba，而不是 Python 的 LangChain，有两个原因：第一，我想在 Java 后端领域积累 AI 应用开发经验；第二，Spring AI Alibaba 原生支持阿里云的大模型服务，国内调用更稳定。

### 核心架构设计

**StateGraph 工作流引擎**：这是我自研的一个轻量级工作流编排框架。传统做法是把生成流程写死在代码里：先调标题 API，再调大纲 API，再调正文 API。问题是流程不可配置、不可组合、不好扩展。

我借鉴了 LangGraph 的思路，设计了一个基于状态机的工作流引擎。核心抽象是三个概念：

- **Node（节点）**：一个具体的任务，比如"生成标题"、"生成大纲"、"生成正文"、"配图"
- **Edge（边）**：节点之间的流转条件，支持串行、并行、条件分支
- **State（状态）**：在节点之间传递的共享上下文，比如已经生成的标题、大纲、正文

用这个引擎，一个完整的文章生成流程可以定义为：

```
Start → [标题节点] → [大纲节点] → (并行: [正文节点1, 正文节点2]) → [配图节点] → End
```

新增一种生成模式（比如"新闻稿模式"），只需要配置新的节点和边，不需要改引擎代码。这就是我说的"代码可扩展性显著提升"。

**异步任务体系**：文章生成是耗时操作（可能 30 秒以上），如果同步等待会阻塞 HTTP 线程。我的方案是：

1. 前端提交生成请求，后端立即返回一个任务 ID
2. 后端用 `ThreadPoolTaskExecutor` + `@Async` 把生成任务提交到异步线程池
3. 任务执行过程中通过 SSE 实时推送进度（"正在生成大纲...已完成 30%...正在撰写第二段..."）
4. 生成完成后，结果存入 Redis，前端通过轮询或 WebSocket 获取

异步线程池我配置了核心 8 线程、最大 32 线程、队列容量 100。超过容量的任务会触发拒绝策略（CallerRunsPolicy，让调用方线程执行，起到降速作用）。

**SSE 流式输出**：这是用户体验的关键。大模型生成文本是逐 Token 的，如果等全部生成完再返回，用户要等很久。SSE 让后端把每个 Token 实时推送到前端，前端做打字机效果。Spring Boot 3 原生支持 SSE，配合 Spring AI 的 `StreamingResponse` 就能实现毫秒级首字上屏。

**结构化输出与多模型适配**：不同大模型的输出格式不一样，有的返回纯文本，有的返回 JSON。我封装了一个 Prompt 模板引擎 + StructuredOutputConverter，统一把各种模型的输出转换为标准格式（标题 + 大纲 + 正文 + 配图描述）。底层用 Pydantic 的 schema 校验，格式不对自动重试。

**多源配图降级**：配图功能我设计了策略模式。默认从 Pexels（免费图库）获取配图，如果 Pexels 失败（API 限流或图片不匹配），自动降级到 SVG 矢量图生成（用预设模板 + 文字渲染）。单一图源失败不影响整体生成，生成成功率 99%+。

### 成果

系统完整实现了从"输入主题"到"输出图文并茂的完整文章"的自动化闭环。生成速度：500 字文章约 15 秒，2000 字文章约 45 秒。首字延迟 200ms 以内。异步任务体系使接口吞吐量提升 50%。

## 4.3 高频追问与回答

**Q: StateGraph 和 Spring StateMachine 有什么区别？**
Spring StateMachine 适合业务流程审批这种有限状态机场景，状态转移是预定义的。我的 StateGraph 更像是一个 DAG（有向无环图）执行引擎，节点可以并行执行，状态可以在节点间自由传递，适合 AI 工作流这种数据驱动的场景。Spring StateMachine 的状态转移是事件驱动的，我的 StateGraph 是数据驱动的——上一个节点的输出决定下一个节点的输入。

**Q: 异步任务失败了怎么办？**
任务状态有四种：PENDING → RUNNING → SUCCESS / FAILED。FAILED 的任务会进入重试队列（RocketMQ 延迟消息），最多重试 3 次。超过次数进入死信队列，触发告警。用户端可以通过任务 ID 查询状态，看到"生成失败，请重试"的提示。

**Q: 为什么不用 WebSocket 而用 SSE？**
SSE 更简单——它是单向的（服务端推），基于 HTTP，天然支持断线重连和负载均衡。WebSocket 是双向的，对于"AI 生成文本推送到前端"这个场景，双向通信是多余的。而且 SSE 在 Spring Boot 中的实现更简洁，一个 `StreamingResponse` 就够了。

**Q: 这个项目和农业问答项目的技术栈区别？**
农业问答是纯 Python（LangChain + FastAPI），适合快速原型和 AI 生态组件的使用。灵犀写作是 Java（Spring Boot + Spring AI），更注重工程化——异步任务管理、状态追踪、错误重试、多源降级这些企业级特性。两个项目体现了我在 Python AI 和 Java 后端两个方向的实践能力。

## 项目深挖回答框架（STAR）

每个项目回答都按这个结构：

```
S - Situation（背景）: 为什么做这个项目？解决什么问题？
T - Task（任务）: 你具体负责什么？目标是什么？
A - Action（行动）: 你做了什么？用了什么技术？为什么这样选？
R - Result（结果）: 量化指标是什么？有什么成果？
```

## 如何应对"你还有什么问题问我"

推荐问法：

1. "请问这个岗位日常的技术栈是什么？团队在技术选型上有什么规划？"（展示技术兴趣）
2. "请问团队目前面临的最大的技术挑战是什么？"（了解业务痛点）
3. "请问新人入职后的培养机制是怎样的？"（展示上进心）
