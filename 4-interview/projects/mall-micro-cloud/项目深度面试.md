## 二、核心模块深度剖析

### 2.1 秒杀链路（4 层防护）

秒杀是项目的核心高并发场景，也是面试最高频的技术点。代码实际实现分为 4 层，每层解决不同的问题。

#### 第 1 层：布隆过滤器（Bloom Filter）—— 拦截无效请求

**代码位置**: `mall-common/src/main/java/itcast/cloud/mall/common/filter/CacheBloomFilter.java`

```java
// 布隆过滤器初始化（项目启动时执行）
@PostConstruct
public void init() {
    bloomFilter = redissonClient.getBloomFilter(fullName);
    bloomFilter.tryInit(expectedInsertions, falseProbability);
}

// 库存预热时写入布隆过滤器（在 ProductServiceImpl.loadStockCache() 中）
public void loadStockCache() {
    // ... 从 DB 加载商品库存到 Redis
    for (SeckillGoodsDTO goods : goodsList) {
        String stockKey = SeckillRedisKeyConstant.stockKey(activityId, goods.getSkuId());
        redisTemplate.opsForValue().set(stockKey, goods.getStoreCount());
        cacheBloomFilter.add(stockKey);  // 写入布隆过滤器
    }
}
```

**设计思路**: 秒杀活动开始前，通过 `loadStockCache()` 将商品库存从 MySQL 预加载到 Redis，同时将库存 key 写入布隆过滤器。在 `decreaseStock()` 方法中，首先检查布隆过滤器：

```java
// 请求到达时先查布隆过滤器
if (!cacheBloomFilter.mightContain(stockKey)) {
    log.warn("商品不存在");
    throw new BusinessException(7003, "库存不存在");
}
```

布隆过滤器用 10KB 左右的内存，就能以 1% 的误判率拦截 1 万个不存在的商品 ID。它的核心价值是：**防止缓存穿透**——恶意请求大量不存在的商品 ID 时，直接被打回，不会打到 Redis 甚至 MySQL。

#### 第 2 层：Redisson 分布式锁 —— 防止并发超卖

**代码位置**: `mall-seckill-service/.../impl/ProductServiceImpl.java`

```java
// 库存扣减核心方法
public void decreaseStock(StockDeductDTO stockDeductDTO) {
    String stockKey = SeckillRedisKeyConstant.stockKey(
        stockDeductDTO.getActivityId(), stockDeductDTO.getSkuId());
    String lockKey = SeckillRedisKeyConstant.stockLockKey(
        stockDeductDTO.getActivityId(), stockDeductDTO.getSkuId());
    RLock lock = redissonClient.getLock(lockKey);

    // 1. 布隆过滤器校验
    if (!cacheBloomFilter.mightContain(stockKey)) {
        throw new BusinessException(7003, "库存不存在");
    }

    try {
        // 2. 获取分布式锁（等待3秒）
        boolean isLocked = lock.tryLock(3, TimeUnit.SECONDS);
        if (!isLocked) {
            throw new BusinessException(7001, "系统繁忙，请稍后重试");
        }

        // 3. 查询当前库存
        Object stockObj = redisTemplate.opsForValue().get(stockKey);
        if (stockObj == null) throw new BusinessException(7003, "库存不存在");
        int beforeStock = Integer.parseInt(stockObj.toString());
        if (beforeStock <= 0) throw new BusinessException(ResultCodeEnum.STOCK_SHORTAGE);

        // 4. Redis 原子扣减
        Long remainCount = redisTemplate.opsForValue().decrement(stockKey);
        if (remainCount == null) throw new BusinessException(ResultCodeEnum.STOCK_SHORTAGE);

        // 5. 超卖回滚（remainCount < 0 说明超卖了）
        if (remainCount >= 0) {
            log.info("库存扣减成功，剩余库存：{}", remainCount);
        } else {
            redisTemplate.opsForValue().increment(stockKey);  // 回滚
            throw new BusinessException(ResultCodeEnum.STOCK_SHORTAGE);
        }

        // 6. 发送 MQ 消息（异步同步到数据库）
        StockDeductMessageDTO message = new StockDeductMessageDTO();
        message.setActivityId(stockDeductDTO.getActivityId());
        message.setSkuId(stockDeductDTO.getSkuId());
        message.setTransactionId(lockKey + ":" + System.currentTimeMillis());
        streamBridge.send("stockDeductOutput-out-0", message);
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

**关键设计点**:

- **锁粒度**: `lock:seckill:{activityId}:{skuId}`，按商品维度加锁，不同商品的请求不互相阻塞
- **锁超时**: `tryLock(3s)`，等待 3 秒获取不到就放弃，避免请求堆积
- **看门狗**: Redisson 自动续期，默认 30 秒，业务没执行完锁不会过期
- **原子扣减**: `decrement()` 是 Redis 原子操作，返回扣减后的值，比 `get + decrement` 两步操作安全
- **超卖回滚**: 扣减后 `remainCount < 0` 说明超卖了，立即 `increment()` 加回来，保证数据一致性

#### 第 3 层：RocketMQ 异步落库（MQ 消息 + 幂等消费）

**代码位置**: `mall-seckill-service/.../consumer/StockDeductConsumer.java`

```java
@Bean
public Consumer<Message<String>> stockDeductInput() {
    return message -> {
        String body = message.getPayload();
        StockDeductMessageDTO dto = JsonUtils.toObj(body, StockDeductMessageDTO.class);

        // 1. 幂等校验（基于 transactionId，30s 窗口足够覆盖重试）
        String lockKey = "que:lock:stock:" + dto.getTransactionId();
        Boolean acquired = redisTemplate.opsForValue().setIfAbsent(lockKey, "1", 30, TimeUnit.SECONDS);
        if (!Boolean.TRUE.equals(acquired)) {
            log.debug("重复消息跳过: {}", dto.getTransactionId());
            return;
        }

        // 2. 写入流水 + 同步库存 + 更新状态（单事务）
        seckillStockFlowService.recordStockFlow(dto);
        log.info("库存同步完成：activityId={}, skuId={}, afterStock={}",
                dto.getActivityId(), dto.getSkuId(), dto.getAfterStock());
    };
}
```

**幂等设计**: 用 `transactionId` 作为唯一键，通过 Redis `SETNX` 加锁，30 秒过期。同一 `transactionId` 重复到达时，SETNX 返回 false，直接跳过。这解决了 MQ 重试机制导致的重复消费问题。

public void restoreStock(StockDeductDTO stockDeductDTO) {

    RLock lock = redissonClient.getLock(lockKey);
    try {
        lock.tryLock(3, 10, TimeUnit.SECONDS);

## 三、技术难点与解决方案

### 难点 1：Redis 预扣库存 + MQ 异步落库的一致性

**问题**: Redis 扣减库存后，MQ 消息异步写数据库。如果 Redis 扣减成功但 MQ 发送失败，或 MQ 消费失败，Redis 和 MySQL 的库存数据就不一致了。

**方案**: 三层保障机制
1. 分布式锁 + 原子 decrement 保证 Redis 扣减的原子性
2. MQ 消息在递送成功后消费者才返回 ACK，消息确认后才写数据库
3. Elastic-Job 定时对账任务，每 10 分钟校验 Redis 和 MySQL 库存一致性

### 难点 2：布隆过滤器的误判处理

**问题**: 布隆过滤器有 1% 的误判率——某些不存在的商品会被误判为"可能存在"，放行到 Redis 层。

**方案**: 布隆过滤器只是第一道防线，Redis 层还有 `get(stockKey) == null` 检查。误判的商品到 Redis 会发现没有库存数据，同样返回"库存不存在"。误判不会导致超卖，只会多一次 Redis 查询。

### 难点 3：跨服务分布式事务

**问题**: 创建订单需要同时扣库存、删购物车、创建支付记录，三个操作分散在不同微服务。

**方案**: Seata AT 模式 + `@GlobalTransactional`。Seata 通过拦截 SQL 执行，自动生成 undo log。任一服务异常时，Seata TC 协调器通知所有参与者回滚。AT 模式对业务代码零侵入，缺点是性能开销比 TCC 大。

### 难点 4：MQ 消息重复消费

**问题**: RocketMQ 的 At Least Once 语义导致消息可能重复到达。

**方案**: 基于 `transactionId` 的 Redis 幂等锁。`SETNX transactionId` 30 秒过期，同一事务的消息重复到达时直接跳过。`transactionId` 的生成规则是 `lockKey + System.currentTimeMillis()`，确保全局唯一。

### 难点 5：Java 与 Python 跨语言联调

**问题**: AI 搜索服务需要 Java 后端调用 Python AI 服务，但 Java 语言类型系统和 Python 的动态类型之间需要数据转换。

**方案**: 通过 OpenFeign + FastAPI 的 HTTP JSON 接口，Java 端用 `CamelCastUtils.jsonToObject()` 将 Python 返回的 JSON 转换为 Java 的 ProductDTO 对象。驼峰下划线自动转换解决了命名风格差异。

## 五、高频面试题深度问答

**Q1: 为什么秒杀不用纯 Redis 分布式锁，而是先加布隆过滤器？**

布隆过滤器是低成本过滤层。秒杀活动中，大量请求可能携带无效商品 ID（恶意攻击、已下架商品）。布隆过滤器用 10KB 内存即可拦截 99% 的无效请求，只有 1% 的误判流量会落到 Redis 层。如果不加布隆过滤器，所有无效请求都要走到 Redis 的 `get` 操作，Redis 连接数会大幅增加。（追问：误判的 1% 怎么办？答：Redis 层还有 `get(stockKey) == null` 检查，误判不会导致错误，只会增加一次 Redis 查询开销。）

**Q2: Redisson 看门狗机制的原理是什么？**

Redisson 的 `RLock` 默认锁超时 30 秒。如果业务执行时间超过 30 秒，看门狗会每 10 秒检查一次锁是否还在持有，如果是则自动续期到 30 秒。锁释放后停止续期。这解决了原生 Redis SETNX 的痛点：锁超时设置太短会导致业务没执行完锁就释放，设置太长会导致死锁时间长。

**Q3: 为什么扣减库存用 `decrement()` 而不是 Lua 脚本？**

`decrement()` 是 Redis 原生原子操作，返回值就是扣减后的值，可以立即判断是否超卖。Lua 脚本虽然也能做到原子性，但需要额外加载脚本的操作。单次 `decrement()` 能满足需求时，优先用原生操作，性能更好。

**Q4: Seata AT 和 TCC 怎么选？**

AT 模式对业务代码零侵入，适合我们项目阶段快、团队对分布式事务经验不深的情况。TCC 虽然性能更好，但需要每个参与者手写 Try/Confirm/Cancel 三个接口，开发成本高。如果未来性能瓶颈出现，核心链路（订单创建）可以升级为 TCC。

**Q5: 布隆过滤器的误判率怎么配置的？**

在 `application.yml` 中配置 `cache.bloom.falseProbability=0.01`（1% 误判率），`expectedInsertions` 根据商品数量预估。误判率越低，占用的内存越大。1% 误判率对应 10 万条数据约 120KB 内存，性价比最高。

**Q6: 库存回滚的场景有哪些？**

两种：一是 Redis 扣减后 `remainCount < 0` 说明超卖了，立即 `increment()` 回滚；二是业务异常（如 MQ 发送失败）时，在 catch 块中调用 `restoreStock()` 恢复库存。第二种情况通过 `transactionId` 做幂等，防止重复恢复。

**Q7: AI 搜索的 Python 服务挂了怎么办？**

降级策略：AI 搜索服务不可用时，自动降级到纯 ES 关键词搜索模式。用户在界面上看到的"智能推荐"按钮变为灰色或不可用，但"关键词搜索"不受影响。通过 `try-catch` 捕获 Feign 调用异常，熔断后走 ES 兜底。

**Q8: 为什么要用 `streamBridge.send()` 而不是直接用 RocketMQ 原生 API？**

Spring Cloud Stream 封装了 MQ 的底层实现，可以切换不同的消息中间件（RocketMQ/Kafka/RabbitMQ）而不改业务代码。`streamBridge` 是编程式发送的入口，适合在 Service 层直接发送消息，比 `@EnableBinding` + `@StreamListener` 的组合更灵活。

**Q9: 订单表的分表策略是什么？**

按用户 ID 哈希分表，`order_0` 到 `order_15` 共 16 张表，用 MyBatis-Plus 的 `@TableName` 动态解析。分表键是 `userId`，保证同一用户的订单在同一张表，方便查询。分表粒度是 16 张，当前数据量够用，未来可增加到 64 或 128 张。

**Q10: 秒杀商品详情页为什么用静态化？**

秒杀活动开始前，通过 `generateHtml()` 方法生成商品详情页的静态 HTML 文件，推送到 Nginx 静态服务器。用户请求直接走 Nginx 返回静态页面，不需要打到 Java 后端。静态页的 QPS 可以到 10 万+，而动态页面受限于 Tomcat 线程池，单机 QPS 约 2000。
