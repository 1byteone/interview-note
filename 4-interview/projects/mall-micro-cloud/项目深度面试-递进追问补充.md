# 分布式微云商城—项目深度面试递进追问补充

> 本文为独立补充稿，不修改原有面试文档。优化方向必须明确说成“后续演进”，不要包装为已上线能力。
>
> **事实基线**：Spring Boot 3 + Spring Cloud Alibaba；12 个模块；秒杀使用布隆过滤器、Redisson、Redis、消息异步落库；RocketMQ/Stream 消费；Nacos、Gateway、Sentinel、OpenFeign、Seata、Elasticsearch；AI 搜索通过 Feign 调用 Python 服务。团队 4 人，我负责秒杀、搜索/RAG、一致性和研发规范。

## 一、项目介绍 STAR 模板

> **S**：平台面向高并发电商交易，秒杀场景会在短时间产生大量无效请求和库存竞争，普通数据库扣库存容易形成连接池和锁竞争。
>
> **T**：我负责把库存扣减从同步数据库链路改造成可抗突发流量、可恢复的分层链路，并兼顾最终落库和重复消息问题。
>
> **A**：活动开始前预热 Redis 库存和布隆过滤器；请求先过滤不存在的库存 key，再按活动和 SKU 粒度加 Redisson 锁，使用 Redis 原子扣减；成功后发送消息异步同步数据库，消费者用 transactionId 做幂等，并保留库存流水。
>
> **R**：形成“过滤—并发控制—原子扣减—异步持久化”的四层防护。后续仍需补强消息发送与库存扣减的一致性、死信、对账和压测指标。

## 二、递进追问：微服务架构与选型

### Q1：为什么拆成 12 个服务？

**标准回答**：按业务边界和变化速度拆分：商品、订单、支付、库存、用户、搜索各自有清晰职责，秒杀和搜索的资源模型与普通 CRUD 不同，可以独立限流和扩容。拆分的代价是网络调用、配置、部署、链路追踪和分布式事务，因此不是模块越多越好。

**追问：为什么不全部做成单体？** 单体更简单，适合早期；但秒杀隔离、搜索独立扩容和团队并行开发会受影响。选择微服务的依据是边界清晰且确有独立伸缩需求，而不是为了“显得先进”。

### Q2：为什么选 Nacos，而不是 Eureka？

Nacos 同时提供服务注册发现和配置中心，适合 Spring Cloud Alibaba 体系；Eureka 更偏注册发现。我们减少组件数量和运维成本，并利用命名空间、分组隔离环境。代价是引入 Nacos 依赖，生产必须考虑集群、持久化、权限和配置变更审计。

### Q3：Gateway、Feign、Sentinel 分别解决什么问题？

Gateway 解决外部统一入口、路由和入口级鉴权；Feign 解决服务间声明式 HTTP 调用和实例发现；Sentinel 解决资源级限流、熔断与降级。三者不是替代关系：一个管入口，一个管通信，一个管保护。

### Q4：一次请求如何定位慢在哪里？

先看网关 RT、状态码和路由；再用 traceId 关联 Feign 调用、数据库、Redis 和 MQ 日志；拆分客户端、网关、业务、下游和序列化耗时，结合连接池、线程池和 Sentinel 指标。不能只看总 RT 后直接加机器。

## 三、递进追问：秒杀与库存

### Q5：为什么先用布隆过滤器？

它用很小内存判断 key“绝对不存在”或“可能存在”，可以拦截恶意随机 SKU 请求，防止缓存穿透。它有误判但没有漏判：误判仍会继续查 Redis，不能把布隆过滤器当最终库存事实。

### Q6：为什么还要 Redisson 锁？Redis decrement 已经原子了，锁是否多余？

单纯扣减可以原子，但完整流程还包含读取、库存判断、流水、状态和消息构造。按活动+SKU 加锁可以保护组合操作，不过会降低热点 SKU 并发。更高吞吐的演进方向是 Lua 将校验和扣减合并，减少锁依赖；必须通过压测验证，不应盲目声称锁越多越安全。

### Q7：`get` 后 `decrement` 有什么问题？

并发下多个请求都可能读到相同库存；虽然 decrement 本身原子，但“判断库存”和“扣减”分离会产生竞态。应使用 Lua 原子脚本，或在锁内完成完整判断。扣减后返回负数再 increment 属于补偿，不能替代原子设计。

### Q8：库存扣 Redis 成功但 MQ 发送失败怎么办？

这是关键一致性窗口。当前实现若直接发送失败，可能出现 Redis 少库存、数据库没扣的偏差。生产化可采用 Outbox 本地消息表、事务消息、可靠重试或定时对账；消息必须包含幂等业务 ID。面试时应诚实说明当前实现的边界。

### Q9：为什么消费者必须幂等？

消息通常是至少一次投递，网络重试、消费者重启都可能重复。用 transactionId 做 Redis SETNX 只能提供窗口内去重，最终还需要数据库唯一索引或库存流水唯一约束。幂等不是“收到重复就 return”这么简单，还要保证数据库状态和缓存状态可重复执行。

### Q10：Redis 库存与数据库库存不一致如何修复？

明确数据库或库存流水为审计权威，定时比较活动库存、扣减流水、订单状态和 Redis 值；发现差异记录对账任务，按订单状态补扣或释放。对账任务必须可重复、可观测，不能直接覆盖线上值而不留审计记录。

### Q11：秒杀如何防止一人重复下单？

以活动、SKU、用户组成幂等键，在 Redis 或数据库建立唯一约束；订单创建和库存扣减必须有清晰状态机。Redis 快速拦截只能提升性能，数据库唯一索引负责最终兜底。支付超时、取消和库存恢复也必须沿同一业务 ID 幂等。

## 四、递进追问：RocketMQ、Seata 与分布式事务

### Q12：RocketMQ 和 Kafka 如何选？

本项目需要延迟消息、事务消息和业务事件，RocketMQ 的业务消息能力更贴合；Kafka 更擅长高吞吐日志、流式分析。选择不是绝对优劣，要看消息顺序、重试、消费模型、生态和运维能力。

### Q13：Seata AT 的原理是什么？

一阶段由代理数据源记录业务 SQL 前后镜像和 undo log；全局事务协调器管理事务状态；提交时清理日志，回滚时用反向 SQL 恢复。它侵入较小，但依赖代理数据源、主键和 SQL 可回滚性；复杂外部副作用不适合只靠 AT。

### Q14：为什么订单、库存、支付不能无限依赖 Seata？

跨服务长事务会持有锁、增加网络等待，并且支付平台、MQ、第三方接口无法通过数据库 undo 回滚。更合理的是本地事务 + 可靠事件 + 状态机 + 补偿；Seata 只覆盖适合数据库事务的短链路。

### Q15：Feign 调用超时怎么降级？

设置连接和读取超时、有限重试；对非幂等写操作谨慎重试；配置 fallback 或 fallbackFactory 返回可识别的降级结果并记录原因。降级不能伪造成功，例如库存服务不可用时不能直接返回“下单成功”。

## 五、递进追问：搜索、ES 与 AI 搜索

### Q16：为什么 ES 不直接用 MySQL LIKE？

商品搜索需要倒排索引、IK 分词、相关性排序和分页，ES 更适合文本检索；MySQL 仍适合交易事实和强一致写入。两者存在同步延迟，商品变更要通过事件或可靠同步更新索引，失败需重试和全量重建。

### Q17：ES 数据与 MySQL 不一致怎么办？

明确 MySQL 是商品事实源，ES 是查询投影。通过消息同步、失败重试、索引版本号和定时全量对账恢复；删除和更新要保证事件顺序或使用版本控制。不能把 ES 查询结果直接当库存和价格最终事实。

### Q18：为什么 AI 搜索不直接替换关键词搜索？

关键词搜索精确、稳定、可解释；AI 搜索适合意图理解、推荐和属性抽取，但有延迟、成本和不可控输出。采用传统搜索作为基础能力，AI 作为增强或兜底，避免模型故障影响核心交易。

### Q19：Python AI 服务调用失败怎么办？

Feign 设置超时和熔断，返回明确降级状态；记录模型耗时、错误类型和请求 traceId；不要把原始用户输入和敏感信息完整写日志。模型服务恢复后可重试，但不能让同步接口无限等待。

## 六、技术选型与反事实追问

| 追问 | 标准回答 |
|---|---|
| 为什么不用原生 Redis 锁？ | Redisson 提供锁语义、看门狗和异常处理；原生 SETNX 需要自行续期和释放，简单场景可用但容易遗漏边界。 |
| 为什么不用 JPA？ | 商品和库存查询更偏明确 SQL、批量和分页；MyBatis-Plus 保留 SQL 可控性，同时减少单表 CRUD 样板。复杂领域不是绝对不能用 JPA。 |
| 为什么不把库存放数据库？ | 秒杀突发流量会集中竞争数据库；Redis 适合快速原子扣减，数据库负责最终落库和审计。 |
| 为什么不全链路同步？ | AI、搜索和库存落库都可能慢；异步能削峰，但必须用状态、重试、幂等和监控补足一致性。 |
| Sentinel 和网关限流有何区别？ | 网关限入口总流量，Sentinel 保护具体资源；二者可叠加，但规则和降级口径要一致。 |

## 七、故障演练题

1. **Redis 宕机**：秒杀进入快速失败或降级，不回源数据库承受洪峰；恢复后重新预热并校验库存。
2. **MQ 积压**：看积压量、消费延迟和失败率，扩消费者前先检查数据库写入能力，必要时限流生产端。
3. **Nacos 不可用**：服务使用本地缓存的实例列表和配置，关键配置预置；生产需集群和配置持久化。
4. **订单已创建但扣库存失败**：订单进入待确认/失败状态，由补偿任务关闭或释放，不向用户返回虚假成功。
5. **重复支付回调**：以支付流水号做幂等，状态机只允许合法迁移，回调可重复到达但业务结果只能生效一次。

## 八、STAR 亮点：技术选型与复盘

> 我没有把所有问题都用分布式事务解决，因为事务只能覆盖本地数据库，无法回滚支付和消息。我的取舍是：短事务保证本地原子性，消息负责解耦，状态机和对账负责最终一致性。这样复杂度更高，但更符合电商系统的真实边界。
