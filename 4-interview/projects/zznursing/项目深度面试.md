## 二、核心模块深度剖析

### 2.1 健康评估引擎（百度千帆 AI + Redis 缓存）

**代码位置**: `zzyl-nursing-platform/.../service/impl/HealthAssessmentServiceImpl.java`

**数据流**:
```
护理人员上传PDF → AliyunOSSOperator.upload() → OSS 存储
                 → PDFUtil.pdfToString() → 提取文本
                 → Redis Hash(healthReport, idCard, content) ← 缓存24h
                                                      ↓
护理人员提交评估 → HealthAssessmentServiceImpl.insertHealthAssessment()
                 → getPrompt(idCard) 从 Redis 取文本
                 → 拼装 JSON 结构化输出的 Prompt
                 → AIModelInvoker.qianfanInvoker(prompt)
                    → OpenAI SDK (兼容百度千帆) → baidu.qianfan.apiKey/baseUrl/model
                 → JSON.parseObject → HealthReportVo (结构化)
                 → saveHealthAssessment: 健康分/风险等级/建议入住/护理等级/八大系统
                 → insert 到 health_assessment 表
```

**AI Prompt 设计要点**:
- 角色设定: 专业医生视角
- 输出六项: 总检日期 / 风险等级+健康指数 / 五级风险分布 / 异常数据(7字段) / 八大系统评分 / 总结
- 强制 JSON 输出: `responseFormat` 设置为 `json_object`
- 健康指数映射护理等级: **≥90→四级, ≥80→三级, ≥70→二级, ≥60→一级, <60→特级**

**性能优化收益**: AI 分析耗时约 8 秒，但缓存 PDF 文本避免了每次提交都重复上传和解析。优化后整体响应 1 秒内，护理人员评估效率提升约 30%。

### 2.2 IoT 设备管理（华为云 IoTDA + Redis）

**代码位置**: `zzyl-nursing-platform/.../service/impl/DeviceServiceImpl.java`、`DeviceDataServiceImpl.java`

**产品同步**: 全量同步到 Redis → 后续查询走 Redis（3 分钟→10 秒）

**设备注册**: 校验设备名唯一/节点 ID 唯一/同位置同产品不重复 → 生成随机 secret → 华为云注册 → 本地保存

**设备数据消费 (AMQP)**:
```
应用启动 → AmqpClient.run() → 建立 AMQP 连接(默认4个连接)
IoT设备上报 → 华为云 IoTDA → AMQP Queue
  → MessageListener → executorService.submit(processMessage)
  → JSON 解析 → IotMsgNotifyData
  → DeviceDataServiceImpl.batchInsertDeviceData()
    → 根据 iotId 查本地 device 表
    → Map<functionId, value> 遍历 → 批量插入 device_data 表
    → 同时写入 Redis Hash(iot:device_last_data, iotId, JSON)
```

**Redis Key 常量**:
- `iot:all_product_list` (String) — 产品列表缓存
- `iot:device_last_data` (Hash) — 设备最新数据, field=iotId

### 2.3 统一鉴权（拦截器 + ThreadLocal）

微信小程序用户的无感登录流程：首次打开小程序引导授权 → 拿 openid 调后端登录接口 → 后端生成 JWT token 存入 Redis → 返回前端。后续请求前端自动带 token，后端拦截器校验 token 有效性，用户信息解析后存入 ThreadLocal，Service 层直接获取当前用户 ID。

**ThreadLocal 内存泄漏防护**：拦截器 finally 块中必须 remove；线程池用自定义 ThreadFactory 每次执行完清理。

## 三、技术难点与解决方案

### 难点 1：AI 分析响应时间慢（8s → 1s）

**问题**: 百度千帆大模型调用耗时 2-3 秒，加上 PDF 解析和数据库查询，单次分析响应 8 秒，早高峰体验差。

**方案**: Redis Hash 缓存 PDF 解析文本（24 小时 TTL），提交评估时直接取缓存，省去重复解析。响应降到 1 秒以内。

### 难点 2：IoT 设备同步慢（3min → 10s）

**问题**: 500+ 台设备全量同步需要 3 分钟，大部分设备状态没变化。

**方案**: 产品列表全量同步到 Redis（String 类型），后续查询直接走 Redis。设备数据消费用 AMQP 消息订阅 + 线程池并发处理，批量插入数据库。

### 难点 3：多线程环境下的数据隔离

**问题**: 微服务 + 线程池环境下，用户信息如何在请求链路中传递且不串数据？

**方案**: ThreadLocal 存用户上下文 + 拦截器销毁。必须注意：用完之后必须 remove，否则在线程池复用线程时会导致数据泄露，严重时可导致串号安全漏洞。

## 四、高频面试题

**Q1: 百度千帆大模型调用失败怎么降级？**

自动切换回规则引擎模式，给出基础的指标对比结果（每项指标与正常范围比对，超标的标注警示）。虽然不如 AI 分析精准，但至少能用。同时记录失败日志触发告警。

**Q2: IoT 设备断网后数据怎么处理？**

设备本地缓存最近一次上报的数据，恢复网络后批量上报。我们的设备数据消费服务支持批量写入，不会因为数据堆积导致超时。华为云 IoTDA 本身也有离线消息缓存能力。

**Q3: ThreadLocal 为什么会导致内存泄漏？怎么避免？**

ThreadLocal 的 key 是弱引用，value 是强引用。当线程池线程复用且 ThreadLocal 不再使用时，value 无法被回收。三个措施：拦截器 finally remove、线程池自定义 ThreadFactory 清理、代码 Review 重点检查。

**Q4: 为什么用 RuoYi 二次开发而不是从零写？**

RuoYi-Vue 提供了成熟的后台管理基础（RBAC 权限、代码生成器、字典管理、操作日志），直接复用可以节省 3-4 周的开发时间，把精力聚焦在养老业务的核心模块上。二次开发的关键是理解框架的扩展点和约束。
