> **定位**：本文件是对《项目深度面试.md》《大厂面试官QA.md》的独立补充，不修改原文。适合进行 30～60 分钟的项目深挖面试。
>
> **使用原则**：回答必须以实际源码和真实经历为准。文中标记为“优化方向”的内容，面试时应明确说成“如果继续迭代，我会……”，不能包装成已经上线的功能。

## 一、面试官的递进追问方法

面试官通常沿着下面的路径判断候选人是否真正做过项目：

```text
你做了什么
  ↓
为什么这样做
  ↓
具体怎么实现
  ↓
出现异常怎么办
  ↓
并发、性能、安全如何保证
  ↓
为什么不用另一种方案
  ↓
如果规模扩大，下一步怎么演进
```

### 1. 每道题的回答结构

建议使用“结论 → 依据 → 实现 → 取舍”的四段式，而不是只背组件名称：

1. **结论**：先用一句话回答选择或设计结论。
2. **依据**：说明业务约束、数据规模和风险。
3. **实现**：说清楚调用链、关键类、状态和异常分支。
4. **取舍**：承认当前方案的边界，并给出有优先级的优化方向。

### 2. STAR 不是流水账

- **S（Situation）场景**：养老业务中谁遇到了什么问题？影响是什么？
- **T（Task）任务**：你负责的范围、目标和限制条件是什么？
- **A（Action）行动**：你做了哪些技术决策，为什么这样做？
- **R（Result）结果**：用指标、稳定性、交付效果或复盘结论证明结果。

> 量化数据必须能解释口径。例如“8 秒降到 1 秒”应说明是接口端到端耗时、平均值还是 P95，以及测试样本和优化前后的链路差异。

## 二、90 秒项目自我介绍（STAR 版）

### 面试官问题：请介绍一下这个项目，以及你主要负责什么？

**标准回答：**

> **S**：这是一个面向中型养老机构的综合护理管理平台，既有管理后台，也有家属微信小程序。系统需要处理健康评估、入住护理和物联网设备数据，稳定性和数据安全比单纯的功能数量更重要。
>
> **T**：团队 6 人，我主要负责三个方向：体检报告驱动的健康评估、华为云 IoTDA 设备同步与数据接入、小程序用户的登录鉴权。同时需要和入住、护理、系统权限模块协作，保证模块能落地交付。
>
> **A**：健康评估链路采用“OSS 保存原文件、PDFBox 提取文本、Redis 缓存解析结果、百度千帆结构化分析”的方式，减少重复解析；IoT 侧通过华为云 IoTDA 和 AMQP 接收数据，使用线程池异步处理、批量入库，Redis Hash 保存设备最新值；小程序侧使用微信 code 换 openid，再签发 JWT，通过拦截器解析用户上下文，并在请求结束时清理 ThreadLocal。
>
> **R**：健康评估链路在项目测试口径下从约 8 秒降低到 1 秒以内，护理人员查阅效率提升约 30%；设备产品同步从约 3 分钟降低到约 10 秒，支撑 500+ 设备接入和日均 2000+ 家属端访问。复盘后我认为还需要补强消息幂等、失败补偿、审计和全链路监控。

### 继续追问 1：这段介绍中哪些是你亲自完成的？

**考察点**：辨别项目归属，避免把团队成果说成个人成果。

**建议回答：**

明确到模块和动作：我负责健康评估服务中的报告上传后处理、缓存和模型调用封装；负责 IoT 设备产品同步、设备注册校验、AMQP 消费和设备数据批量保存；负责小程序端 token 解析、用户上下文和接口鉴权。前端页面、部分入住业务和 RuoYi 原有 RBAC 是团队其他成员负责或框架已有能力，我能讲清接口契约和协作边界，但不会把它们说成自己从零实现。

### 继续追问 2：如果去掉百度千帆和华为云，这个项目还剩什么核心价值？

**建议回答：**

外部 AI 和 IoT 是差异化能力，但不是全部价值。系统核心仍是老人档案、入住办理、护理计划、预约、合同和权限等业务闭环。AI 是提高评估效率的辅助决策工具，IoT 是补充实时数据来源，最终结果仍需要业务规则、人工复核和系统审计兜底。

## 三、第一组：整体架构与 RuoYi 二次开发

### Q1（L1）：为什么采用 RuoYi-Vue 二次开发，而不是从零搭建？

**标准回答：**

采用它的核心原因是项目交付周期和基础能力复用。RuoYi 已经提供后台登录、RBAC、代码生成、操作日志、字典和通用管理能力，从零实现这些能力会消耗大量时间，而且容易出现权限边界和审计缺陷。我们把精力集中在健康评估、养老业务、IoT 接入和小程序认证这些差异化部分。

**STAR 组织方式：**

- **S**：团队需要在有限周期内交付管理后台和养老业务。
- **T**：既要快速完成基础 CRUD，又要保证权限和日志可用。
- **A**：保留 RuoYi 的框架层和系统管理模块，在 `zzyl-nursing-platform` 增加养老领域模块，扩展 AI、IoT、OSS 和小程序认证。
- **R**：减少基础设施开发工作量，通常可节省约 3～4 周；同时降低重复造轮子的风险。

### Q2（L2）：二次开发最容易踩什么坑？

**标准回答：**

主要有三类：第一，直接修改框架核心代码会增加升级和排查成本；第二，公共模块职责过重会形成循环依赖；第三，沿用代码生成器的表结构和权限约定，却没有补充领域校验，容易得到“能 CRUD、不能保证业务正确”的系统。

我的做法是优先使用扩展点和新增业务模块，公共能力只放跨模块复用的代码；业务规则放在业务 Service，不把规则塞进 Controller；对生成代码再补充事务、校验、幂等和审计。

### Q3（L3）：为什么采用多模块单体，而不是微服务？

**标准回答：**

从当时规模看，多模块单体更合适。500+ 设备和 2000+ 日访问量并不天然要求微服务，真正的瓶颈在外部 IoT 消息处理、AI 网络调用和数据写入，而不是模块数量。多模块可以做到代码边界隔离、统一部署和较低运维成本。

如果未来出现多个养老机构独立部署、IoT 消费需要水平扩展、AI 任务需要独立弹性伸缩，再考虑拆分。拆分前应先抽离领域接口、事件契约和数据边界，而不是直接按 Maven 模块拆成多个服务。

### Q4（L4）：这个系统的架构瓶颈在哪里？你会如何定位？

**标准回答：**

我会先按指标定位，而不是凭感觉重构：

1. 网关或接口层看 QPS、RT、错误率和超时比例。
2. AI 链路拆分 PDF 解析、Redis、模型请求、JSON 解析、数据库写入耗时。
3. IoT 链路看 AMQP 队列积压、消费者处理耗时、线程池活跃数、拒绝数、批量 SQL 耗时。
4. 数据库看慢查询、连接池使用率和批量插入吞吐。
5. Redis 看命中率、内存、慢命令和连接数。

初步判断，AI 的主要瓶颈是外部模型延迟，IoT 的主要瓶颈是消息消费和批量落库；二者应分别优化，不能只增加 Web 容器线程数。

**面试官继续追问：为什么不直接加机器？**

加机器只能缓解无状态接口的并发，不能解决单个外部 AI 请求慢、数据库写入慢、消息确认不可靠等问题。扩容前先确认瓶颈是否可水平分摊，并补上幂等、监控和容量评估。

## 四、第二组：AI 健康评估深挖

### Q5（L1）：一次健康评估请求完整经过哪些步骤？

**标准回答：**

上传阶段先校验文件并保存到 OSS，再用 PDFBox 提取文本，按身份证号或报告标识写入 Redis，设置 24 小时过期。提交评估时从 Redis 取文本，拼接包含角色、字段、范围和 JSON 约束的 Prompt，调用百度千帆；收到结果后先做 JSON 反序列化，再做必填字段、分值范围和风险等级校验，最后把健康分、风险、护理等级和建议写入数据库。

关键原则是：原始文件进 OSS，解析文本进缓存，结构化结果进数据库；不同数据承担不同生命周期。

### Q6（L2）：为什么缓存 PDF 文本，而不是只缓存 AI 结果？

**标准回答：**

缓存解析文本可以复用在重试、重新评估和模型切换场景；如果只缓存 AI 结果，模型参数、Prompt 或规则变化后无法重新分析。文本是相对稳定的中间产物，AI 结果是可重算的派生产物，因此缓存文本更利于解耦。

但文本可能包含身份证号、疾病等敏感信息，生产环境需要设置合理 TTL、访问控制、脱敏日志、加密传输，并评估 Redis 持久化和备份风险。缓存不是永久存档，原始文件的权威版本仍在 OSS。

### Q7（L2）：Redis Hash 为什么这样设计？key 和 field 如何选择？

**标准回答：**

健康报告文本适合按报告维度快速取值；Hash 可以把同类报告放在一个逻辑 key 下，field 使用报告标识或用户标识，value 保存文本。IoT 最新数据则使用 `iot:device_last_data` 作为 Hash key，以 `iotId` 作为 field，读取单个设备最新状态时不需要扫描整张表。

需要注意 Hash 的 TTL 是 key 级别，不是 field 级别。如果不同报告的过期时间不同，就不能简单依赖整个 Hash 的 TTL，需要拆分 key、额外记录过期时间，或使用 Redis String/JSON 结构。

### Q8（L3）：AI 输出不合法或字段缺失时，为什么不能直接保存？

**标准回答：**

健康评估结果涉及护理等级和入住建议，模型输出即使语法合法，也可能业务语义不合法。例如健康指数超出 0～100、风险等级不存在、系统评分缺失。直接落库会把不可信结果扩散到后续护理流程。

我会做三层防护：Prompt 约束输出、模型 JSON 模式约束、后端 DTO 反序列化和业务校验。失败时记录原始响应摘要和 traceId，不把完整敏感报告写入普通日志；可以重试一次，仍失败则走规则引擎或提示人工复核。

### Q9（L3）：规则引擎降级会不会产生误导？

**标准回答：**

会，所以降级结果必须标识来源和可信度，不能伪装成 AI 结论。规则引擎只做明确的指标范围比对和风险提示，结果标记为“规则评估/需人工复核”，并保留失败原因和模型调用状态。

这体现了降级的边界：降级目标是保证基本可用，不是保证与主流程完全等价。涉及高风险指标时，可以直接转人工审核而不是自动给出护理结论。

### Q10（L4）：AI 服务超时、限流、返回 429 或 5xx，如何设计可靠调用？

**标准回答：**

我会把外部调用视作不可靠依赖：

- 连接超时和读取超时分开设置，避免请求无限占用线程。
- 只对可重试错误重试，例如临时网络错误、部分 5xx；参数错误和内容违规不重试。
- 使用指数退避并限制次数，避免重试风暴。
- 设置并发舱壁或信号量，隔离 AI 请求与普通业务线程池。
- 超过阈值熔断，转规则评估或人工审核。
- 记录成功率、P95/P99、token 消耗、超时数和降级数。

如果接口已经是异步任务，则任务状态应有 `PROCESSING/SUCCESS/FAILED/RETRYING`，并配套超时补偿，而不是让 HTTP 请求一直等待。

### Q11（L4）：健康指数到护理等级的映射为什么放在后端？

**标准回答：**

这是影响业务结果的规则，不能放在前端，否则不同客户端可能计算出不同结果，也容易被篡改。后端统一映射可以保证一致性、审计和版本管理。当前规则是健康指数分段映射护理等级，后续可把阈值配置化并记录规则版本。

需要特别说明：规则映射不是医疗诊断，系统输出应定位为辅助评估，关键结果需要护理人员或医生复核。

### Q12（L4）：如何避免重复提交和并发生成两份评估？

**标准回答：**

接口需要幂等键，例如 `userId + reportId + assessmentVersion`。提交时使用 Redis `SETNX` 加 TTL 抢占处理权，成功者进入任务，重复请求返回已有任务状态；数据库再用唯一索引做最终兜底。任务成功或失败后更新状态，异常中断由 TTL 和定时补偿释放。

仅使用“先查询再插入”不可靠，因为两个请求可能同时查询到不存在。仅依赖 Redis 也不够，因为 Redis 故障或状态丢失时仍需数据库约束保证最终一致。

## 五、第三组：IoT、AMQP 与数据一致性

### Q13（L1）：为什么 IoT 数据不用同步 HTTP 接收？

**标准回答：**

设备上报具有突发性，HTTP 同步处理会让接入请求直接承受解析、业务处理和数据库写入压力。通过 IoTDA 投递 AMQP 消息，接入端只负责接收，业务线程异步消费，可以削峰并把消费速度与接入速度解耦。历史数据写 MySQL，最新状态写 Redis，分别满足查询和实时展示。

### Q14（L2）：Qpid JMS 监听器和业务线程池各自负责什么？

**标准回答：**

监听器负责连接、接收消息和提交处理任务，不应该在回调线程里执行耗时 SQL。业务线程池负责 JSON 解析、设备映射、批量入库和最新状态更新。这样可以避免单条慢消息阻塞消息接收。

但异步提交后要重新审视 ACK 时机：如果监听器已经自动确认，而业务线程尚未落库，进程宕机就可能丢消息。因此当前 `AUTO_ACKNOWLEDGE` 是实现简单但可靠性有限的选择，生产化应改为成功后确认或引入可靠的落盘缓冲。

### Q15（L2）：为什么同时写 MySQL 和 Redis？

**标准回答：**

MySQL 保存可追溯的历史设备数据，适合按时间范围查询和审计；Redis Hash 保存每个设备的最新值，适合大屏或详情页的低延迟读取。两者用途不同，不是简单复制同一份数据。

写入顺序需要根据业务取舍。若先写 Redis 后写库，实时页面可能先看到数据但历史记录落库失败；若先写库后写 Redis，实时页面可能短暂滞后。我会选择“先保证历史数据落库，再更新最新缓存”，并在缓存失败时通过重试或下一条上报修复。

### Q16（L3）：AMQP 消息重复投递怎么办？

**标准回答：**

消息系统通常至少一次投递，不能假定只消费一次。消费端需要幂等：优先使用消息唯一 ID；没有唯一 ID 时可组合 `iotId + 上报时间戳 + 功能标识` 生成去重键。Redis `SETNX` 可以做短期去重，数据库则用唯一索引做最终兜底。

批量入库时不能只依赖“整批成功或整批失败”。应记录批次号，失败批次进入重试表或死信队列；重试必须可重复执行，避免因为重试产生重复历史数据。

### Q17（L3）：设备注册的三重校验为什么还需要数据库唯一索引？

**标准回答：**

名称、节点 ID、位置与产品组合的查询校验只能降低正常重复，不能保证并发下的原子性。两个请求可能同时通过查询，然后同时插入。数据库唯一索引是最终一致性边界，应至少对 `node_id`、`iot_id` 以及业务要求的组合字段建立唯一约束；应用层捕获唯一键异常后返回友好提示。

### Q18（L4）：设备断网和云端数据补偿如何设计？

**标准回答：**

设备侧可以缓存最近数据，网络恢复后批量上报；云端通过消息通道承接上报；应用侧需要关注消息是否成功消费。完整方案应包括：

1. 记录设备最后上报时间和消息序号。
2. 通过定时任务识别超过阈值未上报的设备，标记离线并告警。
3. 消费失败进入重试或死信，不直接丢弃。
4. 按时间范围从云端或设备侧补拉缺失数据，做对账。
5. 明确历史数据允许重复但不允许丢失，利用幂等键去重。

### Q19（L4）：IoT 数据量扩大 100 倍，你怎么演进？

**标准回答：**

先估算每秒消息数、单条大小、保留周期和查询模式，再决定方案：

- 接入层增加消费者实例和连接数，但设置上限，避免压垮数据库。
- 消费线程池与数据库写入线程池隔离，使用有界队列和背压。
- 批量写入、分区表、按设备或时间建立索引，冷热数据分层。
- 最新状态继续使用 Redis，历史明细评估时序数据库或数据湖。
- 增加队列积压、消费延迟、失败重试、数据库写入耗时等监控。

不能只回答“加线程、加机器”，因为吞吐提高后数据库和消息确认可能成为新的瓶颈。

### Q20（L4）：时区为什么要统一？

**标准回答：**

设备、云平台、应用服务器和数据库可能使用不同默认时区，直接保存本地时间会出现 8 小时偏差，跨夏令时区域还会出现重复或不存在的本地时间。推荐传输带偏移的时间，服务端转换为 UTC 存储，展示时按机构或用户时区转换。Java 侧优先使用 `Instant`、`OffsetDateTime` 或 `ZonedDateTime`，不要依赖服务器默认时区。

## 六、第四组：小程序登录、安全与 ThreadLocal

### Q21（L1）：小程序登录为什么不能直接把 openid 当登录凭证？

**标准回答：**

openid 是用户在小程序范围内的标识，不是带签名、带过期时间的访问凭证。如果前端直接提交 openid，攻击者可以伪造其他用户标识。正确流程是前端取得临时 code，后端通过微信服务端接口换取 openid，再由后端签发短期 JWT；后续请求只携带 token，服务端验证签名和有效期。

### Q22（L2）：为什么管理端和小程序端要隔离认证？

**标准回答：**

两端用户模型、权限粒度和风险不同。管理端是员工账号，采用 Spring Security + JWT + RBAC；小程序端是家属用户，使用微信 code/openid/手机号链路和独立拦截器。隔离可以避免把家属身份错误映射为后台角色，也能分别制定 token 生命周期、登录限制和审计策略。

“共用 Token 工具”不等于“共用用户权限”，必须在 token 的 issuer、audience、subject 类型或用户类型 claim 上做区分，并在服务端严格校验。

### Q23（L2）：ThreadLocal 为什么适合传递用户 ID？有什么边界？

**标准回答：**

一次同步请求会经过拦截器、Controller 和 Service，使用 ThreadLocal 可以避免每层显式传参，适合存放当前请求的轻量上下文，例如 userId、tenantId、traceId。但它只绑定当前线程，不能天然跨线程池、异步任务或消息消费线程；业务不能把 ThreadLocal 当作持久化或跨请求会话。

异步任务需要显式传递上下文，并且要防止把用户上下文错误传播到另一个请求。更重要的是请求结束必须清理。

### Q24（L3）：ThreadLocal 内存泄漏原理和工程防护是什么？

**标准回答：**

线程池线程生命周期很长，ThreadLocalMap 中 Entry 的 key 是弱引用，但 value 仍可能被线程持有。如果请求结束不 remove，线程复用时旧用户信息可能继续存在，既有内存泄漏风险，也有串号和越权风险。

工程上在拦截器 `afterCompletion` 或过滤器 finally 中统一 `remove()`，异常路径也必须执行；线程池任务不要隐式依赖请求 ThreadLocal，必要时显式复制并在任务 finally 中清理。代码审查应把“set 必须对应 remove”作为检查项。

### Q25（L3）：JWT 是无状态的，为什么还要 Redis？

**标准回答：**

JWT 本身只负责签名和有效期校验，Redis 可以承担登录态辅助管理：保存 refresh token、登录失败次数、锁定状态、token 黑名单或会话版本。这样得到的是“JWT 负责快速校验，Redis 负责可控状态”的混合方案。

代价是引入 Redis 可用性和一致性问题。对于 access token，可以短时效减少黑名单依赖；对于登出、封禁和高风险操作，则需要黑名单或 token version 做主动失效。

### Q26（L4）：如何防止登录接口被暴力破解？

**标准回答：**

按账号、IP、设备三个维度组合防护：连续失败计数达到阈值后短时锁定；IP 维度限流防止单 IP 高频请求；多次失败后增加验证码；异地或异设备登录触发风险告警；手机号验证码接口单独限频。计数与过期时间要原子设置，不能只在 Java 层“查询次数再加一”。

锁定是缓解措施，不应设计成永久锁死账号；还要保留登录审计，便于区分用户输错和攻击行为。

### Q27（L4）：如果 refresh token 泄露，怎么吊销？

**标准回答：**

refresh token 只能访问刷新接口，存储和传输要比 access token 更谨慎。刷新时采用轮换机制：旧 refresh token 立即失效并签发新 token；服务端在 Redis 保存 token 的 jti、用户、设备和过期时间；登出或风控命中时加入黑名单；必要时修改用户 token version，使该用户全部旧会话失效。

JWT 无法凭空“删除”，主动吊销必须依赖服务端状态，这是无状态便利和可控撤销之间的取舍。

## 七、第五组：事务、预约与业务一致性

### Q28（L1）：入住办理为什么需要事务？

**标准回答：**

入住办理不是单表写入，通常包含老人档案、床位状态、合同、入住记录和相关配置的联动。如果床位已经占用但合同没有生成，会造成业务数据不可用；如果合同生成但床位没有锁定，又会出现重复入住。单数据库多表写入时用本地事务保证原子性，并在事务内完成必要的状态校验。

### Q29（L2）：`@Transactional` 哪些情况下会失效？

**标准回答：**

常见情况包括：同类内部通过 `this.method()` 自调用，绕过 Spring 代理；方法不是可被代理拦截的公开方法；异常被 catch 后没有重新抛出；受检异常没有配置 `rollbackFor`；跨多个数据源却误以为一个本地事务可以覆盖；事务边界放得太大，把远程调用也长时间包在数据库事务里。

我会让事务只覆盖本地关键写操作，远程调用采用状态机、事件或补偿处理，并通过集成测试验证回滚。

### Q30（L3）：两个家属同时预约最后一个名额，怎么防止超卖？

**标准回答：**

不能先 `count` 再 `insert`，因为检查和写入之间存在竞态。可选方案：

- 数据库为时段维护容量行，使用 `select for update` 串行扣减；
- Redis 使用原子计数并配合失败回滚，但仍需数据库唯一约束兜底；
- 设计“时段 + 序号”唯一资源，抢到唯一序号才算成功。

选择取决于并发量和一致性要求。养老预约通常更重视不超卖和可审计，我会优先考虑数据库约束或容量行锁，Redis 只作为高并发削峰和快速拒绝层。

### Q31（L3）：每天最多取消 3 次，为什么不能只查数据库 count？

**标准回答：**

高并发下并行请求可能同时读到相同 count，然后都通过检查。可以用 Redis `INCR` 做按用户和日期的原子计数，设置到当天结束的 TTL；最终业务记录仍应落数据库，用于审计和纠纷处理。若 Redis 操作成功但数据库写失败，需要补偿计数或改为以数据库事务记录为准，因此要明确哪个系统是权威来源。

### Q32（L4）：数据库事务与 Redis 计数不在一个事务里，如何保证一致？

**标准回答：**

不能宣称二者具备强一致。可按场景选择：

1. 低并发、高一致：数据库锁和唯一约束作为主方案，Redis 只做缓存。
2. 高并发、最终一致：Redis 先抢名额，数据库异步确认，失败进入补偿队列并释放名额。
3. 需要可靠事件：本地事务写业务表和 outbox 事件表，再异步更新 Redis 或下游系统。

关键是定义“超卖”和“少卖”哪个更不可接受，并用监控和对账发现偏差。

### Q33（L4）：为什么不能把 AI 调用放在入住事务里？

**标准回答：**

AI 是外部网络依赖，延迟不稳定且可能超时。把它放进数据库事务会长时间占用连接和锁，降低吞吐；如果 AI 成功但本地事务失败，还会出现难以回滚的外部副作用。更合理的是先保存待评估状态，异步完成 AI 任务，再通过状态机和人工确认推动业务，不让外部调用持有本地事务资源。

## 八、第六组：异常处理、日志、文件与数据安全

### Q34（L1）：为什么要统一异常和响应？

**标准回答：**

统一响应让前端、小程序和接口调用方可以用同一方式处理成功、业务失败和系统异常；全局异常处理器集中映射错误码，避免 Controller 到处 try/catch，也避免把堆栈、SQL 或第三方密钥泄露给用户。日志记录详细上下文，响应只返回安全且可理解的信息。

### Q35（L2）：日志中哪些内容不能直接打印？

不能打印明文密码、JWT、手机号全量、身份证号、体检报告全文、AI API Key、OSS 临时签名和完整外部响应。应使用脱敏值、摘要、traceId、用户内部 ID 和错误码。排查问题时通过 traceId 关联安全日志和业务日志，不依赖打印敏感原文。

### Q36（L2）：PDF 上传如何防止恶意文件？

不能只看文件名后缀。应限制大小和页数，校验 MIME 和文件头，设置 OSS 对象访问权限，解析过程限制超时和资源消耗，捕获 PDFBox 异常；解析服务最好与 Web 请求线程隔离。对加密 PDF、损坏 PDF 或超大文件返回明确提示，不让异常堆栈直接暴露给用户。

### Q37（L3）：OSS URL 直接返回给前端安全吗？

如果对象包含体检报告，公开永久 URL 不合适。应使用私有 Bucket，通过后端鉴权后签发短期预签名 URL；数据库保存对象 key 而不是把访问权限交给 URL 本身。下载时还要校验用户是否有权访问对应老人档案，防止仅凭猜测 object key 越权下载。

### Q38（L3）：健康报告缓存 24 小时是否合理？

TTL 不是越长越好，需要结合评估流程、隐私要求和重复使用频率。24 小时可以减少重复解析，但也延长敏感数据暴露时间。应设置主动删除、用户/机构隔离、访问审计和 Redis 权限；如果报告内容更新，应使用版本号或内容摘要避免读取旧文本。

### Q39（L4）：如何建设健康评估的可审计性？

保存报告版本、Prompt 模板版本、模型名称、请求时间、结果来源（AI/规则/人工）、结构化结果、审核人和状态变化；原始 PDF 通过 OSS 对象版本或不可变 key 管理。日志只保存必要摘要，敏感原文放受控存储。这样既能解释“为什么得出这个护理等级”，又能在模型或规则升级后重现历史结果。

## 九、第七组：工程质量、测试与发布

### Q40（L1）：这个项目怎么测试？

**标准回答：**

按风险分层：Service 层测试健康分映射、重复提交、默认状态和异常分支；集成测试验证 MyBatis-Plus 映射、事务回滚和 Redis key；IoT 消费测试覆盖合法消息、未知设备、字段缺失、重复消息和批量失败；AI 调用通过 Mock 隔离外部网络，验证合法 JSON、非法 JSON、超时和降级；接口测试覆盖登录、权限、参数校验和统一异常响应。

### Q41（L2）：为什么 AI 不适合只做单元测试？

模型输出具有概率性，线上依赖还会变化。单元测试应 Mock 固定响应，验证解析、校验、映射和降级逻辑；另行做少量集成测试验证 SDK 配置和真实接口契约；再用离线样本集检查结构化字段和风险边界。不能用一次真实调用成功就宣称 AI 链路可靠。

### Q42（L2）：如何验证“8 秒到 1 秒”的优化结果？

固定同一批报告、同一环境和并发条件，分别测量上传、解析、Redis 命中、AI 调用、数据库写入的耗时，至少报告平均值和 P95。缓存命中和未命中要分开统计，否则会把偶然的命中结果当成整体性能。压测前还要确认没有因为减少校验或异步丢失而虚假变快。

### Q43（L3）：线程池如何配置和监控？

AI、IoT 消费和普通 Web 请求不能无界共享线程池。根据任务类型设置独立线程池：IO 密集型适当增加并发，但必须有界队列；拒绝策略不能静默丢任务；线程命名便于排查；监控活跃线程、队列长度、完成数、拒绝数和任务耗时。线程池参数应通过压测而不是经验拍脑袋确定。

### Q44（L3）：发布后如何知道系统是否健康？

至少建立四类指标：接口 QPS/RT/错误率，AI 成功率/超时/降级数，IoT 队列积压/消费延迟/失败重试数，数据库连接池和 Redis 命中率。配合结构化日志、traceId 和关键业务告警，例如设备离线、评估任务长时间 PROCESSING、预约失败率升高。没有监控就无法证明优化结果在生产仍成立。

### Q45（L4）：如果让你负责下一版，你会按什么优先级优化？

我会按“先可靠性，再安全性，再性能，最后体验”的顺序：

1. **可靠性**：AMQP 手动确认、消费幂等、死信/重试、评估状态 TTL 和对账。
2. **安全性**：敏感数据分级、OSS 私有访问、refresh token 轮换、登录风控、审计。
3. **性能**：消息批处理、数据库索引/分区、AI 并发隔离、缓存命中监控。
4. **可运维性**：统一 traceId、指标看板、告警和故障演练。
5. **体验**：评估任务异步化、进度查询、人工复核和失败重试入口。

这样的顺序是因为“更快但会丢消息”的系统不适合养老场景。

>
> **R**：按项目测试口径，整体响应降到 1 秒以内，护理人员查阅效率提升约 30%。复盘发现还应补充模型调用指标、缓存敏感数据治理和任务状态超时补偿。

### 亮点二：IoT 数据接入优化

> **S**：500+ 设备的产品同步原先需要约 3 分钟，设备上报又具有突发性，直接同步写库容易阻塞请求。
>
> **T**：缩短查询耗时，并把接入和持久化解耦。
>
> **A**：产品列表同步后写入 Redis；设备上报经 IoTDA 转为 AMQP 消息；监听器只负责接收并投递线程池，业务线程解析消息、批量写入设备历史数据，同时更新 Redis Hash 中的最新值。
>
> **R**：产品查询耗时降到约 10 秒，实时状态查询和历史追溯分别得到优化。当前仍需补强手动 ACK、幂等键、死信和消费积压监控。

### 亮点三：小程序鉴权与上下文隔离

> **S**：小程序用户和管理后台用户的身份模型不同，不能复用同一套 RBAC 逻辑；同时请求需要在 Service 层获取当前家属 ID。
>
> **T**：完成无感登录并避免身份混淆和线程复用导致的数据泄露。
>
> **A**：后端通过微信服务端接口用 code 换 openid，再签发 JWT；小程序请求经独立拦截器校验 token，将 userId 写入 `UserThreadLocal`；请求完成或异常时统一 remove，管理端继续使用 Spring Security + RBAC。
>
> **R**：实现前后台用户体系隔离和统一的请求上下文访问方式。后续会加入 token version、refresh token 轮换、黑名单和设备风控，增强主动吊销能力。

- 能主动说出至少 3 个当前实现边界，并给出可落地优化顺序。
- 所有指标都能回答“怎么测出来的”。

## 十三、建议反问面试官的问题

1. 这个岗位更关注养老业务的领域建模，还是 AI/IoT 基础设施建设？
2. 目前线上更核心的指标是设备消息实时性、数据完整性，还是 AI 评估响应时间？
3. 团队对外部模型调用的审计、数据脱敏和人工复核有什么统一规范？
4. 如果系统服务多个养老机构，是否已经规划租户隔离、数据分区和机构级时区？
5. 目前是否有消息重试、死信、对账和全链路监控平台？

> 好的反问不是为了显得“懂得多”，而是帮助确认岗位真正需要解决的问题，并把自己的项目经验映射到对方的业务场景。
