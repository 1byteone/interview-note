# 灵犀智能写作 — 大厂面试官标准QA

## 一、项目概述

**一句话定位**：基于自研StateGraph DAG工作流引擎的AI智能写作系统，支持多模型适配、结构化输出、SSE流式实时生成、多源配图降级，实现"一句话需求→完整文章+配图"的全自动化写作体验。

**技术栈全景**：
- 自研StateGraph DAG工作流引擎（非LangGraph）
- 异步任务体系：ThreadPoolTaskExecutor（核心8/最大32/队列100/CallerRunsPolicy）
- SSE流式输出（首字200ms）
- 结构化输出与多模型适配（OpenAI/Claude/文心等）
- 多源配图降级（Pexels→SVG，99%成功率）

**核心指标**：
| 指标 | 数值 |
|------|------|
| 首字延迟 | 200ms |
| 生成速度(500字) | 15s |
| 生成速度(2000字) | 45s |
| 配图成功率 | 99% |

### 【第二层：深度】自研工作流引擎

#### ⭐⭐ Q2：为什么自研StateGraph工作流引擎，而不是用LangGraph？自研的代价和收益怎么权衡？

**标准答案**：
**为什么不自研**的考量（面试官会问）：
市面上已有成熟的开源方案（LangGraph/LangChain），自研的维护成本高、社区生态弱。

**我们的回答（自研的理由）**：
1. **业务场景特定**：我们的写作流程是确定性的（需求→大纲→段落→配图→排版），不是通用的Agent流程。用LangGraph的图状态机能力过剩（我们不需要循环、不需要sub-agent、不需要人机交互），反而增加了复杂度
2. **控制力**：自研引擎可以精确控制每个节点的执行顺序、超时、重试策略、并发度。LangGraph黑盒度高，出问题时定位困难
3. **性能优化**：我们的DAG引擎支持节点级并发（如大纲生成后，各段落可以并行撰写），线程池可以精细调优
4. **依赖可控**：不引入LangGraph的依赖链（LangChain→langchain-core→community→...），减少版本冲突和兼容性问题

**代价**：开发周期约2周，初次实现+测试；后续随业务迭代持续维护
**收益**：性能更好（比LangGraph快约30%），故障定位时间更短，业务定制灵活

**加分点**：给出"自研vs开源"的决策框架（复杂度/控制力/维护成本/生态），体现架构权衡能力

**常见错误**：盲目吹"自研强"，说不出"什么情况下用开源更好"

#### ⭐⭐⭐ Q3：你的StateGraph DAG引擎怎么设计的？节点间如何通信？支持条件分支和循环吗？

**标准答案**：
**核心设计**：
- 每个节点是一个`Runnable<NodeContext>`，NodeContext包含输入数据、元数据、状态信息
- 节点间通信通过**共享上下文（SharedContext/WorkflowState）**，类似Map
- 引擎内部维护**有向无环图（DAG）**，拓扑排序确定执行顺序

```java
// 简化设计
public class StateGraph {
    private Map<String, Node> nodes;          // 节点注册
    private Map<String, List<String>> edges;  // 边：前置节点→后置节点
    private WorkflowContext context;          // 共享上下文
    
    public void execute() {
        // 拓扑排序
        List<String> sorted = topologicalSort();
        // 按层执行（支持并行）
        for (String nodeId : sorted) {
            Node node = nodes.get(nodeId);
            // 执行节点，结果写入context
            node.execute(context);
            // context支持后续节点读取
        }
    }
}
```

**支持条件分支和循环吗？**
- **条件分支**：支持，通过`ConditionalEdge`，节点根据context中的数据选择不同下游
- **循环**：**不支持**（DAG的特性）。如果业务需要循环（如"内容质量不够→重新生成"），我们通过**重试机制**替代：节点失败/质量不达标，重新执行该节点（进入同一节点的另一条路径），而非循环引用

**加分点**：能说出"为什么选择DAG而不是有环图"——确定性的写作流程不需要循环，有环图增加复杂度且可能导致死循环

**常见错误**：把DAG引擎说成"工作流引擎"，但说不出拓扑排序、节点级并发、上下文传递等核心设计

#### ⭐⭐⭐ Q4：模板方法和策略模式也"几乎等价"于状态机，你为什么不直接用设计模式而要自研引擎？

**标准答案**：
这是个好问题，面试官想考察"设计模式 vs 框架"的边界判断。

**设计模式可以实现**：通过模板方法定义流程骨架，策略模式实现各步骤的替换。但问题在于：
1. **无法动态编排**：模板方法在编译期固定了流程，无法在运行时根据业务需求调整节点顺序/跳过/重试
2. **跨节点状态管理**：模板方法中，数据传递依赖类成员变量，并发场景下有线程安全问题
3. **可观测性**：模板方法没法在节点间埋点（每个节点执行耗时、入参出参、失败原因），引擎可以在框架层面统一打点
4. **并行控制**：模板方法线性执行，DAG引擎支持按层并行（无依赖的节点同时跑），提速明显

**总结**：设计模式适合小规模、固定流程的场景；自研引擎适合"需要编排、监控、并行、动态调整"的场景。我们的项目有多个节点（需求分析→大纲→分段→配图→排版），且支持中间态持久化，值得用引擎。

**加分点**：展示"重构决策树"——先想设计模式，发现不足再升引擎

### 【第三层：陷阱】线程池与异步

#### ⭐⭐⭐ Q5：线程池核心8/最大32/队列100/CallerRunsPolicy，这个参数怎么算出来的？CallerRunsPolicy有什么坑？

**标准答案**：
**参数计算依据**：
- **核心8**：服务部署实例数(2) × CPU核数(4) = 8，确保核心线程充分利用CPU而不过度竞争
- **最大32**：考虑IO密集型任务（AI生成等待网络IO），高峰期可扩展线程数
- **队列100**：假设峰值QPS=50，任务平均耗时=2s，队列长度=50×2=100，正好容纳1秒内的峰值请求
- **CallerRunsPolicy**：拒绝策略，线程池和队列都满时，提交任务的线程自己执行

**CallerRunsPolicy的坑**：
1. **主线程阻塞**：如果Tomcat线程（HTTP请求线程）提交任务，拒绝时主线程执行任务，导致HTTP响应延迟暴涨，可能引发**Tomcat线程池耗尽**
2. **非预期慢**：用户调用接口本来应该快速返回"任务已提交"，结果发现自己线程在跑任务，接口RT飙升到几十秒
3. **死锁风险**：如果主线程跑任务时需要调用当前线程池的其他方法，可能互相等待

**改进方案**：
- 方案A：**DiscardPolicy + 队列监控告警**，拒绝的任务前端提示"服务繁忙，请稍后重试"
- 方案B：CallerRunsPolicy但**设置超时**，超过2秒直接放弃
- 方案C：**独立线程池**，HTTP请求直接返回任务ID，由后台线程池独立执行

**加分点**：能说出"线程池参数不是拍脑袋，是通过压测得出的"；能分析CallerRunsPolicy的适用场景（不丢任务但接受响应变慢）

**常见错误**：说"CallerRunsPolicy最好，不会丢任务"，不考虑主线程阻塞风险

#### ⭐⭐⭐⭐ Q6：SSE流式输出首字200ms是怎么做到的？如果模型响应慢，200ms还能保证吗？

**标准答案**：
**首字200ms的实现**：
1. **模型预热**：模型实例常驻内存，避免冷启动
2. **流式接口**：使用模型的stream=True参数，模型生成第一个token立即返回，而不是等完整响应
3. **SSE直出**：服务端拿到第一个token就通过SSE推给前端，不做额外缓存/后处理
4. **网络优化**：服务器和模型部署同区域，减少网络延迟
5. **池化连接**：HTTP连接池复用，避免每次请求建立TCP连接

**模型响应慢时怎么办**：
- 200ms是**目标值**，基于在线模型的P99延迟。如果模型响应变慢（如高峰期），但SSE流式机制本身不会丢数据
- 优化方向：**模型级联**——先用小模型快速生成开头（如文章大纲/引言），同时大模型生成正文，前端先展示小模型的内容，大模型生成后无缝替换

**加分点**：提到"首字延迟≠体验好"——更关键的是"吐字间隔稳定性"（TTFT和ITL的平衡）

**常见错误**：把"首字200ms"说成"200ms内生成完整文章"，混淆概念

### 【第四层：架构权衡】多模型适配与结构化输出

#### ⭐⭐⭐⭐ Q7：多模型适配怎么做的？不同模型输出格式不一致怎么办？

**标准答案**：
**适配层设计**：
```java
public interface ModelProvider {
    Flux<Chunk> stream(String prompt, ModelConfig config);
    StructuredOutput parse(String rawResponse);
}

// 各模型实现
@Component
public class OpenAIModelProvider implements ModelProvider { ... }
@Component
public class ClaudeModelProvider implements ModelProvider { ... }
@Component
public class WenxinModelProvider implements ModelProvider { ... }
```

**结构化输出格式不一致的处理**：
1. **统一输入**：每个模型都收到相同的System Prompt + JSON Schema定义
2. **统一输出适配器**：模型返回后，经过适配器层（parsing + validation），将各模型格式转为统一内部格式
3. **降级策略**：某模型JSON解析失败，自动切换到另一个模型重试

**加分点**：强调"模型适配不是简单的if-else，而是适配器模式+策略模式+降级策略的组合"

#### ⭐⭐⭐⭐ Q8：多源配图降级怎么做的？Pexels搜不到图怎么办？SVG兜底占99%的配图成功率，那SVG图的质量怎么样？

**标准答案**：
**降级链路**：Pexels搜索 → Pexels无结果 → 自建图库 → 自建图库无结果 → SVG兜底

**Pexels搜不到**：可能是关键词太抽象（如"数字化转型"），此时：
1. 先用LLM将抽象关键词转成可搜索的关键词（"数字化转型"→"digital transformation, technology, business"）
2. 仍无结果，走自建图库
3. 仍无结果，走SVG兜底

**SVG质量**：SVG是**信息图风格的占位图**（如标题+图标+渐变色），不是真实照片。在产品层面，SVG有明确标注"AI生成配图"或"占位图"，且用户可手动替换。

**99%成功率**：来源是Pexels(70%)+自建图库(15%)+SVG(14%)，SVG兜底保证100%有图，但Pexels和自建图库的占比是质量指标

**加分点**：能说出"降级策略的核心是永远不空配图"，以及"降级层级越多，维护成本越高"

### 【第五层：陷阱】容错与稳定性

#### ⭐⭐⭐⭐⭐ Q9：你的工作流引擎经过层层层编排，如果中间某节点（如配图）失败，整个流程回滚吗？怎么保持部分已有结果？

**标准答案**：
**工作流失败的三种策略**：
1. **全部回滚**（不推荐）：已生成的内容全部丢弃，浪费已经完成的AI调用成本
2. **部分成功**（推荐）：已完成的节点结果保留，失败节点标记失败，前端显示"文章已生成，但配图失败，可手动补充"
3. **重试**：自动重试失败节点（最多3次），重试成功继续流程

**部分成功实现**：
```java
// 工作流上下文记录每个节点状态
context.getNodeStatus("content_generation").isSuccess(); // true
context.getNodeStatus("image_matching").isSuccess(); // false
// 前端根据状态展示不同UI
```

**加分点**：强调"部分成功是AI场景的常态"——AI的不可靠性决定了你必须设计优雅的降级策略

---

#### ⭐⭐⭐⭐⭐ Q10：生成500字15s、2000字45s，如果用户要生成10000字的长文，性能和稳定性怎么保证？

**标准答案**：
10000字超出了单次生成的能力边界，需要特殊处理：

**方案**：
1. **分段生成**：将10000字拆分为4-5个主题段落，每个段落独立生成，再拼接
2. **并行生成**：各段落之间无依赖关系，可以并行（工作流引擎的节点级并发）
3. **渐进式输出**：每生成一段就推送给前端，用户看到"第1段已生成...第2段已生成..."
4. **超时控制**：单段生成超过5分钟，放弃该段并标记"该段生成超时，请重试"
5. **内存管理**：长文本全部在内存中拼装可能OOM，需要流式写入文件/数据库

**加分点**：能说出"分段+并行+渐进式输出"的组合策略，以及"长文本生成不是线性扩展"的认知

## 四、挑刺点/隐患分析

### 隐患1：CallerRunsPolicy阻塞主线程 ⚠️ 高
**问题**：线程池满时，HTTP请求线程自己跑任务，接口RT飙升，可能耗尽Tomcat线程池
**改进**：DiscardPolicy + 队列监控告警，或独立线程池分离HTTP路径和后台任务路径

### 隐患2：自研引擎缺少分布式能力 ⚠️ 高
**问题**：当前引擎是单机内存状态，如果需要多实例部署、任务持久化、断点续跑，引擎需要重构
**改进**：状态持久化到Redis/DB，引擎支持分布式锁和任务分片

### 隐患3：SSE连接断开无重连 ⚠️ 中
**问题**：SSE是长连接，网络抖动/服务重启导致连接断开，前端已展示的内容不完整
**改进**：SSE带lastEventId，前端断连后重连时从断点续传；或后端提供"获取已生成内容"接口

### 隐患4：配图SVG兜底质量参差 ⚠️ 中
**问题**：SVG是占位图，用户可能对"AI生成的配图"不满
**改进**：SVG模板持续优化（增加更多模板），或引入DALL·E/Midjourney作为第四级降级

### 隐患5：多模型适配测试成本高 ⚠️ 中
**问题**：维护多个模型适配器，每次模型升级/API变更都要同步更新
**改进**：加一层模型抽象层（model-agnostic schema），用JSON Schema统一约束输入输出，模型适配器只做协议转换

### 隐患6：无全链路监控 ⚠️ 中
**问题**：工作流引擎的节点级耗时、失败率、重试次数缺少统一监控
**改进**：引擎内嵌Metrics（节点耗时、状态、重试次数），暴露到Prometheus/Grafana

### 隐患7：队列100可能不够 ⚠️ 低
**问题**：100个队列长度在突发流量下可能填满，触发CallerRunsPolicy
**改进**：动态队列（根据当前负载调整），或限流降级（前端展示排队等待）

## 五、可以反杀的亮点

### 面试被问"你项目最大的挑战是什么？"

> **挑战**：如何在一个**自研工作流引擎**上，让AI写作的每一步都"可观测、可控制、可容错"，而不是黑盒调用。
>
> **方案**：
> 1. **自研StateGraph DAG引擎**：每个节点独立、可观测、可重试，不同节点可以并行执行
> 2. **SSE流式 + 首字200ms**：用户体验优先，边生成边看，不用等全部完成
> 3. **多源配图三段降级**：永远不空配图，且降级链路透明
> 4. **多模型适配器**：不绑定单一供应商，模型切换用户可选
>
> **反思**：最想补的是**分布式能力**——当前引擎是单机状态存储，如果要做成SaaS服务，需要支持任务持久化、跨实例调度、断点续跑。这也是我从"自研引擎"到"自研+开源融合"的下一步方向——把分布式调度交给成熟的框架（如Temporal/Camunda），业务逻辑保留在自研引擎中。
