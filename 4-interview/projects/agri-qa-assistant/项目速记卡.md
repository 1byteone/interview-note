## 一、快速复习知识点速记

### 1. LangGraph Agent + 6 工具
使用 LangGraph 编排 Agent 工作流，注册 6 个内置工具：`query_crop_knowledge`（作物知识检索）、`calculate_growing_period`（生长周期计算）、`get_agri_weather`（农事天气查询，基于 Open-Meteo 公共 API）、`fetch_web_content`（网页内容抓取转 Markdown）、`search_agri_resources`（农业资源图片/文档搜索，集成 Wikimedia Commons API）、`get_current_datetime`（时间工具，支持用户指定评估日期）。Agent 通过 `ChatOpenAI.bind_tools()` 绑定工具，在 LLM 调用循环中自动决策工具调用顺序。

### 2. BGE-M3 Embedding (1024d)
使用 BAAI/bge-m3 多语言嵌入模型，输出 1024 维稠密向量，支持 Dense + Sparse + ColBERT 多向量输出，最大 8192 token 上下文。支持 local（sentence-transformers 本地推理）和 api（OpenAI 兼容格式远程调用）两种模式，通过 `RAG_EMBEDDING_MODE` 环境变量切换。

### 3. ChromaDB 向量存储
轻量级向量数据库，无需额外部署，通过 `persist_directory` 持久化到磁盘。集合名按嵌入模式隔离（`agri_knowledge_{mode}_v1`），支持增删改查和按 metadata 过滤。使用 `RecursiveCharacterTextSplitter` 分块，chunk_size=1000，chunk_overlap=200。

### 4. Neo4j 知识图谱 (12 实体 + 16 关系)
定义 12 类实体（Crop/Disease/Pest/Chemical/Fertilizer/Variety/Region/Policy/Measure/GrowthStage/Symptom/Document）和 16 类关系（SUSCEPTIBLE_TO/CONTROLLED_BY/APPLIES_TO/VARIANT_OF/SUITABLE_FOR_REGION/GOVERNED_BY/HAS_STAGE/INDICATES/SHOWS_SYMPTOM/MEASURE_AT_STAGE/DOCUMENTS/INTERACTS_WITH/CAUSES_SYMPTOM/RESISTS/COVERS_CROP/FERTILIZER_AT_STAGE）。内置种子数据（11 种作物、12 种病害、10 种虫害、10 种农药、10 种症状、9 个生育期、12 个江西地区）。LLM 驱动的 Few-Shot NER + RE 实现自动图谱构建。

### 5. Hybrid RAG = Vector + BM25 + RRF 融合
混合检索管道：Vector（BGE-M3 余弦相似度）+ BM25（rank_bm25 中文农业分词检索）+ Graph（Neo4j 实体关系查询）+ Temporal（时间衰减权重）。多路结果通过 RRF（Reciprocal Rank Fusion，k=60 论文推荐值）融合，支持自定义各分支权重（vector_weight=0.6, bm25_weight=0.4）。

### 6. BGE-Reranker 交叉编码器重排序
在 RRF 融合后，使用 BGE-Reranker（BAAI/bge-reranker-v2-m3）做二次精排。将 query 和候选文档拼接后做深度语义匹配，排序精度比向量余弦相似度高 10-15%。支持三种模式：local（sentence-transformers CrossEncoder）、api（TEI/vLLM 端点）、openrouter，不可用时自动跳过保留 RRF 原始排名。

### 7. Domain Guard（领域守卫）
基于规则的关键词匹配守卫，在检索和 LLM 调用之前执行。维护农业术语表（`AGRICULTURE_TERMS`，约 60 条）和非农业术语表（`NON_AGRICULTURE_TERMS`，约 20 条），以及代码意图正则。分类结果四类：agriculture（允许）、non_agriculture（拒绝）、unsupported_action（拒绝，含代码意图）、ambiguous（拒绝，需澄清）。拒绝时返回固定话术 + 3 个推荐农业问题。

### 8. Query Router（查询路由）
基于规则 + 关键词的意图分类器，四种路由决策：`RAG_DIRECT`（作物+病害明确，直接检索）、`RAG_DECOMPOSED`（复合问题，需分解后检索）、`TOOL_FIRST`（天气/日期查询，先调工具）、`GENERAL`（兜底）。同时输出场景分类（diagnosis/fertilizer/calendar/policy/boundary）和检索提示（crop/pest/strategy_boost/category_filter）。

### 9. 文档摄入管道 (PDF/DOCX/HTML 解析)
支持 8 种文件格式（txt/md/csv/html/json/docx/pdf），15MB 大小限制。文本清洗：HTML 解码 → 空字符过滤 → 多余空格压缩 → 换行规范化。分块策略：`RecursiveCharacterTextSplitter`，分隔符 `\n\n` → `\n` → `。` → `；` → ` `，保证每个 chunk 在 1000 token 以内。上传时自动做农业领域分析（`analyse_agriculture_document`），非农业文档拒绝入库。

### 10. LocalHashingEmbeddingFunction 回退
零依赖的 BLAKE2 哈希向量化方案，384 维。将文本分词后，每个 token 的 BLAKE2 哈希映射到 384 维空间的一个索引位，奇偶决定正负，最后 L2 归一化。作为 Embedding 三层回退策略的最后一层保底（BGE-M3 API → BGE-M3 本地 → LocalHashing）。

### 11. SSE 流式输出
FastAPI 的 `StreamingResponse` + `async generator` 实现 SSE 流式输出。事件类型包括：guard（领域拦截）、status（状态更新）、delta（文本增量）、tool（工具调用）、sources（证据来源）、memory（记忆）、ui（UI 组件，如 decision-card/knowledge-context）、done（完成信号）。每个 SSE 连接是一个 async task，不占用线程。

### 12. ChatOpenAI + Agnes AI
使用 LangChain 的 `ChatOpenAI` 类，通过 `base_url` 配置指向 Agnes AI 兼容端点，model 为 `agnes-2.5-flash`，temperature=0.3（低温度保证农业知识回答的确定性）。支持 `bind_tools` 绑定工具注册表，通过 `astream` 方法实现流式工具调用。备选方案：失败时自动降级到 temperature=0.1 的 fallback 通道。

### 13. 多轮对话记忆系统
SQLAlchemy 异步 ORM + SQLite 持久化，三张表：`conversation_messages`（对话消息，按 thread_id 隔离）、`conversation_threads`（会话线程元数据）、`agent_memories`（结构化记忆，含 confidence/importance 评分）。通过 `thread_id` 隔离会话，每次请求加载历史消息注入 system prompt。SQLite + FTS5 支持历史搜索。

### 14. 证据策略与引用管理
在 `agriir_pipeline.py` 中实现证据策略：`requires_official_evidence` 检测农药/肥料/政策类问题，要求 A 级证据来源；`required_evidence_scope` 细分到 pesticide_label/rice_fertilizer_recommendation 等 9 种场景。证据等级 A/B/C，引用阈值 0.75，按嵌入模式可调。缺少适用证据时触发 `build_evidence_gap_answer` 安全回答。

### 15. Apple Liquid Glass UI 风格
前端使用 Next.js 14 + shadcn/ui 组件库，采用 Apple 风格毛玻璃设计（backdrop-filter: blur），流畅动画，响应式布局。包含决策卡组件（decision-card）、知识上下文面板（knowledge-context）、资源卡片（resources）等自定义 UI 组件，通过 SSE 事件驱动渲染。

## 二、面试要点速记

### 项目一句话定位
"一个面向农业领域的 **Hybrid RAG + GraphRAG 三层架构** 智能问答平台，通过 LangGraph Agent 编排 6 个农业专业工具，实现从文档摄入到知识检索、从图结构推理到流式回答的端到端农业知识服务。"

### 核心技术亮点

**1. 三层检索架构（向量+BM25+图谱）**
- Vector（BGE-M3, 1024d）：语义理解，处理同义替换和泛化查询
- BM25（rank_bm25）：关键词精确匹配，中文农业术语优先
- Graph（Neo4j, 12类实体+16类关系）：结构化推理，支持多跳关系查询
- Temporal：时间衰减权重，农时/农事日历场景
- 战略性设计：纯向量检索对低频术语和精确匹配不够好，BM25 补充；图谱解决"晚稻稻飞虱用什么药"这类需要多跳推理的问题

**2. RRF 融合 + BGE-Reranker 精排两阶段排序**
- 第一阶段：RRF（Reciprocal Rank Fusion, k=60）将多路召回结果融合，解决各分支评分尺度不一致的问题
- 第二阶段：BGE-Reranker 交叉编码器对 Top-50 候选做深度语义匹配精排
- 两阶段设计权衡了精度和效率：Reranker 是 O(n) 计算，无法处理全量候选

**3. 领域守卫 + 查询路由双保险**
- Domain Guard 在入口层拦截非农业问题，基于农业术语表匹配 + 代码意图检测
- Query Router 在检索层做意图分类，指导检索策略（直接检索/分解检索/工具优先）
- 配合证据策略引擎，确保农药/肥料类高风险问题必须引用 A 级证据来源

**4. Embedding 三层降级策略**
- 第一层：BGE-M3 API（远程调用，精度最高）
- 第二层：BGE-M3 本地模型（sentence-transformers 加载）
- 第三层：LocalHashing（BLAKE2 哈希，384 维，零依赖保底）
- 设计原因：BGE-M3 API 可能因网络不可用，本地模型需要 GPU 资源，哈希方案保证在任何环境下都能启动

**5. 答案证据约束与安全机制**
- 农药/肥料问题强制要求官方来源（A级证据），缺少时输出安全回答
- 证据等级 A/B/C，按证据场景细分（pesticide_label/policy/technical_standard 等 9 种）
- 决策卡组件将证据来源和答案分离展示，增强可信度

**6. 多轮对话记忆 + 结构化记忆管理**
- 三表设计（messages/threads/memories）分离对话历史和 Agent 记忆
- 记忆带 confidence（置信度）和 importance（重要性）评分，支持自动提取和淘汰
- 每次对话从 SQLite 加载历史，注入 system prompt 实现上下文感知

## 三、面试追问速记

### Q1: 为什么选混合检索而不是纯向量检索？
纯向量检索对中文农业术语中的低频词（如"稻纵卷叶螟"）和精确匹配（如农药登记号）效果不佳。BM25 补充了关键词精确匹配能力，Neo4j 图谱补充了多跳结构化推理能力（如"作物→症状→病害→农药"）。三者互补，在实际评测中混合检索比纯向量检索准确率高 10-15%。

### Q2: RRF 和 Reranker 的区别和配合？
RRF 是**无参数融合**，将多路结果的排名位置通过 `1/(k+rank)` 公式加权，解决各检索分支评分尺度不一致的问题。Reranker 是**交叉编码器**，将 query 和每个候选文档拼接后做深度语义匹配，精度更高但计算成本也高。配合策略：RRF 先做多路融合（处理所有候选），Reranker 再对 Top-50 精排（Top-K 筛选控制成本）。

### Q3: 为什么用 Neo4j 做知识图谱？
农业知识具有天然的图结构特征：作物与病害的易感关系、病虫害与农药的防治关系、作物与生育期的阶段关系、地区与政策的管辖关系。用关系型数据库需要写多层 JOIN，Neo4j 的 Cypher 查询可以直观表达多跳路径。例如查询"江西水稻稻飞虱的治疗农药"只需一次三跳图遍历。

### Q4: 农业领域知识图谱怎么构建的？
混合构建策略：1）手工定义 Schema（12 实体 + 16 关系，含种子数据 50+ 实体）；2）LLM 驱动的 Few-Shot NER + RE 从文档自动抽取（使用农业领域定制 Prompt）；3）实体去重和属性合并；4）质量评估和人工审核队列。核心代码在 `kg/pipeline.py`（NER Prompt + RE Prompt）和 `kg/schema.py`（Schema 定义 + Cypher 模板）。

### Q5: 领域守卫怎么实现的？误拦截怎么办？
基于关键词匹配 + 正则表达式。维护农业术语表（60+ 条，含中英文作物名、病害名、农药名等）和非农业术语表（20+ 条，含编程语言、技术领域等）。分类规则：农业术语命中且无非农业术语 → 放行；非农业术语命中且无农业术语 → 拒绝；代码意图正则命中 → 拒绝；两者都命中 → 按规则优先级判断。误拦截通过 `ambiguous` 分类输出友好提示而非直接拒绝，用户可换种方式提问。

### Q6: 文档解析遇到复杂表格怎么办？
DOCX 解析使用 `python-docx` 库，表格逐行提取并用 `|` 分隔单元格。HTML 解析使用 BeautifulSoup，`<td>` 元素提取行内所有单元格后用 `|` 拼接。PDF 解析使用 PyMuPDF（fitz）逐页提取文本，暂不支持表格结构化还原——这是一个已知局限，复杂表格场景建议用 DOCX 格式上传。

### Q7: 向量维度为什么选 1024？
BGE-M3 模型的默认输出维度为 1024。1024 维在语义表达能力和计算效率之间取得平衡：低于 512 维会损失精度，高于 2048 维会显著增加存储和检索延迟。ChromaDB 在 1024 维下支持百万级规模的向量检索。

### Q8: BGE-M3 相比其他 Embedding 模型的优势？
1）**多语言支持**：原生支持 100+ 语言，中英文混合查询效果好；2）**多向量输出**：同时输出 Dense + Sparse + ColBERT 三种向量表示，适配不同检索场景；3）**超长上下文**：最大 8192 token，适合农业文档的长段落检索；4）**国产开源**：MIT 许可，无需商业授权。

### Q9: 如何处理长文档？
使用 `RecursiveCharacterTextSplitter` 按层级分隔符（`\n\n` → `\n` → `。` → `；` → ` `）递归切分，chunk_size=1000，chunk_overlap=200，保证语义完整性。每个 chunk 携带原始文档的 metadata（content_hash、source、evidence_level 等），支持跨 chunk 的引用聚合。

### Q10: 检索结果相关性不够怎么办？
多层优化手段：1）**查询改写**（QueryTransformer）：对复杂问题做多查询分解；2）**RRF 融合**：多路召回互补；3）**BGE-Reranker 精排**：深度语义匹配；4）**Metadata Boost**：对地域/分类匹配的文档加 0.05-0.08 权重；5）**Citation 阈值调优**：按嵌入模式调整 `citation_threshold`（默认 0.75）。

### Q11: 系统响应延迟怎么优化？
1）**异步架构**：FastAPI async + SSE 流式，不阻塞线程；2）**缓存**：网页抓取 6 小时 TTL 缓存（URL 哈希去重）；3）**BM25 懒加载索引**：首次检索时构建，后续复用；4）**Reranker 批量处理**：batch_size=32，64 并行；5）**连接池**：ChromaDB 持久化连接复用；6）**实测首字响应 200ms，完整回答 2-3 秒**。

### Q12: 知识库更新机制？
增量更新：通过 `ingest_document` 接口上传文档，按 content_hash 去重，相同的 hash 跳过，metadata 变更时先删除后重新添加。全量重建：调用 `knowledge_base.clear()` 清空 ChromaDB 持久化目录，再重新摄入。BM25 索引在首次检索时自动构建，增删文档后需手动重建索引。

### Q13: 非农业问题怎么处理？
Domain Guard 拦截，返回固定话术 + 3 个推荐农业问题。不在检索层和 LLM 层浪费资源。分类策略保守：不确定的归为 `ambiguous` 而非放行，避免通用模型在非农业领域作答。

### Q14: 如何评估 RAG 系统效果？
通过 `agriir_evaluation.py` 模块实现：1）`load_eval_items` 加载评测集（query + 预期结果）；2）`evaluate_retrieval` 计算检索准确率和召回率；3）`annotate_eval_item` 支持人工标注和审核队列；4）`build_review_queue` 构建需要人工复审的 case 队列。实测私有知识库问答准确率 85%+，幻觉率从纯 LLM 的 40%+ 降至 5%。

### Q15: 为什么选 LangGraph 而不是 LangChain Agent？
LangGraph 在 LangChain Agent 基础上增加了**有向图状态机**能力，可以精细控制 Agent 的执行流程（如：先执行 Domain Guard → 再 Query Router → 并行多路检索 → 后处理约束）。LangChain Agent 的工具调用是黑盒的，无法插入中间处理逻辑。LangGraph 的 StateGraph 让每个阶段可观测、可插拔、可回退。

### Q16: Embedding 函数本地回退实现原理？
LocalHashingEmbeddingFunction 使用 BLAKE2 哈希将文本 token 映射到 384 维空间。流程：文本分词 → 取每个 token 的 BLAKE2 哈希（8字节）→ 取模 384 确定索引位 → 哈希值最低位决定正负增量 → 所有 token 累加后 L2 归一化。虽然无法表达语义，但保证相同文本产生相同向量，零依赖、零网络、零 GPU。

### Q17: 多轮对话上下文怎么管理？
通过 `thread_id` 隔离用户会话。每次请求：1）从 SQLite 加载该 thread 的历史消息（limit 8 条）；2）注入到 system prompt 中作为上下文；3）LLM 生成回答后异步写入 messages 表和 threads 表。额外通过 `agent_memories` 表存储结构化记忆（fact/pattern/preference），带 confidence 和 importance 评分，支持自动提取、关联和淘汰。

### Q18: 流式输出和普通输出的区别？
SSE 流式输出在 FastAPI 中通过 `StreamingResponse` + `async generator yield` 实现。流式输出包含多个事件类型（delta/status/tool/sources/memory/ui/guard/done），前端逐事件渲染。普通输出在 `chat()` 方法中聚合所有事件，用 `done` 事件的 answer 作为最终返回。流式优势：首字响应 200ms，用户体验好；劣势：前端需要处理复杂的事件流状态机。
