## 一、项目全景概述

### 1.1 项目定位

CropWise 是一个面向农业领域的智能问答平台，核心目标是将 PDF 农技手册等私有知识转化为可检索的知识库，让农民通过自然语言就能获取专业的病害防治建议。项目采用 Hybrid RAG（向量 + BM25 + RRF 融合）+ GraphRAG（Neo4j 知识图谱）+ LangGraph Agent 的三层架构，由我独立完成从文档预处理、向量化入库到 Agent 调度、流式接口的全链路开发。

### 1.2 技术架构

```
前端: Next.js 14 + shadcn/ui (Apple Liquid Glass 风格)
后端: FastAPI + LangGraph Agent
  ├── Domain Guard (领域守卫) — 农业术语过滤 + 非农问题拒绝
  ├── Query Router (查询路由) — 知识库优先 / 通用知识兜底
  ├── Hybrid Retrieval (混合检索层)
  │   ├── Vector (BGE-M3 Embedding, ChromaDB)
  │   ├── BM25 (Lucene全文检索)
  │   ├── Graph (Neo4j 知识图谱, 12类实体+16类关系)
  │   └── RRF Fusion + BGE-Reranker 重排序
  ├── LLM (ChatOpenAI, 0.3 temperature)
  └── Post-process (证据约束 + 结构化输出 + 格式化)
存储层: ChromaDB + Neo4j + SQLite + Redis
```

### 1.3 技术选型理由

| 技术 | 选型理由 |
|------|---------|
| LangGraph | 支持复杂 Agent 工作流编排，比 LangChain Agent 更灵活 |
| ChromaDB | 轻量级向量库，无需额外部署，适合个人项目 |
| Neo4j | 农业知识实体关系复杂，图数据库天然适合 |
| BGE-M3 | 国产开源 Embedding 模型，1024 维，支持多语言 |
| BGE-Reranker | 交叉编码器精排，比向量余弦相似度召回更准确 |

### 2.2 知识库与向量检索

**代码位置**: `backend/knowledge_base.py`

```python
class LocalHashingEmbeddingFunction:
    """无依赖的中文向量回退函数，用于本地 RAG 操作"""
    dimension = 384

    def _embed(self, text: str) -> List[float]:
        # 使用 BLAKE2 哈希将文本映射到 384 维向量空间
        vector = [0.0] * self.dimension
        for token in self._tokens(text):
            digest = hashlib.blake2b(token.encode("utf-8"), digest_size=8).digest()
            value = int.from_bytes(digest, "big")
            index = value % self.dimension
            vector[index] += -1.0 if value & 1 else 1.0
        # L2 归一化
        norm = math.sqrt(sum(v * v for v in vector)) or 1.0
        return [v / norm for v in vector]

class BGEEmbeddingFunction:
    """BGE-M3 Embedding 函数，优先使用 BGE-M3 API，不可用时回退到本地哈希"""
    dimension = 1024
    # 支持三种模式: bge_m3 / local / remote
    # 配置: RAG_EMBEDDING_MODE 环境变量
```

**Embedding 三层回退策略**:
1. BGE-M3 API（远程调用，1024 维，精度最高）
2. BGE-M3 本地模型（本地加载，需 GPU 或 CPU 推理）
3. LocalHashing（零依赖哈希向量，384 维，仅做保底）

### 2.3 会话记忆系统

**代码位置**: `backend/memory.py`

使用 SQLAlchemy 异步 ORM + SQLite 持久化存储，三张表管理对话记忆：

| 表 | 用途 | 关键字段 |
|-------|------|---------|
| `conversation_messages` | 对话消息 | thread_id, role, content, created_at |
| `conversation_threads` | 会话线程 | thread_id, title, last_message, updated_at |
| `agent_memories` | Agent 记忆 | user_id, thread_id, scope, memory_type, content, confidence, importance |

**多轮对话机制**: 通过 `thread_id` 隔离不同用户的会话上下文。每次请求带上 `thread_id`，服务端从 SQLite 中加载该会话的历史消息，注入到 LLM 的 system prompt 中。SQLite + FTS5 全文索引支持历史搜索。

**记忆管理**: `agent_memories` 表存储 Agent 从对话中提取的结构化记忆（fact/pattern/preference 类型），每个记忆带 `confidence`（置信度）和 `importance`（重要性）评分，支持记忆的自动提取和淘汰。

## 三、高频面试题

**Q1: 为什么用 BGE-Reranker 而不是只用向量检索？**

向量检索（余弦相似度）是粗排，召回 Top-K 后交给 BGE-Reranker 做交叉编码器精排。Reranker 将 query 和每个候选文档拼接后做深度语义匹配，排序精度比向量检索高 10-15%。代价是 Reranker 只能处理少量候选（Top-50），所以先用向量检索粗排缩小范围，再精排。

**Q2: 知识库优先的策略具体怎么实现的？**

Agent 收到用户问题后，先查私有知识库（ChromaDB + Neo4j），如果检索结果的相似度得分低于 0.6，切换到通用知识查询。0.6 阈值通过 20 组测试问答手动标注确定。0.8+ 为高度相关，0.6-0.8 为可能相关，0.6 以下为不相关。

**Q3: SSE 流式输出怎么处理并发？**

FastAPI 的 async 模型让每个 SSE 连接是一个 async task，不占用线程，单机能支持 100+ 并发连接。如果连接数增长，加 Nginx 做反向代理，利用 Nginx 的 epoll 模型分担连接压力。
