# 农业知识库问答智能体（Agri-QA Assistant）— 大厂面试官标准QA

## 一、项目概述

**一句话定位**：面向农业领域的RAG知识库问答智能体，基于LangGraph编排、FastAPI服务化、ChromaDB向量检索、图谱增强检索，为农户提供水稻等作物的诊断决策、施肥方案、农事天气预警与政策查询，输出专业"决策卡"而非简单文本。

**技术栈全景**：
- LangGraph（Agent状态机编排）
- FastAPI（服务层）+ SSE流式输出
- ChromaDB（向量库）+ SQLite（元数据）
- Next.js（前端）+ Apple Liquid Glass UI
- MCP-compatible工具层（内嵌，不宣称外部MCP Server）
- 图谱检索（GraphRAG式，83实体/365关系/22社区）

**核心模块**：
| 模块 | 职责 |
|------|------|
| answer-modes | professional决策卡 / brief短答 双模式契约 |
| memory-contract | 4层记忆体系（thread/task/user/knowledge_evidence） |
| mcp tool layer | 6个领域工具（作物知识/时间/生育期/天气/资源/网页） |
| streaming-ui | SSE流式+客户端状态机+生成式UI白名单 |
| graph-retrieval | 图谱多跳检索+向量混合召回+评估体系 |
| answer-quality-audit | 领域边界守卫+证据分级+质量审计 |

---

## 二、核心卖点/差异化

1. **专业决策卡输出**：不是"聊天机器人答一句"，而是结构化农业决策卡（结论→现场摘要→优先判断→现在做什么→风险边界→复查节点），对农户真正可用
2. **4层记忆体系 + 契约化设计**：thread/task/user/knowledge_evidence分层隔离，SSE事件驱动记忆写入，全部写成契约文档
3. **图谱+向量混合检索**：Recall@5达65%（与Crop GraphRAG论文对比提升16.8pp），并公开评估数据
4. **诚实可信的Agent**：`external_process_connected=false`如实标记，证据分级（弱证据·不作结论依据），领域守卫拦截非农业问题
5. **流式体验工程化**：POST+SSE、半字符处理、客户端状态机、每帧≤14字符限速、AbortController取消

### 【第一层：广度】LLM应用架构

#### ⭐ Q1：简单介绍一下你这个项目是做什么的？技术选型为什么用LangGraph + FastAPI + ChromaDB？

**标准答案**：
这是一个农业领域的RAG问答Agent，回答水稻病虫害诊断、施肥、农事天气、政策等专业问题，核心价值是**把大模型"聊天"变成"可用的专业决策工具"**。

技术选型理由：
- **LangGraph**：相比裸调LLM，提供有向图状态机，适合"检索→判断→追问→生成→审计"这种多步骤确定性流程；比LangChain的Chain更灵活，支持循环、条件分支、状态持久化
- **FastAPI**：异步原生，天然支持SSE流式输出；Pydantic做结构化输出校验
- **ChromaDB**：轻量、本地部署，适合小规模知识库（农业垂直场景文档量不大）；支持metadata过滤
- **SQLite**：零运维，适合记忆和会话元数据存储

**加分点**：主动指出"如果数据量上万、需要分布式，会迁移到Milvus/Qdrant"——体现架构演进思维

**常见错误**：说"大家都在用LangChain我就用了"，没有给出技术对比和选型依据

---

#### ⭐⭐ Q2：你在LangGraph里怎么组织节点？和传统if-else流程控制相比有什么本质区别？

**标准答案**：
LangGraph的核心是**图状态机**：每个节点是一个状态转换函数，边可以是条件边（routing），支持循环（追问、重试），状态（State）显式定义并在节点间传递。

我的流程举例：
```python
graph = StateGraph(AgentState)
graph.add_node("gate", domain_guard)          # 领域守卫
graph.add_node("retrieve", hybrid_retrieve)   # 向量+图谱多路召回
graph.add_node("judge", evidence_judge)       # 证据相关性判断
graph.add_node("ask", clarify)                # 主动追问（最多2个关键追问）
graph.add_node("generate", decision_card_gen) # 决策卡生成
graph.add_node("audit", quality_audit)        # 质量审计
graph.add_edge("gate", "retrieve")
graph.add_conditional_edges("judge", route_by_evidence)  # 证据不足→ask
```

本质区别：
1. **显式状态**：状态在图上流动，可持久化、可断点续跑
2. **条件路由/循环**：传统if-else是线性，图可以"证据不足→追问→再检索"这种环
3. **可观测**：每个节点可打点，调试时能看状态流转
4. **可嵌套**：子图复用，如"检索子图"可以在多个场景复用

**加分点**：提到StateGraph的状态reducer、checkpointer（断点续跑）、human-in-the-loop

**常见错误**：把LangGraph说成"流程编排框架"，但说不出和Simple Chain本质区别

### 【第二层：深度】RAG与检索

#### ⭐⭐⭐ Q3：你们的"图谱+向量"混合检索是怎么设计的？为什么图谱Recall只有65%还坚持用？

**标准答案**：
**双通道设计**：
1. **向量通道**：query embedding → ChromaDB top-k
2. **图谱通道**：先做实体识别/映射，再在图谱中做多跳扩展（如"水稻→病虫害→稻瘟病→防治方案"）

**为什么图谱Recall@5只有65%还坚持用**：
- 分场景看：diagnosis场景Recall@5=75%、fertilizer=76%，这两个是核心高频场景，图谱增益明显
- policy（政策）只有50%、weather只有52%，因为政策属于时序性、临时性文档，实体关系抽取难度高
- 混合检索的价值在**互补性**：向量擅长语义相似，图谱擅长多跳推理。虽然总体Recall 65%不算高，但**图谱通道带来的新增命中**（向量没召回但图谱召回的）才是它的核心竞争力，所以我评估时重点看"融合后Recall提升"

**调优方向**（已在文档中给出）：
- policy场景补充实体词典（专有名词→实体）
- weather只覆盖"农事风险"类（气象实体+农事动作+风险标签）
- 用LLM辅助实体抽取，人工审核后再入库

**加分点**：展示"评估体系"思维——120条测试集、分场景统计、与Crop GraphRAG论文（89.4% vs 72.6%）对标

**常见错误**：只说"我们做了RAG"，说不出Recall数字、分场景差异、失败场景分析

---

#### ⭐⭐⭐ Q4：材料里提到CRAG对比"89.4% vs 72.6% +16.8pp"，这个对比科学吗？你怎么保证评估的严谨性？

**标准答案**：
这是容易被面试官**挑刺**的地方，我会主动承认对比的局限：
1. **评估集不同**：Crop GraphRAG用的是他们自己的垂直数据集，我用的是农业场景120条自建集（diagnosis 40/fertilizer 25/weather 25/policy 20/safety 10），不能直接横向对比
2. **指标口径**：论文可能用的是多种指标（Recall/Precision/Answer Accuracy），我只对比了Recall@5，口径要说明
3. **随机性**：LLM输出有随机性，需要多次运行取均值

**严谨做法**：
- 评估集标注了gold答案（人工/领域专家审核）
- 分场景统计而不是笼统一个数
- 记录失败case，做错误分析（为什么policy低？天气数据源时效问题？）

**加分点**：主动召面试官质疑，并给出"如何把评估做得更科学"的方案（扩大样本、专家标注、多指标、消融实验）

**常见错误**：拿一个不严谨的对比到处吹，被追问就露馅

### 【第三层：陷阱】记忆系统

#### ⭐⭐⭐⭐ Q5：你们的4层记忆系统怎么设计的？为什么RAG证据永不写入用户记忆？

**标准答案**：
**4层记忆**：
| 层级 | 生命周期 | 用途 |
|------|----------|------|
| thread | 最近8条 | 当轮对话上下文 |
| task | 默认14天 | 同一农事任务（如"我这块田"）的连续咨询 |
| user | 用户确认后长期 | 农户的田块信息、作物偏好（需显式确认才写入） |
| knowledge_evidence | 单次不存储 | RAG检索到的证据片段，仅本次回答使用 |

**RAG证据永不写入用户记忆**的原因：
1. **隐私边界**：证据来自知识库（公开文档/政策），属于"知识"不属于"用户画像"，混入会造成记忆污染
2. **时效性**：证据可能被更新/废弃，写进长期记忆会导致过期信息持续影响回答
3. **审计要求**：每次回答的证据必须可追溯（哪个文档、哪一段），如果进了记忆就丢了来源

**SSE事件设计**：memory-candidate（候选记忆）→ memory-action（是否采纳）→ memory-organized（组织入层）→ memory（已生效），全程前端可感知、可展示，用户能"看到"Agent在记什么。

**加分点**：提到"记忆是产品功能而非技术装饰"，用户可管理、可删除自己的记忆

**常见错误**：笼统说"我们用了Memory"，说不清分层、生命周期、写入触发条件

---

#### ⭐⭐⭐⭐ Q6：相关性阈值0.32是怎么来的？低于0.32的相似内容为什么只进"相似但未使用"而不是直接丢弃？

**标准答案**：
0.32是一个**经验调优值**（基于评估集上Precision/Recall平衡），不是拍脑袋：
- 阈值太高 → 召回不足，好答案被过滤
- 阈值太低 → 噪声混入，影响回答质量

**"相似但未使用"设计**的意义：
1. **可解释性**：用户/开发者能看到"系统认为xxx相似但没有采用"，解释为什么没答
2. **评估数据积累**：这些case是后续优化阈值/召回策略的训练素材
3. **兜底**：如果主要召回都失败，这一步可以作为弱证据兜底（明确标注"弱证据·不作结论依据"）

**加分点**：强调"阈值不是固定值，会随评估数据回流动态调整"，体现数据闭环思维

### 【第四层：架构权衡】工具协议与流式

#### ⭐⭐⭐⭐⭐ Q7：你们的MCP工具层特别强调"不宣称外部MCP Server"，为什么不直接接真正的MCP Server？

**标准答案**：
这是**精心设计的诚实边界**：
- **真正的MCP Server**：需要独立的stdio/SSE进程管理、工具发现（list_tools）协议、认证授权体系，是跨进程/跨机器协议
- **我们的实现**：内嵌的MCP-compatible工具层——**协议风格对齐**（函数签名、参数Schema、工具描述），但运行在同一进程内，是函数调用而非进程间通信

**为什么这样取舍**：
1. **部署复杂度**：真实MCP Server要管理进程生命周期、健康检查、版本兼容，对一个垂直场景Agent是过度设计
2. **性能**：进程内调用延迟低（微秒级），SSE跨进程有毫秒级开销
3. **演进路径**：工具层接口与MCP协议完全兼容，未来要暴露成真正MCP Server时，只需加一层协议适配，无需改业务代码

**诚实标记**：`external_process_connected=false` 在响应中如实暴露，不冒充"我们接入了MCP生态"。

**加分点**：展示架构演进思维 + 诚实工程文化（不夸大技术能力）

**常见错误**：把内嵌工具层包装成"MCP Server"，被追问细节立刻穿帮

#### ⭐⭐⭐⭐ Q8：SSE流式输出为什么用POST而不用WebSocket？"每帧最多14字符"是怎么定的？

**标准答案**：
**POST + SSE而非WebSocket的原因**：
1. **语义匹配**：这是"一次性请求→持续响应"的场景，SSE天然单向（服务端→客户端），WebSocket双向能力是多余的开销
2. **基础设施友好**：SSE走普通HTTP，天然支持CDN、负载均衡、超时重连、断点续传（Last-Event-ID）；WebSocket需要网关层特殊配置、连接保持
3. **易调试**：curl直接能看到流式响应

**14字符/帧**的来历：
- 通过requestAnimationFrame驱动渲染（~16.6ms/帧）
- 目标首字延迟200ms内、滚动流畅、避免积压导致"猛跳"
- 实测平衡点：单帧渲染14字符以内不触发明显重排，太快会导致文字跳动、太慢会导致体验卡顿。这是**前端节流（throttle）**，不是后端限速，后端仍然全速推送，由前端消费速度控制渲染

**半字符处理**：SSE按块（chunk）到达，一个UTF-8中文字符可能被拆到两个chunk，TextDecoder默认stream:true模式处理，不会出现乱码。

**加分点**：能画出客户端状态机（idle→connecting→streaming→draining→complete/cancelled/error）并解释AbortController如何联动服务端取消

**常见错误**：说不出14字符的实验依据；或把节流说成后端限速

### 【第五层：领域特殊性】

#### ⭐⭐⭐⭐ Q9：农业领域问答和通用问答最大的不同是什么？"领域守卫"拦截的是什么？

**标准答案**：
**三大不同**：
1. **错误的代价不对称**：通用问答答错最多是"不准确"，农业建议答错可能导致**整季歉收、经济损失、用药安全事故**。所以必须做证据分级（弱证据明确标注"不作结论依据"）
2. **决策靠现场信息**：通用问答一次性回答，农业回答需要"现场摘要"（发现了什么症状、什么时期、什么环境），缺信息时明确标"待补充"，而不是硬答
3. **时效与地域**：农事操作强依赖时间和地点（播种期、天气、当地政策），所以工具层特意设计了`get_current_datetime`时间预检，日期语义用服务端时钟而非评估日期

**领域守卫**：进入主流程前的gate节点，拦截非农业问题（如"帮我写首诗""推荐一部电影"），避免消耗RAG资源和误导。设计上还注意边界：**不越界给医疗建议**（防止"AI治病"式风险转移）。

**加分点**：展示对"领域专业Agent"的深度思考——不是技术炫技，是风险、流程、信任的综合设计

## 四、挑刺点/隐患分析

### 隐患1：评估集规模偏小 ⚠️ 高
**问题**：120条测试集（safety只有10条），统计显著性存疑；safety 10条样本的Accuracy波动大
**改进**：扩充到500+条，safety类至少30条；引入交叉验证、专家双盲标注

### 隐患2：向量库选型边界 ⚠️ 中
**问题**：ChromaDB单机运行，数据量上来后检索性能、容灾、并发都会成问题
**改进**：明确扩容路径（Milvus/Qdrant云原生向量库），接口层抽象（VectorStore接口），当前实现可替换

### 隐患3：图谱召回低场景未闭环 ⚠️ 中
**问题**：policy/weather Recall只有50%-52%，文档里给了调优方向但未验证落地效果
**改进**：补充实体词典→重跑评估→给出"调优前后对比"数据，形成闭环

### 隐患4：记忆的用户确认机制依赖前端交互 ⚠️ 中
**问题**："用户确认后长期"如果确认弹窗被跳过/用户忽略，长期记忆永远写不进去，功能形同虚设
**改进**：确认机制降级（如"默认采纳+72小时内可撤销"），或定期汇总"待确认记忆"由用户批量处理

### 隐患5：SSE断连重连不完整 ⚠️ 低
**问题**：AbortController支持取消，但未说明服务端断连时如何断点续传（Last-Event-ID是否下发）
**改进**：SSE事件带id，客户端存lastEventId，重连时从断点续传

### 隐患6：fetch_web_content工具的风险 ⚠️ 中
**问题**：允许拉取外部网页内容，存在SSRF（服务端请求伪造）和内容注入风险
**改进**：SSRF防护（内网IP黑名单、DNS rebinding防护）、URL协议白名单（仅http/https）、内容大小限制、渲染前消毒

## 五、可以反杀的亮点

### 面试被问"你项目最大的挑战是什么？"

> **挑战**：让大模型在农业这种"答错代价极高"的领域输出**可信、可用、可审计**的回答，而不是更流畅的废话。
>
> **方案**：
> 1. **结构化决策卡**：把自由文本改成"结论→证据→风险边界→复查节点"的固定结构，逼着Agent把推理过程显性化
> 2. **证据分级**：低相关证据明确标注"弱证据·不作结论依据"，宁可不说不可错说
> 3. **评估驱动迭代**：120条测试集分场景统计，图谱调优方向都有数据支撑，不拍脑袋
> 4. **诚实工程**：工具连接状态如实标记，不夸大"接入MCP生态"
>
> **反思**：评估集还是太小（尤其政策类），这块是我最想继续投入的——**评价体系是Agent质量的天花板**。

### 引导话题技巧

- "我们图谱Recall只有65%" → 引导"分场景拆解+错误分析+融合增益评估"的系统评估方法
- "我们没接真MCP Server" → 引导"MCP协议演进路径与进程内/进程外架构权衡"
- "我们阈值0.32是调出来的" → 引导"如何用评估数据闭环驱动超参优化"
- "决策卡缺现场信息标'待补充'" → 引导"AI系统如何管理不确定性（calibration）"
